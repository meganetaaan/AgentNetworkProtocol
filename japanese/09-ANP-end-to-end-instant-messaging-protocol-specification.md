## 1. ANPエンドツーエンド・インスタントメッセージングとは

ANPエンドツーエンド・インスタントメッセージングは、**ドメインをまたぐエージェント間のインスタントメッセージング**のためのプロトコル仕様群です。

設計上の課題は「ある製品内でチャットする方法」ではなく、次の点です。

- 異なるドメイン、プラットフォーム、実装に属するエージェントが、互いを発見する方法
- ダイレクトメッセージとグループメッセージを送信する方法
- 必要に応じてエンドツーエンド暗号化を提供する方法
- 添付や大きなオブジェクトを転送する方法
- ドメイン間で、ルーティング、中継、順序付け、結果の証明を実現する方法

ANPのビジネス上の識別と認可の終端は、引き続き**Agent DID**です。Messaging 1.2では、通常の非E2EEのDirect、Group、Mention、Attachment操作は引き続きDIDを宛先とし、エンドポイントへの配信展開は受信ドメイン内で行います。P3はv1を維持し、P4はメンバーシップとDID更新の契約が変わるためv2を使います。ドメイン間の安全な暗号通信に必要な最小限のデバイスの意味を公開するのは、E2EE v2 Profileだけです。`device_id`は、同じDID配下の1つの暗号エンドポイントを識別します。新しいビジネス上の識別、グループメンバー、`target.kind`ではありません。

## 2. 中核原則

### 2.1 単一の中心ではなくフェデレーション

ANPは**フェデレーション型**のアーキテクチャを採用します。概念的には、単一の中央サーバー構成より電子メールに近いものです。

エージェントやグループはそれぞれ異なるドメインに属することができ、ドメイン同士は標準化されたサービス発見、サービス間の直接呼び出し、結果の証明機構を通じて通信します。すなわち、次の性質を持ちます。

- 識別は分散しています。
- サービスエンドポイントは分散しています。
- ドメインをまたぐサービス呼び出しが発生します。
- ただし、各種類の操作には明確な責任の境界があります。

ダイレクトメッセージングでは、対象Agentが属するドメインの入口サービスがメッセージの受信を担います。グループでは、グループのHost Serviceが、グループ状態の順序付けとグループイベントの直列化を担います。

### 2.2 識別とサービス発見を優先

ANPの第一級の識別子は、ユーザー名やデバイス番号ではなく、次のものです。

- `agent_did`
- `group_did`

ANPはDID文書から対話用サービスエンドポイントを発見し、それを使って後続のメッセージ送信、鍵の発見、グループサービスの発見、オブジェクトサービスの発見経路を確立します。現行バージョンでは、DID文書で公開するANPサービスエンドポイントを`ANPMessageService`に統一しています。ダイレクトメッセージング、グループメッセージング、鍵情報へのアクセス、オブジェクト制御などの機能は、この統一されたサービスエンドポイントが担います。

Messaging 1.2では、デバイス宛てE2EE v2 Profileを広告するDIDは、P2の規定に従って、適用されるDIDメソッドで検証されたDID Document内に、完全な`deviceManifest`を公開しなければなりません。WBA固有のルート署名要件を、ネイティブ`did:web`に課してはなりません。Manifestの各項目は、現在のデバイスエンドポイント識別子、署名鍵参照、E2EE鍵参照、および依存関係を含む対応Profile識別子だけを公開します。Baseだけの発見では、Manifestは不要です。製品ローカルの役割、トークン、回復状態、レジストリーバージョン、文書チェックポイントは、ANPの通信セマンティクスではありません。

### 2.3 「1つの統一プロトコル」に詰め込まず階層化

ANPは、すべての課題を1つの文書に詰め込まず、9つのProfileに分割します。

- P1/P2: コアバインディング、および識別と発見
- P3/P4: ダイレクト／グループメッセージングの基本的なビジネスセマンティクス
- P5/P6: ダイレクト／グループメッセージングのE2EE Overlay
- P7: 添付と大きなオブジェクト
- P8: フェデレーション、ドメイン間のサービス呼び出し、グループイベント配布
- P9: グループメッセージのメンションとセレクターのセマンティクス

この設計には、次の利点があります。

- 基本的なメッセージセマンティクスとセキュリティセマンティクスを分離できます。
- 平文モードと暗号化モードを共存させられます。
- ダイレクトメッセージング、グループメッセージング、添付、フェデレーションを明確に分離できます。
- 特定の層を後から更新しても、プロトコル全体を作り直す必要がありません。

### 2.4 制御プレーンとデータプレーンの分離

ANPは、次のものを明確に区別します。

- **制御プレーン**: グループ作成、参加、メンバー追加・削除、機能交渉、チケット発行、ドメイン間のサービス呼び出しなど。
- **データプレーン**: ダイレクトメッセージ、グループメッセージ、添付オブジェクトの内容。

特に添付では、ANPは次の方針を明示的に採用します。

- メッセージには**Manifest**を含めます。
- オブジェクトの内容は、独立したHTTP(S)チャネルからダウンロードします。
- ドメイン間のサービス呼び出し経路では、オブジェクトのバイトストリームを転送しません。

## 3. 中核となる設計

### 3.1 統一された外側のバインディング: JSON-RPC

ANPの統一された外側のバインディングは**JSON-RPC 2.0**を採用し、自由度を次のように絞っています。

- `params`はオブジェクト形式を使います。
- `id`は文字列を使います。
- バッチは使用しません。
- Notificationは、明示された非同期通知の場面でだけ使います。

目的は、実装を簡潔に保ちつつ、異なる言語、プラットフォーム、サービス間で、要求・応答・エラーのモデルを統一することです。

### 3.2 ダイレクトメッセージングとグループメッセージングを別々にモデル化

ANPは「メッセージ」を曖昧で巨大なオブジェクトにせず、次のように明確に区別します。

- `direct.send`: ダイレクトメッセージング
- `group.send`: グループメッセージング

同時に、グループメッセージングには「メッセージの送信」以外にも次の操作を含めます。

- `group.create`
- `group.join`
- `group.add`
- `group.remove`
- `group.leave`
- `group.update_profile`
- `group.update_policy`

これにより、グループの統治、状態、暗号化を自然につなげられます。P4 v2は、`group.invite`、`group.accept_invite`、標準のinvitationオブジェクトを定義しません。招待リンクやJoin Tokenは配備環境の拡張であり、`group.join`が成功する前に標準のメンバーシップを確立することはできません。

Messaging 1.2は、デバイスレベルのビジネスメンバーシップを作りません。P3 Direct Base v1の配信、およびP4 Group Base v2のメンバーシップ、役割、ポリシー、送信、通知は、引き続きDIDの範囲で扱います。P4 v2はDIDだけに基づくメンバーシップと、P2の検証に従ってHostが調整するメンバーDID更新を使います。デバイスの範囲で扱うのは、P5/P6 v2 E2EE配信とMLSの暗号リーフだけです。

### 3.3 平文とE2EEの共存

ANPは、次のモードを許可します。

- `transport-protected`: トランスポートの安全性だけに依存します。
- `direct-e2ee`: ダイレクトメッセージングのエンドツーエンド暗号化。
- `group-e2ee`: グループメッセージングのエンドツーエンド暗号化。

つまり、Base Profileは単独で動作でき、その上にセキュリティOverlayを重ねます。これは、段階的な導入や、状況に応じた異なるセキュリティ水準の採用に役立ちます。

## 4. 中核となる技術方針

### 4.1 トランスポートとメッセージバインディング: JSON-RPC 2.0

ANPは、統一されたメッセージバインディング層としてJSON-RPC 2.0を使います。その役割は「関数呼び出しの模倣」ではなく、次のものを統一することです。

- 要求形式
- 応答形式
- エラーモデル
- 機能交渉インターフェース
- 非同期通知機構

これによりANPは、ダイレクトメッセージング、グループメッセージング、添付の制御、ドメイン間のサービス呼び出しといった異なる場面で、外側のプロトコル形式を統一できます。

### 4.2 ダイレクトメッセージングのエンドツーエンド暗号化: X3DH-like + Double Ratchet-like

ANPのダイレクトメッセージングE2EEは、次の技術方針を採用します。

- 識別の基点: `did:wba`とネイティブ`did:web`を含め、ANP-02とP2に従って検証されたAgent DID
- 鍵の発見: DID文書が公開する`ANPMessageService`から取得
- 最初の通信関係の確立: `X3DH-like`
- 後続メッセージの保護: `Double Ratchet-like`

具体的には、次のとおりです。

- DID文書の認証鍵を、識別の証明に使います。
- DID文書の`keyAgreement`（X25519など）を、鍵合意に使います。
- 非同期・オフラインの通信関係の確立にPrekey Bundleを使います。
- 後続のメッセージごとの鍵更新、順序逆転への許容、リプレイ保護にRatchetを使います。

Direct E2EE v2では、Prekey Bundle、非同期セッション、Ratchet状態、AAD、リプレイ状態、Mailboxを、両端の具体的な`(DID, device_id)`ペアに結び付けます。1つの論理メッセージを、適格な受信デバイスごとに個別に暗号化・送信します。秘密状態をデバイス間で共有することはありません。

この方針はエージェントの非同期通信に適し、より強力な方式へ更新する余地も残します。

### 4.3 グループのエンドツーエンド暗号化: MLSとDID・デバイスのバインディング

ANPのグループE2EEの本流は、次のものを採用します。

- グループ鍵の状態機械としての**MLS**
- 識別の基点としての、**そのメソッドに従って検証されたAgent DID**。デバイス適格性はP2 Manifest規則で定義します。
- 順序付けと受領証の権威主体としての**Group Host Service**

これは、次のことを意味します。

- グループのアプリケーションメッセージは`PrivateMessage`で運びます。
- メンバー追加・削除、Welcome、外部からの参加などは、MLSの`KeyPackage / Commit / Welcome / External Commit`で実現します。
- `group_did`、`group_state_version`、`policy_hash`を、暗号学的なグループ状態に結び付けます。
- `group_receipt`は、「操作やメッセージがグループに受理され、順序を割り当てられた」ことの証明を担います。

Group E2EE v2では、1つのビジネスメンバーDIDが、認証済みのMLSリーフを複数所有できます。各リーフは、デバイスに結び付いた個別のKeyPackageと秘密状態を使います。1つのデバイスリーフを追加・削除するだけでは、DIDレベルのグループメンバーを追加・削除したことにはなりません。

この方針は、独自のグループ暗号状態機械を発明するより、長期的な標準に適しています。

### 4.4 添付とオブジェクト: Manifest + 独立したHTTPSダウンロード + 任意のオブジェクトレベル暗号化

添付の仕組みは、3層構造を採用します。

1. **メッセージ層**: `attachment_manifest`だけを含めます。
2. **アクセス層**: Object Serviceと短期ダウンロードチケットでダウンロードを制御します。
3. **内容層**: 必要に応じて、オブジェクト自体をオブジェクトレベルで暗号化（`object-e2ee`）します。

したがって、次の性質を持ちます。

- 大きなオブジェクトを、ドメイン間のサービス呼び出し経路で転送しません。
- ダウンロードリンクは、長期有効な直接リンクではなく、ロケーターにできます。
- リンクが漏洩しても、オブジェクトレベル暗号化によって、第三者が平文を取得できないようにできます。

Direct E2EE v2では、1つのアップロード済みオブジェクトと`object_key`を、複数のデバイス別暗号化メッセージから参照でき、鍵は受信デバイスごとに個別に届けます。Group E2EE v2では、現在のepochのMLS Application Messageで鍵を運びます。P7は引き続き`anp.attachment.v1`です。オブジェクト、Access Grant、Ticketの状態をデバイスごとに複製しません。

### 4.5 フェデレーション: サービス間の直接呼び出し

ANPのフェデレーション層は、次のことを定義します。

- サービス発見
- ドメインをまたぐサービス間の直接呼び出し
- Group Hostによる順序付け
- 添付の制御プレーンのドメイン間呼び出し
- `attachment.get_download_ticket`の最終的な到達先

重要な原則には、次のものがあります。

- ドメイン間では、独立したRelay包装プロトコルを追加せず、元のビジネスメソッドや制御メソッドを直接使って、対象サービスと対話します。
- オブジェクトのバイトストリームは、HTTPSで独立してダウンロードしなければなりません。
- グループ操作のドメイン間成功の意味は、Group Hostによる受理と順序付けです。
- ダイレクトメッセージングのドメイン間成功の意味は、対象Agentの入口サービスによる受理です。
- P8 v1フェデレーションは、外側のE2EE v2 Profileが宣言する場合に限り、送受信者のデバイス識別子を保持・検証します。通常のP3/P4/P7操作は引き続きDIDを宛先とし、エンドポイントへの配信展開は受信ドメイン内で行います。ゲートウェイは、これらの操作にデバイスセレクターを追加せず、E2EE配信のための隠れた配信展開も行いません。

## 5. 主な設計上のトレードオフ

ANPには、意図的に選択した設計上のトレードオフがいくつかあります。

### 5.1 ビジネス上の識別とデバイスエンドポイントを分ける

v1.1の基準では、デバイス、端末、複製をAgent内部の詳細として扱います。Messaging 1.2は、通常のDID宛てメッセージングを維持します。P3、P7、P8はv1を維持し、P4はDIDだけに基づくメンバーシップとHostが調整する更新のためにv2を使います。P5/P6 v2はE2EEの暗号エンドポイントの境界を変更し、共有デバイス鍵、共有Ratchet、隠れた暗号化配信の展開、曖昧なMLSリーフを避けるために必要な、最小限のデバイス識別子と鍵バインディングを公開します。DIDは引き続きビジネス上の識別であり、製品ローカルのデバイス管理は引き続き対象外です。

### 5.2 究極の匿名性よりグループの統治を優先する

グループでは、ANPは次のものを同時に維持します。

- 発信者の証明（要求を開始したのは誰か）
- グループでの結果の証明（グループが受け入れたか）
- グループ内メッセージの秘匿性（MLS）

このため、純粋な匿名チャットプロトコルというより、「統治しやすいエージェントプロトコル」という性格を持ちます。

### 5.3 添付の安全性を「隠されたリンク」に依存させない

ANPは、「完全に隠されたダウンロードリンク」を中核のセキュリティ手段にせず、次のものを使います。

- 制御されたダウンロードチケット
- 短いURL
- オブジェクトレベル暗号化

これにより、リンクが漏洩しても、意味のある平文を取得できないようにします。

## 7. まとめ

ANPの中核は、単なる「チャットプロトコル」を作ることではなく、**エージェントのエコシステムにおけるドメイン間通信標準群**を作ることです。

基本方針は、次のように整理できます。

- **フェデレーション:** 電子メールのようなドメイン間の相互運用。
- **識別の優先:** DIDを統一された基点とする。
- **デバイスに配慮したE2EE v2:** 1つのDIDが複数の独立した暗号エンドポイントを公開でき、DIDレベルのビジネス上の識別や通常のメッセージ宛先指定は変えない。
- **階層化設計:** ビジネスセマンティクス、暗号化、添付、フェデレーションを相互に分離する。
- **任意のE2EE Overlay:** 基本プロトコルは単独で動作でき、必要に応じてセキュリティOverlayを有効にできる。
- **添付の直接ダウンロード:** メッセージはManifestを運び、オブジェクトは独立したHTTP(S)データプレーンを使う。
- **統治のしやすさ:** 特にグループにおいて、識別、順序付け、受領証、暗号化のバランスを取る。

これによりANPは、実装可能なプロトコル群であるとともに、長期的な標準化と将来の進化に向けた基盤となります。
