# リポジトリのガイドライン

## 共有ルール

エンジニアリング作業が続きます [AIコーディングルール](../../../awiki-harness/rules/ai-coding-rules.md).
動作の変更と検証は関連する規則に従います。 [検証ポリシー](../../../awiki-harness/rules/verification-policy.md)
セクション。生産動作には、ユニットの対象範囲と該当するシステム/製品の E2E レビューを所有する必要があります。
Harness が不在の場合は、ローカルのドキュメント/テスト/CI を使用し、不足している承認証拠を開示します。

## プロジェクトの構造とモジュールの構成

- ルートにはプロトコル仕様とホワイト ペーパーが含まれています (例: `01-*.md`, `06-*.md`, `07-*.md`, `08-*.md`).
- ルートと `chinese/` 現在の ANP 1.2 コア ドキュメントと ANP-05 DID ベースの OAuth および VC 認可ドラフトを保持します。 ANP-05 は v0.7 / ドラフト / 未リリースのままであり、ANP 1.2 の範囲外です。 `message/` そして `chinese/message/` Messaging 1.2 の完全なカタログを保持します。 ANP-06 はドラフトのままであり、P6 は登録された MLS ExtensionType リリース ゲートまで保留中の候補のままです。
- ルート `vnext/` ANP-01 ホワイト ペーパー リビジョンと P4 グループ メッセージング リビジョンを両方の言語で保持しています。これらのリビジョンは未リリースのドラフトであり、ANP 1.2 の一部ではありません。既存の仕様またはホワイト ペーパーの vNext コピーは、その内容が変更された場合にのみ追加します。元のホワイトペーパーを揃えておいてください `origin/main` そしてそのリビジョンを編集します `vnext/`.
- `docs/` そして `docs/chinese/` ガイド、リンク、コミュニティ運営を行っています。
- ANP-05 の詳細な検証シナリオと安定した `AUTHZ-*` 識別子が存在する `docs/anp-05-validation-guide.md` そして `docs/chinese/anp-05-validation-guide.md`;プロトコルのセクション 14 には適合要件とこれらのガイドへのリンクが含まれています。
- `chinese/` 中国語の主要文書に加えて、研究ノートやプロセス文書も反映されています。
- `blogs/` そして `blogs/cn/` 長文記事を保存します。 `blogs/images/` ブログ資産を保持しています。
- `images/` そして `standard/` 共通の図と標準参照を提供します。
- `examples/` サンプルの ADP アセットと API インターフェイス YAML が含まれています。
- `scripts/` リポジトリをメンテナンスするための、依存関係のない Python および JavaScript ユーティリティが含まれています。

## プロトコル所有権境界

- このリポジトリによってインデックス付けされたプロファイル仕様は、ANP プロトコル セットに属します。実装所有のプロファイルを外部に追加しないでください。 `anp.*` ANP メッセージを転送するか、ANP 機能検出を使用するという理由だけで、名前空間を ANP プロファイル インデックスに追加します。
- ベンダーまたは製品のプライベート プロトコル、フィクスチャ、ストレージ制限、クライアント スケジューリング ルール、および UI ウォッチドッグは、所有する製品リポジトリに残ります。 ANP 文書では、ANP 仕様としてプライベート プロファイルを採用せずに、一般的な拡張メカニズムを説明する場合があります。

## ビルド、テスト、開発コマンド

このリポジトリはドキュメントファーストであり、メンテナンスの自動化に重点を置いたテストが行われています。

- UV を使用してメンテナンス スクリプトを実行します。
  - `uv run python scripts/add_copyright.py`
  - `uv run python scripts/rename_images.py`
  - `uv run python scripts/replace_spaces_with_hyphens.py`
- ANP 1.2 のドキュメントと vNext のドラフト境界を確認してください。 `node scripts/check-release-docs.mjs`、実行します `node scripts/generate-anp02-vectors.mjs` そして `node scripts/check-anp02-vectors.mjs` オフラインの治具チェック用。以前の抽出ベースラインは Git 履歴に残っています。
- オンボーディングと支払いステータスの回帰を確認する `node --test tests/release-doc-entrypoints.test.mjs`。リリース チェッカーには、3 つの最新のオンボーディング ガイドが含まれています。 AP2 チェックはステータス/バージョンのみを対象とし、支払いの適合性は対象としません。
- ANP-05 ドラフトのメタデータ、バイリンガル ワイヤの例、およびドラフトとリリースの分離をチェックします。 `node --test tests/did-oauth-draft.test.mjs`。これらはドキュメントのチェックであり、OAuth ランタイムや暗号適合テストではありません。
- 貢献者のアバター自動化をテストする `node --test tests/update_contributors.test.js`.

## コーディングスタイルと命名規則

- ドキュメントはマークダウンです。見出しを簡潔にし、セクションを区切る `##`/`###`.
-  可能な場合、新しいドキュメントやアセットにはわかりやすいケバブケースのファイル名を使用してください。
- Python スクリプトの場合は、Google Python スタイルに従ってください。コメントとログは英語で保存してください。
- 次のような明確でアクション指向のタイトルを好みます。 `add`, `update`, `docs:` コミットメッセージで。

## 試験ガイドライン

- 共同作成者の同期を変更するときに、焦点を当てた自動テストを実行します。ドキュメントの変更については、以下を手動で確認してください。
  - リンクは内部で解決されます `README.md` そして `docs/`.
  - Markdown で参照される画像は以下に存在します。 `images/` または `blogs/images/`.

## コミットリクエストとプルリクエストのガイドライン

- 仕様、プロファイル、ホワイトペーパー、例、インデックス、関連する検証スクリプト/テストを含むプロトコル関連のすべての変更について、編集と必要なチェックを完了し、ユーザーレビューのために変更の概要と検証結果を提示します。その変更セットをコミットまたはプッシュする前に、ユーザーの明示的な承認を待ちます。自動的にコミットまたはプッシュしたり、以前の変更セットの承認を後の変更に引き継いだりしないでください。ユーザーがレビュー済みの変更セットに対してコミットとプッシュの両方を明示的に承認する場合、承認にはコミットとプッシュの両方が含まれる場合があります。
- コミットメッセージは短く、命令的なものであるのが一般的です。 `add ...`, `update ...`、または `docs: ...`.
- PR には、変更の明確な説明と、関連する問題がある場合はリンクを含める必要があります。
-  コンテンツの更新については、影響を受けるドキュメントのパスに言及し、前後のコンテキストを提供します。

## セキュリティと設定のヒント

- Markdown、画像、または例にシークレットや資格情報を追加しないでください。
-  新しい仕様を公開する場合は、外部参照が安定しており、適切に帰属されていることを確認してください。

## エージェント固有の指示

- CLI インタラクションで中国語で応答します。
- Python の依存関係管理に UV を使用し、スクリプトを実行します。 `uv run`.
-  コードのコメントとログインは英語で行ってください。
