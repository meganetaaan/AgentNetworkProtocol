# リポジトリのガイドライン

## 共有ルール

エンジニアリング作業は[AIコーディングルール](../../../awiki-harness/rules/ai-coding-rules.md).
動作の変更と検証は、[検証ポリシー](../../../awiki-harness/rules/verification-policy.md)
の該当する節に従います。本番環境の動作には、担当部分のユニットテストによる網羅と、該当するシステム・製品のE2Eレビューが必要です。
Harness が不在の場合は、ローカルのドキュメント/テスト/CI を使用し、不足している受け入れ検証の証拠を開示します。

## プロジェクトの構造とモジュールの構成

- ルートにはプロトコル仕様とホワイト ペーパーが含まれています (例: `01-*.md`, `06-*.md`, `07-*.md`, `08-*.md`).
- ルートと`chinese/`には、現在の ANP 1.2 コア ドキュメントと ANP-05 DID ベースの OAuth および VC 認可ドラフトを保持します。 ANP-05 は v0.7 / ドラフト / 未リリースのままであり、ANP 1.2 の範囲外です。 `message/`と`chinese/message/`にはMessaging 1.2の全カタログを置きます。 ANP-06 はドラフトのままであり、P6 は登録された MLS ExtensionType リリース ゲートまで保留中の候補のままです。
- ルートの`vnext/`には、ANP-01 ホワイト ペーパー リビジョンと P4 グループ メッセージング リビジョンを両方の言語で保持しています。これらのリビジョンは未リリースのドラフトであり、ANP 1.2 の一部ではありません。既存の仕様またはホワイト ペーパーの vNext コピーは、その内容が変更された場合にのみ追加します。元の白書は`origin/main`と整合させ、その改訂版は`vnext/`で編集してください。
- `docs/`と`docs/chinese/`には、ガイド、リンク、コミュニティ運営の文書を置きます。
- ANP-05 の詳細な検証シナリオと安定した `AUTHZ-*` 識別子は`docs/anp-05-validation-guide.md`と`docs/chinese/anp-05-validation-guide.md`に置きます。プロトコルのセクション 14 には適合要件とこれらのガイドへのリンクが含まれています。
- `chinese/`には中核文書の中国語版に加え、研究ノートや過程を記録する文書を置きます。
- `blogs/`と`blogs/cn/`には長文記事を置きます。 `blogs/images/` ブログ資産を保持しています。
- `images/`と`standard/`には共通の図と標準の参考資料を置きます。
- `examples/`にはADPのサンプルアセットとAPIインターフェースのYAMLを置きます。
- `scripts/`には、リポジトリ保守用の、依存ライブラリを必要としないPython・JavaScriptユーティリティを置きます。

## プロトコル所有権境界

- このリポジトリの一覧に載せるProfile仕様は、ANPのプロトコル群に属します。ANPメッセージを運ぶ、またはANPの機能発見を利用するという理由だけで、`anp.*`名前空間の外にある実装固有のProfileをANP Profile一覧へ追加しないでください。
- ベンダーまたは製品のプライベート プロトコル、フィクスチャ、ストレージ制限、クライアント スケジューリング ルール、および UI ウォッチドッグは、所有する製品リポジトリに残ります。 ANP 文書では、ANP 仕様としてプライベート プロファイルを採用せずに、一般的な拡張メカニズムを説明する場合があります。

## ビルド、テスト、開発コマンド

このリポジトリはドキュメントファーストであり、メンテナンスの自動化に重点を置いたテストが行われています。

- UV を使用してメンテナンス スクリプトを実行します。
  - `uv run python scripts/add_copyright.py`
  - `uv run python scripts/rename_images.py`
  - `uv run python scripts/replace_spaces_with_hyphens.py`
- ANP 1.2 のドキュメントと vNext のドラフト境界を確認してください。 `node scripts/check-release-docs.mjs`、実行します `node scripts/generate-anp02-vectors.mjs` そして `node scripts/check-anp02-vectors.mjs` によって、オフラインfixtureを検査します。以前の抽出ベースラインは Git 履歴に残っています。
- オンボーディングと支払いステータスの回帰を確認する `node --test tests/release-doc-entrypoints.test.mjs`。リリース チェッカーには、3 つの最新のオンボーディング ガイドが含まれています。 AP2 チェックはステータス/バージョンのみを対象とし、支払いの適合性は対象としません。
- ANP-05 ドラフトのメタデータ、バイリンガル ワイヤの例、およびドラフトとリリースの分離をチェックします。 `node --test tests/did-oauth-draft.test.mjs`。これらはドキュメントのチェックであり、OAuth ランタイムや暗号適合テストではありません。
- 貢献者のアバター自動化をテストする `node --test tests/update_contributors.test.js`.

## コーディングスタイルと命名規則

- 文書はMarkdownです。見出しを簡潔にし、`##`/`###`で節に分けてください。
-  可能な場合、新しいドキュメントやアセットにはわかりやすいケバブケースのファイル名を使用してください。
- Python スクリプトの場合は、Google Python スタイルに従ってください。コメントとログは英語で保存してください。
- コミットメッセージには、`add`、`update`、`docs:`など、行為が明確に分かる題名を使ってください。

## 試験ガイドライン

- 貢献者の同期を変更するときに、焦点を当てた自動テストを実行します。ドキュメントの変更については、以下を手動で確認してください。
  - `README.md`と`docs/`内のリンクが解決できること。
  - Markdownが参照する画像が`images/`または`blogs/images/`に存在すること。

## コミットリクエストとプルリクエストのガイドライン

- 仕様、プロファイル、ホワイトペーパー、例、インデックス、関連する検証スクリプト/テストを含むプロトコル関連のすべての変更について、編集と必要なチェックを完了し、ユーザーレビューのために変更の概要と検証結果を提示します。その変更セットをコミットまたはプッシュする前に、ユーザーの明示的な承認を待ちます。自動的にコミットまたはプッシュしたり、以前の変更セットの承認を後の変更に引き継いだりしないでください。ユーザーがレビュー済みの変更セットに対してコミットとプッシュの両方を明示的に承認する場合、承認にはコミットとプッシュの両方が含まれる場合があります。
- コミットメッセージは短い命令形にし、一般に`add ...`、`update ...`、`docs: ...`などを使います。
- PR には、変更の明確な説明と、関連する問題がある場合はリンクを含める必要があります。
-  コンテンツの更新については、影響を受けるドキュメントのパスに言及し、前後のコンテキストを提供します。

## セキュリティと設定のヒント

- Markdown、画像、または例にシークレットや資格情報を追加しないでください。
-  新しい仕様を公開する場合は、外部参照が安定しており、適切に帰属されていることを確認してください。

## エージェント固有の指示

- CLI インタラクションで中国語で応答します。
- Pythonの依存関係管理にはUVを使い、スクリプトは`uv run`で実行してください。
- コードのコメントとログは英語にしてください。
