# 付録A::wba `k1_` 互換性の延長

- ステータス: リリース

### A.1 適用範囲

この付録は定義します `k1_` ウォレットエコシステムと既存のsecp256k1実装との互換性のためのパスバインディングプロファイル。 `k1_` 主仕様のデフォルトスキームには属しません。 新規展開 SHOULD 利用する優先順位をつけて下さい `e1_` 主要な指定のプロフィール。

### .2 の `k1_` パスの構文

実装がこの付随を許すと、パスタイプのDIDの最後のパスセグメントが使用できる:

```plaintext
k1_<fingerprint>
```

Appendix AのABNF拡張子は以下の通りです。

```abnf
k1-fingerprint = "k1_" 43base64url-char
wba-k1-path-did = "did:wba:" domain-name 1*(":" path-segment) ":" k1-fingerprint
```

事例:

```plaintext
did:wba:example.com:user:alice:k1_<fingerprint>
did:wba:example.com%3A3000:user:alice:k1_<fingerprint>
```

### .3 の `k1_` 指紋生成方法

とりあえず `k1_` 指紋は secp256k1 の境界公鍵と DID を関連付けるために使用されます。 生成方法は、次のようになります。

1. DID バインディング キーを選択します。バインディングキー MUST 次の条件を満たしていること。
   - secp256k1 公開鍵です。
   - 代表として `publicKeyJwk` DID 文書で;
   - によって認可されました `authentication` DID ドキュメントの関係。

2. 結合キーに対応するJWKの公開鍵オブジェクトを取得し、RFC 7638で必要なフィールドのみを保持します。

```json
{
  "crv": "secp256k1",
  "kty": "EC",
  "x": "...",
  "y": "..."
}
```

3. 次の規則に従って JWK サムプリント入力を生成します。 [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638):
   - 必要なフィールドだけを保持する。
   - フィールド名は、典型的にソートされます。
   - 余分空白なしでJSON文字列を使用します。
   - UTF-8 エンコーディングを使用してください。

4. SHA-256ハッシュを、ステップ3で取得したUTF-8バイトのシーケンスで32バイトのダイジェスト値を取得。

5. Base64url は 32 バイトのダイジェスト値をエンコードし、末尾の文字列を削除します。 `=` パディング。エンコード結果の長さは 43 文字に固定されます。

6. を追加します。 `k1_` 最終的なパスセグメントを取得するには、エンコード結果の前にプレフィックスを付けます。

### .4 の `k1_` DID ドキュメント制約

DID が使用するとき `k1_` プロフィール、DID文書は少なくとも会う必要があります:

1. `id` 要求された DID と同じです。
2. 少なくとも1秒のsecp256k1があります `publicKeyJwk` でん `verificationMethod` 結合のキーとして;
3. 結合キー MUST 認定される `authentication` 関係;
4. 結合のキーのRFC 7638の指紋 MUST 最後と同じです `k1_` DID パスの指紋セグメント。

推奨k1結合検証方法形状は以下の通りです。

```json
{
  "id": "did:wba:example.com:user:alice:k1_<fingerprint>#key-1",
  "type": "EcdsaSecp256k1VerificationKey2019",
  "controller": "did:wba:example.com:user:alice:k1_<fingerprint>",
  "publicKeyJwk": {
    "crv": "secp256k1",
    "kty": "EC",
    "x": "...",
    "y": "...",
    "kid": "<fingerprint>"
  }
}
```

### A.5 書類の証明 `k1_` (対応拡張機能)

DID の使い方 `k1_` プロファイル、この付録は定義します **非標準、任意secp256k1 DIDの文書の証拠のプロフィール** ウォレットエコシステムや既存の secp256k1 実装で DID ドキュメントの完全性実証機能を提供する。

この証拠プロファイルは、この仕様のメインラインによって定義されたW3C規格相互運用性の範囲内で落ちません。 このセクションをサポートする実装を選択した場合、このセクションを生成して検証する必要があります。 `k1_` このセクションのルールに従って DID ドキュメントの証拠; このセクションをサポートしていない実装は、可能性があります(MAY) 無視する `proof` フィールドの `k1_` DID ドキュメント。

#### A.5.1 証拠の目的分野

`k1_` DID ドキュメントに最上位の `proof` フィールドが含まれる場合、`proof` オブジェクトには次のフィールドが含まれます。

- `type`: 必須フィールドです。に固定 `DataIntegrityProof`
- `cryptosuite`: 必須フィールドです。に固定 `didwba-jcs-ecdsa-secp256k1-2025`
- `created`: 必須フィールドです。プルーフ作成時刻 (XML スキーマ日時形式)
- `verificationMethod`: 必須項目 証拠を生成するために使用されるDID文書のsecp256k1検証方法を示すフルID URL
- `proofPurpose`: 必須フィールドです。に固定 `assertionMethod`
- `proofValue`: 必須項目 署名値、エンコーディングルールは後述のセクションで参照します
- `domain`: オプションのフィールド
- `challenge`: オプションのフィールド

追加の制約:

1. おすすめです(SHOULD)直接使用する `k1_` 結合キーとして `proof.verificationMethod` DID 結合および文書の完全性の証明を統一するため;
2. 認証方法が示す `proof.verificationMethod` 実際に生成するために使用されるプライベートキーで1対1に対応する必要があります `proofValue`.

#### A.5.2 プルーフ生成プロセス

`k1_` プロファイルを使用し、DID 文書証明を生成する必要がある実装では、次のプロセスに従う必要があります。

1. DID ドキュメントをコピーして、トップレベルの署名と削除を行います。 `proof` フィールドを取得する `unsecuredDocument`;
2. 以下を含む証明オプション オブジェクトを構築します。
   - `type`
   - `cryptosuite`
   - `created`
   - `verificationMethod`
   - `proofPurpose`
   - 任意 `domain`
   - 任意 `challenge`
3. DID Document および Proof オプションのそれぞれについて JCS 標準化を実行します。
4. 両方の SHA-256 ハッシュ値を計算します。
5. スパイシー `hash(proofOptions) || hash(document)` 署名するバイト文字列を取得するには;
6. 指す secp256k1 プライベートキーを `verificationMethod` DER のエンコードされた署名を得るために、バイト文字列で ECDSA + SHA-256 署名を実行します。
7. DER のエンコードされたシグネチャを固定長 64 バイトに変換 `R || S`;
8. エンコーダ `R || S` base64url(パディングなし)で書きます `proofValue`;
9. 生成された追加 `proof` DID ドキュメントのトップレベルに戻ります。

#### A.5.3 証拠検証プロセス

`k1_` プロファイルを使用しており、DID Document Proof の実装を検証する必要がある場合は、次のプロセスに従う必要があります。

1. 最上位レベルをお読みください `proof` DID文書の;
2. 次のフィールドが存在するかどうかを確認します。
   - `type`
   - `cryptosuite`
   - `created`
   - `verificationMethod`
   - `proofPurpose`
   - `proofValue`
3. チェック:
   - かわい `type` は、 `DataIntegrityProof`
   - かわい `cryptosuite` は、 `didwba-jcs-ecdsa-secp256k1-2025`
   - かわい `proofPurpose` は、 `assertionMethod`
4. 削除 `proof` DID ドキュメントから検証する文書を入手します。
5. 削除 `proofValue` から `proof` 証拠の選択を得るために;
6. 文書と証明オプションに対してそれぞれ JCS 正規化を実行します。
7.  SHA-256 ハッシュを個別に計算し、次のように連結します。
   - `hash(proofOptions) || hash(document)`
8. secp256k1 の公開鍵を指す `verificationMethod`;
9. デコード `proofValue` base64url で 64 バイトを復元 `R || S`;
10. コンバーター `R || S` ECDSA 署名検証に許容される署名表現に。
11. 対応するsecp256k1の公開鍵を使用して、SPLICYバイト文字列でECDSA + SHA-256署名検証を実行して確認します。
12. 署名検証が成功した場合は、証拠認証パス; そうでなければ、検証は失敗します。

#### A.5.4 解析戦略

のために `k1_` DID、校正証明書はデフォルトでオプションの強化された整合性チェックです。しかし、ローカルポリシーが認証、校正検証、DIDバインディング検証を有効化したら、secp256k1パブリックキーと同時に完了する必要があります。 `proof.verificationMethod`.

導入事例 MAY モードの2つを選択します。

1. リラックス モード: DID ドキュメントに次の内容が含まれていない場合 `proof`、解析は引き続き続行できます。
2. 厳格なモード:ローカルポリシーがその必要である場合 `k1_` 文書は証拠を、それから欠落するDIDの文書運びまなければなりません `proof` MUST 確認の失敗とみなします。

実装が厳格な証拠チェックを可能にした場合、 MUST 追加のチェック:

1. 認証方式は、 `proof.verificationMethod` は、 `EcdsaSecp256k1VerificationKey2019`;
2. この検証方法に対応したsecp256k1公開鍵を使用して、RFC 7638のサムネイルを再計算します。 結果は、最後に完全に一致しなければなりません `k1_` DID パスの指紋セグメント;
3. 証拠に参加していないDID文書の他のsecp256k1キーは、所定の場所で使用してはならない `proof.verificationMethod` 結合検証を完了します。

### .6 の `k1_` アイデンティティ認証

実装がこの付随を許すと、 `k1_` DID は、定義されたクロスプラットフォーム HTTP 認証フローを使用できます。 [ANP-02 第3章](../02-anp-did-authentication-protocol-specification.md#http-binding), WBAの対象 `k1_` この付録のメソッド制約。

認定要件は以下の通りです。

1. デフォルトでは、クライアント SHOULD secp256k1 の結合キーをバインドするのに使用します。 `k1_` 署名のためのパス;
2. `keyid` MUST DID 文書の secp256k1 結合検証方法に点在する。
3. 署名アルゴリズムは、secp256k1曲線のECDSA + SHA-256です。
4. 署名出力は固定長を使用します `r || s` バイト文字列エンコーディング;
5. 検証するときは、サーバーが()必要であるMUST) 同時にチェックします。
   - 認証方法が示す `keyid` 存在;
   - この検証方法は、 `authentication`;
   - この検証方法のサムネイルは、一貫性のあるものです。 `k1_` 指紋の区分。

### アクア・アワー7 `k1_` DID 文書の証拠相互運用性指示

この付録は、wba の独自を定義します。 **`k1_` 互換性のある証拠のプロフィール** (secp256k1結合のシナリオで任意DID文書の完全性証拠の機能を提供するのに使用されているA.5)を参照してください。 W3C規格ではありません `eddsa-jcs-2022` mainline の証拠は、do:wba の互換の拡張です。

したがって:

1. `k1_` DID ドキュメント MAY レベルがトップレベルのものを含んでいません `proof`;
2. 実装が校正認証を有効にしている場合、それに応じて実行する必要があります `didwba-jcs-ecdsa-secp256k1-2025` A.5のルール
3. 実装が検証を有効化していない場合、 MAY 証拠を無視する `k1_` ドキュメント;
4. 証拠の検証が有効になったら、証明書に関与していないDID文書内の他のsecp256k1キーは、代わりに使用してはならない `proof.verificationMethod` 結合検証を完了します。
