# エージェントのアイデンティティ、認可、および暗号化

エージェントの ID、承認、および暗号化された通信は、エージェントのセキュリティの中核であり、2 つのエージェント間の効率的かつ安全なコラボレーションの基盤です。

今日は、これら 3 つの問題についての私の理解を包括的に説明したいと思います。

## エージェント ID

### エージェントIDの説明

最初の質問は、エージェントのアイデンティティについて議論するとき、実際に誰のアイデンティティについて話しているのかということです。エージェントはアイデンティティを持っていますか?

一般的な対話シナリオでは、ソフトウェアの一部としてのエージェントはそれ自体のアイデンティティを持たないと私は考えています。タスクを完了するためにその人の ID を使用することがその人によって許可されるだけです。

したがって、エージェントのアイデンティティの問題について議論するとき、私たちは本質的に、エージェントが他のエージェントとの対話において安全かつ効率的に人々を代表し、人々がタスクを完了できるように支援できるようにする方法に取り組んでいます。

###  従来の ID ソリューションと比較して、エージェント ID にとって最も緊急なものは何か

当社には、OIDC、DID、SAML など、すでに多くの ID ソリューションがあります。どのソリューションがエージェントにとってより適していますか?

これには、「エージェント ID 認証の最も重要かつ緊急の側面は何ですか?」という質問に答える必要があります。

それはアイデンティティの相互運用性だと私は考えています。

ID の相互運用性とは、あるプラットフォームの ID が別のプラットフォームによって認識および信頼される機能を指し、それによってクロスプラットフォームの相互認証と使用が可能になります。これは電子メールと非常に似ています。電子メール アカウントを持っている場合は、ネットワーク全体のすべての電子メール ユーザーと通信できます。

相互運用性がエージェントにとって非常に重要なのはなぜですか?

なぜなら、現在のインターネットは孤立した島で構成されており、各プラットフォームには独自の ID システム、独自のユーザー、独自のデータがあると考えているからです。これにより、エージェントが完全なコンテキストを取得することが大幅に妨げられ、エージェントが人々のタスクの実行を支援することができなくなり、賢く、ユーザーを理解し、多くのことを支援してくれるインテリジェントなエージェントを配置することが不可能になります。

したがって、すべてのエージェントが相互接続され、オープンになっているインターネットだけが AI 機能を最大限に解放し、強力なエージェント ネットワークを構築できると私たちは考えています。

特に異なるプラットフォームのエージェントの相互接続に向けた最初のステップは、それらの間でクロスプラットフォーム ID 認証を有効にすることです。

### エージェントに最適な ID ソリューション

現在知られているすべてのソリューションの中で、DID は最も優れた相互運用性を備えています。したがって、私は常に DID がエージェントにとって最適な本人認証ソリューションであると信じてきました。もちろん、DID には適用範囲が限られている、標準の認証ソリューションがないなどの問題がないわけではありません。

幸いなことに、ほとんどのエージェントは新しく構築されたソフトウェアであるため、新しいソリューションを完全に採用できます。 W3C ZCAP-LD プロジェクトは推奨標準にはなりませんでしたが、DID を使用したきめ細かい認証のソリューションを提供するものであり、注目に値します。

ただし、他のソリューションでも本人確認の相互運用性を向上させる方法が検討されており、将来的には選択肢が増える可能性があります。

## エージェントの承認

エージェントの認証とエージェントのアイデンティティは関連していますが、別の問題です。承認は ID 認証に依存することが多いため、これらは関連していますが、解決する問題が異なるため異なります。1 つはユーザーが誰であるか、もう 1 つはユーザーが何ができるかに対応します。

まず、将来的に考えられるいくつかの認証モードを見てみましょう。
- エージェントが既存のインターネット アプリケーションからデータを読み取る
- 異なるエージェントが異なるユーザー データを所有し、ユーザーはエージェント間のデータ アクセスを承認できる
- 統合されたユーザー データ ストレージにより、異なるエージェントが異なるデータにアクセスできるようになります
- 他のユーザー/企業のエージェントとのやり取りにおいて代理人をエージェントに許可するユーザー

### エージェントが既存のインターネット アプリケーションからデータを読み取る

既存のインターネットアプリケーションからデータを読み込みるエージェントは、エージェントが完全なコンテキストを取得するための重要な方法です。 例えば、エージェントを通して、Googleの質問とGitHubコードにアクセスします。 この場合、GoogleやGitHubから承認を取得する必要があります。 このプロセスは、一般に、インターネット上で最も広く使用されている技術である OAuth を使用します。

![既存のインターネットアプリケーションからのデータを読み出すエージェント](../../blogs/images/agent-authorization/agent-connect-existing-app.png)

### 相互にエージェントのデータアクセス許可

将来的には、各エージェントに独立したIDを持つユーザーと、異なるユーザデータを保持する各エージェントが複数のエージェントを所有することができます。 1つのエージェントがより完全なユーザーコンテキストを取得できるようにするには、ユーザーはこのエージェントを他のエージェントのユーザーデータにアクセスすることができます。

![相互にエージェントのデータアクセス許可](../../blogs/images/agent-authorization/multi-agent-auth.png)

数値に示すように、クロスエージェントのデータアクセスには2つの手順が含まれます。
- エージェントBでは、ユーザーはエージェントCを認可してB内のデータ権限にアクセスします。 例えば、C の ID をエージェントで認証することで実現できます。
- Agent C は、ユーザの認可を使用して、B のエージェントでユーザーデータにアクセスします。 エージェントBが承認を検証した後、データを返します。

### ユニファイドデータストレージ認証

これは私の好きなモードです。将来的には、人々のデータは一箇所に均一かつ安全に保存でき、データに対する絶対的な社会性を持つ人々です。 エージェントはデータ権限を保有していませんが、ユーザーのデータのアクセス(読み込みまたは書き込み)の部分にアクセスするユーザーによって許可されます。 ユーザーは、エージェントのデータをいつでもデータへのアクセスを再開できます。これにより、ユーザーが自由に使用するエージェントを選択することができます。

![ユニファイドデータストレージ認証](../../blogs/images/agent-authorization/one-data-center.png)

このモードでは、A, B, C のエージェントに独立した ID がユーザデータがデータセンターに均一に保存されます。 ユーザーは、エージェント A、B、C を認証して、データセンター内のデータの一部にアクセスすることができます。

このモードは、ユーザーが完全に制御するアカウントを所有しているか、エージェントがこれらのアカウントを使用してデータセンター内のユーザーデータにアクセスできるようにすることで、さらにかかる可能性があります。

### 相互にエージェントのインタラクション認証

このモードは、他のユーザー/エンタープライズのエージェントとの相互作用でそれらを表すためにエージェントを認可するユーザを表していることを意味します。

![相互にエージェントのインタラクション認証](../../blogs/images/agent-authorization/agent-interact.png)

例えば、アリスがホテルを予約するのに役立つエージェントを望んでいるならば、アリスのエージェントはアリスのIDを使ってホテルのエージェントにアクセスし、アリスのIDを使用してホテルの予約をするためにAliceのIDを識別する必要があります。

これらは、二つの種類の承認を含みます。
- 一般の許可:アリスは、客室や価格など、ホテルの代理店から一般情報にアクセスするために彼女のアイデンティティIDを使用するためにエージェントを承認します。 それぞれの情報へのアクセスには、アリスのマニュアルの承認を要求しないため、1回の許可が十分である。 それ以外の場合、インタラクションプロセスは面倒なものになります。
- 特別許可:アリスは、予約ホテルなどの重要な業務を遂行し、注文のために支払いを行うために、自分の身元IDを使用する代理店を承認します。 ライセンスの認証は、毎回Aliceのマニュアル承認が必要です。 それ以外の場合、セキュリティリスクがあります。

### エージェントの認可ソリューション

既存のシステムとの相互運用性が必要な場合は、既存のシステムがOAuthのみをサポートするOAuthなどの既存システムでサポートされている認可ソリューションを使用します。

しかし、新築のエージェントは、エージェントに適した認可ソリューションを探求する。

上記エージェントのアイデンティティセクションでは、DIDがエージェントにとって最も適したアイデンティティソリューションであると述べましたが、DIDベースの認可ソリューションはまだ開発されていないと述べました。 W3C DID が付属するW3C VC(検証可能な認証)は、特に「ユーザは組織の従業員」や「ユーザーが法的年齢である」などの属性、許可、資格を表現するために、いくつかの承認シナリオに使用することができます。

「30分程度の特定のリソースへのアクセスを読み込む」などの表現をする際にVCソリューションはやや複雑で、発行費用、検証、および再発のコストが比較的高い可能性があります。 W3C ZCAP-LDは、この問題を解決するための興味深い技術ですが、現在コミュニティドラフト状態にあります。

IETFのGNAP(Grant Negotiation and Authorization Protocol)は、IETF GNAPワーキンググループが提案し、OAuth 2.0の欠点を柔軟に、セキュリティ、拡張性に取り組むことで、AIエージェントやIoT、分散型アイデンティティなどの新しいシナリオに適応させる権限プロトコルを可能にしています。

GNAPは、DIDをサポートし、注意を払う価値のあるソリューションです。

## エンドツーエンド暗号化

2つのエージェントがメッセージを通して通信し、メッセージ中継のためにサードパーティのサービスを使用する場合、この通信は保護されない場合があります。メッセージは傍受されるか、または第三者によって復号化される可能性があるからです。

この場合、サードパーティサービスがコンテンツを復号化できないままメッセージを便利に中継できるようにエンドツーエンドの暗号化技術が必要です。

これらの2つのエージェントが直接通信する場合、例えば各プラットフォームがパブリックネットワークエンドポイントに適用される異なるプラットフォームに属する2つのエージェントは、エンドツーエンドの暗号化を必要としないメッセージセキュリティを確保するために、従来のHTTPSまたはWSSを直接接続して使用できます。
