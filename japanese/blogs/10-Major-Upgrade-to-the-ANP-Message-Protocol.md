# ANP メッセージ プロトコルへのメジャー アップグレード: エージェントのコラボレーションのために設計されたプロトコル

最近、ANP メッセージング プロトコルに大幅な調整を行いました。また、コミュニティ ミーティングでもこのアップグレードの背後にある考え方を共有しました。この記事では、変更点を体系的に説明します。

まず、いくつかの重要な質問に大まかに答えてみましょう。より詳細な技術的な概要については、記事の後半で説明します。全体的な理論的根拠に興味がある場合は、以下のセクションを参照するだけで十分です。技術的な詳細が必要な場合は、読み続けてください。

1. なぜプロトコルが必要なのでしょうか?

これについては、これまでの記事で何度も取り上げてきました。一言で言えば、将来のエージェントは単一の組織内で連携するだけではありません。また、インターネット上のドメインを越えてコラボレーションすることもできます。プロトコルは、特にオープンなインターネット上でコンテキストを送信する最も効率的な方法です。

2. なぜ新しいプロトコルが必要なのでしょうか?

メッセージングには、XMPP、Matrix、電子メールなど、すでに多くのプロトコルがあります。なぜ別のものをデザインするのでしょうか？

最も重要な理由は、既存のプロトコルのほとんどが人間向けの IM または電子メール システム用に設計されており、そのほとんどが ID と通信を密接に結び付けていることです。エージェントのシナリオでは、ID は通信に使用されるだけではありません。また、支払い、取引、承認、その他多くのアクティビティもサポートする必要があります。

したがって、エージェントネイティブのプロトコルが必要です。 ANP は、アイデンティティとビジネス ロジックを他のアプローチよりも疎結合に保ちます。

3.  DID に基づいており、アイデンティティと通信を分離する DIDComm を使用してみませんか?

私たちは設計プロセスの早い段階で DIDComm を研究しました。 DIDComm は、DID に基づく汎用の安全なメッセージング フレームワークです。これは完全な IM プロトコルではありません。チャット システムというよりも、「安全なメッセージ エンベロープ + ルーティング + 上位層プロトコル キャリア」に近いものです。

また、グループなどの核となる IM 概念も欠如しています。

4. このアップグレードは主にどのような問題を解決しますか?

このアップグレードには少し時間がかかりましたが、その価値は十分にありました。主な改善点は次のとおりです。

- **セキュリティの強化。** 署名では RFC 9421 および RFC 9530 を使用してセキュリティを強化し、より標準化された ID 検証方法を採用するようになりました。
- **より強力なクロスドメイン機能。** 以前の設計では、クロスドメインのコラボレーションにまだギャップがありました。たとえば、メッセージがサーバーによって構築されたものではなく、実際に特定の人から送信されたものであることを暗号的に証明するにはどうすればよいでしょうか?新しい設計では、プルーフを使用して、クロスドメイン フローのすべてのステップが安全であることを保証します。
- **より強力な E2EE。** 当社は常にエンドツーエンドの暗号化を重視してきました。これは世界的にも大きな焦点となっています。たとえば、イーロン・マスク氏の XChat の目玉機能の 1 つは、エンドツーエンドの暗号化です。このアップグレードでは、ダイレクト メッセージ E2EE は Signal スタイルのアプローチに合わせて調整され、グループ メッセージングは​​ IETF MLS を使用します。 MLS と DID を組み合わせることで、メンバーシップ変更の複雑さなど、以前のグループ E2EE 設計の多くの欠点が解決されます。
- ** ファイル転送とファイル E2EE のサポート。** 以前のバージョンではファイルのサポートが弱かった。このバージョンでは、ダイレクト メッセージおよびグループ内のファイル、ファイル セキュリティの考慮事項、ファイルのエンドツーエンド暗号化など、包括的なファイル サポートが提供されます。
- ** より柔軟なメッセージ エンベロープ。** メッセージは JSON-RPC 2.0 でカプセル化されます。 JSON-RPC 2.0 はメッセージ エンベロープとして非常に柔軟なので、それを直接再利用します。

5. このアップグレードに含まれないものは何ですか?

- ** マルチデバイス サポートは含まれていません。** Matrix と Signal には強力なマルチデバイス サポートがありますが、このアップグレードではプロトコル レベルでは追加されませんでした。私たちは、ANP がクロスドメイン相互運用性プロトコルとして位置付けられていると考えています。エージェントが持つデバイスの数はドメイン内の問題であり、複雑さを他のドメインにさらすべきではありません。言い換えれば、別のドメインのエージェントにメッセージを送信するとき、そのエージェントがメッセージを 1 つのデバイスで受信するか複数のデバイスで受信するかは、エージェント自身の判断となります。気にする必要はありません。これにより、プロトコル全体の複雑さが軽減され、実装の柔軟性が向上します。そうしないと、プロトコルが非常に複雑になってしまいます。
- **このアーキテクチャは現在、リレー転送のみをサポートしています。** これはどういう意味ですか?エージェントが別のプラットフォーム上のエージェントとメッセージを交換したい場合は、独自のメッセージ サービスが必要です。メッセージを他のエージェントに直接送信することはありません。技術的には、エージェント間の直接メッセージングが可能です。今回はこれを含めませんでしたが、主な理由は、エージェントが近くのメッセージ サービスに接続し、それらのメッセージ サービスが中継機能を提供するアーキテクチャが主流になると考えているからです。このアーキテクチャは最高の QoS も提供します。

6. アップグレード中に最も驚いたことは何ですか?

DIDは本当に便利です。 DID ID をエージェントだけでなく、グループやサービスにも適用しました。これにより、マルチパーティ フローにおける複雑な ID、権限、資格情報の問題が完全に解決されました。

最後に、このテクノロジーに興味がある場合は、明日のコミュニティ ミーティング (5 月 14 日) でアップグレードを再度紹介します。ディスカッションに参加して貢献することを歓迎します。

## 要約

このプロトコルのアップグレードの焦点は、古い仕様に少しずつパッチを適用することではありません。代わりに、「ID 認証」と「インスタント メッセージング」の両方を「機能する」状態から「より標準化され、より検証可能になり、クロスドメインの相互運用性により適した」状態に引き上げます。

ID の面では、新しい `did:wba` は単なる「DID に基づくリクエスト署名」ではなくなりました。さらに、**パスベースの DID とバインドされた公開鍵フィンガープリント間の強力なバインディング**、**DID ドキュメントのトップレベルの整合性証明**、**RFC に基づく HTTP メッセージ署名が導入されています。 9421**、および **RFC 9530** に基づくコンテンツ ダイジェスト。これらのメカニズムは、DID、キー、ドキュメント、リクエストの 4 つのレイヤーを組み合わせて接続します。

メッセージング側では、新しい ANP は、すべてのセマンティクスを伝送するために 1 つの大きなモノリシック仕様を使用しなくなりました。これは 8 つのプロファイルに分割されています: ** コア バインディング、アイデンティティと検出、ダイレクト メッセージングの基本セマンティクス、グループ メッセージングの基本セマンティクス、ダイレクト E2EE、グループ E2EE、添付ファイルとオブジェクト転送、およびフェデレーション/クロスドメイン通信**。その結果、ビジネス セマンティクス、セキュリティ セマンティクス、オブジェクト転送、およびクロスドメイン呼び出しは分離されますが、統合されたバインディング層を通じて再構成されます。

新しい設計の価値を一言で言えば、次のようになります。 **ID の信頼性が高まり、メッセージングがより階層化され、暗号化がより標準化され、クロスドメインのコラボレーションがエンジニアリングの現場で真に展開可能になります。**

## I。アップグレードを続ける理由

以前の `did:wba` とインスタント メッセージング プロトコルは、すでに重要なアップグレードが行われていました。以前の ID スキームでは、クロスプラットフォーム認証に DID が導入されていました。以前のインスタント メッセージング プロトコルも、以前の WebSocket ルーティングと対話型ハンドシェイクから、JSON-RPC 2.0 ベースのメッセージ形式、HPKE ベースのダイレクト メッセージ E2EE、および送信者キー ベースのグループ E2EE に進化しました。言い換えれば、以前のデザインは原始的なものではありませんでした。エージェントがチャットしてメッセージを暗号化できるようにするという核心的な問題はすでに解決されていました。

ただし、プロトコルがクロスドメイン相互接続、グループ ガバナンス、添付ファイル転送、フェデレーション サービス呼び出し、および長期的な標準化に向けてさらに進むにつれて、以前の設計では新たなボトルネックが明らかになり始めました。

1. **ID 認証が標準化されていないか、十分に強く束縛されていませんでした。**
以前の Did:wba はすでに署名付き認証を実行できましたが、DID パスとバインドされた公開キーの間にデフォルトの強力なバインディングがありませんでした。リクエスト署名では引き続きカスタム `Authorization: DIDWba ...` ヘッダーが使用されました。トップレベルの DID 文書証明、最新の TLS サービス ID 検証ルール、および標準化されたチャレンジ メカニズムはまだ不完全でした。

2. **メッセージング プロトコルは依然としてモノリシックすぎました。**
以前のインスタント メッセージング仕様では、メッセージ フォーマット、トランスポート バインディング、E2EE、グループ、インターフェイスの例、およびその他の機能が 1 つのドキュメントにまとめられていました。これにより、簡単に始めることができましたが、プロトコルが進化し続けるにつれて、その境界はますます曖昧になってきました。

3. **グループ、アタッチメント、フェデレーションなどの複雑なシナリオには、より明確な抽象化レイヤーが必要でした。**
以前のグループ E2EE では、送信者キー + エポック ローテーションが使用されていました。それは機能しましたが、大規模グループのスケーラビリティ、標準化、グループ状態との結合、およびグループ結果の確認にはまだ改善の余地がありました。オブジェクト転送とフェデレーションクロスドメイン通信も、明確な独立した機能層に分割されていませんでした。

したがって、新しい設計は以前の設計を覆すものではありません。その基盤を継続し、長期にわたって維持できるプロトコル スタックに向けて進化します。

## Ⅱ.新しい ID 認証: 「署名可能」から「強力なバインディング、強力な検証、強力な相互運用性」へ

### 2.1 新しいdid:wbaの背後にある全体的な考え方

新しい `did:wba` の中心的な目標は、「ドキュメントはどこで見つけられますか?」という質問以上の DID 回答を作成することです。また、次の質問にも答える必要があります。

1. この DID は実際にどのキーにバインドされていますか?
2. この DID ドキュメントはプラットフォームによってサイレントに置き換えられましたか?
3. このリクエストは、DID に対応する秘密キーの所有者によって開始されましたか?
4. サーバーは余分なラウンドトリップを追加せずに標準化された検証を完了できますか?

これらの疑問を解決するために、新しい Did:wba では 4 層の設計が導入されています。

* **DID レイヤー**: パスベースの DID は、デフォルトでバインドされた公開キーのフィンガープリントを保持します。
* **ドキュメントレイヤー**: `e1_` パスベースのDIDはトップレベルを必要とします `proof` DID ドキュメントで。
* **リクエストレイヤー**: リクエストは署名されます `Signature-Input` / `Signature` / `Content-Digest`.
* **セッションレイヤー**: 認証が成功すると、アクセストークンは経由して返されます `Authentication-Info`.

### 2.2 パスベースのDIDが導入 `e1_` デフォルトでバウンドパブリックキー指紋

新しいdo:wba の最大の構造変更は、デフォルトの設計です。 **新しく作成したパスベースのDID**: DID パスの最後のセグメントは、 `e1_` パブリックキー指紋をバインド。 単なる「サフィックスを追加」ではなく、DID自体がバインドの公共キーに関連する検証可能なセマティクスを直接運ぶ。

これにより、次の 3 つの直接的なメリットがもたらされます。

* **DID とユーザーが保持するキー間の強力なバインディング**
* **プラットフォームが ID 公開キーをサイレントに置き換えるリスクの軽減**
* **ハンドル/WNS**に安定した名前が委任された、ID ローテーションのより明確な境界

新しいメイン仕様のデフォルトプロファイルは `e1_`つまり、 **でぶっかけ25519**. . . 同時に、 `k1_` 互換性拡張は、付録に残ってサポートします **秒数256k1** エコシステム。 これは、新しいデザインのメインパスが、既存の生態系との互換性を放棄することなく、標準化と長期間の相互運用性を強調することを意味します。

対照的に、以前の Did:wba のパスベースの DID は通常のパスでした。バインドされた公開キーの指紋を DID パス内に直接配置しませんでした。

### 2.3 DID 文書が「公開鍵のリスト」から「結合関係の証明」にアップグレード

以前の Did:wba DID ドキュメントでは、すでに `authentication`、`keyAgreement`、`service` などのフィールドを表現でき、複数の検証方法タイプが許可されていました。ただし、新しいバージョンでは、DID ドキュメントの役割が強化されています。「キーをリストする」だけでなく、「このドキュメントが DID パス バインディングと一致していることを証明する」必要もあります。

したがって、デフォルトの `e1_` プロファイルに対して、新しいバージョンではいくつかの重要な制約が追加されています。

* DID ドキュメント **レベルトップレベルを持っている必要があります `proof`**.
* とりあえず `proof` **必須 必須** 利用条件 `DataIntegrityProof + eddsa-jcs-2022`.
* 対応するEd25519公開鍵のRFC 7638サムネイル `proof.verificationMethod` **最終的な一致を丁度とらなければなりません `e1_` DIDパスの指紋**.

このステップは非常に重要です。以前の Did:wba は主に「認証要求」層で署名を検証していました。新しいバージョンでは、**DID パス、バインドされたキー、文書証明、および認証関係** が 1 つの継続的な検証チェーンに統合されます。

### 2.4 カスタム ヘッダーから標準 HTTP メッセージ署名への認証アップグレードの要求

以前の Did:wba リクエスト認証方法はカスタムでした。

```http
Authorization: DIDWba did=..., nonce=..., timestamp=..., verification_method=..., signature=...
```

この設計は機能しますが、本質的にはプロトコルのプライベート形式であるため、既存の HTTP セキュリティ メカニズムや標準エコシステムとの統合が困難になります。

新しい Did:wba は、標準化されたパスに直接移行します。

* 利用条件 **RFC 9421の特長** `Signature-Input` とりあえず `Signature` リクエスト署名を表すヘッダー。
* 利用条件 **RFC 9530の特長** `Content-Digest` メッセージ本文の完全性を結合する。
* アクセストークンを通して返す **`Authentication-Info`** 認証を成功させる。
* チャレンジ情報と次のリクエストがカバーされるコンポーネントを返す **`WWW-Authenticate` + `Accept-Signature`** 認証が失敗したとき。

これは、新しい ID 認証スキームが「カスタム DID 署名ヘッダー」ではなくなったことを意味します。代わりに、DID ID 検証を成熟した HTTP 標準セマンティクスに組み込みます。エンジニアリングの実装にとって、この変更は非常に価値があります。

* リクエストの対象範囲がより明確になりました。
* サーバーチャレンジがより標準化されました。
* ミドルウェアとゲートウェイの統合が容易になります。
* 標準ライブラリと既存の実装は再利用しやすくなっています。

### 2.5 TLS、トークン、高保証認可セマンティクスもより明確に

新しい Did:wba では、エンジニアリング上重要ないくつかの問題も強化されています。

* **TLSサービスID認証**: 以前のバージョンは「共通名マッチングを証明する」に近いでした。新しいバージョンは明示的に要求します `subjectAltName.dNSName` もはや共通名に依存しません。
* **トークンリターン方法**: 以前のバージョンはアクセストークンを通常の状態に戻すために近づいた `Authorization: Bearer ...` 応答ヘッダー。 新しいバージョンは、サーバーがアクセストークンを通し、 `Authentication-Info`.
* **ヒューマン確認のセマンティクス**: 以前のDID文書には、 `humanAuthorization` フィールド。 新たにバージョンは、このフィールドを明示的に削除し、DID文書から上層認証ポリシーやインターフェイスのセマンティックスなど、DID文書から「人間の存在が要求されるかどうか」に移動します。 `authorizationLevel: user-presence-required`. . . これにより、DID文書は適切な責任に立ち向かう: アイデンティティ機能を宣言するだけでなく、あまりにも多くのビジネス認可のセマンティックスで混合するよりも。

| メッセージ本文の完全性 | 統一された標準フィールドなし | 利用方法 `Content-Digest` | クリアーアンチ改ざんセマティクス |
| 成功の後のトークン | 比較的緩いセマンティックス | 返品について `Authentication-Info` | HTTP認証のセマティクスと整列する |
| 人員確認 | `humanAuthorization` DID ドキュメント | 認可ポリシー層まで移動 | 本人と権限の責任を分離 |
| TLS検証 | CNマッチングに近づく | 明示的に使用 `subjectAltName.dNSName` | 現代のTLSの練習と整列が良くなる |

一文で言えば、**新しい Did:wba は、「DID が誰であるか」、「ドキュメントが信頼できるかどうか」、「リクエストが DID によって開始されたかどうか」を、完全で標準化された検証可能なチェーンに変えます。**

## III.新しいエンドツーエンドのインスタント メッセージング プロトコル: 「モノリシック メッセージング プロトコル」から「階層化プロトコル スタック」へ

### 3.1 1 つの大きな仕様から 8 つのプロファイルまで

以前のインスタント メッセージング プロトコルの利点は、直感的であることでした。あるドキュメントでは、メッセージ フォーマット、トランスポート バインディング、ダイレクト メッセージング、グループ メッセージング、E2EE、およびインターフェイスの例が説明されていました。読者は、それを読んだ後に基本バージョンを実装できます。

しかし、その問題も明らかでした。プロトコルが成長するにつれて、あらゆる機能を 1 つの仕様にまとめると、境界がますます曖昧になります。たとえば、バインディング層の問題、ビジネス層の問題、暗号化層の問題、オブジェクト転送の問題、およびクロスドメイン フェデレーションの問題が徐々に混在していきます。

新しい ANP のコア アップグレードは、プロトコルを 8 つのプロファイルに分割することです。

| プロフィール | 役割 | 解決した問題 |
| --- | --- | --- |
| P1コア結合 | 外部メッセージの結合を統一 | JSON-RPC制約, `meta/auth/body`、機能交渉、idempotencyの間違いモデル |
| P2 アイデンティティとディスカバリー | DIDとサービスディスカバリーの未然化 | 代理店のID、グループDID、 `ANPMessageService`, 発見と選択 |
| P3はメッセージング・ベースのSemanticsを指示します | ダイレクトメッセージングビジネスレイヤーの特定 | `direct.send`、コンテンツ モデル、受け入れの皮下主義、 `sender_proof` |
| P4グループメッセージングベースセマティクス | グループライフサイクルとグループメッセージの統一 | グループ作成、メンバーの追加、メンバーの削除、グループポリシー、 `group_receipt`、グループ ホストの発注 |
| P5 直接エンドツーエンド暗号化 | 直接 E2EE オーバーレイを定義 | プレキー バンドル、X3DH のような、ダブル ラチェットのような |
| P6グループエンドツーエンド暗号化 | グループ E2EE オーバーレイを定義する | MLS、KeyPackage、外部コミット、 `did_wba_binding` |
| P7 添付ファイルとオブジェクト転送 | アタッチメントと大型のセマティクスを統一 | `attachment_manifest`、オブジェクト サービス、チケットをダウンロードし、オブジェクトレベルの暗号化 |
| P8 フェデレーションとクロスドメイン | クロスドメイン呼び出し原則を統合 | サービス検出、クロスドメイン転送、グループホスト、オブジェクトサービス宛先 |

この分割の最大の価値は、**ベース ビジネス ロジック、E2EE、セキュリティ証明、オブジェクト転送、およびフェデレーション/クロスドメイン通信が、同じ外部バインディングを共有しながら独立して進化できることです。**

### 3.2 新しいプロトコルは「チャット API」ではなく、エージェント エコシステムのクロスドメイン通信標準です

以前のプロトコルは「メッセージング システム API 仕様」に近いものでした。新しいプロトコルは 1 つ上のレベルに位置し、**さまざまなドメイン、プラットフォーム、実装のエージェントがどのように相互運用するか** を解決することを目的としています。

したがって、新しいプロトコルでは、いくつかの第一級の概念が強調されています。

* **エージェント DID**
* **グループ DID**
* **ANPメッセージサービス**
* **グループホストサービス**
* **オブジェクトサービス**

これは、プロトコルが単に「メッセージを送信する」だけのものではなくなったことを意味します。次のことを明確に説明し始めます。

* 身元がどのように発見されるか、
* メッセージのアドレス指定方法、
* 誰がグループ状態を命令するか、
* オブジェクトを管理するのは誰ですか、
*  そしてどの層でクロスドメイン成功セマンティクスが確立されるか。

## IV.新しいメッセージング プロトコルの中核となる技術的方向性

### 4.1 統合された外部バインディング: より厳格な JSON-RPC 2.0

1 つの点を特に強調する必要があります。**ANP が JSON-RPC 2.0 を導入するのはこれが初めてではありません。** 以前のインスタント メッセージング プロトコルでは、すでに統一メッセージ形式として JSON-RPC 2.0 が使用されていました。新しいバージョンの本当の変更点は、この基盤をさらに強化し、形式化したことです。

P1 でのキーの締め付けには次のものが含まれます。

* `params` **必須 必須** オブジェクトになります。
* `id` **必須 必須** 空でない文字列になります。
* バッチリクエストは**禁止**です。
* 通知は、明示的に定義された非同期通知にのみ使用されます。
* 一般的なトップレベル `params` 構造は固定されますとして `meta / auth / body`.
* `anp.get_capabilities` 機能交渉のために導入されます。
* `operation_id` とりあえず `message_id` 統一された出欠およびメッセージの識別のために導入されます。
* `security_profile` 明示的に区別 `transport-protected`, `direct-e2ee`と `group-e2ee`.

つまり、新しいプロトコルは「JSON-RPC への切り替え」ではありません。これにより、JSON-RPC がプロトコル スタック全体の統合バインディング層に昇格します。

### 4.2 統一されたアイデンティティの発見: `ANPMessageService` 統一された記入項目としてポイント

P2の重要な変化は、エージェント、グループ、オブジェクト、および関連性が統一された状態でできるだけ多く収束されていることです。 **`ANPMessageService`**. . . 本サービスの背後にある実装は、ホーム、キー、グループ、参加、機能、オブジェクトなどの役割を担うことができます。

前バージョンのより「一般的な概要」スタイルのインターフェイスとエンドポイントの説明と比較して、新バージョンでは「検出エントリ ポイント」と「機能ネゴシエーション」がよりプロトコル化され、フェデレーションにより適したものになっています。

### 4.3 ダイレクトメッセージ セキュリティ モデル: 「ワンステップ HPKE Init」から「Prekey Bundle + X3DH-like + Double Ratchet-like」へ

これは正確に述べなければなりません。**以前のダイレクト メッセージ E2EE は、初期の 3 ステップの ECDHE ハンドシェイクではありませんでした。それはすでに HPKE のワンステップ初期化とチェーンラチェットでした。** したがって、新旧の設計の比較を「安全でないものから安全なものへ」というように単純化すべきではありません。これは、「使用可能な HPKE セッション初期化モデルから、より成熟した非同期セッション確立モデルへ」と説明されるべきです。

新しいダイレクト メッセージ E2EE の中核となる技術スタックは次のとおりです。

* **プレキーバンドル**
* **署名付きプレキー/ワンタイムプレキー**
* **X3DH のような初期非同期セッション確立**
* **後続のメッセージに対するダブルラチェットのような保護**
* **AAD バインディング、アウトオブオーダー処理、リプレイ保護、およびセッションの再構築**

この設計が重要なのは次の理由からです。

1. **非同期オフライン シナリオにより適しています**: 送信者は、受信者がオンラインになって応答するまで待つ必要がありません。
2. **単純な HPKE init よりも成熟した IM セキュリティ モデルに近いです。**
3. **セキュリティ境界は明確です**: P5 は、署名/注意キーを明示的に分離する必要があります `keyAgreement` キーとバンドルの署名が省略できないことを強調します。
4. **将来のアップグレードの余地を残す**: P5 は、v1 はポスト量子スキームではないが、PQXDH のような設計にアップグレードする余地を確保していると明確に述べています。

### 4.4 グループ セキュリティ モデル: メイン パスとしての送信者キーから MLS まで

以前のグループ E2EE 設計のコアは、**送信者キー + エポック ローテーション** でした。これは中小規模のグループにはうまく機能しますが、限界も明らかです。

* 送信者キーの配布は、**O(N)**です。
*  グループ メンバーシップの変更、ウェルカム フロー、外部参加、およびグループ状態の証明は、長期的に標準化されたグループ暗号化モデルでエレガントに表現するのが困難です。

以前の仕様自体は、**MLS 統合** を将来の方向性として特定していました。 P6 では、新しいバージョンはこの「将来の方向性」をメインパスに移動します。

* **MLS** はグループ鍵ステートマシンとして機能します。
* **did:wba** はアイデンティティ アンカーとして機能します。
* **行なった_ウィバ_結合の** MLS の葉の署名キーを結合します `agent_did`.
* **グループ ホスト サービス** は注文と受領書を処理しますが、デフォルトではグループ プレーンテキストを保持しません。
* `group_did`, `group_state_version`と `policy_hash` 暗号グループの状態にバインドされます。
* グループ メッセージは、**MLS PrivateMessage** として伝送されます。

これは大きな一歩です。**グループ E2EE はもはや「機能するカスタム グループ暗号化設計」ではありませんが、長期的な標準化パスに直接接続されています。**

### 4.5 証拠モデル改善: `sender_proof`, `actor_proof`と `group_receipt`

以前のプロトコルでは、メッセージの暗号化とメッセージ送信が主な焦点でした。新しいバージョンでは、「誰がリクエストを開始したか」「誰がリクエストを受け入れて命令したか」「誰が復号化権限を持っているか」という 3 つの質問が厳密に分離されています。

ダイレクトメッセージの場合:

* `sender_proof` 与えられたことを証明します `direct.send` 確かに、その始まりは `sender_did`.
* ホップレベル認証は、特定のホップでの発信者の身元を証明するだけです。 **元の送信者の証明** を置き換えることはできません。

グループの場合:

* `actor_proof` グループ操作やグループメッセージの開始を証明する。
* `group_receipt` グループホストが、グループが受け入れられ、操作やメッセージの注文をしていることを証明するために生成されます。
* MLS メンバーの署名は、どの暗号メンバーがハンドシェイクまたは暗号文を作成したかを証明します。

これにより、新しいグループ プロトコルがガバナンス シナリオにより適したものになります。すべての問題を 1 つの署名に混合するのではなく、**開始者の証明、グループ結果の目撃、およびグループ内の機密性** という 3 つのセマンティクス層を同時に保持します。

### 4.6 添付ファイルとオブジェクト: インラインメッセージからマニフェスト + オブジェクトサービスまで

以前のプロトコルは、`image` や `file` などのメッセージ タイプをサポートし、大きなファイルの効率の問題を認識していましたが、独立した完全な、クロスドメインで再利用可能な添付オブジェクト仕様を提供していませんでした。

P7 は添付ファイルを形式化します。

* メッセージレイヤーは、メッセージレイヤーのみを運ぶ **`attachment_manifest`**.
*  オブジェクト層は、**オブジェクト サービス** を通じてアップロードおよびダウンロードします。
* アクセス制御は、**有効期限の短いダウンロード チケット**を使用します。
* より高い機密性の条件のため、 **オブジェクトレベルの暗号化()`object-e2ee`)** 有効化できます。
* リレー**はオブジェクト バイト ストリーム**を転送しません。

これは、新しいプロトコルが「メッセージ コントロール プレーン」を「オブジェクト データ プレーン」から完全に分離することを意味します。エンジニアリングの実装では、この手順はクロスドメイン メッセージング リンクと大きなバイト ストリームの間の結合を大幅に軽減するため、ほぼ必須です。

### 4.7 フェデレーションとクロスドメイン通信: 「後で定義」からスタックのファーストクラスの部分へ

以前のプロトコルでは、メッセージ サーバー間の通信は仕様の範囲外であり、サーバー間の相互運用性は今後の課題であると明示的に述べられていました。

P8 では、この部分が正式に主要仕様システムに組み込まれます。

* クロスドメイン通信**は、新しいリレーメソッドでラップする代わりに、元のビジネスメソッド**を直接使用します。
* 直接クロスドメインメッセージングの使用 `direct.send` 直接。
* 横断グループ操作の使用 `group.create`, `group.send`, `group.add`, `group.remove`、および同じような方法直接。
* `attachment.get_download_ticket` 最終オブジェクトサービスに直接送信します。
* オブジェクト バイト ストリーム**は、クロスドメイン サービス呼び出しチェーンを通過してはなりません**。
* クロスドメイングループ操作の成功セマンティクスは、**グループホスト**による受け入れと順序によって決まります。
* ダイレクト クロスドメイン メッセージの成功セマンティクスは、**ターゲット エージェントのエントリ サービスによる受け入れ**によって決まります。
* オリジナル `sender_proof` / `actor_proof` ドメインを越えて保存し、中間サービスで書き換える必要は無い。

これは、新しいプロトコルが単なる「単一ドメインのメッセージング API」ではなくなったことを示しています。 **フェデレーテッド エージェントの相互運用性** に必要なプロトコル境界が設定されました。

| フェデレーションとクロスドメイン | 将来の課題として扱われる | P8 がクロスドメイン接続と成功セマンティクスを正式に定義する | 真のフェデレーテッド プロトコルになる |

一文で言えば、**以前のバージョンはすでに動作するメッセージング プロトコルでした。新しいバージョンでは、長期的に進化し、クロスドメイン エージェント エコシステムをサポートできるプロトコル スタックにアップグレードされます。**

## VI.最も重視すべき5つの特徴

### 6.1 特徴 1: 高度な標準化

アイデンティティ面では、RFC 9421、RFC 9530、および W3C データ整合性と一致する設計になっています。グループ暗号化側では、MLS に移行しています。メッセージ バインディング レイヤーは、JSON-RPC 2.0 をベースに構築され続けますが、その使用は強化されます。新しい設計は明らかに、社内独自のプロトコルではなく、長期的な標準化の道に近づいています。

### 6.2 特徴 2: より強力なアイデンティティ結合

`e1_` フィンガープリント パスと DID ドキュメント証明は、DID、キー、ドキュメントの間のバインディングを、「論理的に正しい」ものから「プロトコルによって義務付けられ検証可能な」ものに変えます。これは、新しい ID 設計における最も重要なセキュリティの改善点の 1 つです。

### 6.3 特徴 3: ビジネス層とセキュリティ層間の真の分離

`transport-protected`、`direct-e2ee`、および `group-e2ee` は、構成可能なセキュリティ プロファイルです。基本ビジネス層は独立して動作でき、必要に応じてセキュリティ オーバーレイを追加できます。この設計は、段階的な導入と将来のアップグレードの両方に適しています。

### 6.4 特徴 4: フェデレーションとオブジェクト転送がメインパスに入る

添付ファイル オブジェクト、ダウンロード チケット、クロスドメイン転送、グループ ホストの順序付け、およびオブジェクト サービスの宛先は、以前は「エンジニアリング実装の問題」または「将来の作業」として扱われていました。これらは現在、主要な仕様パスの一部になっています。

### 6.5 特徴 5: チャットだけでなくエージェントのコラボレーションに適しています

新しいプロトコルのキーワードは「メッセージ」だけでなく、次のことも含みます。

* DID
* 発見
* プルーフ
* ガバナンス
* オブジェクト
* フェデレーション
* 領収書

## VII.アップグレードを説明するための推奨される説明

この記事が社外または社内のプレゼンテーションに使用される場合は、次のような説明をお勧めします。

### 第 1 層: アップグレードの目標を説明する

これは用語を変えるということではありません。それは、ID をより信頼できるものにし、ドメイン間の対話をより自然にし、グループ ガバナンスをより明確にし、プロトコルをより長期的な進化に対応できるようにすることです。

### 第 2 層: アイデンティティの説明

3 つの用語を強調表示します。

* **パスバインド**
* **書類証明**
* **標準リクエスト署名**

### 第 3 層: メッセージング プロトコルの階層化について説明します

新しいプロトコルが「チャット インターフェイス ドキュメント」ではなく、階層化されたプロトコル ファミリであることを聴衆が理解できるようにします。

### 第 4 層: 暗号化ルートの変更に焦点を当てる

* ダイレクト メッセージングが「HPKE init」から「Prekey Bundle + X3DH-like + Double Ratchet-like」にアップグレードされました。
* グループ メッセージングは、「送信者キー + エポック」から「メイン パスとしての MLS」にアップグレードされます。

### 第5層：工学的価値で終了

アタッチメントは独立したデータ プレーンを使用します。クロスドメイン通信では、ダイレクト ビジネス メソッドが使用されます。グループ結果には領収書が付いています。サービス検出には統合されたエントリ ポイントがあります。これは、この設計が単なる暗号化ではないことを示しています。それは現実世界のシステムのためのプロトコル エンジニアリングです。

---

## VIII.結論

新しい ID 認証スキームと新しいエンドツーエンドのインスタント メッセージング プロトコルは、次の一文に要約できます。

** アイデンティティ面では、新しい Did:wba は「認証可能」から「強力な結合、強力な証明、および強力な標準化」にアップグレードされています。メッセージング側では、新しい ANP は「チャットと暗号化が可能」から「階層化され、管理可能で、フェデレーションされ、長期的な進化が可能な」プロトコル スタックにアップグレードされます。**

以前の設計で「エージェント通信の構築」の問題が解決された場合、新しい設計では次の問題、**エージェント通信を真に相互運用可能、検証可能、拡張可能なインフラストラクチャにする方法** が解決されます。

## 付録: スライドデッキに対応できる 12 スライド構造

### スライド 1: タイトル

* did:wba から ANP まで: 次世代 ID 認証とエンドツーエンドのインスタント メッセージング プロトコルを理解する
* 一文のポジショニング: エージェントエコシステムのクロスドメイン通信標準

### スライド 2: アップグレードする理由?

*  ID バインドが十分に強くありませんでした。
* プロトコル構造がモノリシックすぎました。
* グループ、アタッチメント、フェデレーションには独立した抽象化レイヤーがありませんでした。

### スライド 3: 新しい ID 認証の背後にある全体的な考え方

* DID パス バインディング
* DID 文書証明
* HTTP メッセージ署名
* コンテンツダイジェスト
* アクセストークンセッションの最適化

### スライド 4: Did:WBA の古いものと新しいもの

* `e1_` / `k1_`
* `proof`
* `Signature-Input`
* `Authentication-Info`
* 移動する `humanAuthorization` レイヤーを上回る皮脂

### スライド 5: 新しいメッセージング プロトコルのアーキテクチャ図

* P1～P8の階層関係
* ビジネス層/セキュリティ層/オブジェクト層/フェデレーション層

### スライド 6: 統合結合層

* 強化された JSON-RPC 2.0
* `meta/auth/body`
* `operation_id`
* `message_id`
* `anp.get_capabilities`

### スライド 7: 直接 E2EE

* プレキーバンドル
* X3DH様
* ダブルラチェット状
* 非同期セッションの確立
* リプレイとアウトオブオーダーの処理

### スライド 8: グループ E2EE

* グループ DID
* グループホスト
* MLS
* `did_wba_binding`
* `group_receipt`

### スライド 9: オリジナル送信者の証明とグループ結果の証人

* `sender_proof`
* `actor_proof`
* ホップレベル認証
* `group_receipt`

### スライド 10: 添付ファイルとオブジェクトの転送

* `attachment_manifest`
* オブジェクトサービス
* チケットをダウンロード
* オブジェクトレベルの暗号化
* 独立したデータプレーンのダウンロード

### スライド 11: フェデレーションとクロスドメイン通信

* ドメインを超えて既存のビジネス手法を直接使用します。
*  グループの成功は、グループ ホストの順序に依存します。
* オブジェクト サービスがチケットの最終宛先です。
* リレーはオブジェクトのバイト ストリームを転送しません。

### スライド 12: 概要

* より信頼できるアイデンティティ
* より標準化された暗号化
* レイヤープロトコル
* より導入可能なエンジニアリング設計
* 横断型のエージェントエコシステムに適した

必要であれば、この材料は10分のプレゼンテーションスクリプトにさらに凝縮することができます。
