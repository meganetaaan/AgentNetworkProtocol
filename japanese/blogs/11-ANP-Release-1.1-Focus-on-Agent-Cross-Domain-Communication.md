# ANP リリース 1.1 が登場: クロスドメイン エージェント通信に焦点を当てた

3 か月にわたる改良を経て、ANP 1.1 は先週正式にリリースされました。

私たちはこのバージョンについてコミュニティミーティングで何度も議論しました。その過程で、コミュニティからのフィードバックと私たち自身の実装作業に基づいて、かなりの調整を行いました。この記事は、このリリースの主な改善点とその背後にある考え方の一部をより正式にまとめたものです。

このアップグレードの核心は主に 2 つです。自己制御 ID とメッセージ プロトコルのアップグレード、特にクロスドメイン通信と安全な通信です。

## 自己管理されたアイデンティティ

ANP は常に、エージェントの ID レイヤーとして DID を使用してきました。

DID の最大の利点は、ID、キー、サービス エンドポイントを検証可能なドキュメントに配置できることです。これにより、異なるプラットフォームや組織が、同じアカウント システムに依存することなく、相互に認識および認証できるようになります。

`did:web` は非常に良い方法です。 DID を既存の Web インフラストラクチャと組み合わせ、ドメイン名、HTTPS、`.well-known` などの成熟したメカニズムを直接再利用します。導入の障壁は比較的低く、既存のインターネット システムとの統合も簡単です。

しかし、`did:web` にも問題があります。DID ドキュメントは Web サーバーでホストされています。つまり、サーバーが DID ドキュメントを変更できる場合、一部の高度なセキュリティのシナリオでは、ユーザーの ID とキーの信頼性に影響を与える可能性があります。

たとえば、エンドツーエンドの暗号化通信に DID を使用し、サーバーが DID ドキュメント内のキー マテリアルをサイレントに置き換えることができる場合、双方は特定のエージェントと安全に通信していると信じている可能性がありますが、実際にはキーがすでに置き換えられている可能性があります。これは通常のログイン認証ではあまり明らかではないかもしれませんが、エンドツーエンドの暗号化やクロスドメイン ID 検証などのシナリオでは重要になります。

そこで、このリリースでは、`did:wba` をアップグレードしました。

正確に言うと、ユーザーの秘密キーを DID に入れているわけではありません。秘密キーを DID に書き込んではなりません。 `did:wba` が行うことは、バインドされた公開鍵のフィンガープリントをパス形式の DID に入れることです。簡単に言えば、DID 自体は、ユーザーが管理する公開キーとの検証可能なバインディングを確立します。

この変更後は、DID ドキュメントが Web サービスによってホストされている場合でも、検証者は DID パス内の公開キーのフィンガープリントが DID ドキュメントで宣言されたキーと一致するかどうかを確認できるようになります。これにより、サーバーによるサイレントキーの置き換えが非常に困難になります。

その結果、秘密キーに対するユーザーの制御を DID ID 自体により直接反映できるようになります。 DID はもはや、Web アドレスの下にある単なる文書ではありません。ユーザーが実際に制御するキーとの関係が強化されました。

もちろん、`did:web` にも独自の利点があります。これは、特に多くの障壁の低い導入シナリオにおいて、安定しており、シンプルで、高い互換性を備えています。したがって、ANP 1.1 は `did:web` を放棄するものではありません。代わりに、ネイティブの `did:web` と `did:wba` の両方をサポートします。シナリオごとに異なるアプローチを選択でき、相互に連携できます。

1.1 のもう 1 つの重要なアイデンティティ設計はハンドルです。

なぜハンドルをデザインしたのか?主に 2 つの理由があります。

一つ目の理由は読みやすさです。

DID は機械には優しいですが、人間には優しくありません。完全な DID は通常長いです。チャット ウィンドウ、名刺、連絡先リスト、招待リンクには適していません。また、ユーザーが手動で入力して覚えるのも困難です。

したがって、次のような人間により適した識別子が必要になります。

```text
alice.example.com
```

このフォームは、ユーザーにとって非常に理解しやすく、共有しやすいです。

2 番目の理由は、`did:wba` に安定した ID を提供するためです。

`did:wba` パスは公開キーのフィンガープリントをバインドするため、基になるキーが変更されると、DID 自体も変更する必要がある場合があります。セキュリティの観点からすると、これは合理的です。しかし、ユーザーエクスペリエンスの観点から見ると、人々は依然として長期的に安定した名前を期待しています。

ハンドルはこの問題を解決するために設計されました。ハンドルは安定したままですが、基になる DID はキー、セキュリティ ポリシー、またはデバイスの変更に応じてローテーションできます。ユーザーにはハンドルが表示されます。プロトコルが ID を検証する必要がある場合、ハンドルを現在の有効な DID に解決します。

したがって、Handle は DID に代わるものではありません。これにより、「人間がアイデンティティをどのように認識するか」という問題が解決されます。 DID は、「プロトコルがどのように検証するか」という問題を解決します。

ハンドルと DID の関係は、ドメイン名と IP アドレスの関係に似ています。

## メッセージプロトコルのアップグレード

ANP 1.1 のもう 1 つの主な改良点は、メッセージ プロトコルです。

メッセージ プロトコルの最初のドラフトは実行できましたが、実装作業を続けると、いくつかの潜在的な問題が見つかりました。

たとえば、添付ファイルのサポートが十分ではありませんでした。クロスドメインコラボレーションには依然としていくつかの難しい問題がありました。エンドツーエンドの暗号化設計は、特に前方秘匿性とグループ キー管理に関して、成熟した業界のアプローチにまだ十分に近づいていませんでした。

設計の最適化を続ける前に、まず問題を再定義しました。

私たちは、ANP を Matrix のような完全な IM プロトコルに変えたくありません。 Matrix は、クライアントからサーバー、サーバーからサーバー、マルチデバイスの同期、ルームの状態、メッセージ履歴など、一連の問題をすべて解決します。その方向性は力強いですが、非常に重いものでもあります。

ANP は別の問題を解決しています。

私たちがさらに関心を持っているのは、異なるドメインおよび異なるシステムにあるエージェントがドメイン間でどのように通信できるかということです。

各ドメインが内部アカウント システムをどのように実装するか、クライアントがどのように登録するか、ユーザーが電話番号と電子メールで認証されるかどうか、エージェントが内部に複数のデバイスや複数の実行者を持っているかどうかについては、メイン プロトコルで定義する必要はありません。

これらすべてを含めると、プロトコルは非常に複雑になります。これらのトピックの多くは内部システムの問題であり、クロスドメインの相互運用性の問題ではありません。

したがって、1.1 のメッセージ プロトコルは、次の 3 つの主要なシナリオに焦点を当てています。

まず、エージェントがダイレクト メッセージとグループ メッセージを送信する方法について説明します。

次に、添付ファイルと大きなオブジェクトがメッセージでどのように送信されるかです。

3 番目は、エージェントが必要に応じてエンドツーエンドの暗号化通信を使用する方法です。

これが問題の境界を定義する方法です。

問題の境界が明確になると、次の設計上の決定が容易になります。ANP 1.1 では、プロトコル層でのマルチデバイスの動作が定義されていません。

マルチデバイスのサポートにより、プロトコルが大幅に複雑になります。デバイスが状態を同期する方法、キーを同期する方法、オフライン メッセージとメッセージ履歴を処理する方法 - これらはすべて複雑です。システムが異なれば、マルチデバイスのサポートに対する要件も異なります。

私たちは、エージェントが内部に持つデバイス、実行ノード、またはレプリカの数は、各システム自体が処理する必要があると考えています。 ANP は、エージェントをクロスドメイン通信の対象として扱います。エージェントが外部にメッセージを送受信できる限り、その内部スケジューリングはプロトコルの相互運用性の境界に入りません。

この決定により、プロトコルは軽量化され、より焦点が絞られたものになります。

### メッセージ プロトコルと DID の組み合わせ

このメッセージ プロトコルのアップグレードにおける非常に重要な設計は、メッセージングと DID の間の緊密な統合です。

当社では、人物やエージェントだけに DID を割り当てることはありません。グループおよびメッセージ サービス用の DID も紹介します。これにより、メッセージング システムにいくつかの異なる役割が作成されます。

1 つ目はエージェント DID で、メッセージの送信者と受信者を表します。もちろん、人間も DID を持つ可能性があります。

2 番目はグループ DID で、グループの ID を表します。グループは、サーバー内の単なる内部ルーム ID ではありません。これは、ドメイン全体で認識、検出、検証できるプロトコルの主題です。

3 番目はサービス DID で、メッセージ サービスを提供するサーバーの ID を表します。クロスドメイン通信では、サービスは相互に認証する必要もあります。ビジネス メッセージ内の送信者が誰であるかだけを確認することはできません。

このデザインの後、アイデンティティ層がより明確になります。

エージェント DID は、誰がメッセージを開始したかを証明します。グループ DID は、グループの ID、グループの状態、およびグループ イベントの順序を証明します。サービス DID は、どのサービスがこの特定のクロスドメイン呼び出しを開始したかを証明します。

これらの DID を混在させてはなりません。

たとえば、サーバーは、Alice のエージェントがメッセージを別のドメインに転送するのを支援することはできますが、メッセージが自分自身で送信されたとは主張できません。サービス ID は、「これを中継している」ことしか証明できません。ビジネス アイデンティティに代わることはできません。

同じことが完全性証明にも当てはまります。異なるロールは独自の DID を使用して、異なるレイヤーでオブジェクトを証明できます。エージェントは、メッセージを開始したことを証明できます。グループホストは、グループメッセージがグループによって受け入れられ、注文されたことを証明できます。サービスは、特定の HTTP 呼び出しが実際にそれ自体から発信されたものであることを証明できます。

これは、実装から得た最も強い印象の 1 つでもあります。DID はクロスドメイン システムに非常に適しています。

クロスドメイン システムにおける最大のリスクは、アイデンティティ セマンティクスに関する混乱です。 DID を使用すると、すべての主体が、同じ集中アカウント システムに依存することなく、独自の ID、独自のキー、および独自の証明メカニズムを持つことができます。

いつかマルチデバイスのサポートが必要になった場合、各デバイスが独自の DID を持つ可能性もあります。

### クロスドメインメッセージが別のレイヤーでラップされない

このリリースにおけるもう 1 つの重要な設計上の決定は、クロスドメイン メッセージが追加のリレー プロトコルでラップされないことです。

つまり、クロスドメインのダイレクト メッセージでは引き続き `direct.send` が使用されます。クロスドメイン グループ メッセージでは引き続き `group.send` が使用されます。グループ メンバーシップの変更には、引き続き元のグループ管理方法が使用されます。クロスドメイン プロファイルは、ターゲット サービスを検出する方法、現在のサービスを認証する方法、元の送信者証明を保存する方法、および操作が成功したとみなされるタイミングのみを定義します。

この選択は単純そうに見えますが、重要です。

ドメイン内に 1 つのメソッド セットがあり、ドメイン間で別の Relay メソッドを発明した場合、プロトコルは時間の経過とともにますます複雑になります。ビジネス セマンティクスは 2 つの層に分割されるため、実装者は混乱しやすくなります。リレー層を検証する必要があるのか​​、それとも元のビジネス層を検証する必要があるのか​​?

そこで私たちはビジネス手法を一貫させることにしました。クロスドメイン通信は呼び出し境界を変更しますが、ビジネス セマンティクスを再定義するべきではありません。

### 添付ファイルとオブジェクトの転送

アタッチメントは、このリリースで強化されたもう 1 つの領域です。

メッセージ サービスがファイル リレー サービスになることは望ましくありません。大きなファイル、画像、オーディオ、またはビデオ オブジェクトがメッセージとともにドメイン間で直接転送される場合、コストと信頼性の問題が重大になります。

したがって、1.1 ではメッセージとオブジェクトが分離されます。

メッセージには添付ファイルの説明、つまり添付ファイルのマニフェストのみが含まれます。実際のオブジェクトのアップロードとダウンロードは、独立した HTTPS チャネル経由で行われます。クロスドメイン メッセージ サービスは、アップロード スロットの要求、オブジェクトのコミット、ダウンロード チケットの取得など、コントロール プレーンにのみ参加します。ファイルのバイトを最後まで中継するわけではありません。

この設計はエンジニアリングにとってより実用的であり、実際の導入により適しています。

オブジェクトにさらに強力な機密性が必要な場合は、オブジェクト レベルの暗号化を有効にすることもできます。オブジェクト サービスは、オブジェクトの平文を知らなくても、オブジェクトを保存および配布できます。

### エンドツーエンドの暗号化通信

最後に、エンドツーエンドの暗号化について話しましょう。

私たちはこれを非常に真剣に受け止めています。一部の重要なシナリオでは、エージェント間のメッセージをサーバーが利用できないようにする必要があります。サーバーはメッセージのルーティング、順序付け、保存、配布を支援できますが、コンテンツを自動的に読み取る機能を備えるべきではありません。

直接メッセージ送信エンドツーエンド暗号化のために、シグナルのアイデアから学んだこと。 送信者は、受信者がオンラインになるのを待つ必要はありません。 受信者の公開鍵の挨拶資料を最初に取得し、暗号化されたセッションを開始することができます。 後続のメッセージは、二重ラチェットのような機構を介してキーを継続的に更新し、より優れた前進秘密を提供します。

グループエンドツーエンド暗号化では、メッセージングレイヤーセキュリティの略でIETF MLSを使用しています。

独自のSender Keyグループキースキームの設計は行いません。 従来のSender Keyスキームは、少人数グループで簡単に見えますが、メンバーの参加、葉、除去、キーの回転が素早く複雑になります。 横断的なシナリオでは、キーを更新するような質問、状態を同期させる人、そして現在のグループの状態を証明する人はさらに問題を作成します。

MLSのメリットは、グループ間のコミュニケーションをしっかり確保するために設計されていることです。 比較的明確なグループキーの状態機械があり、メンバーの変更、キーの更新およびグループのメッセージの暗号化を扱いやすくなります。 ANPでは、DIDを使用してメンバーのアイデンティティ、グループホストをバインドし、ビジネスの注文とレシートを処理するため、およびMLSを使用してグループの暗号化状態を処理します。

グループの暗号化プロトコルを自分で再発明するよりも、この責任の分離はより明確で信頼性が高くなります。

弊社の主な業務は、MLS と DID を統合しています。

## 次のステップ

ANP 1.1 のリリース後、次の2つの方向に焦点を合わせます。

第一方向は、エージェントの許可制御と監査です。

エージェント間のコラボレーションは、メッセージの送信だけでなく、メッセージの送信も行います。 誰が何をするか、最終結果が監査できるかを知る必要があります。 ここでは、W3C DIDをVCと組み合わせます。通常、検証可能な認証情報として、より細かいグラインドされた許可式と結果の証拠をサポートします。

VCは今日多くの分野に研究されており、エージェントのコラボレーションにおいて認可、委任、監査シナリオに非常に適しています。

2番目の方向はメッセージシステムでコンテキスト共有です。

エージェント通信は、ひとつの文を送るだけでなく、 エージェントは、タスクの背景、ツールコール結果、コンテキストの状態、コラボレーションプロセスを共有する必要があります。 プロトコルを重くすることなく、メッセージシステムを通じて、エージェントがコンテキストをより良く共有できるかを引き続き探していきます。

全体的に、ANP 1.1はかなり重要なバージョンのアップグレードです。 「接続可能」から「ドメイン間でのコラボレーションや、識別性の確認、コンテンツの保護」にさらにANPを移動します。

エージェントがオープンに繋げ、独立してデプロイし、今日のWebサービスと同様にドメイン間でコラボレーションできるようにするという目標は同じままです。

1.1をリリースすると、その方向にもう一歩進んでいます。
