# ANP Release 1.1公開：ドメインをまたぐ、エージェントの通信に集中する

三か月の改善を経て、先週、正式に公開しました。

コミュニティの会議で何度も議論し、反応や実装の経験を基に、多くを調整しました。主な改善と、その背景を、正式にまとめます。

中心は二つ、自分で管理するアイデンティティと、メッセージの更新です。特に、ドメインをまたぐ通信と、安全な通信を重視しています。

## 自分で管理するアイデンティティ

ANPは、一貫してDIDを使います。

アイデンティティ、鍵、サービスの入り口を、検証可能な文書に置けるのが利点です。同じアカウントシステムに頼らず、異なる企業や組織が、認識し、認証できます。

`did:web`は優れた方式です。ドメイン、HTTPS、`.well-known`などの成熟したWeb基盤を再利用し、導入が容易で、既存のシステムと統合しやすいものです。

ただし、`did:web`では、WebサーバーがDID文書を変更できると、高い安全性を求める用途では、本人性と鍵への信頼に影響します。

例えば、エンドツーエンド暗号化で、サーバーが鍵を密かに差し替えると、当事者は安全だと思っていても、実際には別の鍵かもしれません。通常のログインでは目立たなくても、暗号化や、ドメインをまたぐ本人確認では重要です。

そこで、`did:wba`を更新しました。

正確には、DIDに秘密鍵を入れるのではありません。秘密鍵は、決して書くべきではありません。`did:wba`は、パス型のDIDに、結び付ける公開鍵のフィンガープリントを入れ、利用者の管理する公開鍵と、検証可能な関係を作ります。

Webで文書を預かっていても、検証者は、DIDのパスのフィンガープリントと、文書の鍵を比較できます。密かな差し替えは、難しくなります。

秘密鍵への利用者の支配が、DID自体に、より直接反映されます。単にWebアドレスにある文書ではなく、実際の鍵との関係が強くなります。

もちろん、`did:web`の安定、単純、互換性の高さも残ります。1.1は、`did:web`を捨てず、ネイティブの`did:web`と`did:wba`の両方をサポートします。用途に応じて選び、相互に接続できます。

もう一つの重要な設計は、Handleです。理由は二つです。

第一は、読みやすさです。DIDは機械向けで、人には長すぎます。チャット、名刺、連絡先、招待リンクに不向きで、入力や記憶も困難です。

そこで、次のような、人向けの名前を使います。

```text
alice.example.com
```

理解し、共有しやすい形です。

第二は、`did:wba`に、安定したIDを与えることです。

`did:wba`は、公開鍵のフィンガープリントを結び付けるため、鍵が変われば、DIDも変わるかもしれません。安全上は合理的でも、人には長期的な名前が必要です。

Handleは安定したまま、鍵、安全方針、端末の変化に合わせ、DIDを更新できます。人はHandleを見て、プロトコルは、現在有効なDIDに解決し、検証します。

DIDの代替ではありません。Handleは「人がどう識別するか」、DIDは「どう検証するか」を担います。ドメイン名とIPアドレスに似た関係です。

## メッセージの更新

最初の草案は動きましたが、実装を進めると、問題が見えました。添付が不十分で、ドメイン間の協働にも難しさがあり、特に前方秘匿性とグループの鍵管理は、成熟した業界の方式に及んでいませんでした。

改善の前に、まず問題を定義し直しました。

Matrixのような、完全なIMプロトコルにはしません。クライアントとサーバー、サーバー同士、複数端末の同期、ルームの状態、履歴などを、すべて解く方向は、強力でも重いものです。

ANPの問題は違います。異なるドメインやシステムのエージェントが、どうメッセージを交換するかです。

各ドメイン内部のアカウント、登録、電話やメールの確認、複数端末や実行器などは、主なプロトコルに含めたくありません。複雑になり、多くは内部の問題で、相互運用の問題ではないからです。

1.1は、三つに集中します。
1. ダイレクトメッセージとグループメッセージ。
2. 添付と、大きなオブジェクト。
3. 必要な場合の、エンドツーエンド暗号化。

これが、問題の境界です。

その結果、1.1のプロトコル層では、複数端末の動作を定義しません。

状態や鍵の同期、オフラインのメッセージや履歴は複雑で、システムごとに要件も違います。端末、実行ノード、複製がいくつあるかは、各システムが扱うべきです。

ANPは、エージェントを、ドメイン間で通信する一つの主体と捉えます。外部へ送受信できれば、内部のスケジューリングは、相互運用の境界に入りません。これで、軽量で焦点を絞れます。

### メッセージとDIDを組み合わせる

重要なのは、深く統合したことです。

人やエージェントだけでなく、グループとサービスにもDIDを与え、役割を分けます。

Agent DIDは、送信者と受信者です。人もDIDを持てます。

Group DIDは、グループの本人性です。単なる内部のルームIDではなく、ドメインを越えて認識、発見、検証できる主体です。

Service DIDは、メッセージを提供するサーバーの本人性です。業務メッセージの送信者だけでなく、サービス同士も認証する必要があります。

Agent DIDは、誰が発信したか、Group DIDは、グループの本人性、状態、イベント順序、Service DIDは、今回のドメイン間呼び出しの開始元を証明します。

混同してはいけません。Aliceのメッセージを転送したサーバーは、自分が送信者だと言えません。「私が中継する」と証明できても、業務の本人性を置き換えられません。

完全性の証明も、層ごとに役割を分けます。エージェントは発信、Group Hostは、グループの受理と順序付け、サービスは、HTTP呼び出しの出所を証明します。

実装を通じ、DIDはドメイン間に適すると実感しました。最も危険なのは、本人性の意味の混乱です。各主体が、独自のID、鍵、証明を持ち、同じ中央アカウントに依存せずに済みます。

将来、複数端末が必要なら、各端末にもDIDを作れます。

### ドメイン間で、もう一層包まない

追加のRelayプロトコルで包まないことも、重要な判断です。

ダイレクトは`direct.send`、グループは`group.send`、メンバー変更は既存の管理方法を使います。ドメイン間のProfileは、相手の発見、現在のサービスの認証、元の送信者の証明の保持、成功の条件だけを定めます。

単純に見えて、重要です。内部とドメイン間で、別々のメソッドを作れば、複雑さが増し、業務の意味が二層に分かれます。Relayと元の業務のどちらを検証するか、混乱します。

境界が変わるだけで、業務の意味は作り直しません。

### 添付とオブジェクトの転送

メッセージサービスを、ファイルの中継にはしません。大きなファイル、画像、音声、動画を一緒に送れば、コストと信頼性の問題が大きくなります。

1.1は、メッセージとオブジェクトを分けます。

メッセージは、attachment manifestという説明だけを運びます。実際のアップロードとダウンロードは、別のHTTPS経路です。メッセージサービスは、アップロード先の予約、オブジェクトの確定、ダウンロード用の券など、制御だけを行い、全経路でバイト列を中継しません。

実装上、現実的で、配備にも適します。さらに秘匿性が必要なら、オブジェクト単位の暗号化を使え、Object Serviceは、平文を知らずに保存・配布できます。

### エンドツーエンド暗号化

特に重要な用途では、サーバーに内容を見せるべきではありません。経路選択、順序付け、保存、配布をしても、自動的に読む能力を与えるべきではありません。

ダイレクトでは、Signalを参考にしました。受信者がオンラインになるのを待たず、公開された鍵合意の材料を取得し、暗号化セッションを開始します。その後、Double Ratchetに似た方式で鍵を更新し、前方秘匿性を高めます。

グループでは、IETFのMLS（Messaging Layer Security）を使います。

独自のSender Key方式は作りません。小さいグループでは単純でも、加入、退出、削除、鍵の更新で複雑になります。ドメイン間では、誰が鍵を更新し、状態を同期し、現在を証明するか、さらに難しくなります。

MLSは、もともと安全なグループ通信向けで、鍵の状態機械が明確です。メンバーの変化、更新、暗号化を、より適切に扱えます。

ANPでは、DIDがメンバーの本人性、Group Hostが業務の順序と受領証、MLSが暗号化の状態を担います。この分担は明確で、自作するより信頼できます。主な仕事は、DIDとMLSの統合です。

## 次の計画

二つの方向に進みます。

第一は、権限の制御と監査です。送れるだけでなく、誰が何をしてよく、結果を監査できるかも必要です。W3C DIDとVC（Verifiable Credentials）を組み合わせ、細かな権限の表現と、結果の証明を実現します。

VCは多くの分野で研究され、エージェントの認可、委任、監査にも適すると考えます。

第二は、メッセージシステムでのコンテキスト共有です。一言を送るだけでなく、タスクの背景、ツールの結果、状態、協働の過程を共有する必要があります。重くしすぎず、よりよい共有を探ります。

1.1は、「接続できる」から、「ドメインを越えて協働し、本人確認し、内容を守れる」へ進む、重要な更新です。

Webサービスのように、開放的につながり、独立して配備し、ドメイン間で協働する、という目標は変わりません。Release 1.1は、そのための一歩です。
