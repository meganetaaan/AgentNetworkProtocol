# W3C-WebAgents-CGにてANP発表

2025年2月14日、Chang Gaowei社とJames WaughがANPのオープンソースコミュニティであるATPに、W3C WebAgents CGミーティングにて発表しました。

W3C WebAgents コミュニティは、Web ベースのマルチエージェント システム (MAS) の設計に焦点を当てており、Web アーキテクチャと一貫性のある MAS の新しいタイプを開発することを目指しています。 このMASは、透明性とトレーサビリティを広く普及させ、Webのグローバルでオープンで永続的な特性を継承し、透明性を高めます。 コミュニティは、リンクされたデータとセマンティックなウェブ規格を使用して、人、AI、デバイス、デジタルサービスなどの多様なエンティティティティティティティティティティ間の統一的な相互作用を可能にするマルチメディア構造(hMAS)を作成することに特に重点を置いています。 コミュニティサイト: [https://www.w3.org/community/webagents/](https://www.w3.org/community/webagents/).

ANPの技術的哲学は、WebAgentsコミュニティの多くの側面と整列し、同様にリンクされたデータやセマンティックなウェブテクノロジーを価値として評価します。 設計プロセス中に、WebAgentsコミュニティの議論も参照しました。 今回の発表では、ANPの考え方や実践について、WebAgentsコミュニティに紹介しました。

今回の発表は、チャン・ガオウェイとジェームズ・ワフが共同で配信されました。 以下は、会議中に議論したプレゼンテーションスライドとスクリプト、およびトピックです。

ADPとは? エージェントの説明文書を定義するプロトコルです。 エージェントの「ホームページ」として、ウェブサイトのホームページと同様の機能がすべてアクセスできる文書です。

## 営業品目

### 完全な分散化を追求しないもの

ブロックチェーンソリューションは、完全な分散化を表すものであり、構造全体に集中したモジュールが存在しないと考えています。 しかし、ブロックチェーンのスケーラビリティの課題は、現在良い解決策を欠くことではありません。

そのため、私たちが追求する分散化は、ブロックチェーンの完全な分散化ではなく、メールの分散化のようなものです。 電子メールアカウントは、他のメールアカウントに電子メールを送信および受信することができます。 電子メールサービスプロバイダは一元化されますが、ビジネス全体が分散され、何のアカウント間の通信を可能にし、数十億人のユーザーをサービスを提供しています。

弊社が設計する理念は、Eメールと同じです。 今回、この段階で一番適したソリューションだと私は思います。

### JSON-LD から TTL/RDF マッピングの問題

**詳しい質問:** JSON-LD を TTL/RDF マッピングにインストールしますか? 私のビューでは、JSON-LD 設計は、通常、認識されていない空白のノードに関する問題があります。

**回答(補足応答):** 現在、JSON-LD を TTL/RDF マッピングに使用していません。 JSON-LD は、JSON-LD を主に2つの機能に使用しています。
- データ接続:AIがアクセスしやすいネットワークにデータを接続できるだけでなく、人のために設計されたネットワークではなく、データに接続することができます。
- 著名な理解の一貫性:Schema.orgを使用することにより、既にセマンティックWeb技術によって定義されているため、異なるエージェント間でのセマンティックな理解の一貫性を高めています。

### データ理解における一貫性の確保

**詳しい質問:** コーヒーをお伝えしました。2つのエージェントがコーヒーの一貫した理解を持っていることを確実にする方法は?

**回答:** 実際、何もしない場合でも、エージェントは現在、99%のシナリオでコーヒーの一貫性のある理解を維持することができます。 私たちがする必要があることは、さらに2つのエージェント間のコーヒーの一貫性を把握するために、セマンティックな理解を高めることです。

特定のアプローチは、エージェントの説明仕様のJSON-LD設計で、現在のセマンティックWebによって既に定義されているSchema.orgフィールドの多くを使用することです。 複数のエージェントが同じフィールドの一貫性を保ち、プログラム処理を容易にすることを可能にします。

フィールドが未定義の場合、Schema.orgの定義、定義、およびLLMの事前学習資料として当社の仕様を赤色化して学習します。 このようにして、LM2は同じ分野を一貫した理解を維持することができます。

### IoTデバイスにアクセスできるエージェント

**詳しい質問:** IoTデバイスにアクセスできますか?

**回答:** 理論的には、彼らはすることができます。 IoTデバイスのインターフェースを定義し、インターフェイスの説明が ADP (エージェント 説明プロトコル) ドキュメントに置く限り、AI は IoT デバイス向けのスキームを理解し、開始することができます。

### HTTP と OpenAPI は、よりよい伝送プロトコルではないかもしれません。

**詳しい質問:** IoT シナリオでは、HTTP および OpenAPI は非同期通信に直面しているとき、特に伝送プロトコルが向上するわけではありません。

**回答:** あり。 ANPは、輸送層プロトコルの要件を理論的に持っていません。 現在、HTTP、WSS を経由して他のプロトコルで利用することができます。 しかし、下層プロトコルは変更が必要である。 例えば、現在 HTTP 認証情報は HTTP ヘッダで実行され、他のプロトコルでは新しい認証スキームを設計する必要があります。

### 既存の API インターフェイスを使用する方法、既存の OpenAPI 仕様など

**詳しい質問:** エージェントの説明仕様では、既存のOpenAPIインターフェースなどの既存のインターフェイスを使用できますか?

**回答(補足応答):** あり。 エージェントの説明仕様では、外部アクセスのエージェントが提供しているインターフェイスはオープン設計です。 OpenAPI インターフェイス文書などの仕様書インターフェースを既存の仕様書に記述することができます。 AIは、これらのインターフェイスへの呼び出しを理解し、開始することができます。

ひとつの状況です。 コミュニケーションに使用するインターフェイスを交渉し、他のエージェントと標準として交渉されたインターフェイスを共有したい2つのエージェントが交渉できるというよりエキサイティングな状況だと思います。 これはメタプロトコルの役割です。

### エージェントがサーバーの代わりにコーヒーショップを表現する理由

**詳細な質問(投稿前記の質問):** 例えば、エージェントはサーバーではなくコーヒーショップを表していますか?

**回答:** エージェントは、組織内の人、組織、サブ組織、あるいはオブジェクト内での任意のエンティティティを表現できます。 例えば、このエージェントはコーヒーショップを代表しています。なぜなら、私たちのシナリオはコーヒーカップを購入している人であり、インタラクションオブジェクトはコーヒーショップです。 人のエージェントは、アフターセールスの問題やパーソナライズ問題を解決するために、自然言語を介してコーヒーショップのエージェントと相互作用することができます。 この場合、構造化された API は問題を解決できず、パーソナライズされた自然言語インターフェイスが必要です。
