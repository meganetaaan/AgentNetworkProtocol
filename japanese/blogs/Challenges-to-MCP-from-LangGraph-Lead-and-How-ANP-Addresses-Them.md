# LangGraph責任者がMCPに提起した課題と、ANPによる対応

最近、MCP（Model Context Protocol）がインターネット上で注目されています。LangChainのウェブサイトで、FounderParkにも転載されたブログ記事を読みました。

原文：https://blog.langchain.dev/mcp-fad-or-fixture/  
中国語版：https://mp.weixin.qq.com/s/etvDsU422z8uiknCn6fw4A

この記事では、LangChain共同創業者兼CEOのHarrison Chaseと、LangGraph責任者のNuno Camposが、MCPについて議論しています。一時的な流行なのか、それとも将来の標準になるのか、という内容です。

MCPプロトコルの定義や使い方を含め、すべての見解に賛成するわけではありませんが、Nuno Camposが指摘した問題には的確なものがあります。

私たちは以前からエージェント通信プロトコルに取り組んでおり、私たちのANP（Agent Network Protocol）は、おそらくエージェント専用に設計された世界初の通信プロトコルです。そのため、MCPの公開直後に調査し、Nuno Camposが挙げたのと同じ課題を認識していました。

実際、ANPでは、初期の設計段階ですでにこれらの課題を検討していました。今日は、ANPがどのように対応しているかを説明します。

## Nuno CamposがMCPについて指摘した中心的な問題

Harrison Chaseとの議論で、Nuno Camposは、MCPについていくつかの中心的な問題を挙げています。

- **プロトコルの複雑さ**：MCPはツール呼び出しのプロトコルに加え、プロンプトとLLMの補完サービスも提供します。この設計によって、プロトコルが大幅に複雑になっています。
- **実装の難しさ**：MCPは双方向通信の仕組みを採用しています。特に開発者にとって実装の複雑さが増し、追加の負担になります。
- **サーバー側の拡張の難しさ**：現在のMCPの設計はステートレスではないため、サーバー側の拡張が難しくなっています。特に分散環境では、認証と状態管理の問題が顕著になります。
- **ツールの品質とモデルへの適合の問題**：ツールについて何も知らないエージェントに無作為なツールを追加すると、ツール呼び出しの品質が必然的に下がり、利用体験に影響します。

## ANPの解決策

ANPでは、当初からこれらの問題を深く考え、それぞれに対応する解決策を提供しています。

### エージェントのアイデンティティの問題

私たちは、これがプロトコルにとって最も重要な課題だと考えています。MCPの公開当初はローカルサーバーしかサポートしていませんでした。その主な理由は、アイデンティティの問題をどう解決するか、まだ見いだしていなかったからです。私たちはMCPコミュニティと正式に意見交換しましたが、提案は採用されませんでした。

その後、MCPは認証方式としてOpenID Connectを選びました。しかし、OpenID Connectは集中型の方式であり、分散された非中央集権型の認証を提供できません。これは、エージェントの協働に本質的な制約をもたらします。

ANPの設計を始めた初日から、私たちはエージェントの分散型アイデンティティの問題を解決しようとしてきました。最終的な方式は電子メールに似ています。各プラットフォームの内部では集中管理されますが、全体では分散ネットワークを形成し、異なるプラットフォーム同士が通信できます。

詳しい比較はこちらです：[did:wbaとOpenID Connect、APIキーの比較](comparison-of-did-wba-with-openid-connect-and-api-keys.md)。

MCPがOpenID Connectを選んだ理由は理解できます。チャットボットのアプリケーションと既存のインターネットとの統合を解決するためです。ただし、エージェントインターネットが発展するにつれ、ANPの分散型でエージェント中心の設計思想の方が、将来のエージェントネットワークの要求に適するようになると考えています。

### プロトコルの複雑さの問題

ANPは、モデルのコンテキストのためのプロトコルではなく、エージェント間の通信プロトコルに集中するという位置付けを明確にしています。モデルの補完サービスやプロンプトは提供せず、エージェントがどのように認証し、情報を交換し、協働するかを定義することに集中しています。

ANPの設計思想は「エージェント中心」です。各エージェントはネットワーク上で対等なノードです。プロトコル自体は、エージェント間の通信規則とデータ形式だけを定めるため、プロトコルの複雑さを大幅に減らせます。

私たちはオープンソースのOpenManusプロジェクトにANPプロトコルのサポートを追加しました。コード（app/tool/anp_tool.py）はこちらで確認できます：https://github.com/agent-network-protocol/OpenManus-ANP （現在、コミュニティでベータテスト中です。ご意見をお待ちしています。）

エージェントへのANPの統合に必要なのは、わずか200行のコードです。中心となるのは一つのプロンプトと一つのHTTP関数で、残りはモデルが動かします。

このHTTP関数はモデルのブラウザーとして働き、ANPプロトコルを通じて接続されたデータネットワークに、モデルが容易にアクセスして巡回できるようにします。**AIがアクセスしやすいデータネットワークを構築することが、ANPの一貫した目標です。**

ANPに基づく接続は、AIに自然に適した接続方法です。

### サーバー側の拡張の問題

ANPを基盤とするエージェント記述プロトコルは自己記述的であるため、ANP自体は内部のプロトコル状態を定義しません。自己記述により、モデルは文書の中でインターフェースの呼び出し方を宣言できます。そのインターフェースは、状態を持つものでも、ステートレスなものでもよく、ANPは両方をサポートします。

エージェントは、外部に公開するインターフェースを、状態を持つものにするか、ステートレスにするか、自由に決められます。

### ツールの品質とモデルへの適合の問題

これはモデルが解決すべき問題であり、プロトコルとは関係がないと考えます。プロトコルが提供できるのは、よりよい説明情報とツールの利用方法です。この点については、彼の理解に偏りがあるか、あるいはこのプロトコルのモデルそのものを疑問視しているのかもしれません。

## 中心となる概念の違い

ANPとMCPでは、中心となる概念に大きな違いがあります。MCPでは、ツール、リソース、プロンプトがプロトコルの中心です。ANPには、これらの概念がありません。

ANPは、エージェントが公開する情報の記述を提供します。それは、コーヒー店で販売しているコーヒーのような基本情報の場合もあれば、コーヒーを購入できるAPIインターフェースの説明の場合もあります。

情報は、ANPにとって唯一であり、最も中心となる概念です。リソース、ツール、プロンプトという区分はありません。すべては、モデルとエージェントの開発者が決めます。
