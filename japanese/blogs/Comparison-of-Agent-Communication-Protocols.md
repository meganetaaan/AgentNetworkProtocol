# オープンソースの通信プロトコルの比較分析:MCP、ANP、アゴラ、agent.json、LMOS、AITP

エージェント通信プロトコルの開発中、業界に存在する様々なプロトコルを収集し、OpenAIの深層調査を用いた解析を実施しました。 分析は、ターゲットの問題、キー技術、適用シナリオ、技術的なアーキテクチャ、互換性と拡張性、オープンソースのエコシステム、将来の開発見通しなどの側面をカバーしています。 一部の詳細は完全に正確ではないかもしれませんが、この分析は貴重な参考として役立ちます。

昨年、オープンソースエージェント通信プロトコルの設計と開発をスタートしました。 今回研究する最も早いチームの一つとして、過去2〜3ヶ月にわたって注目と関心の大きな増加を明らかにしました。

オープンソースプロジェクトをフォローし、コミュニティに参加してくださるまで、温かく招待します。 個々の開発者やAI業界に所属する企業であっても、参加は歓迎されます。 エージェント通信プロトコルの重要性は、協業産業の努力に依存します。

## MCP(モデルコンテキストプロトコル)

### ターゲット問題
注目すべき点 **大きい言語モデル(LLM)のコンテキスト統合**:
- 外部データソースとコンテキストのフラグメントでAIモデルを統合する難しさを伝えます。
- LLM が、さまざまなコンテンツリポジトリ、ツール、環境を便利に安全にアクセスし、データサイロを破壊し、各データソースのカスタマイズされた統合を回避することを可能にする統一規格を提供します。

### 主要技術

**RPCフレームワークを開く**:
- JSON-RPC 2.0 に基づく標準リクエスト/レスポンス/通知メッセージのフォーマットを定義します。
- 導入事例 **機能交渉** メカニズムは、クライアントとサーバーがサポートするプロトコル機能(細かい段階のサブフィードを含む)に動的に同意し、柔軟性と拡張性を強化することができます。
- 現在、ローカル双方向ストリーミング通信(例えば、標準IOパイプ、HTTP + SSEストリーミング出力)をサポートしています。アイデンティティ認証やサービスディスカバリーなどのリモートコミュニケーション機能が計画されています。

### 適当なシナリオ

**AIアプリケーション統合**:
- LLMをビジネスシステムに組み込むことを必要とするシナリオや、エンタープライズナレッジベースQ&Aなどの複数のデータソースやツールと急速に接続するなど、プログラミングアシスタントは、コードリポジトリ/IDEと統合し、オフィスのアシスタントがカレンダーやメールにアクセスします。
- MCP を通じて、開発者は、データベース、クラウド文書、開発環境などの統一されたインターフェイスで LLM を提供できます。
- 現在主に使用しています **ローカルまたはイントラネット** 内部ツールとのエージェント統合のための環境; 将来のリモートサポートでは、クロスサービスクラウドエージェントの統合に拡張できます。

### テクニカル・アーキテクチャ

**クライアント・サーバーのアーキテクチャ**:
- MCP は、クライアントと外部のデータソースを MCP サーバーとして扱う。
- 両側は、RPC 呼び出しに似て事前定義された JSON メッセージを交換します。
- 現在、トランスポートレイヤーがサポートしています。 **ローカルパイプ** (標準入力/出力ストリーム) **SSE と HTTP の永続的な接続** (リクエスト/応答またはストリーミングメッセージのサーバー・セント・イベント一方向ストリーム)。
- 各輸送方法に特定のメッセージ交換の要件があります。
- 現在、ローカルまたはイントラネット通信に制限されているため、シンプルさとセキュリティ(外部接続なしでリモートアイデンティティの問題はありません)を確保できます。
- 将来の計画には、認証、認可、サービス発見、およびステートレスな操作を含むリモート接続機能が含まれます。
- そのため、MCPアーキテクチャは好意 **ワンツーワン** プラグインの呼び出しに類似したモデルとリソースサービス間の通信、マルチエージェントルーティングは処理しません。

### 互換性と拡張性

**簡単な統合**:
- MCP は、JSON や HTTP などの一般的な技術を採用し、透明性が高く、ローカル展開が容易になります。 既にMCPクライアントをサポートしているクローデやその他モデル。
- Anthropic は、仕様と SDK をオープンにソースし、MCP サーバーの一般的なシステム (Google Drive, Slack, GitHub など) で簡単に統合できます。
- 開放的な性質により、他の大型モデル(オープンソースLMを含む)はMCPを実装し、相互モデル対応が可能です。
- 現在、リモート呼び出し機能が不足していますが、認証とネットワークの将来の追加により、マイクロサービスやクラウドAPIへの適応が可能になります。
- コンセプト **機能交渉** メカニズムは、互換性を崩さずに新しい機能モジュールを追加し、既存のクライアントが新しい機能を交渉および活用できるようにします。
- 全体的に、MCPは既存のシステム(特にREST-styleサービス)と容易に統合し、LMLプラグインの標準的なコンポーネントとして機能することができます。

### オープンソースとエコシステム

**不整形オープンスタンダード**:
- MCP仕様と部分的なSDK実装が公開されています。
- Anthropic はローカル MCP サーバーを Claude デスクトップ アプリケーションに統合し、データの統合を実証しています。
- 初期のエコシステムには、ブロックやアポロなどの早期採用者や、Zed、Replit、Codeium、 Sourcegraphなどの開発者向けツール会社がMCPを用いたコード関連エージェントを強化する共同で導入されています。
- GitHub、サードパーティのツール(オープンソースMCP可視化管理クライアントなど)でMCP仕様を維持しています。
- 2024年の終わりにリリースされたエコシステムはまだ初期段階ですが、強力なサポートと積極的な議論(例えば、MCPの画期的なReddit開発者のディスカッション)で、重要な注目を集めています。
- MCP はオープンライセンスでリリースされ、コミュニティの貢献を促進し、メカニズムやサーバーの実装に寄与します。
- 将来のリモート機能とLLMの互換性が広く、MCPエコシステムは「LLMプラグイン市場」に拡大する見込みです。

### 今後の展望

**短期リード、拡大を待っています**:
- 人類学的および早期採用者から支持されるMCPは、近い用語でLMツールの統合のためのデファクト規格の一つになることを期待しています。
- リモート機能を追加した時点で、MCPはアプリケータを素早く拡大し、エンタープライズアプリケーションで足場を確立することができます。
- その利点は、その **シンプルで実用性**大手企業様が開発・サポートをしております。
- しかしながら、長期的には、MCP は現在分散型アイデンティティとマルチエージェントのインタラクション機能が欠如し、大規模なエージェントネットワークを構築できる能力を制限する。
- Anthropic とコミュニティが ID 認証などのモジュールを反復し、追加し続けると、MCP はより一般的なプロトコルに進化する可能性があります。
- 全体的に、MCPは明るい未来を視野に備えています **LLM コンテキスト統合**, 潜在的に「AI時代のUSBインターフェース」になってきています。しかしながら、エージェントの相互接続性を視野に入れるために、他のプロトコルと共同作業する必要があります。

## ANP(エージェントネットワークプロトコル)

### ターゲット問題
注目すべき点 **エージェントの相互接続性**:
- 複数のエージェント間でのコミュニケーションとコラボレーションの問題を解決し、「エージェントのためのHTTP」というビジョンで
- エージェントネットワークにおけるアイデンティティの信頼と接続の課題を克服し、プラットフォーム間で直接通信を可能にし、コラボレーション作業のためのネットワークを形成する代理店を支援します。

### 主要技術

**3層アーキテクチャ+分散型アイデンティティ**:
- 利用する **W3C分散型識別子(DID)** アイデンティティレイヤーを構築し、信頼の認証とエンドツーエンド暗号化された通信を実現するための標準。
- 暗号化を使用して、中央当局を交換し、大規模な展開で分散化のバランスをとるための独自のDIDメソッドを設計します。
- 導入事例 **メタプロトコルレイヤー**, "プロトコルのプロトコル" は、エージェントが自然言語を使用して通信プロトコルを自動的に交渉し、アプリケーションレイヤープロトコルコードを生成できるようにします。, 自動インターフェイスとプロトコルのアップグレードを有効にします.
- アイデンティティ認証、暗号化された通信、メタプロトコル交渉、およびアプリケーションレイヤープロトコルの説明を含む機能の完全なスタックを備えています。
- エージェントは、LM を活用してネットワークを自動整理し、コミュニケーションスキームの交渉を行い、人間介入なしにネットワークコラボレーションを自己組織化することができます。

### 適当なシナリオ
**多国籍コラボレーション**:
- 建物のために適した **分散型エージェントネットワーク**パーソナルAIアシスタントなどの第三者サービスエージェント、IoTデバイスインテリジェントエージェントの交渉行動、複数の自動運転エージェントが連携して複雑なタスクを完了します。
- 特に、高いセキュリティ要件を持つシナリオや、統一された信頼センター(例えば、クロスプラットフォームの個人データ統合)を欠如するのに適しています。
- エージェントのコミュニティにも利用でき、異なるチームからエージェントがオープンプロトコルに従ってやり取りできるようにします。

### テクニカル・アーキテクチャ

**ピアツーピアメッシュ**:
- ANPは採用します **分散型P2P** アプローチにより、エージェントは暗号化された通信接続を直接確立することができます。
- 通信プロトコルとフォーマットの交渉により、DID ID交換と検証を通じてTrustが確立されます。
- アーキテクチャは3つのレイヤーに分けられます。 **アイデンティティと暗号化レイヤー** 安全で信頼できるチャネルを確保します。 **メタプロトコルレイヤー** エージェント(または複数のエージェント)間のアプリケーションプロトコルの自動交渉を処理します。 **アプリケーションプロトコルレイヤー** 特定のビジネスデータ交換を実行し、エージェントは、このレイヤーのプロトコルを選択または生成して、セマンティックな説明に基づいて実行します。
- このアーキテクチャは、エージェントネットワークが人的ネットワークのように緩やかに結合することができます。障害の単一のポイントはありません。各々に発見し、接続するエージェントです。
- 実装は、フレームワークを提供する公式の AgentConnect 実装で、既存の Web インフラストラクチャ(WebSocket や P2P ライブラリなど)上で実行できます。
- ネットワーク トポロジは、**マルチホップ ネットワーク** をサポートしており、エージェントは集中サーバーに限定されず、コラボレーションのための特定の条件を満たす他のエージェントを動的に見つけることができます。

### 互換性と拡張性

**オープンで包括的**:
- ANP は完全にオープンソース (仕様とリファレンス実装を提供) であり、既存の Web 標準 (例: DID 標準、セマンティック Web に基づく) と統合するように設計されています。
- ID 認証とメタプロトコル層を実装している限り、さまざまなエージェント フレームワークをサポートし、ANP ネットワークに参加できます。
- その **層構造** は明確であり、各層は交換またはアップグレード可能です (例: 新しい暗号化アルゴリズムの将来の使用、新しいアプリケーション層プロトコル タイプの追加)。
- **セマンティック機能の説明** を通じて、サードパーティは新しいエージェント機能を定義し、ネゴシエーション中にそれらを認識して利用できます。
-  互換性の点では、ANP のプロトコル ドキュメントとコードは中国語と英語の両方で利用できるため、統合の敷居が低くなります。
- 分散設計により、特定のプラットフォームに依存せず、インターネット参加者が独自の ANP エージェントを実装できます。
- 理論的には、既存のプロトコルをブリッジすることもできます。エージェント プロキシを実装し、DID 認証をサポートする既存のサービスは、ANP プロキシと通信できます。
- そのため、ANP は業界の導入率をボトルネックにしながらも、大規模ネットワークにスムーズに拡張できます。

### オープンソースとエコシステム
**国内オープンソースの先駆け**:
- ANP は中国のチーム (Chang Gaowei を含む) によって開発およびオープンソース化されており、仕様とコードは GitHub で公開されています。
- 最も初期に提案されたエージェント通信プロトコルの1つとして、業界初の真のエージェント通信プロトコルと呼ばれ、国内のAI開発コミュニティで注目を集めています。
- 現在のエコシステムには、AgentConnect 実装フレームワークとサポートされる DID メソッド仕様が含まれています。
- このコミュニティは主に国内でコミュニケーションをとっており、CSDN などのプラットフォームで複数の分析チュートリアルを提供しています。
-  ただし、世界的な認知度は比較的限られており、より多くの国際的な開発者が参加する必要があります。
- ANP は最先端に歩調を合わせており (そのメタプロトコルの概念はオックスフォードの Agora と一致しています)、標準を改善し、多言語 SDK を提供するためにコミュニティを集めることができれば、ANP はエージェントティック Web の重要な部分になる可能性があります。
- そのオープンソース ライセンスはフレンドリーで、商用および個人での使用を歓迎します。
- 国内では、ANP はローカルの大規模モデル/アプリケーションによるエコシステムを形成すると予想されています。国際的には、開発者をエコシステムに参加させ、真にグローバルなエージェント ネットワークの相互接続を実現するためのプロモーションが必要です。

### 今後の展望

**技術的には包括的、エコシステムが必要**:
- ANP はコンセプトにおいて先進的であり、**高い技術的成熟度** (エンドツーエンドのネットワーク通信の実現) により、アイデンティティの信頼性と自動ネゴシエーションの課題を事前に解決します。
- これにより、将来のオープン エージェント ネットワーク競争において優位性が得られます。
-  ANP が広く採用されれば、Agentic Web の基礎となる通信フレームワークになる可能性があります。
- しかし、現在、ANP は主に国内チームによって推進されており、国際的な影響力が比較的弱いため、**生態系規模**が懸念されています。
-  将来の利点は次のとおりです。まず、より多くの開発者や組織を惹きつけてエコシステムに参加し、改善できるかどうか。第二に、大手企業が DID ルートをサポートするかどうか。
- 分散型エージェント ネットワークがトレンドになると (例: Web が分散型アイデンティティに移行する)、ANP は輝くでしょう。
-  逆に、大手企業が独自のプロトコルを好む場合、ANP はニッチな標準になる可能性があります。
- MCP チームもオープン アイデンティティの重要性を認識していることを考慮すると、ANP の主要な設計は参照または統合され、主導的な地位を維持する可能性があります。

## Agora (オックスフォード大学メタプロトコル)

### ターゲットの問題
**LLM エージェント ネットワークの 3 つのジレンマ** に焦点を当てる:
- 通信における高い**汎用性、効率性、可搬性**を同時に実現しようとします。
- 大規模モデルの機能を使用してさまざまなシナリオに適応し、現在のモデル間の相互通信の分離と困難に対処するためのスケーラブルな「ワールドクラスの LLM エージェント ネットワーク」を構築することを提案します。

### 主要テクノロジー
**LLM 主導のメタプロトコル**:
- 核となる革新は、通信プロトコルを平文で記述する**プロトコルドキュメント (PD)** メカニズムです。
- エージェントは、中央登録を行わずに、ハッシュ値によって一意に識別される転送可能なオブジェクトとしてプロトコル記述を使用できます。
- LLM の 3 つの主要な機能 (自然言語の理解と生成、指示に従ったコード作成、複雑なコンテキストでの自律的なネゴシエーション) を活用することで、Agora によりエージェントはさまざまなシナリオに応じてさまざまな通信形式を採用できます。
- 一般的な高頻度のインタラクションは、効率を向上させるために既存の効率的なプロトコル/ルーチンを使用して処理されます。珍しいまたは非標準のプロトコル シナリオの場合、エージェントは構造化データまたは自然言語を使用して新しいプロトコル スキームをネゴシエートし、LLM を使用して対応するルーチンを動的に生成および実行します。
- このアダプティブ レイヤリングは、**高い汎用性**（ほぼすべてのコンテンツを交換可能）、**高効率**（最適化された共通パス）、**高いバランスを実現します。移植性** (LLM は人間の介入なしでネゴシエーションと実装を処理します)。

### 該当するシナリオ

**最先端の研究と複雑性の高いタスク**:
- Agora は現在、主に学術的な実験シナリオで検証されています。
-  研究指向のマルチエージェント システムなど、**柔軟性の高いプロトコル** を必要とするマルチエージェント環境に適しており、エージェントが自律的に通信方法を進化させることができます。
-  たとえば、エージェントは最適な通信方法を動的にネゴシエートして、さまざまなタスク要件のコラボレーション効率を向上させたり、未知の環境での新しい問題を解決するためにその場で通信プロトコルを作成したりします。
- これは、**AGI 研究** および大規模エージェント シミュレーションで価値があります。
- 短期的には、Agora は、LLM が特定のタスクを解決するためのプロトコルを自動的に生成できるかどうかの実験など、**概念実証** に向いています (論文では 2 つのシナリオ実験を示しています)。
- 将来的に成熟すれば、すべてのインタラクションを事前に標準化する必要がないため、大規模で異質なエージェント ネットワークに適用できます。

### 技術アーキテクチャ

**アダプティブレイヤードプロトコルスタック**:
- Agora は固定ネットワーク トポロジ プロトコルではありませんが、さまざまな抽象化レイヤーで通信方法を切り替える戦略をエージェントに提供します。
- これは、エージェント内に**「プロトコルルーター」**を実装すると理解できます。エージェントAがBと通信するとき、まず、適用可能な効率的な確立されたプロトコル(双方が既知で実装しているPD)があるかどうかを確認し、存在する場合はそれを直接採用します(例:標準APIコールまたはカスタムバイナリプロトコル)。
- そうでない場合は、LLM によって動的に記述された必要な解析ルーチンと構築ルーチンを使用して、JSON ベースの往復など、**構造化データ交換** にフォールバックします。
- さらに複雑さや交渉の問題が発生すると、**自然言語コミュニケーション** に低下します。2 つのエージェントは、LLM によって生成された人間の言語でニーズとデータを直接記述し、対応する LLM が解析して実行します。
- このアーキテクチャは基本的に**動的に**通信プロトコルをアプリケーション層で選択しますが、基礎となる層は依然として基本的な接続を必要とします(既存のネットワーク/ソケットを介してテキストストリームを送信すると想定されています)。
- Agora はプロトコル自体を交渉可能なコンテンツとして扱い、特定のデータ交換の前にプロトコル文書 (PD) を交換することで合意に達します。
- したがって、トポロジは本質的に**ピアツーピア通信** (どのエージェントも会話可能) であり、既存のネットワーク上で実行されますが、非常に柔軟な通信コンテンツ層を備えています。
- Agora は「ゼロレイヤー プロトコル」と呼ばれます。これは、メタレイヤーでさまざまな特定のプロトコルを調整し、LLM 間の高レベルのコラボレーションの基盤を提供することを意味します。

### 互換性と拡張性

**概念実証段階**:
- Agora は学術論文に由来しており、現時点では成熟した産業実装が不足しており、移植性は理論的にはさまざまなプロトコル記述と互換性があります (ほとんどの既存の RFC は PD として使用できます)。
- したがって、実装されれば、多数の既存のプロトコル標準を直接利用でき、エージェントは対応する PD テキストを取得し、実行/解析する機能だけを必要とします。
- 拡張性はほぼ無制限です。テキストで記述されている限り、新しいプロトコルをシステムに組み込むことができ、LLM が理解と展開を担当します。
-  ただし、プロトコル コードを正しく生成および解析するには、強力な LLM 機能も必要です。
- 現在の互換性は主に、LLM で生成されたプロトコルを実行するための十分な知識とツール ライブラリを備えたエージェントに依存します (たとえば、通信用に Python コードが生成される場合、エージェント環境はそれを実行できなければなりません)。
- Agora は、ハッシュ識別子を使用してグローバル調整の必要性を軽減し、集中的なプロトコル ID 登録を回避します。
- エージェントのやり取りが増えると、プロトコル文書共有ライブラリ（分散配布）が形成される可能性があります。
- 全体的に、Agora はあらゆる通信パラダイムに対応できるように設計されていますが、統合実装の前に、さまざまなチームの実験が断片化される可能性があります。
- 現在のエコシステムは主に**研究コミュニティ**に焦点を当てており、そのオープンソースステータスは論文著者のチームによって異なります。オープンソース コードが後で実装され、GitHub にアップロードされた場合、開発者エコシステムが正式に開始されます。
-  長期的には、LLM が自動プロトコル生成を完全に実行できるようになると、このアーキテクチャは新しいデバイスや通信のニーズに適応して拡張できます。

### オープンソースとエコシステム

**学術的リーダーシップ**:
- Agora はオックスフォード大学のチーム論文 (2024 年 10 月提出) に由来しており、現在のエコシステムは主に学術的な議論と評価で構成されています。
- 機械学習コミュニティは、「3 つのジレンマ」の定義と解決策によく反応しており、Reddit ではそのイノベーションに焦点を当てた議論が行われています。
-  ただし、Agora のアイデアを実装するオープンソース フレームワークはまだありません。おそらく、新しい LLM 機能に依存しているためです。
-  コードがなければ、エコシステムは理論的なもののままです。
- 一部の研究者は、この論文に基づいて GPT-4 や他のモデルを使用して実験を行い、部分的な機能を検証する可能性があります。
- これは **最先端の探査** に属し、短期的には商用アプリケーションがエコシステムに加わることはありません。
-  ただし、その概念は他のプロジェクトに影響を与える可能性があります。たとえば、ANP のメタプロトコル部分は同様のアイデアを反映しており、エコシステムの応答と考えることができます。
- Agora が効果的であることが証明されれば、将来のエージェント フレームワークにはそのアイデアが組み込まれ、必ずしも Agora アーキテクチャを完全に採用することなく LLM の柔軟なプロトコル適応が機能として追加される可能性があります。
- オープンな論文として、そのコンセプトは誰でも制限なく利用できます。
- 作成者またはオープンソース コミュニティが後でリファレンス コードを実装し、GitHub にアップロードすると、開発者エコシステムが正式に開始されます。
- 現在は主に**論文引用や学術議論**のレベルで「エコシステム」を構築しています。

### 今後の展望

**壮大なビジョン、挑戦の道**:
- Agora は、AI が自律的に通信方法を定義できるようにすることで、人間が課したプロトコルの制限を打ち破るという、非常に先進的な方向性を示しています。
-  **遠い将来** では、エージェントがより高い知能レベルに達すると、Agora の適応型コミュニケーションがデフォルトになる可能性があります。エージェントは人間が定義したルールを必要とせず、タスクのコラボレーションに最適な対話プロトコルを自律的に作成し、真に自己組織化機械社会を実現します。
-  したがって、Agora の概念は、AGI 時代にとって深い意味を持ち、将来の高レベル プロトコルのプロトタイプと見なされます。
-  ただし、その短期的な見通しは限られています。現在の LLM 機能と信頼性によって制限されているため、Agora のソリューションを現実の環境に実装するのは困難です。
-  最初は研究シミュレーションに適用され、その後のプロトコルの参考となる可能性があります (ANP の設計はすでに同様のアイデアの統合を反映しています)。
- LLM テクノロジーと自動コード実行テクノロジーが今後数年で画期的な進歩を遂げた場合、Agora はおそらく新しい名前と標準の下で紙から実装に移行する可能性があります。
-  大手企業もこのアイデアに注目し、密かにエージェント システムの実験を行う可能性があると予想されます。
- 標準レベルでは、Agora が将来成功することが証明されれば、プロトコル設計に「3 つのジレンマ」の概念を組み込んだ、**新世代プロトコル標準** の策定が促される可能性があります。
- 要約すると、Agora は、**将来のゲーム** の重要なコンセプトに似ており、その利点は長期的な競争で徐々に明らかになります。従来のプロトコルではカバーできないシナリオが発生した場合、Agora は解決策を提供します。
-  したがって、現時点ではアリーナの主要プレイヤーではありませんが、長期的には、Agora によって作成されたパラダイムは、後のプレイヤーに多大な影響を与え、最終的にはエージェントのコミュニケーションの基盤として勝ち残る可能性があります。

## agents.json

### ターゲットの問題
**Web サイト/サービスのエージェント アクセシビリティ** に焦点を当てる:
-  Web サイトが自律エージェントによってどのように検出され、対話できるかを宣言するためのオープン標準を提供します。
- 人的インターフェイスをクロールし、機械で読めるインターフェイスがない必要があるAIの代理店の現在の問題に解決して下さい、サイトが容易にエージェント フレンドリー インターフェイスの位置、許可の条件および相互作用の規則を通した提供できるようにすることによって `agents.json` ファイルの拡張子
- 不明な自動化によるリスクを軽減するために、エージェントの身元確認メカニズムも導入されています。

### 主要テクノロジー

**Web 宣言標準**:
- インスピレーション `robots.txt`/`sitemap.xml`, 定義 **エージェントインターフェイス** マシン読みやすいJSONファイルで。
-  サイト情報、利用可能な API エンドポイントとその入出力モード、認証方法 (OAuth2 など)、必要な許可範囲、使用ポリシー (レート制限、サービス規約) などが含まれます。
- 従来パス(例:エージェント自動検出用)による、 `/.well-known/agents.json`).
- 進化的な互換性を確保するために、バージョン フィールドとカスタム拡張機能をサポートします。
- **エージェント ID** 検証メカニズムにリンクすることもでき、サイトがエージェントに ID と権限の宣言を要求できるようになります。
- 全体的に構造化された**能力宣言** を提供し、Web ページの解析における曖昧さと摩擦を軽減します。

### 該当するシナリオ

**エージェント ウェブ**:
- AI エージェントにサービスを公開することを希望する**Web サイト/オープン API** に適用されます。
- 任意のオンラインサービス(eコマース、旅行予約、政府データインタフェースなど)は、マシンインターフェイスを通し宣言することができます `agents.json`, AutoGPTのようなエージェントは、Webページ上で人間のクリックをシミュレートするのではなく、機能的なエンドポイントを発見し、それらを呼び出します.
- それにも適用可能 **社内APIディレクトリ**: 企業は、部門別サービスインターフェイスを通すことができます `agents.json`社内AIエージェントによる自動検出と統合の促進
- 要約で、 `agents.json` 人工知能が効率的にアクセスしたいWebサイトなど、幅広い業界に適したウェブレベルのプロトコルです。

### 技術アーキテクチャ

**宣言 + 標準インターフェース**:
- `agents.json` コミュニケーションチャネルを定義するだけでなく、既存のWebアーキテクチャに統合する。
- 典型的には、最初に代理店 **取得する `/.well-known/agents.json`** HTTP 経由でファイル (サイトのルートディレクトリやよく知られているパスでpossily)。
-  ファイルの内容には、利用可能な API エンドポイント (多くの場合、HTTP RESTful インターフェイス、GraphQL、または WebSocket エンドポイント) とそれらの呼び出し方法が記述されているため、実際の通信モードはファイルにリストされているインターフェイスによって異なります。
- たとえば、このファイルは、エージェントが URL を呼び出して POST 経由で注文を送信するか、WebSocket 経由でメッセージを購読する必要があることを示している場合があります。
- ですから、 `agents.json` として役立つ **メタデータレイヤー**, 上位層の実際の通信では、RPC, REST, メッセージキューが使えます。
- また、**オープン API ドキュメント** またはスキーマを参照することもでき、エージェントが指定されたデータ形式に従ってリクエストを構築できるようになります。
- アーキテクチャ全体がWebと非常に互換性があります。DNS -> でサイトを検索 `agents.json` -> 定義されたインタフェース規格に従って相互作用します。
- このように、コミュニケーションは **クライアントサーバ** (クライアントがサービス API を呼び出すようにエージェント) または将来的に P2P 要素を拡張する(例えば、 `agents.json` 分散型サービスアドレスを指す)

### 互換性と拡張性
**ウェブフレンドリー**:
- `agents.json` 標準的なHTTPファイルフォーマットを使用してウェブサイトへの軽量な拡張です、それを作る **非常に簡単に統合**: サイト開発者は、JSON 宣言(一部が OpenAPI 文書から生成)を記述し、固定 URL でホストする必要があります。
-  クライアント エージェントの場合、JSON の解析は HTML の解析よりもはるかに簡単で、多くの既存の HTTP ライブラリで取得を処理できます。
- **既存の ID システムと互換性**: サイト上の既存の OAuth2 認証プロセスを参照できます。
- **ツールやフレームワークに依存しない**: 既存のネットワーク プロトコルを使用して、任意の言語エージェントが JSON を読み取り、記述に従って HTTP インターフェイスを呼び出すことができます。特別なランタイム ライブラリは必要ありません。
- 拡張性の高いこの標準では、カスタム フィールド/名前空間で新しい機能を試すことができ、古いエージェントによる解析エラーを防ぐバージョン フィールドも含まれています。
- まだ提案段階にあるため、合意に達するか、W3C 標準を確立するにはコミュニティのサポートが必要です。
- 標準化されれば、そのエコロジー的な可能性は計り知れません。ブラウザー ベンダー、クローラー、エージェント フレームワークは、agents.json の自動検出をサポートして自動化を強化できます。

### オープンソースとエコシステム
**草案提案段階**:
- 現時点では、agents.json は概念的な提案にすぎません。
-  アイデアはコミュニティ (Reddit ディスカッションおよび AgentProtocol コミュニティ) によって集合的に提案されましたが、正式に最終決定されていません。
- まだ組織による正式な承認はありませんが、W3C または Open Web Alliance で議論される可能性があります。
- それにもかかわらず、そのシンプルで実現可能なコンセプトは、すでに一部の開発者の注目を集めています。
- 同様のアイデアが一部のメディア記事にも掲載されており、エージェント クローラーの使いやすさについての議論が巻き起こっています。
- 実装コストが低いため、一部の最先端の Web サイトでは、agent.json のリリースを実験する可能性があります。
- 草の根の実践が形成されれば、標準化団体が規範の確立を促進する可能性があります。
- 現在のエコシステムは主に擁護と議論に焦点を当てており、サンプル リポジトリや JSON スキーマ ドラフトが GitHub で入手できる可能性があります。
- 双方向の実装が必要な MCP とは異なり、agents.json は**サイト サポート** に依存しています。サイトでの広範な採用によってのみ、エージェント エコシステムが真に繁栄することができます。
- 大手コンテンツプロバイダー（検索エンジン、ソーシャルプラットフォーム）が最初にこれを採用すれば、エコシステムが大幅に強化されるでしょう。
- オープンソース エージェント プロジェクト (AutoGPT など) が、agents.json の自動検索を開始すると、サイトも同様の圧力を受ける可能性があります。
- 全体として、そのエコシステムの発展は、**双方向** のサポート、つまりサイトの意欲とエージェント ツールのサポートに依存します。

### 今後の展望
**潜在的な Web 標準の補完**:
- agents.json の概念はシンプルですが重要であり、Web の「人間指向」から「エージェント指向」への進化に沿ったものです。
- 将来、**大規模モデルエージェントが普及**した場合、サイトはマシン訪問者を考慮する必要があり、robots.txtに似たエージェントプロトコルが登場する可能性があります。
- Agents.json は、**既存ネットワークとの互換性** と低い導入コストという利点により、このギャップを完全に埋め、業界のコンセンサスになりやすくなっています。
-  近い将来、コミュニティの推進により、W3C がブラウザ/検索エンジンをサポートする公式標準を提案し、agents.json の地位を確立する可能性があると予想されます。
- 他の通信プロトコルを置き換えるものではありませんが、**補完標準** として広く存在します。たとえば、MCP または AITP を使用するエージェントは、Web サービスにアクセスする前に、agents.json をチェックして呼び出し方法を決定できます。
- 長期的には、agents.json がエージェント エコシステムに統合されることはほぼ確実ですが、その見通しは採用の速度と詳細な策定によって決まります。将来的には**成功する可能性が高い**と言え、おそらく「エージェントフレンドリーなWebサイト」の標準設定ファイルとなるでしょう。

## LMOS (言語モデルオペレーティングシステム)

### ターゲットの問題
**マルチエージェント システム インフラストラクチャ** を対象としています:
- オープンなマルチエージェント プラットフォームとエコシステムの構築に取り組み、開発と展開の複雑さを軽減します。
- さまざまなエージェント プラットフォーム間の非互換性、拡張の問題、複雑なスケジュール管理の問題に対処します。
- オペレーティング システムに似た統合環境を提供し、異種エージェントが互いの能力を簡単に発見し、効率的に通信してタスクを共同作業できるようにします。
### 主要テクノロジー
**オープン マルチエージェント アーキテクチャ**:
-  **エージェント記述形式** を提供して、エージェント/ツールの機能とメタデータの記述を標準化し、セマンティック抽象化を通じてクロスプラットフォームの相互運用性を確保します。
- **検出メカニズム**: mDNS ブロードキャストを介したローカル検出と、**中央レジストリ** を介したクロスネットワーク検出を実装します。
- は、ディレクトリ サービスとして機能する**エージェント レジストリ**を提供し、適切なエージェントに一致するメタデータ ベースの検索機能をサポートします。
- 通信プロトコルは柔軟でプラグイン可能であり、単一の転送方法を強制するものではないため、エージェントはニーズに応じて HTTP、メッセージ キュー (MQTT/AMQP)、または P2P などの最適なオプションを選択できます。
- **エージェント グループ管理** をサポートし、信頼できるグループ内での共同操作を可能にします。
- また、LLM、メモリ、およびツール インターフェイスを抽象化するための **Agent ReaCtor** フレームワークも提供し、エージェントの仮想「オペレーティング システム」カーネルとして機能します。
- インテリジェントなタスク スケジューリングは、NLU 主導のルーティングと最適なエージェントへのタスク割り当てを通じて実現されます。

### 該当するシナリオ
**エンタープライズレベルのマルチエージェント システム**:
- LMOS は、**大規模なインテリジェント エージェント** の展開と管理を必要とするシナリオ (コールセンターの多数の会話エージェント、カスタマー サービス アシスタントのクラスター、または大規模な自動ワークフローにおけるさまざまな専門知識を持つエージェントのコラボレーションなど) に適しています。
-  LMOS のクラウドネイティブ アーキテクチャが有利な可能性がある、柔軟なスケーリングを必要とするマルチチャネル (Web、モバイル、音声 IVR) エージェント サービスで特に効果的です。
- マルチエージェントエコシステムの**研究開発テスト**にも適用でき、統一プラットフォーム上で異なるエージェントフレームワークの連携を実験します。
- ベンダーロックインの回避を重視し、企業や研究機関はLangChainやLlamaIndexなどの既存のエージェントをLMOSに統合して統合管理できます。

### 技術アーキテクチャ
**クラウド クラスター + バス**:
- LMOS アーキテクチャには、**コントロール プレーン** および**ランタイム** が含まれます。
- コントロール プレーンは、中央の**エージェント レジストリ サービス**と**スケジューラー ルーター**で構成されます。
- 各エージェント (さまざまなフレームワークで実装可能) は、起動時にその機能の説明と通信アドレスをレジストリに登録します。
- ルーターは、自然言語から解析されたタスクの内容を適切なエージェントに照合し、**RPC 呼び出しまたはメッセージ配信** を実行します。
- LMOS は、エージェント通信 (ドキュメントに WebSocket サブプロトコル仕様が含まれていることを示します) および HTTP インターフェイス用に **WebSocket サブプロトコル** をサポートします。
-  クラスター内では、エージェント通信はパブリッシュ/サブスクライブ メッセージ バスまたは直接ネットワーク呼び出しを通じて発生し、LMOS がプロトコル変換を処理し、信頼性の高い配信を保証します。
-  トポロジは主に ** 星形** です。中央ルーターはユーザー要求またはエージェント メッセージを受信し、それらをターゲット エージェントにルーティングするか、グループにブロードキャストします。
-  ローカル ネットワークの場合、mDNS を使用すると、エージェントが簡単な通信を行うために直接検出して接続できます。サブネット間では、レジストリ センターが仲介者として機能します。
- LMOS ランタイムは Kubernetes に基づいており、エージェント インスタンスはコンテナとして水平にスケーリングします。
- システムの安定性を確保するために、**ライフサイクル管理** (ローリングアップグレード、カナリアリリースなど) を提供します。
- 全体的な通信モデルは、**リクエスト-レスポンス** (ルーター->エージェント->ルーター) と**イベント駆動型** (エージェントがルーター経由でサブスクライバーにメッセージをプッシュする) の両方をサポートします。

### 互換性と拡張性
**フレームワーク間の相互運用性**:
- LMOS はオープン標準で設計されており、さまざまな言語やフレームワークのエージェントの統合をサポートします。
- LangChain、Langchain4j、LlamaIndex などの正式に採用されたフレームワークは、LMOS エージェントとしてシームレスに実行できます。
- Kubernetes などの一般的なクラウド テクノロジーを利用しているため、運用チームにとって使いやすいです。
- **モジュラー** 設計は、豊富な拡張ポイントを提供します。開発者は、新しいツール インターフェイス、スケジューリング戦略、またはカスタム プロトコル サポートを拡張できます。
-  たとえば、カスタム メッセージ キュー システムでデフォルトの通信を置き換えたり、カスタム モニタリングを追加したりできます。
- LMOS の**可観測性** および**セキュリティ/プライバシー** モジュールは、企業要件への準拠を保証します。
-  標準の記述形式と登録 API を通じて、外部の既存システムとエージェントのメタデータを交換でき、他のエージェント プラットフォームとのインターフェースも可能です (理論的には、異なる LMOS 導入も相互運用できます)。
- 唯一の障壁は、LMOS の比較的包括的で大規模なシステムであり、導入にはアーキテクチャの調整が必要ですが、長期的にはベンダーのロックインを回避し、拡張に役立ちます。
- その **スケーラビリティ** は、アーキテクチャを変更することなく、ビジネスの成長に合わせて数百または数千のエージェント ノードを追加できるように設計されています。

### オープンソースとエコシステム
**エクリプス財団インキュベーション**:
- Eclipse オープンソース プロジェクトとして、LMOS は企業の信頼性を持っています。
- 現在はインキュベーション段階にあり、コア コードとドキュメントは Eclipse プラットフォームで公開されています。
- 企業やコミュニティ開発者によってサポートされている Eclipse 公式サイトでは、詳細なドキュメントとその野心を示すビジョン ステートメントが提供されています。
- 生態学的には、LMOS は既存のオープンソース エージェント フレームワークを統合し、他のプロジェクトの成果をそのエコシステムに効果的に組み込むことに重点を置いています (例: ARC フレームワーク、さまざまな LLM 適応)。
- したがって、それは、**生態系インテグレーター**のように機能します。
-  まだ公開されている大規模なアプリケーション ケースはなく、ほとんどが概念実証およびパイロット プロジェクト (おそらく一部の企業内) です。
- マルチエージェントの概念が勢いを増すにつれ、LMOS コミュニティには、アダプタや展開ケースを作成するためのより多くの貢献者が集まる可能性があります。
- Eclipse の承認により、政府や企業による採用も促進されます。
- **アライアンス** が形成されると（たとえば、LMOS 標準に基づいて相互作用する複数のベンダー）、エコシステムは着実に拡大します。
- 現在、公式チームは開発者を惹きつけるためにブログやドキュメントを公開し、LMOSコンセプトを積極的に推進しています。
-  長期的には、そのエコシステムの成功は事実上の標準になるかどうかにかかっています。大手 AI 企業またはクラウド プロバイダーによってエージェント管理レイヤーとして統合されれば、LMOS は継続的なコミュニティ リソースのサポートを受けることになります。

### 今後の展望
**大きな可能性があるが協力が必要**:
- LMOS は、大規模なエージェント管理に対する将来の企業およびクラウドのニーズに合わせて、マルチエージェント オペレーティング システムの包括的な青写真の概要を示しています。
- その **利点は包括性にあります**: 開発フレームワークから導入、運用までワンストップのソリューションをカバーし、成功すれば大規模な AI エージェント アプリケーションの敷居を大幅に下げます。
-  Eclipse 組織とオープン コミュニティのサポートにより、LMOS は業界インフラストラクチャに成長する機会を得ました。
-  ただし、課題にも直面しています。競合するプロトコル (MCP、AITP など) は特定の側面に焦点を当てており、より早く普及する可能性があります。 LMOS は、その大規模なアーキテクチャの実用性とパフォーマンスを証明する必要があります。
- 今後数年間で、LMOS は最初に垂直分野 (大企業内での包括的な導入など) で実験を開始し、成功事例を活用して標準化を推進する可能性があります。
- 業界が**マルチプロトコル共存**の方向に向かう場合、LMOSはその柔軟な適応性により他の標準を統合することもでき、さまざまなプロトコルをサポートする「メタオペレーティングシステム」になります。
- したがって、LMOS の展望は 2 つの道にあります。主流のマルチエージェント プラットフォーム標準になるか、またはさまざまなプロトコルをサポートする統合フレームワークとして機能するかのいずれかです。
-  いずれにせよ、エージェント システムの複雑さが増すにつれて、エージェント システムには独自の価値があり、将来性が期待できます。
-  短期的には、エコシステムの成熟度を改善する必要があり、推進ペースは特殊なプロトコルよりも遅くなる可能性があります。

## AITP (エージェントインタラクションおよびトランザクションプロトコル)

### ターゲットの問題
**エージェント間の安全な対話とトランザクション**に焦点を当てます:
- AI エージェントが**信頼境界** を越えて通信および取引する問題に対処します。
-  さまざまな組織/個人のエージェントが自律的に通信し、合意に達し、価値交換 (支払いなど) を安全に実行できるようにする標準を提供し、「エージェント インターネット」におけるエージェント間および人間とエージェント間の対話と取引をサポートします。
- 断片化したインターフェイスを統一プロトコルに置き換え、ブラウザが Web サイトにアクセスするのと同じように、エージェントがあらゆるサービスと自由に対話できるようにします。

### 主要テクノロジー
**スレッドセッション + 拡張機能**:
- **会話コンテキスト** 内での構造化メッセージ交換に、チャット スレッドと同様の対話モデル (OpenAI のアシスタント スレッド API を参照) を利用します。
- 永続的な通信セッションを確立するために、**Thread** 抽象化と複数のトランスポート メソッド (HTTP、WebSocket など) を定義します。
- **機能モジュール**を介して拡張し、支払いリクエスト(AITP-01)、意思決定交渉(AITP-02)、データクエリ(AITP-03)、オンチェーンID/ウォレット検証(AITP-04/05)などの構造化された対話タイプを実現します。
- これらの機能は、標準メッセージ形式を使用して会話に組み込まれており、エージェントはテキストだけでなく、フォーム UI や支払い資格情報などの複雑なデータも交換できます。
-  信頼境界を越えたメッセージの署名と検証を強調し、異なるエンティティ エージェント間の信頼できる対話を保証します。
- プロトコル全体は、**トランザクション操作** (暗号通貨または法定通貨の支払いを含む) をサポートし、エージェントが経済活動を直接実行できるようにします。

### 該当するシナリオ
**ユビキタスエージェントインタラクション**:
- さまざまな組織や個人の AI エージェントが **直接通信および取引** する必要がある「エージェント インターネット」の構築に適しています。
- たとえば、銀行/航空会社の代理店と直接通信して業務を処理し、支払いを自動的に実行する携帯情報端末。または複数の企業の AI エージェントがサプライ チェーンで交渉し、発注します。
- これらのシナリオでは、標準化された会話インターフェイスと**トランザクション プロトコル**が必要です。 AITP は、**オンライン サービス市場、エージェント マイクロサービス、クロスドメイン エージェント コラボレーション**、その他のアプリケーションに適した、構造化された会話と支払い機能を提供します。
NEARのようなブロックチェーンエコシステムの- エージェントもターゲットユーザーであり、AITPを活用してオンチェーンとオフチェーンの相互作用を橋渡しし、**価値交換**（トークン支払いなど）主導のエージェントサービスを実現します。

### 技術アーキテクチャ
**セッション駆動型の対話**:
- AITP は、**各会話をスレッド** として扱い、あるエージェントによって開始され、別のエージェントまたはユーザーとのセッションを開きます。
- スレッドには一意の ID があり、HTTP ロング ポーリング、WebSocket、メールボックス スタイルのリレーなど、さまざまなトランスポート チャネルを介して伝送できます。
- スレッド内の通信では、**メッセージ本文 + メタデータ**形式が使用され、特定の「機能」メッセージをサポートしながら、通常のチャット メッセージ構造と互換性があります。
- たとえば、支払いが必要な場合、支払いリクエスト機能を含むメッセージが送信され、受信エージェントはウォレット モジュールを通じて支払いを処理します。
- AITP の定義された機能メッセージは拡張 RPC に似ており、会話コンテキスト内でトランザクションを完了します。
- したがって、アーキテクチャはエージェント間の**ピアツーピアセッションベースの通信**であり、会話コンテキストとリモートプロシージャコールの特性を組み合わせています。
- どのエージェントもスレッド内でサーバーとクライアントの両方として機能できます (ユーザー間のチャットと同様)。一方、標準化された機能モジュールは、特定のメッセージ タイプが定義された処理フローを持っていることを保証します (たとえば、支払い機能は明確なマルチステップ インタラクション プロトコルに対応します)。
- ID 検証は既存のアカウント システム (NEAR ブロックチェーン アカウントや従来の OAuth など) に依存し、セッションの確立前または確立中に資格情報を交換します。
- 要約すると、AITP のアーキテクチャにより、インスタント メッセージングとトランザクション プロトコルの組み合わせに似たエージェント通信が可能となり、必要に応じて構造化トランザクション モードを有効にしながら、**疎結合マルチエンティティ会話** を実現します。

### 互換性と拡張性
**オープンスタンダード + マルチエコシステム**:
- AITP は RFC としてオープンされており、コア仕様とリファレンス実装コードは GitHub で入手できます。
- このプロトコルは、特定のエージェント開発フレームワークに大きく依存しません。 Threads API と機能インターフェイスに従っている限り、AITP は OpenAI の会話形式と**ほぼ互換性** をもつように設計されているため、既存の会話型 AI (OpenAI の ChatCompletion に基づくエージェントなど) は最小限の変更で統合できます。
- その **機能システム** は拡張可能です。既存のモジュールに影響を与えることなく、メッセージ タイプを定義することで新しい機能モジュールを追加できます。
- 特にトランザクション関連の機能については、主流の暗号通貨ウォレットおよび従来の支払い (NEAR ウォレット/EVM ウォレット) と互換性があるように設計されており、より多くの支払い方法の追加が容易になります。
- NEAR によって推進されている AITP は、まず NEAR コミュニティ内で適用され、ブロックチェーン インフラストラクチャ (エージェントの動作のスマート コントラクト検証など) と統合される可能性があります。
-  ただし、プロトコル自体はブロックチェーンに依存せず、従来の Web サービス エージェントで採用できます。
- この設計により、AITP は暗号化ドメインと Web ドメインの両方に拡張できます。
-  広く普及するには、主流の AI アシスタントやブラウザ エージェントとの統合など、より多くのプラットフォームがそれをサポートする必要があります。
- 現在、NEAR AI HubなどがAITPを統合しており、コミュニティのフィードバックがエコシステムの方向性を決定します。

### オープンソースとエコシステム
**NEAR主導のプロモーション**:
- AITP は NEAR 財団によって開始され、NEAR 共同創設者を含む中心著者が参加するため、本質的にブロックチェーン コミュニティ リソースを所有しています。
- RFC は 2025 年 2 月にリリースされ、ドキュメントとディスカッションのために aitp.dev サイトがオープンしました。
- NEAR AI Hub は AITP を統合しており、NEAR エコシステム エージェント (分散型カスタマー サービスなど) がその実装を優先します。
- NEAR は外部の協力も呼びかけており、他のエージェント開発者と標準を共同開発する意欲を表明しています。
-  AI とブロックチェーンのコミュニティが注目: 暗号メディアは「AITP 新標準の誕生」を報じました。
- そのトランザクション機能により、フィンテック AI アプリケーションを引き付ける可能性があります。
- オープンソース的には、AITP コードは MIT または同様のライセンスに基づいてリリースされ、新しい機能モジュールのコミュニティへの貢献を奨励します。
- NEAR の AI チームは、エコシステムを推進するためのディスカッション (オフィス アワー) を定期的に開催しています。
- 潜在的なリスクは、AITP が NEAR コミュニティを超えて拡張し、より広範な AI コミュニティに受け入れられるかどうかです。ただし、そのステートメントは NEAR チェーンにバインドしません。
-  したがって、エコシステムは Web2 企業に拡大する機会があります。
- OpenAI、Anthropic などと提携（オープンエージェント標準提携など）できれば、AITP エコシステムは急速に成長するでしょう。

### 今後の展望
**エージェント インターネットを構築する有力な候補**:
- AITP は、**エージェントの経済活動** に直接焦点を当てているため、非常に期待されています。
- 通信とトランザクションを統合し、将来の自律エージェントのトランザクションとコラボレーションの重要なニーズを満たし、他のプロトコルと区別します。
- AI エージェントによって実行されるビジネス活動が増えるにつれ、AITP が広く受け入れられれば、**インターネット アプリケーションの新しいプロトコル層** (閲覧用の HTTP と同様) になる可能性があります。
- NEAR のサポートは立ち上げを加速しますが、長期的な成功にはより中立的な参加者が必要です。
- AITP は、その斬新なコンセプトとタイムリーなリリース (エージェント ブームと同時) により、すぐに開発者コミュニティを形成し、エージェント間のトランザクションにおける標準的な優位性を確立すると楽観的に考えています。
-  デモンストレーション シナリオ (自動チケット予約のエージェント間プロセスなど) が正常に実装され、従来のスクレイピング ソリューションよりも優れたものになると、業界も追随するでしょう。
- さらに、AITP は必ずしも MCP/ANP と競合するわけではありません。インタラクション層とトランザクション層に焦点を当てており、他のエージェント通信プロトコルと組み合わせることができます。
- したがって、将来的には、**プロトコル融合** のシナリオが見られる可能性があります。ツール統合には MCP、アイデンティティと P2P には ANP、標準的なインタラクションと支払いには AITP がそれぞれの強みを活用します。
- 結論として、AITP は「エージェント相互接続エコノミー」エコシステムを構築し、特に**商用シナリオ** において、将来のプロトコル環境での地位を確保する可能性を秘めています。

## 概要

要約すると、各プロトコルには次のような焦点があります。

- **MCP** は、**LLMs** のツール インターフェイスとして位置付けられており、迅速な導入が可能であり、大手企業によって支援されています。
- **ANP** は、**分散型エージェント ネットワーク** を目指しており、テクノロジーをリードしていますが、エコシステムのサポートが必要です。
- **agents.json** は、Web 環境の**補助標準** であり、広く普及し、他のプロトコルを補完する可能性があります。
- **LMOS** は、**フルスタックプラットフォーム** を提供し、長期的な可能性を伴う大規模導入に適しています。
- **AITP** は、**安全な相互作用と経済取引**、潜在的に主要なエージェントの商用相互接続に焦点を当てています。
- **Agora** は、**将来の適応型コミュニケーション** の方向性を表しており、広範囲に影響を及ぼします。

将来のプロトコルの状況は、単一のプロトコルによって支配されるのではなく、むしろ補完的な融合になる可能性があります。

-  たとえば、AITP を使用してインタラクション形式を定義し、ANP をアイデンティティ信頼に、MCP/agents.json を使用して特定のデータ ソース統合を定義します。

近い将来、**MCP** は、その直接的な問題解決と初期のエコシステム規模により、ツールの統合をリードする可能性があります。しかし、さらに先を見据えると、**ID 認証とトランザクション機能を備えたオープン プロトコル** (ANP、AITP など) は「エージェント インターネット」のビジョンとより一致しており、グローバルなインテリジェント エージェント ネットワークの構築においてより大きな役割を果たす可能性があります。
