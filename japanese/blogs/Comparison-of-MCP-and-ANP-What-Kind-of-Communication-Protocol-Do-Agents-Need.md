# MCPとANPの比較：エージェントには、どのような通信プロトコルが必要か

**中心となる考え：**
- 消費者向けの個人アシスタントには、コストと情報取得という、二つの障壁が残ります。推論の障壁は、急速に解消されつつあります。すべての情報へのアクセスには、エージェント通信プロトコルが必要です。
- 現在、設計と実装が比較的整った、AI関連のオープンソースの通信プロトコルは、AnthropicのMCPと、私たちのANPです。
- 構造、本人認証、情報の構成に、大きな違いがあります。
  - MCPは典型的なクライアント・サーバー（CS）、ANPはP2P方式です。
  - MCPはOAuthで、既存のリソースへのアクセスを容易にします。ANPはW3C DIDで、プラットフォームをまたぐ相互運用性と、すべてのエージェントの接続を重視します。
  - MCPはJSON-RPCで、本質的にはAPI呼び出しです。ANPはセマンティックWebのLinked-Dataで、AIがアクセスし、理解しやすいデータネットワークを目指します。
- 最大の違いは、世界観です。
  - MCPはモデル中心で、インターネット全体が、コンテキストやツールです。
  - ANPはエージェント中心で、対等な立場のノードが、分散して協働します。
- 必要なプロトコルは、将来のAgentic Webの特徴によります。私たちはMCPと異なる見方を持ち、ANPの開発を続けます。

## 通信プロトコルが重要な理由

Deepseek R1、OpenAI O3 Mini、Deep Researchの公開から、複雑なタスクを推論する能力という、中心的な制約が、急速になくなりつつあると分かります。

Deep Researchは、本質的に、知識労働者の個人アシスタントと見なせます。

消費者向けでは、二つの制約が残ります。一つは、2025年までに1～2桁下がると予測するコストです。もう一つは、十分な情報を、どう得るかです。

知識労働者の情報は、公開データベースやサイトにあることが多く、AIも容易に取れます。消費者向けの情報は、より複雑で、プラットフォームの孤立のため、断片化し、閉じています。

ツールの能力も情報の一種と考えられます。それらを、個人アシスタントが、容易かつ効率的に得る方法が、通信プロトコルの解決する問題です。

Computer Useではなく、プロトコルである理由は、[Agentic Webは何が違うのか](What-Makes-Agentic-Web-Different.md)を参照してください。

## MCPとANPの紹介

**MCP（Model Context Protocol）**は、LLMアプリケーションを、外部のデータやツールに円滑につなぐ、オープンなプロトコルです。AIによるIDE、チャットの強化、独自の作業手順などで、必要なコンテキストに接続する、標準の方法を提供します。[MCP仕様](https://spec.modelcontextprotocol.io/)

**ANP（AgentNetworkProtocol）**は、Agentic Webのための、オープンな枠組みです。分散型の本人認証で、任意の二つを接続し、記述仕様によって、効率的なデータ交換と協働を実現します。[GitHub](https://github.com/agent-network-protocol/AgentNetworkProtocol)

ANPは、インターネット上のエージェント向けに、最初に公開されたオープンソースの通信プロトコルかもしれません。まずコードを公開し、仕様はFeishuに置き、その後GitHubに移しました。

ほかによいプロジェクトをご存じなら、ぜひ紹介してください。

## MCPとANPの違い

構造、本人認証、情報の構成の三つを詳しく見てから、理念と、その理由を説明します。

### 構造：CSとP2P

#### MCP

典型的なクライアント・サーバー方式です。クライアントがMCPサーバーにつながり、情報やツールを利用します。

<p align="center">
  <img src="../../blogs/images/mcp-architecture.png" width="50%" alt="mcp-architecture"/>
</p>

stdioやHTTPで双方向の通信路を作れます。HTTPでは、POSTで送信し、SSEでサーバーのイベント通知を受信します。

<p align="center">
  <img src="../../blogs/images/mcp-http-sse.png" width="50%" alt="mcp-http-sse"/>
</p>

#### ANP

任意のエージェントが相手につながる、P2P方式です。

<p align="center">
  <img src="../../blogs/images/anp-architecture.png" width="50%" alt="anp-architecture"/>
</p>

現在の基盤はHTTPです。ほかに接続し、ほかからのメッセージも受信できます。理論上は、WebSocketや独自のトランスポート層も使えます。

P2Pを選んだ理由は、自分から要求するだけでなく、いつでも相手から受け取れるようにするためです。

MCPでは、クライアントが接続していなければ、サーバーから送れません。クライアントがサーバーも兼ねれば、P2Pと見なせますが、不自然です。

本当のP2Pでは、物理的な接続だけでなく、役割と位置付けも対等であることが、中心です。

### 本人認証：OAuthとDID

最も重要で、難しい部分の一つです。すべての相手と協働するには、プラットフォームをまたいで認証できる必要があります。

#### MCP

公開当初には認証がなく、リモートのサーバーに接続しにくいものでした。最新の草案では、クライアントとサーバーの認証をサポートします。

技術の中心は、OAuth 2です。

OAuthは、利用者の認可のもと、第三者のアプリケーションが、別の提供者のリソースに、安全、簡便、柔軟にアクセスする、オープンな認可の枠組みです。利用者名やパスワードを得る必要はありません。GoogleやWeChatによるログインなど、広く使われています。

二つ目のコミュニティ草案では、次が改善されました。
- 草案段階のOAuth 2.1を使い、単純化し、安全性を高める。
- OAuth 2.0 Authorization Server Metadataで、認可サーバーを発見し、認可・トークンのエンドポイント、認可の種類、暗号アルゴリズムなどの設定を、自動取得する。
- OAuth 2.0 Dynamic Client Registration（DCR）で、事前の手作業なしに、クライアントを自動登録し、統合のコストを減らす。

全体の流れ：

<p align="center">
  <img src="../../blogs/images/mcp-authorization.png" width="50%" alt="mcp-authorization"/>
</p>

#### ANP

技術の中心は、W3C DIDです。

[W3C DIDs](https://www.w3.org/TR/did-core/)は、2022年に勧告となった、検証可能で分散型のデジタル識別子です。利用者の管理と、アプリケーション間の相互運用性を実現します。

現在、多くのアプリケーションが使い、特にBlueskyの基盤であるAT Protocolが、本人認証に採用しています。

流れは、次のとおりです。

<p align="center">
  <img src="../../blogs/images/anp-authorization.png" width="50%" alt="anp-authorization"/>
</p>

最大の利点は、相互運用性です。異なるプラットフォームのエージェントが、同じプラットフォームのアカウントを使ったり、相互登録したりせず、認証できます。もともと、分散型の本人性のために設計されているからです。

関連記事：
- [did:wbaとOpenID Connect、APIキーの比較](comparison-of-did-wba-with-openid-connect-and-api-keys.md)
- [did:wba方式の仕様](../03-did-wba-method-design-specification.md)

比較すると、次が分かります。
- 既存の大きなアプリケーションはOAuthを広く使うため、MCPは、既存のインターネットへの接続によい選択です。
- DIDは新しく、普及ではOAuthに及ばず、対応するにはコードの変更が必要です。
- OAuthは、モデルが、既存の利用者のリソースにアクセスする問題を扱います。DIDは、異なるプラットフォームのエージェント同士の認証を扱います。

相互運用性だけを見れば、DIDの方が単純で、やり取りも少なくなります。
- OAuthは、サーバーにIDを登録します。DIDは、自分のIDを直接使い、登録と、相手ごとのIDの管理コストを省きます。
- DIDは、最初の業務リクエストに認証情報を付ける、0-RTT（往復ゼロ）を実現できます。OAuthには、複数回のやり取りが必要です。

根本的には、OAuthは相互運用性のための専用設計ではなく、DIDは、分散型で、それに向いた技術だからです。

なお、難しい課題も残ります。
- 必要な本人の情報を得つつ、プライバシーを漏らさないには、どうするか。
- 一つのIDですべてと通信せず、権限を、どう細かく制御するか。
- 人が手動で認可したリクエストか、どう判断するか。機微な操作を、自律的に始めるべきではありません。
- プラットフォームが与える権限ではなく、本人が完全に所有するには、どうするか。

W3C DIDなら、解決しやすいかもしれません。多くに初期の案があり、順に改善し、公開します。

### 情報の構成：RPCとLinked-Data

外部への情報のまとめ方も異なります。

#### MCP

JSON-RPC（JavaScript Object Notation - Remote Procedure Call）で、リソースやツールを読み、操作します。JSONに基づく遠隔呼び出しで、クライアントは、相手のメソッドを呼び、JSONの結果を得ます。

サーバーが全一覧を示し、指定のものを読んだり呼んだりできます。クライアントがリソースを購読し、状態が変わったら、サーバーが通知することもできます。

形式は、サーバーが決め、モデルが、何を読むか、何を操作するかを選びます。本質的には、特別なAPIと理解できます。

#### ANP

セマンティックWebのLinked-Dataが中心です。

RDF、SPARQL、URIなどのWeb標準に基づき、URIで、異なる出所の構造化データを共有・接続し、機械で読み、意味を理解できるようにします。

実装では、アイデンティティ、能力、主体の情報、APIなどを示す、[Agent Description](../07-anp-agent-description-protocol-specification.md)を定義しています。

JSONに基づくLinked Data形式、JSON-LDを使い、異なるデータをつなぎ、機械で理解しやすくします。

例えば、コーヒー店の名前、所有者、場所、営業時間と、複数の販売商品のURLを記述します。AIは、商品のJSON-LD文書を読み、詳しい情報を得られます。そこにも、新しいURLがあるかもしれません。

こうして、一つの記述文書から、すべての公開情報を得られます。人向けのページの網に対して、AI向けの、JSON-LDの網を作れます。最終的には、人向けとAI向けの、二つのネットワークになります。

もう一つの中心的な特徴は、意味の理解です。schema.orgの、現代のWebを記述する意味のモデルを基礎に、同じフィールドの理解を一致させ、正確さと、プログラムでの扱いやすさを高めます。

また、検索エンジンが公開情報を巡回しやすく、利用者は、サービスを提供する相手を、素早く見つけ、記述文書を基に、協働できます。

### 設計の理念

以上を抽象化すると、世界観の違いになります。
- MCPはモデル中心で、インターネット全体を、コンテキストとツールとします。
- ANPはエージェント中心で、対等なノードの、分散した協働ネットワークとします。

<p align="center">
  <img src="../../blogs/images/mcp-vs-anp-core.png" width="75%" alt="mcp-vs-anp-core"/>
</p>

なぜ、違うのでしょうか。目的が異なるからです。

厳密には、MCPはエージェント通信ではなく、名前どおり、モデルのコンテキストのプロトコルです。現在のインターネットに容易につなぎ、チャットボットを豊かにします。

私たちは、独自のプロダクトを持たずに、未来のAgentic Webの理解から、ANPを設計しました。AIの能力を十分に引き出す、新しいネットワークを作るためです。

## 必要な通信プロトコルは、どのようなものか

MCPは、現在のモデルのアクセスに、最もよい解決策で、Computer Useより持続性があると評価します。Anthropicの影響力によって、業界にも利点が伝わりました。

ただし、現在の最適解である、過渡的な形かもしれません。インターネットが、エージェントで大きく変われば、最適とは限りません。

必要な方式は、将来の特徴によります。私たちは、[Agentic Webは何が違うのか](What-Makes-Agentic-Web-Different.md)で、次を整理しました。
- 隅々に広がり、人や組織には、複数のエージェントがある。
- すべてが相互接続できる。能力を引き出す必要条件です。
- 個人アシスタントが新しい入り口になり、エージェント同士の接続は、人との接続を大きく上回る。
- 平らなネットワークで、第三者のプラットフォームなしに、直接つながる。

これが、ANPの土台です。

もちろん、MCPの進化も歓迎します。これほど重要な業界標準を、一組織や一人で完成させることは、私たちにもできません。業界の皆さんと、協力したいと思います。

## よくある質問

- MCPがあるのに、なぜANPを作るのか：開始したときには、MCPはまだありませんでした。厳密には、私たちが最初のオープンソースのエージェント通信プロトコルであり、公開も先のはずです。
- MCP公開後も、なぜ続けるのか：未来について、異なる見方を持つからです。
