# MCPとANPの比較: どのような通信プロトコルが必要なのか?

**コアアイデア:**
- 消費者指向のパーソナルアシスタントの構築は、コストと情報取得の2つのボトルネックに直面しています。 推論力ネックは急速に解決されます。 エージェントの通信プロトコルは、AIがすべての情報にアクセスできるようにする必要があります。
- 現行の業界AI関連のオープンソース通信プロトコルの中で、AnthropicのMCPとANPは設計や実装において比較的完成しています。
- プロトコルアーキテクチャ、アイデンティティ認証、情報組織においてMCPとANPが大きく異なる。
  - MCPは、典型的なクライアント・サーバー(CS)アーキテクチャで、ANPはPier-to-Peer(P2P)の典型的なアーキテクチャです。
  - MCPのID認証は、OAuth規格に基づいており、クライアントが現在のインターネットリソースへのアクセスを促進します。 ANPのID認証は、W3C DID規格に基づいており、エージェント間で相互プラットフォームの相互運用性に焦点を当て、シームレスな接続を可能にします。
  - MCP は、JSON-RPC テクノロジーを使用して情報を整理し、本質的に API 呼び出しを行います。 ANPは、SEOで容易にアクセス可能かつ理解しやすいデータネットワークを構築するために、セマンティックなWeb Linked-Data技術を使用しています。
- MCPとANPの最大の違いは、その世界観にあります。
  - MCPはモデル中心で、インターネット全体をコンテキストやツールとして表示します。
  - ANPは、各エージェントが同じステータスを持ち、分散型エージェントコラボレーションネットワークを形成するエージェント中心です。
- 通信プロトコルエージェントの種類は、Agentic Web の将来の特性に依存します。 MCP から異なるビューを持たせ、ANP の継続的な開発にコミットしています。

## エージェント通信プロトコルが重要である理由

Deepseek R1、OpenAI O3 Mini、Deep Researchの発売に伴い、明確な傾向が現れます。コアボトルネックヘンダー剤構造は複雑な作業を推論する機能で、急速に消えています。

ディープリサーチは、知識従事者のための個人アシスタントとして基本的に考慮することができます。

消費者指向のエージェントの場合、2本のボトルネックは残ります。コスト、2025年までに2つの注文によって減少すると予想され、情報:個人アシスタントが十分な情報を得る方法?

知識労働者の情報は、オープンデータベースやウェブサイトに格納され、簡単にAIにアクセスすることができます。 消費者指向の情報は、現在のインターネットのデータサイロ現象によって妨げられるより複雑で、情報が整理され、不断に開くことである。

消費者の必要な情報(ツールは、情報の形とも考えられる)を効率的にかつ効果的に取得するために、個人アシスタントを有効にする方法は、エージェント通信プロトコルが解決する問題です。

Note: 「コンピュータ使用」ではなく通信プロトコルが必要である理由は、この記事を参照してください。 [エージェントのWebを異なるものにする](What-Makes-Agentic-Web-Different.md).

## MCPとANPの紹介

**MCP(モデルコンテキストプロトコル):** LLM アプリケーションが外部のデータソースとツールをシームレスに統合できるオープン プロトコル。 AI 主導の IDE の構築、チャットインターフェイスの強化、カスタム AI ワークフローの作成など、MCP は LLM を必要なコンテキストに接続するための標準化された方法を提供します。 [MCPの指定](https://spec.modelcontextprotocol.io/)

**エージェントネットワークプロトコル(ANP):** エージェントWeb用に設計されたオープンなプロトコルフレームワーク。 ANPは、分散型のアイデンティティ認証を実装し、2つのエージェントが接続できるようにします。 エージェントの記述仕様をより効率的なデータ交換とエージェント間のコラボレーションも設計します。 [GitHubでANPを](https://github.com/agent-network-protocol/AgentNetworkProtocol)

エージェント通信プロトコルの現在の状況では、ANPはインターネット上のエージェントのために特別に設計された最初のオープンソース通信プロトコルです。 最初にコードを解放しました。フェシュウのプロトコル文書で、その後GitHubに移行しました。

ほかのオープンソースプロジェクトがよくわかっているなら、ぜひ紹介してみて下さい。

## MCPとANPの違い

以下は、プロトコルアーキテクチャ、アイデンティティ認証、情報組織の3つの側面でMCPとANPの違いを詳しく説明し、設計哲学の違いやその背後にある理由に続いています。

### プロトコルアーキテクチャ:CS対。 プチプチ

#### MCPプロトコルアーキテクチャ

MCP は、典型的なクライアント・サーバーのアーキテクチャです。 クライアントは、MCP プロトコルを使用して MCP Server に接続し、プロトコルを使用して、サーバーからさまざまな情報とツール機能にアクセスします。

</p>

クライアントとサーバーは、stdioまたはHTTP経由で双方向通信リンクを確立できます。 HTTP を使用する場合、クライアントは HTTP POST を使用してメッセージを送信し、HTTP SSE を使用してサーバーイベント通知を受信します。

  <img src="../../blogs/images/mcp-http-sse.png" width="50%" alt="mcp-http-sse"/>
</p>

#### ANPプロトコルアーキテクチャ

ANPは、一般的なピアツーピアアーキテクチャで、ANPを他のエージェントに接続するために使用できるという点です。

<p align="center">
  <img src="../../blogs/images/anp-architecture.png" width="50%" alt="anp-architecture"/>
</p>

ANP は、現在 HTTP プロトコルをコアで使用しています。 エージェントはHTTPを使用して他のエージェントに接続し、HTTP経由で他のエージェントからメッセージを受信することもできます。 WebSocket およびプライベートトランスポートレイヤープロトコルは、理論的にサポートされています。

ANPのP2Pアーキテクチャの選択の主な理由は、エージェントが他のエージェントに積極的にリクエストを開始し、いつでも他のエージェントからの要求を受け取ることを可能にすることです。

MCP の CS アーキテクチャでは、クライアントがサーバーに接続されていない場合、サーバはクライアントにメッセージを送信できません。 もちろん、クライアントがサーバーとして機能できる場合、MCPはP2Pアーキテクチャと見なすことができます。

P2Pアーキテクチャは、物理的接続だけでなく、P2PのコアであるP2Pとしての役割と位置を伴います。

### アイデンティティ認証: OAuth 対 ダイド

アイデンティティ認証は、エージェント通信プロトコルの重要な課題と課題です。 エージェント間でのクロスプラットフォーム認証の問題に対応し、エージェントが他のすべてのエージェントとコラボレーションできるようにします。

#### MCP のアイデンティティ認証

MCP が初めてリリースされたとき、ID 認証をサポートしていないため、リモートサーバ接続の不便性を保ちました。 最新ドラフトバージョンでは、クライアントとサーバー間でのID認証をサポートしています。

MCPのID認証方式は、OAuth2規格を中心に技術的に中心化されています。

OAuth は、ユーザー権限を持つ別のサービスプロバイダでユーザーリソースにアクセスするためのサードパーティアプリケーションのための安全で便利な柔軟な方法を提供するように設計されたオープンな標準認証フレームワークです。ユーザー名やパスワードなどの機密情報を入手することなく、 一般的な例は、GoogleまたはWeChatアカウントを使用してサードパーティのアプリケーションにログインするものです。これはOAuthテクノロジーに基づいており、インターネット上で広く使用されています。

MCP がリリースしたドラフトプロトコルは、コミュニティの第2版です。 最初のバージョンと比較して、次の改善があります。
- OAuth 2.1 を使用する(ステータスをドラフトする)、プロトコルの簡素化とセキュリティの強化
- OAuth 2.0 認可サーバーの検出をサポートし、OAuth 2.0 認証サーバーメタデータプロトコルを使用して、クライアントが承認エンドポイント、トークンエンドポイント、サポートされた認証タイプ、暗号化アルゴリズムなどの認可サーバーの関連設定情報を自動発見し、取得できるようにします。
- OAuth 2.0 動的クライアント登録 (DCR) プロトコルをサポートし、クライアントが事前の手動サーバー登録なしでサーバーに自動的に登録できるようにすることで、クライアントサーバの統合コストを簡素化できます。

#### ANP のアイデンティティ認証

ANPのID認証方式は、W3C DID仕様を中心に技術的に中心化されています。

とりあえず [W3C のディド](https://www.w3.org/TR/did-core/) 2022年にW3Cの推奨として公開された標準は、検証可能な分散型デジタルアイデンティティをサポートする新しいタイプの識別子です。 DID に基づいて、ユーザーは自分のアイデンティティを本当に制御し、異なるアプリケーション間の相互運用性を向上させることができます。

現在、W3C DID仕様書をご使用いただいているアプリケーションの多くは、プロトコルの基幹となるBlueskyが、その認証スキームとしてW3C DIDを使用します。

アイデンティティ認証技術としてDIDを使用する最大の利点は相互運用性です。 異なるプラットフォーム上のエージェントは、単一のプラットフォームアカウントを使用するか、相互登録を実行することなく、DIDを使用してお互いを認証することができます。

DIDは、分散型アイデンティティのために意図的に設計されているため。

ANP DID 本人認証に関する関連記事:
- [OpenID Connect と API キーの比較:wba](Comparison%20of%20did:wba%20with%20OpenID%20Connect%20and%20API%20keys.md)
- [wba メソッドの仕様](../03-did:wba%20Method%20Design%20Specification.md)

MCP と ANP の ID 認証を比較し、いくつかの違いを識別できます。
- MCPのID認証方式は、既存のインターネットに接続するAIに適しています。現在OAuthをサポートしている多くの主要なアプリケーションがサポートされています。
- ANPは、DID技術、比較的新しい仕様、OAuthよりも少ないワイドな機能で、サポート用のコードを修正するアプリケーションが必要です。
- OAuth は、既存のインターネットアプリケーションでモデルにアクセスするユーザーリソースをどのモデルに格納するかを、DID は異なるプラットフォームのエージェントが互いに認証する方法をアドレスします。

相互運用性に関しては、DIDベースのスキームはシンプルで、より少ない相互作用を含みます。
- OAuth は、クライアントがサーバーに ID を登録する必要があり、DID スキームは、独自の ID を使用して、他のパーティとやり取りし、登録プロセスの排除や、異なるサーバー生成された ID の管理コストを削減します。
- 本人認証の際に、IDはより少ない相互作用を伴って0-RTT(ゼロ往復時間、すなわち、最初のビジネスリクエストにおけるアイデンティティ検証情報を運ぶ)達成することができます。 OAuth は複数のインタラクションを必要とします。

基本的理由は、OAuthが特にアイデンティティの相互運用性のために設計されていないことです。 DIDは、分散型アイデンティティ技術であり、相互運用性により友好的です。

エージェントのアイデンティティについては、これは確かに難しい問題です。 問題は解決する必要が多々あります:
- 必要なアイデンティティ情報を入手しながら、ユーザーのプライバシーを侵害することなくクロスプラットフォームのアイデンティティ認証を実現するには?
- ユーザーのより細かい権限管理を実現する方法、単一のIDを使用してすべてのエージェントと通信する方法
- エージェントからのリクエストが手動でユーザーによって承認されているかどうかを判断する方法は? エージェントが自動で動作するべきではない、いくつかの機密操作。
- プラットフォーム付与された許可を使用するのではなく、ユーザーが自分のアイデンティティ所有権を完全に制御できるようにする方法は?

これらはW3C DIDにより解決しやすい問題です。 課題を解決し、徐々に改善・リリースしていきます。

### 情報機関: RPC 対。 連携データ

MCPとANPは、外部の世界に情報出力を整理するためのさまざまな技術を採用しています。

#### MCP情報組織

MCP は、JSON-RPC を使用してサーバーリソースとツールの機能を読み込み/運用します。 JSON-RPC(JavaScript オブジェクトの表記 - リモートプロシージャ呼び出し)は、JSON 形式に基づくリモート・プロシージャ・コール (RPC) プロトコルです。 リモートサーバーでメソッドを呼び出し、JSON の結果を返送できます。

MCP を使用して、サーバーはすべてのリソースやツールリストを一覧表示し、指定されたリソースを読み込み、指定されたツールを呼び出すことができます。 クライアントはリソースを購読することもできます。また、リソースの状態が変化したときにサーバーはクライアントを積極的に通知します。

リソースやツールの形式は、サーバーによってカスタマイズされ、読み出しと操作するためのリソースやツールを決定するモデルです。

MCP サーバーが情報出力を特別 API として本質的に理解できる方法。

#### ANP情報機関

ANPの外部への情報出力の組織は、セマンティック・ウェブ・リンク・データ・テクノロジーを中心にしています。

リンクされたデータは、Web規格(RDF、SPARQL、URIなど)に基づいて構造化されたデータ共有と相互接続のための技術であり、独自の識別子(()を介して異なるソースからデータを接続することを目的として、機械読みやすく、そして意味的に理解できるようにします。

実装では、エージェントの説明仕様()を定義します。[エージェントの説明](../07-ANP-Agent%20Description%20Protocol%20Specification.md))、エージェントのアイデンティティ、機能、エンティティ情報、APIインターフェイスなどを説明するために使用されます。

エージェントの説明文書はJSON-LD形式を使用します。 JSON-LDは、JSON に基づくリンクされたデータ形式で、さまざまなデータをデータネットワークに接続し、機械で読みやすくなります。

例えば、コーヒーショップのエージェントの説明文書は、喫茶店の名前、所有者、場所、労働時間などについて説明しています。 ドキュメントには、複数の製品が販売されているURLも含まれています。 今後も、製品に関するJSON-LD資料にアクセスし、詳細な製品情報を入手することができます。 同様に、詳細な製品情報には、新しいJSON-LD URLも含まれている場合があります。

そのため、エージェントの説明文書がある場合、このエージェントが公開するすべてのパブリック情報を入手できる限り、JSON-LD でリンクした新しいデータネットワークを構築し、AI アクセスに便利です。 これにより、Webページでリンクしている既存のインターネットが、人間のアクセスのために設計されたものに対応します。 最終的には、AIアクセス用に設計された2つのネットワークが形成されます。

データ接続に加えて、リンクされたデータ技術には、もうひとつのコア機能があります。 JSON-LD ドキュメントでは、スキーマの基礎としてスキーマ.org を利用しています。 Schema.orgは、現代のWebを記述するためのセマンティックモデルのセットを定義し、2つのエージェントが同じフィールドの同じ理解を持っていることを可能にし、エージェントとファシリテーションプログラム処理の間の情報理解の正確さを改善します。

リンクされたデータ技術を使用して、エージェントの公開情報は検索エンジンによって簡単にクロールすることができます。 ユーザーは、検索エンジンを通じてサービスを提供できるエージェントをすぐに見つけることができ、エージェントの説明文書に基づいてエージェントとやり取りし、コラボレーションすることができます。

### デザイン哲学の違い

上記は、MCPとANPの意匠詳細の違いです。

抽象的にまとめると、MCPとANPの最大の違いは、その世界観にあります。
- MCPはモデル中心で、インターネット全体をコンテキストやツールとして表示します。
- ANPは、各エージェントが同じステータスを持ち、分散型エージェントコラボレーションネットワークを形成するエージェント中心です。

<p align="center">
  <img src="../../blogs/images/mcp-vs-anp-core.png" width="75%" alt="mcp-vs-anp-core"/>
</p>

こんな違いがあるのはなぜですか?

主として、MCPとANPの異なる目的があります。

厳密に言えば、MCPはエージェントの通信プロトコルではありません。 その名前はモデルのコンテキストプロトコルであり、モデルのコンテキスト機能を提供することを目的としており、現在のインターネットにアクセスし、チャットボット製品の機能を強化するためのモデルがより容易になります。

ANPを設計した時、自社製品がなかった。 今後は、今後のAIのWeb理解に基づいてANPを設計し、直接解決します。 弊社の目標は、AIの能力を完全に解明する新しいエージェントネットワークを構築することです。

## コミュニケーションプロトコルは、エージェントが必要とすることをしますか?

MCPは、インターネットにアクセスするモデルの優れたプロトコルと最高の電流ソリューションであり、「コンピュータ使用」ソリューションよりもはるかに有効であると考えています。 人類性はまた、このソリューションの利点を業界に示すために影響力を使用していました。

しかし、MCPは移行形態である可能性があると確信しています。AIがインターネットにアクセスするための最良のソリューションは、現在入手可能です。 エージェントによりインターネットが大幅に変化する場合、MCPは最善の解決策ではない可能性があります。

そのため、通信プロトコルエージェントは、Agentic Webの将来の特性に依存します。 いくつかのポイントをまとめました(詳細は、この記事を参照してください。 [エージェントのWebを異なるものにする](What-Makes-Agentic-Web-Different.md)):
- エージェントは、個人や組織が複数のエージェントをそれらに提供する可能性があるインターネットのあらゆるコーナーを浸透させます。
- エージェントは、AI機能の削除に必要な条件である相互接続することができます。
- パーソナルアシスタントは、エージェント間の接続が人やエージェント間ではるかに上回るインターネットへの新しいエントリポイントになります。
- 外部プラットフォームなしで直接接続できるエージェントがネットワークをフラットにし、ネットワークがよりフラットになります。

これらは、ANP設計のコア基盤を形成します。

もちろん、MCPも進化し、応援することもあります。 組織や個人が、このような重要な業界標準を独立して完了することができず、また、我々はできる。 業界関係者の皆様とお取引をお待ちしています。

## よくある質問

MCP との関連性については、よくある質問があります。
- MCP が既に存在する後、ANP を作成する理由: 開始すると、MCP はリリースされていない。 厳密に言えば、エージェントのオープンソース通信プロトコルとして初めてのものでなければなりません。また、以前はリリースしました。
- MCP がリリースされた後、ANP を続行する理由:未来のビジョンは異なるからです。
