# Google の最新 A2A、ANP、MCP の包括的な比較

Google は、A2A (Agent to Agent) と呼ばれる新しいエージェント通信プロトコルをリリースしました。この記事では、A2A、ANP、MCPを多角的に徹底比較していきます。

## 問題は解決中です

ANP と A2A はどちらもエージェント間の通信問題を解決することを目的としており、エージェント通信における MCP の限界を認識しています。つまり、MCP はモデルとツールやリソースを接続することに熟達しています。

同時に、ANP と A2A は両方とも MCP を補完すると考えています。 ANP と A2A の間には重複する部分があります。 「一部の重複」の理由は、私が見る限り、A2A は企業内部のエージェントのコラボレーションを解決するように設計されているように見えるためです。ただし、公式 Web サイトにはこれが明示的に記載されていません。これは彼らのデザイン、特にタスクのデザインから感じられます。

## 設計原則

設計原則の観点から見ると、ANP と A2A には多くの類似点があります。
- シンプルさと既存プロトコルの再利用を重視。
- アイデンティティを重視し、エージェントアイデンティティが ANP のコアモジュールです。
-  デカップリング (不透明性): エージェントは思考プロセス、計画、ツールを共有する必要がありません。これは、ANP、A2A、MCP の設計詳細における最大の違いです。

A2A も MCP の複雑さを認識しており、中心概念としてタスクを使用することを選択したようです。実際、タスクはツールやリソースよりも抽象的で高レベルの概念です。

MCP のツールとリソースも MCP に非常に適した概念ですが、サンプリングとルートの設計を再考する必要があると思います。

## プロトコルアーキテクチャ

ANP と A2A は両方とも P2P アーキテクチャとみなすことができます。 MCP は、接続の観点だけでなく、プロトコルの概念やロール設定の観点からも典型的な C/S アーキテクチャです。

間違いなく、P2P アーキテクチャはエージェント ネットワークにより適しています。

## トランスポート層

すべてHTTPをサポートしています。さらに、MCP はローカル リソースにアクセスする必要があるため、便宜上 stdio もサポートしています。

## コアコンセプト

MCP の中心的な概念は、ツール、リソース、サンプリング、ルート、プロンプトです。

A2A の中心的な概念は、タスク、成果物、メッセージ、およびパートです。

ANP の中核概念は、NaturalLanguageInterface や StructuredInterface を含むインターフェイスです。

ANP は、エージェント対話メソッドの定義をインターフェイスに委任します。たとえば、インターフェイスは、結果を直接返すホテルを予約するための API にすることができます。これは、A2A のタスクに似ており、インターフェイス内のタスクの状態を定義することもできます。ただし、プロトコル層では、タスクと状態を直接かつ明示的に定義しません。

不透明度の観点から:
- MCP はホワイトボックスであり、相手の内部ファイル、ツール、リソース、その他の情報を表示できます。
- A2A はグレーのボックスです。エージェントの思考プロセス、計画、ツールは共有しませんが、エージェント間のタスクとタスクの状態を定義します。
- ANP はブラックボックスです。 2 つのエージェントは完全に不透明で、柔軟性を維持しながら最終結果のみを提供します。

## エージェント ID

この領域には非常に大きな違いがあります。

**ANP**

プロトコル自体は ID 情報と ID 検証情報を伝送し、現在主に W3C DID スキームを使用しています。エージェントは、他のエージェント プラットフォームでアカウントを申請することなく、独自の ID 情報を使用して他のすべてのエージェントと対話できます。

私たちは、DID が、特にインターネットのシナリオにおいて、エージェントにとって最も適した ID スキームであると信じています。もちろん、他の認証方法にも拡張できます。

**A2A**

A2A は、HTTP 認証 (Basic、Bearer など)、API キー (リクエスト ヘッダー、クエリ パラメータ、または Cookie に配置できる)、Cookie 認証、OAuth 2.0、OpenID Connect など、OpenAPI でサポートされている認証方法を採用しています。

A2A プロトコル自体は ID 情報を伝送せず、ID 検証情報のみを伝送します。 ID 検証情報はアウトオブバンド、つまり OAuth など、A2A プロトコル外の他の手段を通じて取得されます。

A2A の設計により、既存のエンタープライズ ID システムを完全に活用できます。ただし、エージェント インターネットのシナリオで、エージェント間の接続を実現したい場合は、A2A を使用するのがより面倒になります。

**MCP**

MCP は ID 検証に OAuth を使用します。これはツールとリソースを接続するシナリオに適した一元的なソリューションでもあります。

## エージェントの説明

ANP と A2A は非常に似ており、どちらも JSON を使用します。

A2A のエージェント説明ドキュメントは Agent Card という名前で、本質的には JSON ドキュメントです。

ANP のエージェント記述は、2 つのエージェント間の情報理解の一貫性を向上させることを目的としたセマンティック Web テクノロジーである JSON-LD と schema.org に基づいています。

## エージェントの検出

MCP の検出仕様はまだ見ていませんが、ANP や A2A と同様の検出メカニズムが使用される可能性があります。

ANP と A2A はどちらも RFC 8615 に基づいており、ドメインの .well-known ディレクトリにメタデータ ドキュメントを追加する必要があります。 A2Aのファイル名はagent.json、ANPのファイル名はagent-descriptionsです。

このアプローチを使用すると、どちらも検索エンジンによって非常に簡単にクロールされるようになります。

## エージェント情報組織

エージェントまたは MCP サーバーが外部で情報を整理する方法に関しては、A2A と MCP は両方とも、一種のリモート呼び出しテクノロジーである JSON-RPC を使用します。

ANP はここでは非常にユニークです。 ANP は、AI がアクセスして理解しやすい AI ネイティブのデータ ネットワークを構築することを目的として、セマンティック Web の Linked Data テクノロジーを採用しています。

![](../../blogs/images/ai-native-network.png)

この観点から見ると、ANP の技術的ルートは Web に近いと言えます。私たちは、将来のエージェント インターネットは非常にオープンなネットワークになり、この方法でのみ情報が自由に流れ、AI の機能を解き放つと信じています。

## オープンソースライセンス

ANP のライセンスは MIT、Google-A2A のライセンスは Apache 2.0 です。

私はこれを注意深く研究しましたが、大企業にプッシュし、標準化に参加し、国際的に展開したい場合は、Apache 2.0 が企業の法務部門が優先するプロトコルになるでしょう。 MIT はシンプルですが、潜在的な特許リスクや商業化の道を伴う貴社のようなプロトコル プロジェクトでは、企業の法務チームによって簡単にブロックされる可能性があります。

ANP は、オープン ソース ライセンスのために Apache 2.0 に変更されます。

## トレンド

A2A は MCP を補完すると主張していますが、ドキュメントを読んでいると、漠然と、**ツールがエージェントになり、エージェントがツール**になる可能性が見えてきました。

既存のツールはエージェントに進化できますか?将来のエージェントもツールになるのでしょうか？

この観点から、MCP、A2A、および ANP にはいくつかの重複があるはずです。

## 業界エージェントプロトコルへの影響

MCP はすでにツールやリソースに接続するモデルの事実上の標準となっており、A2A は短期的には挑戦するのが困難です。ただし、ANP には大きな影響があります。

プラスの効果は、エージェントのコミュニケーションとコラボレーションがより多くの人に見えるようになるということです。以前、MCP が流行っていて ANP について話したとき、多くの人が理解していませんでした。これで、エージェントのコミュニケーションとコラボレーションの重要性を強調する必要はなくなりました。

マイナスの影響は、A2A と ANP の機能が大きく重複していることです。 A2A は Google の支援を受けており、非常に大きな影響力を持っていますが、ANP は主にオープンソース コミュニティに依存しており、影響力という点では比較できません。これは ANP の発達にとって好ましくありません。

## 結論

ANP の最も価値のある部分は、実際には、将来のエージェント インターネットに対するコミュニティのビジョン、コミュニティの独自のインターネット哲学 (接続は力です)、および DID + セマンティック Web の技術的ルートです。
