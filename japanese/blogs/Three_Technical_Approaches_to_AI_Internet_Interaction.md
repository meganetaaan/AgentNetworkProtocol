# AI とインターネットの相互作用に対する 3 つの技術的アプローチ: OpenAI のオペレーターからの洞察

OpenAI の Operator のリリースにより、AI エージェントに関する議論が再燃しました。

Operator とは何かを説明する記事は数多くありますが、https://openai.com/index/computer-using-agent/. にある公式の紹介を参照することもできます。

本質的に、オペレーターはブラウザーまたはコンピューターを制御して、日常のさまざまなタスクを完了するのに役立ちます。その最大の重要性は、AI と現在のインターネット エコシステムの橋渡しができることにあります。

この記事では、AI とインターネットの相互作用のための 4 つの新しい技術的アプローチを比較し、要約します。重要なポイントは次のとおりです。

-  AI とインターネットの相互作用に対する現在の技術的アプローチには、コンピューター使用エージェント、ヘッドレス ブラウザー、クライアント側 API、およびリモート API/プロトコルが含まれます。
- Computer Use Agent (CUA): 既存のアプリケーションを変更することなく、AI がインターネット アクセス機能を迅速に獲得できるようにします。ただし、このテクノロジは運用コストが高く、タスクの非同期を実現できません。
- ヘッドレスブラウザ: 運用コストを抑えて非同期タスクの実行をサポートしますが、Web アプリケーションに限定されており、Web 統合には多大なメンテナンス作業が必要です。
- クライアントサイド API: モバイル デバイス上の AI の主流ソリューション。アプリは電話上の AI アシスタント (Siri など) に API を公開します。このアプローチにより、非同期タスクの実行が可能になり、優れたユーザー エクスペリエンスが提供されますが、モバイルとアプリのシナリオに限定され、アプリのオープン性に依存します。
- リモート API/プロトコル: これは、AI がインターネットにアクセスするための最も効率的な方法であり、非同期実行、低い運用コスト、自動認証をサポートします。ただし、アプリケーションのアップグレードが必要であり、統合コストが高くなります。
- 短期的な観点: さまざまな制限にもかかわらず、CUA とヘッドレス ブラウザー テクノロジは両方とも、適切なシナリオでビジネス価値を迅速に提供できます。
- 長期的な観点: API/プロトコルのアプローチが最高のユーザー エクスペリエンスと最低の運用コストを提供するため、私たちは API/プロトコルのアプローチを強く信じています。現在、システム改修コストは高額ですが、AI プログラミング能力の向上に伴い、コストは低下すると予想されます。また、標準プロトコルが登場すると考えています。
- さらに、私たちはプロトコル実装の可能性を積極的に模索しており、大きな進歩を遂げています。

## コンピュータ使用エージェント (CUA)

CUA テクノロジーは、画面イメージをキャプチャし、モデルの視覚機能を使用してボタン、メニュー、テキスト フィールドなどの GUI 要素を認識し、人間の画面の視覚的理解をシミュレートすることによって機能します。

次に、仮想カーソルやキーボード入力を通じてインターフェイスと対話し、クリック、テキスト入力、スクロールなどのアクションを実行して、AI とアプリケーションやインターネットとの対話を可能にします。

このテクノロジーにはいくつかの利点があります。

1. **即時インターネット対話機能**

最も重要な利点は、AI が即座にインターネットと対話し、さまざまなタスクを完了できることです。

現在のインターネットは人間がアクセスできるように設計されているため、AI に人間の行動をシミュレートさせることが AI をインターネットに統合する最も早い方法です。

AI がインターネットにアクセスできるようになると、AI ツールの現在の制限に対処し、人々が多くの貴重なタスクを完了できるようになり、商用実装が加速されます。

2. **データサイロの打破**

CUA テクノロジーは基本的に人間とインターネットの間にパーソナル アシスタントを追加し、すべてのユーザー情報にアクセスすることで既存のデータ サイロを打破し、よりインテリジェントな意思決定を可能にします。

3. **アプリケーション修正コストが低い**

AI がアクセスできるようにするためにアプリケーションを変更する必要はほとんどありません。

ただし、このテクノロジーにはいくつかの顕著な欠点もあります。

1. **高い運用コスト**

CUA テクノロジーは視覚機能に依存しており、画像処理により運用コストが比較的高くなります。これは価値の高いシナリオでは機能するかもしれませんが、一般消費者向けアプリケーションに実装すると大きな課題が生じます。

2. **非同期実行の欠如**

CUA テクノロジーでは、画面キャプチャ中にコンピューター制御を AI に引き渡す必要があるため、この間人間による使用は禁止されています。

理想的なエクスペリエンスは、AI アシスタントがバックグラウンドでタスクを処理し、介入が必要な場合にのみ人間に通知する非同期タスク実行です。

3. **頻繁な手動ログイン要件**

コンシューマー向けシナリオでは、CUA では依然としてユーザーがアプリケーションにアクセスするときに手動でログインする必要があり、認証を自動化できません。

4. **短期的な精度の課題**

CUA は単純な Web タスク (87%) では優れたパフォーマンスを発揮しますが、複雑なローカル操作 (38.1%) や動的な Web インタラクション (58.1%) では重大な制限が見られます。

アプリケーション シナリオに関しては、**CUA が B2B シナリオ、特にパーソナライゼーション要件** を伴う高価値のケースで最初に成功する可能性が最も高いと考えています。純粋に反復的な操作の場合は、RPA の方が適している可能性があります。

消費者向けのシナリオでは、プロのユーザー (ビデオ編集者など) が適切な実装例になる可能性があります。

一般消費者のシナリオでは、運用コスト、ユーザー エクスペリエンスの制限、他の技術的アプローチとの競合により、CUA はあまり競争力がない可能性があります。

## ヘッドレスブラウザ

ヘッドレス ブラウザは、コマンド ラインまたはプログラミング インターフェイスを通じてバックグラウンドで実行される、グラフィカル ユーザー インターフェイス (GUI) のないブラウザです。従来のブラウザと同じ操作 (Web ページの読み込み、JavaScript の実行、ページのレンダリングなど) を実行できますが、ビジュアル インターフェイスはありません。

ヘッドレス ブラウザは AI のインターネット接続にどのように役立つのでしょうか?
- Puppeteer などのヘッドレス ブラウザ フレームワークを使用して、完全な Web アプリケーション ページ データ (コンテンツのみ、レンダリングなし) を取得する
- AI を使用してページ データを処理し、特定の操作に必要なページ要素を特定する
-  AI または手動で記述されたコードを使用して、ヘッドレス ブラウザ フレームワーク API を通じてページ要素を操作する
- インターネット アクセスのために AI がこれらのコード ツールを利用できるようにする

**ヘッドレスブラウザアプローチの利点**:

1. **非同期タスク処理**

ヘッドレス ブラウザはコンピューターの制御を必要とせずにバックグラウンドで実行されるため、必要な場合にのみ人間の介入が必要となり、タスクを非同期で実行できます。

2. **Webアプリケーションフレンドリー、変更不要**

AI と Web アプリケーションの迅速な統合を可能にします。

3. **CUAと比較して運用コストが低い**

テキストを処理し、コードを事前に記述することにより、ヘッドレス ブラウザーのアプローチは、ビジョン依存の CUA テクノロジーよりも運用コストが低くなります。

**ヘッドレスブラウザアプローチの欠点**:

1. **Webアプリケーション限定**

ローカル コンピューター アプリケーションなど、Web 上で実行されないアプリケーションとは統合できません。 CUA にはこの制限はありません。

2. **ページ適応コストが高い**

ページを適応させるために実質的なコードを生成する必要があり、ページのアップグレードや変更により既存のコードが無効になる可能性があるため、再生成、テスト、展開が必要となり、結果としてメンテナンスコストが高くなります。

3. **頻繁な手動ログイン要件**

CUA と同様に、ユーザーは依然として手動でログインする必要があり、認証を自動化できません。

ヘッドレス ブラウザを使用する別のアプローチは、完全なページ データを LLM にフィードして処理することですが、この方法は非効率的でコストがかかります。このシナリオに特化した垂直モデルをトレーニングする方が、より良い解決策となる可能性があります。

ミニプログラム プラットフォームは、ヘッドレス ブラウザーの優れた実装シナリオとなる可能性があります。ミニプログラムは本質的には Web アプリケーションです。このプラットフォームがアカウントの相互接続の問題を解決できれば、ユーザー アカウントを直接使用して、人間の介入なしにヘッドレス ブラウザーを通じてミニプログラムと対話する AI アシスタントを構築できる可能性があります。

## クライアント側 API

クライアント側 API テクノロジーにより、AI はオペレーティング システムによって公開される標準化されたデバイス機能インターフェイスを通じてインターネットと対話できるようになり、センサー、アプリケーション データ、ハードウェア機能に直接アクセスできるようになります。その中心原則は、人間の操作をシミュレートすることなく AI がアプリケーションと正確に対話できるようにするシステムレベルのインテント対話プロトコルを確立することです。

**技術実装原則**

1. インテント登録メカニズム

アプリケーションは、「スキル インテント」 (「メッセージの送信」、「スケジュールの作成」など) をオペレーティング システムに宣言し、パラメーターの形式と権限のスコープを定義して、グローバル機能ディレクトリを形成します。 iOS 18 の App Intents フレームワークは、すでに 200 以上のコア関数インターフェイスの登録をサポートしています。

2. セマンティック マッピング エンジン

システムに組み込まれている自然言語理解 (NLU) モジュールは、ユーザーの指示 (「撮った写真をワーク グループに送信する」) を構造化された API 呼び出しチェーンに変換し、写真 API、連絡先 API、インスタント メッセージング API を自動的にリンクします。

3. セキュリティサンドボックスメカニズム

アプリケーション間のデータ転送は、信頼された実行環境 (TEE) を通じて実装されます。 1 回限りのユーザー認証を取得した後、AI は複数の API 呼び出し (位置情報サービスとメモへの同時アクセスなど) を組み合わせることができますが、生データがデバイスから流出することはありません。

**利点**

1. インターフェース変更コストゼロ

アプリケーションは、既存の UI を変更せずに、標準インターフェイスを登録して実装するだけで済みます。ほとんどの変更は内部機能の変更です。

2. 真の非同期タスク処理

AI はバックグラウンドで複数の API 呼び出し (航空券、ホテル、レンタカーの予約など) を組み合わせることができ、ユーザーはいつでも中断できます。

3. コンピュータを使用するエージェントよりも運用コストが低い

AI ビジュアル機能が必要ないため、コンピューター使用エージェントのアプローチと比較して運用コストが低くなります。

**欠点**

1. 深刻な生態系の断片化

インターフェイスの標準はプラットフォームやメーカーによって異なります (Android、iOS アプリ インテント、HarmonyOS Atomic Services)。

2. アプリケーションのオープン性の問題

アプリケーションは携帯電話メーカーと競合関係にあるため、アプリケーションがコア データをモバイル プラットフォームに公開することが困難になります。

3. シナリオの制限

現在、携帯電話上で使用されるアプリケーションが増えており、モバイル プラットフォームにアクセスできないチャットボットはこのアプローチを使用できません。

## リモート API/プロトコル

このアプローチにより、AI は API またはプロトコルを通じてインターネットと直接対話できるようになります。たとえば、システムが外部 API を提供している場合、AI は関数呼び出しやツール機能を使用して、情報を取得したり対話型操作を実行したりできます。

既存のシステム API は AI 向けに特別に設計されていないため、使用するには手動でのコードの作成と、認証とアクセス制御のためのキーの事前構成が必要になる場合があります。

現在、Anthropic の MCP や ANP など、AI またはエージェント向けに特別に設計されたプロトコルがいくつかあります。彼らの共通の目標は、AI が最も効率的な方法でインターネットにアクセスできるようにすることです。

MCP (モデル コンテキスト プロトコル) は、大規模言語モデル (LLM) と外部データ ソースおよびツール間の通信を標準化し、AI システムがコンテキスト情報に効率的にアクセスして利用できるようにして、応答の品質と実用性を向上させることを目的としています。

ANP(エージェントネットワークプロトコル)、 https://github.com/agent-network-protocol/AgentNetworkProtocol, 業界初のオープンソース通信プロトコルです。 MCPとは異なり、ANPはエージェント中心で、すべてのエージェントを等しく扱い、効率的なエージェントコラボレーションネットワークの構築を目指しています。

**このアプローチの利点**:

1. **データ・コントリクトの相互作用**

人間のインターネット利用をシミュレートするCUA技術やヘッドレスブラウザとは異なり、AIは最も効率的な方法であるデータを直接処理することができます。

2. **非同期タスク実行**

コンピュータ制御を占有することなく、APIやプロトコルを通してバックグラウンドでタスクを処理することができます。

3. **低い運用コスト**

CUAとヘッドレスブラウザと比較して、API/Protocolは運用コストを削減し、画面キャプチャ処理やページデータコードメンテナンスも不要です。

4. **自動認証**

DIDなどの分散認証技術を使用して、クロスプラットフォーム、自動認証、重要な操作(支払いなど)のみのユーザー介入を必要とする。 現在、MCP がまだサポートしていない状態で DID をサポートしている ANP はサポートしています。

**このアプローチの欠点**:

1. **高い修正コスト**

既存のシステムが関連するプロトコルをサポートするために変更される必要があります。このアプローチの最大の欠点です。 しかし、AIプログラミング技術が進むにつれて変更コストは削減されるべきです。

2. **初期段階ドメイン、未クリア規格**

エージェント通信プロトコルドメインは、既存のソリューションや標準の確立がほとんどなく、初期段階に引き続き存在しています。 人類のMCPとANPからの主な研究が始まります。

しかし、W3CやIIFAAなどの国際標準化機関も関連研究に投資しています。

## コンテンツ

これら4つの技術アプローチを目視してみる:

短期的には、様々な制限にもかかわらず、コンピュータ使用エージェント(CUA)とヘッドレスブラウザ技術は、適切なシナリオでビジネス価値を迅速に提供することができます。

長期的には、API/Protocol のアプローチをしっかりと信じています。最高のユーザーエクスペリエンスと運用コストが最も低いためです。 システム変更コストが高まっていますが、AIプログラミング機能が向上するにつれて、削減を期待しています。 プロトコル標準化に関しては、標準プロトコルが出現すると考え、プロトコル標準化に大きな貢献をすることを目指しています。
