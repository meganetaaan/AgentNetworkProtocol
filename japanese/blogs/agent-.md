# エージェントのアイデンティティ、認可、および暗号化

エージェントの ID、承認、および暗号化された通信は、エージェントのセキュリティの中核であり、エージェント間の効率的かつ安全なコラボレーションの基盤です。

今日は、これら 3 つの問題についての私の理解を包括的に述べたいと思います。

## エージェント ID

### エージェントIDの説明

最初の質問は、エージェントのアイデンティティについて議論するとき、実際に誰のアイデンティティについて話しているのかということです。エージェントはアイデンティティを持っていますか?

一般的な対話シナリオでは、ソフトウェアとしてのエージェント自体はアイデンティティを持たないと私は考えています。彼らは単に人間のアイデンティティを使用し、人間がタスクを完了するのを助けるために人間によって許可されているだけです。

したがって、エージェントのアイデンティティの問題について議論するとき、私たちは本質的に、エージェントが他のエージェントと対話する際に人間を安全かつ効率的に代理して、人間がタスクを完了できるようにする方法について話していることになります。

###  従来の ID ソリューションと比較して、エージェント ID にとって最も緊急なものは何か

当社には、OIDC、DID、SAML など、すでに多くの ID ソリューションがあります。エージェントにとって最も適したソリューションはどれですか?

これには、エージェントの ID 認証において、最も重要かつ緊急の要件は何ですか?という質問に答える必要があります。

それはアイデンティティの相互運用性だと私は考えています。

ID の相互運用性とは、あるプラットフォームの ID が別のプラットフォームによって認識および信頼され、クロスプラットフォームでの相互認証と使用が可能になる機能を指します。これは電子メールと非常に似ています。電子メール アカウントを持っている場合は、ネットワーク全体のすべての電子メール ユーザーと通信できます。

相互運用性がエージェントにとって非常に重要なのはなぜですか?

なぜなら、現在のインターネットは孤立した島で構成されており、各プラットフォームには独自の ID システム、ユーザー、データがあると考えているからです。これにより、エージェントが完全なコンテキストを取得することが大幅に妨げられ、エージェントが人々のタスクの実行を支援することができなくなり、賢く、私たちを理解し、多くのことを達成するのに役立つインテリジェントなエージェントを持つことが不可能になります。

したがって、すべてのエージェントが相互接続されているオープン インターネットのみが AI の機能を最大限に発揮し、強力なエージェント ネットワークを構築できると私たちは考えています。

相互接続、特にクロスプラットフォーム エージェントの相互接続に向けた最初のステップは、相互のクロスプラットフォーム ID 認証を有効にすることです。

### エージェントに最適な ID ソリューション

既知のすべてのソリューションの中で、DID は最高の相互運用性を備えています。したがって、私は常に DID がエージェントにとって最適な本人認証ソリューションであると信じてきました。もちろん、DID には適用範囲が限られている、標準的な認可スキームが存在しないなどの問題がないわけではありません。

幸いなことに、ほとんどのエージェントは新しく構築されたソフトウェアであるため、新しいソリューションを完全に採用できます。 W3C ZCAP-LD プロジェクトは推奨標準にはなりませんでしたが、DID を使用したきめ細かい認証のソリューションを提供するものであり、注目に値します。

ただし、他のソリューションでも ID 検証の相互運用性を向上させる方法が検討されており、将来的にはさらに多くのオプションが登場する可能性があります。

## エージェントの承認

エージェントの承認はエージェントの ID に関連していますが、エージェントの ID とは異なります。承認は ID 認証に依存することが多いため、これらは関連していますが、解決する問題が異なるため異なります。1 つは「ユーザーが誰であるか」に対応し、もう 1 つは「ユーザーに何ができるか」に対応するためです。

まず、将来考えられるいくつかの認可モデルを見てみましょう。
- エージェントが既存のインターネット アプリケーションからデータを読み取る
- 異なるエージェントが異なるユーザー データを所有し、ユーザーがエージェント間のデータ アクセスを承認
- 統合されたユーザー データ ストレージにより、異なるエージェントが異なるデータにアクセスできるようになります
- 他のユーザー/企業のエージェントとのやり取りにおいて代理人をエージェントに許可するユーザー

### エージェントが既存のインターネット アプリケーションからデータを読み取る

既存のインターネットアプリケーションからデータを読み込みるエージェントは、エージェントが完全なコンテキストを取得するための重要な方法です。 例えば、エージェントを通して、Google検索結果やGitHubコードにアクセスします。 この場合、GoogleやGitHubからエージェントが承認する必要があります。 このプロセスは、一般に、インターネット上で最も広く使用されている技術である OAuth を使用します。

![既存のインターネットアプリケーションからデータを読み取りするエージェント](../../blogs/images/agent-authorization/agent-connect-existing-app.png)

### 相互にエージェントのデータアクセス許可

将来的には、各エージェントに独立したIDを持つユーザーと、異なるユーザデータを保持する各エージェントが複数のエージェントを所有することができます。 1つのエージェントがより完全なユーザーコンテキストを取得できるようにするには、ユーザーはこのエージェントを他のエージェントからユーザーデータにアクセスすることができます。

![相互にエージェントのデータアクセス許可](../../blogs/images/agent-authorization/multi-agent-auth.png)

数値に示すように、クロスエージェントのデータアクセスには2つの手順が含まれます。
- ユーザーはエージェントCを認可して、エージェントBの部分的なデータ権限にアクセスします。 例えば、C の ID をエージェントで認証することで実現できます。
- Agent C は、ユーザの認可を使用して、B のエージェントでユーザーデータにアクセスします。 Agent B は、認可を検証し、データを返します。

### ユニファイドデータストレージ認証

これからは、人間のデータを一元に安全に保存し、データに対する絶対的な社会性を持つ人間がいる。 エージェントはデータ権限を保有していませんが、ユーザデータのアクセス(読み込みまたは書き込み)部分にアクセスするユーザーによって許可されます。 ユーザーは、エージェントがデータをいつでもデータにアクセスできるようにすることで、ユーザーが自由に使用するエージェントを選択することができます。

![ユニファイドデータストレージ認証](../../blogs/images/agent-authorization/one-data-center.png)

このモデルでは、A,B,C のエージェントに独立したIDが格納されていますが、データセンター内ではユーザーデータを均一に保存します。 ユーザーは、エージェント A、B、C を認証して、データセンター内のデータの一部にアクセスすることができます。

このモデルはさらに進むことができます。ユーザーは、絶対的な制御の下で1つ以上のアカウントを持つこともできます。そして、エージェントは、これらのアカウントを使用してデータセンター内のユーザーデータにアクセスできるようにします。

### 相互にエージェントのインタラクション認証

このモデルは、他のユーザー/エンタープライズのエージェントとの相互作用でそれらを表すためにエージェントを承認するユーザについて説明します。

![相互にエージェントのインタラクション認証](../../blogs/images/agent-authorization/agent-interact.png)

例えば、アリスは彼女のエージェントがホテルを予約するのを助けることを望んでいます。 アリスのエージェントは、Alice ID をホテルのエージェントにアクセスし、Alice ID を使用してホテルの予約を行う必要があります。

これらは、二つの種類の承認を含みます。
- 一般の許可:アリスは、客室や価格など、ホテルの代理店から一般情報にアクセスするために彼女のアイデンティティIDを使用するためにエージェントを承認します。 それぞれのアリスからマニュアルの承認を要求しない情報の種類へのアクセス。一度の許可が不足している。 それ以外の場合、インタラクションプロセスは面倒なものになります。
- 特別許可:アリスは、予約ホテルや注文のために支払いなど、重要な操作を実行する彼女のアイデンティティIDを使用する代理店を承認します。 承認のこのタイプは非常に重要で、毎回アリスからマニュアルの認可が必要です。 それ以外の場合、セキュリティリスクがあります。

### エージェントの認可ソリューション

既存のシステムとの相互運用性が必要な場合は、既存のシステムがOAuthのみをサポートするOAuthなどの既存のシステムでサポートされている認可スキームを使用します。

しかし、新築のエージェントでは、エージェントに適した認可スキームを調べる必要があります。

上記エージェントのアイデンティティセクションでは、DIDがエージェントにとって最も適したアイデンティティソリューションだと述べましたが、DIDベースの認可スキームはまだ開発されていないと述べました。 W3C DIDを補完するW3C VC(検証可能な認証)は、特に「ユーザが組織の従業員であるか」や「ユーザーが法的年齢である」などの属性、許可、または資格を表現するために使用できる認可シナリオに使用できます。

VC ソリューションは、「特定のリソースへの 30 分間の読み取りアクセス」などの権限を表現する場合にやや複雑になり、発行、検証、取り消しのコストが比較的高くなる可能性があります。 W3C ZCAP-LD は、この問題を解決するための興味深いテクノロジーですが、現在はまだコミュニティ ドラフトの段階にあります。

IETF GNAP (Grant Negotiation and Authorization Protocol) は、IETF GNAP ワーキング グループによって提案されており、OAuth 2.0 の後継となることを目指しており、柔軟性、セキュリティ、拡張性における OAuth 2.0 の欠点に対処し、認可プロトコルが AI エージェント、IoT、分散型 ID などの新たなシナリオに適応できるようにします。

GNAP は DID もサポートしており、従う価値のあるソリューションです。

## エンドツーエンドの暗号化

2 つのエージェントがメッセージを介して通信し、メッセージ中継にサードパーティのサービスを使用する場合、メッセージが傍受されたり、サードパーティによって復号化される可能性があるため、通信は安全ではない可能性があります。

このような場合には、エンドツーエンドの暗号化テクノロジーが必要となり、サードパーティのサービスがコンテンツを復号化できない状態でメッセージを簡単に中継できるようになります。

これら 2 つのエージェントが直接通信する場合 (たとえば、プラットフォームがパブリック ネットワーク エンドポイントを申請している異なるプラットフォームに属する 2 つのエージェント) は、直接接続して従来の HTTPS または WSS を使用して、エンドツーエンドの暗号化を必要とせずにメッセージのセキュリティを確保できます。
