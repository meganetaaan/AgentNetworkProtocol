# エージェントのアイデンティティ、認可、および暗号化

エージェントの ID、認可、および暗号化された通信は、エージェントのセキュリティの中核であり、2 つのエージェント間の効率的かつ安全なコラボレーションの基礎です。

今日は、これら 3 つの問題についての私の理解を完全に説明したいと思います。

## エージェント ID

### エージェントIDの説明

最初の疑問は、エージェントのアイデンティティについて議論するとき、誰のアイデンティティについて話しているのかということです。エージェントはアイデンティティを持っていますか?

一般的な対話シナリオでは、ソフトウェアの一部としてのエージェント自体にアイデンティティはないと思います。一部のタスクを完了するために自分の ID を使用することは、他の人にのみ許可されています。

したがって、私たちが議論しているエージェントのアイデンティティの問題は、基本的に、エージェントが人々に代わって他のエージェントと安全かつ効率的に対話し、人々がタスクを完了できるように支援する方法を可能にするかということです。

### エージェント ID の 2 つのモード

アイデンティティは個人によって所有されます。
アイデンティティはプラットフォームに属します。

###  従来の ID ソリューションと比較して、インテリジェント エージェント ID に関して最も緊急なことは何ですか?

現在、OIDC、DID、SAML など、多くの ID ソリューションがあります。どのソリューションがエージェントにとってより適していますか?

これは、インテリジェント エージェントの ID 認証にとって最も重要かつ緊急なものは何か?という質問に答える必要があります。

それはアイデンティティの相互運用性だと思います。

ID の相互運用性とは、あるプラットフォームの ID が別のプラットフォームによって認識および信頼され、それによって相互認証とプラットフォーム間での使用が実現されることを意味します。これは電子メールと非常に似ています。電子メール アカウントを持っている場合は、ネットワーク全体上のすべての電子メール ユーザーと通信できます。

エージェントにとって相互運用性が重要なのはなぜですか?

なぜなら、既存のインターネットは島であり、各プラットフォームには独自の ID システム、独自のユーザー、独自のデータがあると考えているからです。これにより、エージェントが完全なコンテキストを取得することが大幅に妨げられ、また、エージェントが人々のタスクの実行を支援することもできなくなり、賢く、ユーザーを理解し、ユーザーが同時に多くのことを実行できるように支援するインテリジェントなエージェントを入手することが不可能になります。

したがって、すべてのエージェントが相互接続され、オープンになっているインターネットだけが AI の力を最大限に発揮し、強力なエージェント ネットワークを構築できると私たちは考えています。

相互接続の最初のステップ、特に異なるプラットフォーム上のエージェント間の相互接続の最初のステップは、相互にクロスプラットフォーム ID 認証を実行できることです。

### インテリジェントエージェントに最適なアイデンティティソリューション

現在私たちが知っているすべてのソリューションの中で、DID は最高の相互運用性を備えています。したがって、私は常に DID がインテリジェントな ID 認証に最適なソリューションであると信じてきました。もちろん、DID には適用範囲の不足、標準的な認可スキームの欠如などの問題がないわけではありません。

幸いなことに、ほとんどのエージェントは新しく構築されたソフトウェアなので、新しいソリューションを採用できます。 W3C の ZCAP-LD プロジェクトは推奨標準にはなっていませんが、DID を使用したきめ細かい認証のソリューションを提供するものであり、注目に値します。

ただし、他のソリューションでも認証の相互運用性を向上させる方法が検討されており、将来的にはさらに多くのオプションが登場する可能性があります。

## エージェントの承認

エージェントの認証とエージェントの ID は関連していますが、別の問題です。承認は ID 認証に依存することが多いため、これらは関連していますが、解決する問題が異なるため異なります。 1つはあなたが誰であるか、もう1つはあなたが何ができるかです。

まず、将来的にどのようなライセンス モデルが利用可能になるかを見てみましょう。
- エージェントは元のインターネット アプリケーションのデータを読み取ります
-  エージェントごとにユーザーのデータが異なり、ユーザーはエージェント間でのデータ アクセスを承認できます。
- ユーザーデータは均一に保存され、異なるエージェントには異なるデータへのアクセスが許可されます。
-  ユーザーは、エージェントが自分に代わって他のユーザー/企業のエージェントと対話することを許可します。

### エージェントは元のインターネット アプリケーションのデータを読み取ります

インテリジェント エージェントは元のインターネット アプリケーションのデータを読み取ります。これは、エージェントが完全なコンテキストを取得するための重要な方法です。たとえば、私はエージェントを通じて Google の問題や github コードにアクセスします。現時点では、エージェントは Google または github によって承認される必要があります。このプロセスでは通常、現在インターネットで最も広く使用されているテクノロジーである OAuth が使用されます。

![オリジナルインターネットアプリケーションからデータを読み込むスマートボディ](../../../blogs/images/agent-authorization/agent-connect-existing-app.png)

### 相互にインテリジェントな承認データアクセス

将来のエンティティティ(個人または組織)は、異なるデータを維持するために、各ユーザーごとに独立したIDを持つ複数のインテリジェンスボディが持つ可能性があります。 スマートボディを取得して、ユーザーの詳細なコンテキストを把握するには、ユーザーはこのスマートボディを承認して、他のインテリジェントな身体上のデータをアクセスすることができます。

![相互にインテリジェントな承認データアクセス](../../../blogs/images/agent-authorization/multi-agent-auth.png)

数値に示すように、インテリジェンスボディを横断するデータアクセスは2つのステップに分かれています。
- スマートBのユーザーは、スマートCのデータの権利の一部にアクセスします。例えば、これはユーザーの認証をスマートCで使用することで行うことができます。
- スマートCは、ユーザーの ' s 権限を使用して、スマート B およびスマート B でユーザーデータにアクセスし、データを検証して返します。

### データ保存許可の調和

これは私の好きなモデルです: 将来の人のデータは、1つの場所に保存し、安全に保存することができます。そして、人々はそれに対して絶対的な社会を持っています。スマートボディはデータにアクセスできませんが、ユーザーがアクセスを許可するデータの一部です(読み取りまたは書き込み)。ユーザーは、彼らが望むものを選ぶことができるように、いつでもデータをいつでも削除できます。

![データ保存許可の調和](../../../blogs/images/agent-authorization/one-data-center.png)

このモードでは、ユーザーはスマートA、B、CでスタンドアローンIDを持っていますが、ユーザデータは単一のデータセンターに保存されます。 ユーザーは、データセンター内のデータの一部にアクセスするために、スマートA、B、Cを承認することができます。

このモデルは、ユーザーが自分の絶対的な制御の下で複数のアカウントを持っていると、データセンター内のユーザーのデータへのアクセスをスマートに与えることで、さらに進むことができます。

### インターステラ認証

このモデルは、ユーザー権限の知的ボディを記述し、他のユーザー/エンタープライズと相互作用します。

![相互知性のための相互認可](../../../blogs/images/agent-authorization/agent-interact.png)

アリスは、ホテルを予約するためにアリスのスマートボディを望んでいたし、アリスのスマートボディがAliceのIDを使ってホテルのスマートボディをAliceとAliceのIDに代わってホテルの予約をするために使用する必要がありました。

関連する認可には 2 つの異なるタイプがあります。
- 一般的なタイプの承認。つまり、アリスは、エージェントが自分の ID を使用して、ホテル エージェントの一般情報 (客室、料金など) に代理でアクセスすることを承認します。このタイプの情報にアクセスするには、アリスが毎回手動で承認する必要はありません。認可だけで十分です。そうしないと、対話プロセスが煩雑になりすぎます。
- 最初のタイプは特別な承認です。つまり、Alice はエージェントが自分の ID を使用して、ホテルの予約や注文の支払いなどの重要な操作を代理で実行することを承認します。このタイプの認証は非常に重要であり、アリスは毎回手動で認証する必要があります。そうしないと、セキュリティ上のリスクが発生します。

### エージェント認証ソリューション

元のシステムと相互運用したい場合は、元のシステムでサポートされている認証スキームを使用してください。たとえば、元のシステムが OAuth のみをサポートしている場合は、OAuth を使用します。

ただし、新しく構築されたエージェントの場合は、エージェントにとってより適切な認可スキームを検討する必要があります。

エージェントの ID を紹介したときに前述したように、DID がエージェントに最適な ID ソリューションであると考えていますが、DID に基づく認可ソリューションはまだ完全ではありません。まず、W3C DID をサポートする W3C VC (検証可能な資格情報) は、一部の認証シナリオ、特に「ユーザーは特定の組織の従業員である」、「ユーザーは成人に達している」などの属性、権限、または資格を表現するために使用できます。

VC のソリューションは、「30 分以内に特定のリソースを読み取る許可」を表現する場合に少し複雑で、発行、検証、取り消しのコストが比較的高くなる可能性があります。 W3C ZCAP-LD は、この問題を解決する興味深いテクノロジですが、まだコミュニティ ドラフトの段階にあります。

IETF の GNAP (Grant Negotiation and Authorization Protocol) は、IETF GNAP ワーキング グループによって提案されました。これは、OAuth 2.0 の後継となり、OAuth 2.0 の柔軟性、セキュリティ、スケーラビリティの欠陥を解決し、認可プロトコルが AI エージェント、IoT、分散型 ID などの新たなシナリオに適応できるようにすることを目指しています。

GNAP は DID もサポートしており、注目できるソリューションです。

## エンドツーエンド暗号化

2 つのエージェントが相互に通信し、メッセージ転送にサードパーティのサービスを使用する場合、その通信は安全でない可能性が高く、メッセージがサードパーティによって傍受されたり、復号化されたりする可能性があります。

現時点では、サードパーティのサービスがメッセージを簡単に転送できても、その内容を復号化できないようにするために、エンドツーエンドの暗号化テクノロジが必要です。

たとえば、2 つのエージェントが直接通信する場合、たとえば、2 つのエージェントが 2 つの異なるプラットフォームに属し、プラットフォームがそれらのエージェントのパブリック ネットワーク エンドポイントを申請すると、この時点で、従来の HTTPS または WSS を使用して直接接続でき、エンドツーエンドの暗号化を必要とせずにメッセージのセキュリティを確保できます。
