## 1. コアコンセプト

この仕様では、エージェント記述の 2 つの中心的な概念、つまり情報とインターフェイスを定義します。これら 2 つの概念は、エージェントが外部の世界に情報を開示するための標準化されたフレームワークを提供し、エージェントが効果的に相互に発見、理解、対話できるようにします。

### 1.1 情報

情報は、エージェントによって外部エンティティに提供されるデータ リソースを表します。これらのリソースは、エージェントの機能、ステータス、製品、またはサービスを記述する構造化データまたは非構造化データです。

情報リソースには次の種類が含まれますが、これらに限定されません。
- 構造化データ: JSONドキュメント、XMLファイル、データベースクエリ結果
- メディアリソース: 画像、ビデオ、オーディオファイルおよびそれらに関連するメタデータ
- 説明文書: 製品仕様、サービス説明、使用ガイド
- ステータス情報: エージェントの現在のステータス、可用性情報、設定パラメータ

情報には次のような重要な特徴があります。
- **記述可能性 **: 各情報リソースには、他のエージェントがリソースのタイプ、目的、アクセス方法を理解できるようにするために十分なメタデータが含まれている必要があります
- ** 検出可能性 **: 情報リソースは、統合された記述メカニズムを通じて外部エンティティに公開され、自動検出およびインデックス作成プロセスをサポートします。

### 1.2 インターフェース

インターフェイスは、エージェントが外部エンティティと動的に対話するための標準化されたエントリ ポイントを定義します。インターフェイスは、エージェントの機能の呼び出し可能な表現を提供し、他のエージェントまたはシステムがプログラム的にインターフェイスと対話できるようにします。

インターフェイスは、次の 2 つの主なカテゴリに分類されます。

#### 1.2.1 自然言語インターフェース

自然言語インターフェイスは、インテリジェント エージェントに人間の言語に基づく対話機能を提供します。このタイプのインターフェイスでは、自然言語クエリとコマンドを使用してエージェントの機能にアクセスできます。

自然言語インターフェースの特徴は次のとおりです。
- **言語の柔軟性**: 複数の自然言語表現をサポートし、意味の変化とコンテキスト情報を理解できます。
- **パーソナライズされたインタラクション **: インタラクション履歴とユーザーの好みに基づいてカスタマイズされた応答を提供する機能
- **オープンタスク処理**: 創造的思考や複雑な推論を必要とするタスクシナリオに適しています
- **汎用性**: 基本的な相互運用性を確保するために、仕様に準拠したすべてのエージェントが少なくとも 1 つの自然言語インターフェイスを実装することをお勧めします

#### 1.2.2 構造化インターフェース

構造化インターフェイスは、事前定義されたプロトコルとデータ形式に基づいたプログラムによる対話を提供します。このタイプのインターフェイスは、標準化された API 設計原則に従って、予測可能性と効率性を確保します。

構造化インターフェースの特徴は次のとおりです。
- **プロトコル標準化**: OpenAPI、JSON-RPC、GraphQL、WebRTC など、広く採用されているプロトコル標準をサポートします。
- **タイプセーフティ**: 明確なデータ型定義と検証メカニズムを通じて対話の正確さを保証します
- **パフォーマンスの最適化**: 構造化インターフェースは通常、自然言語インターフェースよりも遅延が短く、スループットが高くなります。
- **機能の特化**: 各構造化インターフェイスは特定の機能ドメインに合わせて最適化できます

### 1.3 インターフェースの選択と優先順位

プロトコルを実装するエージェントは、対話インターフェイスを選択する際に、次の優先順位と選択戦略に従う必要があります。

1. **構造化インターフェイスの優先原則 **: 機能要件を満たす構造化インターフェイスがある場合、最高のパフォーマンスと信頼性を得るために、このインターフェイスを優先して対話する必要があります。
2. **機能完全性評価**: インターフェイスを選択する前に、ターゲット インターフェイスが現在のタスクの機能要件を完全に満たすことができるかどうかを評価する必要があります。
3. ** フォールバックメカニズム **: 構造化インターフェースが複雑または非標準化の要件を満たすことができない場合、自然言語インターフェースにフォールバックできます。
4. **コンテキストを意識した選択**: インターフェイスの選択では、タスクの複雑さ、リアルタイム要件、必要なパーソナライゼーションの程度を考慮する必要があります。

## 2. 対話モード

このプロトコルはリンクされたデータに基づく対話モデルを採用しており、これによりエージェントは情報とインターフェイスを URL (Uniform Resource Locator) を介してナビゲート可能なデータ ネットワークに編成できます。この方法は World Wide Web のハイパーリンク構造に似ており、エージェントは公開データをデータ ネットワークに構築でき、すべてのデータ ネットワークを AI がアクセスしやすいデータ ネットワークに接続できます。

### 2.1 ネットワーク化されたデータ構成

インタラクティブ モードの中心原則は、次のアーキテクチャ設計に基づいています。

#### 2.1.1 URLリンクネットワーク

エージェントは、情報リソースとインターフェイス リソースを整理するために、統一されたアドレス指定メカニズムとして URL を使用する必要があります。各 URL は特定のリソースまたはインターフェイス定義を指し、横断可能なリンク グラフを形成します。この設計により、次のことが保証されます。
- **グローバルな一意性 **: 各リソースには一意のネットワーク アドレスがあります
- **間接参照可能性 **: URL を直接使用して、対応するリソースにアクセスできます
- **リンクの整合性**: リソース間の関係は URL リンクを通じて明確に表現されます

#### 2.1.2 エントリーポイントメカニズム

各エージェントがメインのエントリ ポイントを提供することをお勧めします。これは通常、エージェント説明文書によって表されます。このドキュメントは Web サイトのホームページのように機能し、次の内容が含まれています。
- エージェントの基本メタデータと識別情報
- 利用可能なすべての情報リソースのリンクと説明
- 利用可能なすべてのインターフェースへのリンクと仕様参照
- 必要なアクセス制御およびセキュリティポリシー情報

### 2.2 インタラクションプロセス

エージェント間の対話プロセスは、Web クローラーの動作方法に似ており、エントリ ポイントから再帰的なナビゲーションが始まります。クライアント エージェントは、まずターゲット エージェントの説明ドキュメント URL を取得します。 HTTP リクエストを通じてドキュメントを取得した後、ドキュメントに含まれる情報リソース リンクとインターフェイス定義リンクを解析します。タスク要件に基づいて、クライアント エージェントは関連する URL リンクに選択的にアクセスします。取得したリソースにさらにリンクが含まれている場合、タスクを完了するために必要な十分な情報が収集されるまで再帰的取得が継続されます。

情報を取得する際、クライアント エージェントはこれらのデータをローカル環境に統合し、実行戦略を策定し、呼び出す適切なインターフェイスを選択します。プロセス全体はローカルな意思決定処理を重視しており、機密情報は第三者には渡されませんが、クライアント上でローカルに分析および処理されます。最後に、クライアント エージェントは、検出されたインターフェイスを通じて特定の操作を実行し、返された結果を処理してタスクを完了します。このモデルはプライバシーとセキュリティを確保するだけでなく、柔軟なオンデマンドの情報取得を可能にします。

### 2.3 インタラクティブモードのアーキテクチャ上の利点

#### 2.3.1 既存の Web インフラストラクチャとの互換性

既存の Web テクノロジー スタックとインフラストラクチャを最大限に活用します。
- **プロトコル再利用**: HTTP/HTTPS プロトコルに基づいており、既存のネットワーク機器およびミドルウェアと互換性があります
- ** キャッシュメカニズム **: 標準の Web キャッシュ戦略をサポートし、パフォーマンスとスケーラビリティを向上させます
- **検索エンジンに優しい **: 従来の検索エンジンで情報リソースにインデックスを付けることができ、エージェントの発見可能性が向上します。

#### 2.3.2 プライバシー保護とデータ主権

ローカル意思決定モデルには、プライバシーを保護するための重要な利点があります。
- **データのローカリゼーション **: 機密情報はローカルで処理され、データ漏洩のリスクが軽減されます。
- **選択的共有**: クライアント エージェントは、他のエージェントと共有する情報の範囲を正確に制御できます。
