# AIの孤島に別れを：開かれたエージェントネットワークで、AIを前提とするインターネットを作る
# AIはもう孤島ではない：一つのプロトコルで、世界のエージェントをつなぐ

次の場面を想像してください。

AIアシスタントに「来週の上海旅行を計画して」と伝えます。ブラウザー検索も、五つのアプリのダウンロードも要求せず、裏側で天気エージェントに週末の晴天を確認し、ホテルエージェントに外灘の川の見える部屋を押さえ、高速鉄道エージェントで切符を買います。

すべて、数秒で自動的に終わります。

SFではなく、**Open Agent Network（開かれたエージェントネットワーク）**が実現しつつある現在です。

AIが急速に広がり、賢い頭脳である大規模モデルに加え、ChatGPT、Gemini、豆包、夸克、deepseek、kimi、最近公開された千問と霊光など、巨大な入り口を目指す助手があります。

しかし、プラットフォームの壁によって、それぞれは互いにつながらない孤島にいます。

これを破るため、私たちは**世界初の開かれたエージェントネットワーク**を作りました。HTTPがページをつないだように、世界のエージェントを自由につなぎ、協働させ、本当に開かれたインターネットを作ります。

## 開かれたエージェントネットワークとは

公開プロトコルによる基盤で、異なる企業や個人のエージェントが、ドメインを越えて相互接続できます。

> **なぜ必要か**
>
> - **開発者には**：一度作れば、世界のすべての需要につながります（Write Once, Connect Everyone）。
> - **利用者には**：一つの助手で、すべてのサービスを使えます（One Agent, All Services）。

三つの中心的な特徴があります。

### 1. 多者間・ドメイン間の接続：孤島を破る

異なる会社や個人のエージェントには、従来、壁がありました。社内から社外へ、ある個人から別の個人へと、協働することは困難でした。

**公開プロトコルに対応すれば、企業でも個人でも、組織を越えてつながれます。**
- 個人助手が、ホテルに接続して部屋を予約します。
- 旅行エージェントが、天気のリアルタイム情報を得ます。
- 顧客対応エージェントが、物流に注文状況を問い合わせます。

異なる主体が、実際にドメインを越えて協働します。

### 2. 相互運用：すべてのエージェントを自由につなぐ

構想は、**知能の孤島を破り、誰もが自由に接続・協働できるようにすること**です。プラットフォームの制限や、中央の調整者は必要ありません。

- **需要と供給**：個人助手が、ホテル、飲食、教育などに直接接続し、問い合わせから取引まで進めます。
- **需要側同士**：予定管理と健康管理の助手が、適切な生活計画を共同で作れます。
- **供給側同士**：旅行、ホテル、交通、観光地がつながり、サービスの供給網を作れます。

全面的な接続が、単独を大きく上回る価値を生みます。

### 3. 開かれた参加：容易で、高い互換性

**プロトコルに対応し、インターネットにつながれば、参加できます。**

特定のフレームワークへの深い統合は不要です。
- 仕様のインターフェースを実装します。
- 標準のHTTP/HTTPSで通信します。
- 既存の基盤を使い、追加のブロックチェーンや複雑な技術構成は不要です。

**既存の成熟した基盤を十分に利用します。**
- **CDN**：世界からのアクセスを高速化します。
- **DNS**：発見と宛先の解決に使います。
- **検索エンジン**：索引と検索に使います。
- **PKI**：暗号化と本人確認を提供します。

導入の壁を下げ、拡大を速め、開発者がエージェント自身の能力に集中できます。

二つの接続方法があります。

**方法一：ANPによる直接接続**
SDKを使えば、完全な双方向通信と豊富な機能が使えます。新規開発や、最良の性能と全機能が必要な場合に適します。

**方法二：MCP-to-ANPブリッジ**
MCPに対応した既存のエージェントは、ブリッジで、コードを変えずにワンクリックで接続できます。移行費用を大きく下げます。

どちらも、**接続を簡単にし、プロトコルを障害ではなく橋にする**設計です。

## 階層構造

柔軟、安全、拡張可能な通信のため、需要側と供給側を結ぶ、明確な階層を採用します。

```
┌─────────────────────────────────────────────────────────────┐
│                        供给侧 (Supply Side)                   │
│  酒店智能体 | 餐饮智能体 | 教育/娱乐智能体 | ...              │
└─────────────────────────────────────────────────────────────┘
                            ↕
┌─────────────────────────────────────────────────────────────┐
│              连接层 (Connection Layer)                        │
│  Agent Protocol: 智能体发现、描述、交互                        │
└─────────────────────────────────────────────────────────────┘
                            ↕
┌─────────────────────────────────────────────────────────────┐
│                       需求侧 (Demand Side)                    │
│  个人助手 | 垂直智能体 | AI应用 | 个人助手 ...                 │
└─────────────────────────────────────────────────────────────┘
```

中心は**接続層（Connection Layer）**です。

### 接続層の三つの能力

**1. 発見**
ドメイン名と`.well-known`の経路や、専用の検索サービスを使い、需要に合う供給側を標準的な方法で見つけます。

**2. 記述**
各エージェントは、能力、インターフェース、呼び出し方法を示す標準のAgent Descriptionを提供します。人の調整なしに、相手の機能を理解できます。

**3. やり取り**
安全で効率的な通信に、複数の方法を提供します。
- **自然言語**：開放的で柔軟なやり取り向けです。
- **構造化インターフェース**：OpenAPIやJSON-RPCに対応し、効率と型の安全性を提供します。
- **本人確認**：W3C DIDによって、安全性と追跡可能性を確保します。

**特に重要なのが本人確認です。** 各エージェントがネットワーク全体で一意のIDを作り、それでほかのすべてと通信できます。電子メールのように、**既存の身元の孤島を破ります。**

- 各プラットフォームでのアカウント登録は不要です。
- 一つの身元を、複数のプラットフォームで使えます。
- 制御権は、プラットフォームではなく、エージェント自身にあります。

### 供給側と需要側

**供給側（Supply Side）**は、ホテル予約、天気、飲食推薦などの提供者です。標準インターフェースを、対応するすべての需要側に公開します。

**需要側（Demand Side）**は、個人助手、旅行計画などの分野別アプリ、社内エージェントなど、サービスの利用者です。接続層で発見して呼び出し、複雑な課題を解決します。

一つのエージェントが、両方を兼ねることもあります。旅行エージェントは、計画を外部に提供する供給者であり、ホテルや交通を利用する需要者でもあります。

### 階層構造の利点

- **責任が明確**：各層が中心的な機能に集中し、複雑さを下げます。
- **柔軟な拡張**：接続層の安定性を保ち、分野別のアプリ層を拡張できます。
- **既存標準との互換性**：OpenAPIやJSON-RPCによって、移行費用を下げます。
- **安全性**：統一した本人確認と権限管理で保護します。

## プロトコルを基盤にする

**フレームワークではなく、プロトコルを基盤にすること**が、既存のプラットフォームとの大きな違いです。

多くのプラットフォームは、「自分のSDKを、自分の場所と規則で使って」と言います。App Storeに似た、フレームワークの発想です。

私たちは、「PythonでもGoでも、AWSでも手元のパソコンでも、共通の言葉を話せば対話できる」と言います。Webのような、プロトコルの発想です。

**ANPの設計思想**：
- 🔓 **囲い込みを拒む**：エージェントは、あなたのものです。
- 🚀 **技術構成を問わない**：LangChain、AutoGPT、独自コードのどれでも使えます。
- 🤝 **生態系を育てる**：HTTPが商取引、交流、動画配信を生んだように、可能性を広げます。

プロトコルが定めるのは「通信の方法」であって、「実装の方法」ではありません。HTTPが通信形式を定め、言語やフレームワークを制限しないのと同様です。

ANPが定めるのは、次の事項です。
- 能力の記述
- 発見の方法
- 相互の本人確認
- メッセージの伝送と、インターフェースの呼び出し

Python、JavaScript、Java、Goなどの言語、どのフレームワークを使うか、あるいは使わないかを**制限しません**。仕様に従って通信できれば十分です。

- **開放性**：特定の会社に頼らず、誰でも実装できます。
- **相互運用性**：異なる技術で作ったエージェントが協働できます。
- **豊かな生態系**：共通基盤の上に、多様な実装と用途が育ちます。

HTTPと同様に、ANPも、開かれた豊かな生態系を生むでしょう。

## 何ができるか

### 需要と供給の接続

最も直接的な用途は、両者をつないだ、一貫したサービスです。

**例：旅行計画**

「来週末、杭州へ2日間遊びに行きたい」と助手に伝えます。

1. 天気エージェントで、週末の天気を調べます。
2. 旅行推薦エージェントで、観光地を探します。
3. ホテルエージェントで、宿を調べて予約します。
4. 交通エージェントで、往復の鉄道や航空券を予約します。
5. 情報をまとめ、旅行計画を完成させます。

人は自分の助手と話すだけで、裏側で専門サービスが呼ばれます。**意図を表すだけで、AIが調整する**ため、複雑な課題が簡単になります。

### 需要側同士の協働

**例：複数助手による共同計画**

- 予定管理助手：会議や予定を管理します。
- 健康管理助手：運動、睡眠、食事を追います。
- 財務管理助手：収支や投資を管理します。

相互に通信することで、次のように協働できます。
- 睡眠不足に気付いた健康助手が、予定助手に会議の調整と休息時間の確保を求めます。
- 予算超過に気付いた財務助手が、予定助手に外食を減らすよう知らせます。
- 出張を組む予定助手が、健康助手に体調を尋ね、過密日程を避けます。

個々の道具から、**エージェントのチーム**へ変わり、全体的で賢いサービスを提供します。

### 供給側同士の接続：供給網

**例：旅行のサービス網**

旅行エージェントが、次の相手をつなぎます。
- ホテル：宿泊予約
- 交通：鉄道と航空券
- 観光地：入場券と解説
- 飲食：店の推薦と予約
- ガイド：案内

各者が専門に集中し、一つのサービスの連鎖を作ります。**中央のプラットフォームが全体を支配するのではなく、プロトコルで自由に組み合わせます。**

柔軟性と耐障害性が高まり、新しい提供者は審査なしで参加でき、利用者も制約されずにサービスを選べます。

## 実例：ViNoteは3時間で道具からネットワークの一員へ

実際の接続例が、**ViNote**です。

動画を知識に変えるAIノートアプリで、ノート、質問応答、ワンクリック公開、リアルタイム字幕の保存、学習カード、マインドマップを提供します。「Video to Everything」の考え方です。

**開発チームは、ANP SDKでわずか3時間で接続しました。** これによって、ほかのエージェントから使えるようになりました。

- 個人助手が、学習動画をノートにできます。
- 教育エージェントが、授業動画を構造化した教材にできます。
- 制作エージェントが、動画分析で記事の素材を抽出できます。

**容易に接続し、すぐ価値を生める**例です。3時間で生態系に入り、ネットワーク効果を得られます。

利用者向けアプリが、供給側としてほかのエージェントにも提供する、**端末アプリとネットワークの一員という二重の役割**は、今後増えるでしょう。

## 今後の計画

### 最小構成のエージェントネットワーク

需要側、供給側、接続層を備えた、完結した原子単位のネットワークを作り、接続を助ける公開部品を整えます。実現可能性を検証し、大規模な拡張の土台にします。

### 決済

AP2による決済基盤を公開し、次を実現します。
- 安全で信頼できる取引
- 提供者の収益化
- 完全なエージェント商取引の生態系

接続から取引への重要な一歩です。

### 供給の生態系を育てる

- **市場とディレクトリ**：開発者や企業が公開し、利用者が発見できます。
- **ガバナンス**：信頼と品質を確保します。
- **評価と評判**：質の高いサービスを見分けられます。

良質な提供者を増やし、正のネットワーク効果を作ります。

### インスタントメッセージ

誰が作ったエージェントでも、標準の配送と意味の形式で、自然に即時通信し、情報を共有し、複数の往復で協働できるようにします。

- 友人の助手と、集まる時刻を調整します。
- 異なる会社の顧客対応が、会話を引き継ぎます。
- グループを組み、複雑な仕事を共同で進めます。

異なる分野やプラットフォームのAIが、リアルタイムで話せます。

### 追加のプロトコル

ANPを出発点に、対応を増やします。
- **MCP**：Anthropicの標準。ブリッジは提供済みです。
- **A2A**：Googleの標準。互換対応を提供する予定です。
- **ACP**：OpenAIとStripeによる商取引の標準です。
- **分野別の標準**：医療、金融、教育などです。

**複数プロトコルのゲートウェイ**で、次を行います。
- 相互の変換と適合
- 異なる標準を使うエージェントの通信
- 差異を隠した、統一的な接続体験

MCP専用でもANPと対話でき、A2AからACPの決済サービスを呼べるようにします。**プロトコルは、より大きなネットワークへの橋になります。**
