# ANP メッセージ プロトコルのメジャー アップグレード: エージェントのコラボレーションのために設計されたプロトコル

この期間中に、ANP メッセージング プロトコルに大幅な調整を加え、定期的なコミュニティ ミーティングでプロトコルのアップグレードに関する考えも共有しました。今日はこの問題を体系的に議論します。

まず、全体としていくつかの重要な質問に答えてください (アップグレードの詳細な概要は後で説明します。技術的な詳細に興味がある場合は、読み続けてください。全体的な考え方を理解するには、次の段落を読んでください)。

1. なぜ合意が必要なのでしょうか?

この問題については、私の記事で何度も議論してきました。一言で説明すると、「将来的には、エージェントは組織内でコラボレーションするだけでなく、インターネット上のドメインを越えてコラボレーションするようになるでしょう」です。プロトコルは、特にインターネット上でコンテキストを転送する最も効率的な方法です。

2. なぜ新しい契約が必要なのでしょうか?

メッセージ プロトコルに関しては、xmpp、martix、Email など、すでにたくさんあります。なぜ新たに設計する必要があるのでしょうか。

最大の考慮事項は、これらのプロトコルのほとんどが人間が使用する IM または電子メール システム用に設計されており、そのほとんどが ID と通信の統合ソリューションであるということです。インテリジェント エージェントのシナリオでは、ID は通信に加えて、支払い、トランザクション、承認など、さらに多くのことを実行する必要があります。

したがって、エージェントにネイティブなプロトコルが必要です。 ANP は、アイデンティティとビジネスの間の結合度が最も低いです。

3. DIDComm を使用しないのはなぜですか?これはdidに基づいており、アイデンティティとコミュニケーションを分離するためのソリューションでもあります。

私たちは設計の開始時にこのソリューションを検討しました。 DIDComm は、DID に基づく一般的な安全なメッセージング フレームワークであり、完全な IM プロトコルではありません。 「チャット システム」よりも「安全なメッセージ エンベロープ + ルーティング + 上位層プロトコル ベアラー」を好みます。

グループなどの IM に共通する中心的な概念はありません。

4. このアップグレードにより主にどのような問題が解決されますか?

このアップグレードには少し時間がかかりました。しかし、それだけの価値は非常にあります。このアップグレードでは主に次のいくつかの機能が強化されます。
- 新しいセキュリティの強化。 RFC 9421 および RFC 9530 は署名時のセキュリティを強化するために使用され、より標準的な方法が ID 検証に使用されます。
- クロスドメイン機能の強化。以前のソリューションには、クロスドメインのコラボレーションにおいてまだいくつかのギャップがありました。たとえば、メッセージがサーバー自体によって構築されたものではなく、実際に誰かから送信されたものであることを暗号的に証明するにはどうすればよいでしょうか?最新のソリューションでは、証明を使用して、クロスドメイン シナリオにおけるすべてのリンクが安全であることを確認します。
- E2EE (エンドツーエンド暗号化) の機能強化。私たちはエンドツーエンドの暗号化を非常に重視しています。海外の人たちもそれを重視しています。たとえば、マスク氏の XChat はエンドツーエンドの暗号化を備えています。このエンドツーエンド暗号化ソリューションのアップグレードでは、プライベート チャットでは信号調整ソリューションが使用され、グループ チャットでは IETF の MLS が使用されます。 MLSとDIDを組み合わせたものです。 MLS は、メンバー変更の複雑さなど、以前のグループのエンドツーエンド暗号化の欠点の多くを解決します。
- ファイル転送とファイルのエンドツーエンド暗号化をサポートします。以前のバージョン ファイルのサポートは十分ではありませんでしたが、このバージョン ファイルのサポートは非​​常に充実しています。プライベートおよびグループ チャットのファイル サポート、ファイルのセキュリティに関する考慮事項、ファイルのエンドツーエンド暗号化が含まれます。
- より柔軟なメッセージ カプセル化形式を採用し、カプセル化に jsonrpc2.0 を使用します。 jsonrpc2.0 はカプセル化されたメッセージを使用し、非常に柔軟であるため、jsonrpc2.0 を直接再利用できます。

5. 今回のアップグレードでサポートされないもの
- 複数のデバイスはサポートされていません。 martix と signal は複数のデバイスをより適切にサポートしますが、今回のプロトコルでは複数のデバイスをサポートしません。私たちは、ANP がクロスドメインの相互運用性を目的としたプロトコルであると考えています。エージェントが所有するデバイスの数は、エージェントのドメイン内の問題であり、この情報と複雑さをドメインの外部に公開する必要はありません。つまり、別のドメインのエージェントにメッセージを送信します。このエージェントには、メッセージを受け入れるための 1 つまたは複数のデバイスがあります。それは彼自身の仕事であり、私は気にしません。これにより、開発全体が軽減され、実装の柔軟性が向上します。そうしないと、契約が非常に複雑になってしまいます。
-  アーキテクチャの観点からは、現在リレー転送のみがサポートされています。どういう意味ですか？エージェントが別のプラットフォーム上のエージェントとメッセージを交換したい場合は、独自のメッセージ サービスが必要であり、別のエージェントにメッセージを直接送信することはできません。もちろん、メッセージを別のエージェントに直接送信することに技術的な問題はありません。今回これを行わなかった主な理由は、将来的には主流のエージェントが近くのメッセージ サービスにアクセスできるようになり、メッセージ サービスが中継機能を提供すると考えているためです。このアーキテクチャは、QoS にとっても最適なソリューションです。

6. アップグレード中に最も驚いたことは何ですか?

DIDは本当に使いやすいです。エージェントの DID ID の申請に加えて、グループとサービスの DID ID も申請しました。これにより、マルチパーティ プロセスにおける ID、権限、資格情報の複雑な問題が完全に解決されました。

## 概要

このプロトコルのアップグレードの焦点は、古い仕様を部分的に修復することではなく、「ID 認証」と「インスタント メッセージング」を「機能する」レベルから「より標準的で検証可能で、クロスドメインの相互運用性により適した」レベルにアップグレードすることです。

ID の面では、新しいバージョン `did:wba` は単に「DID に基づいてリクエスト署名を作成する」だけではなく、** パスタイプ DID とバインドされた公開鍵フィンガープリント **、** DID ドキュメントの強力なバインディングがさらに導入されています。 ** と ** は、RFC 9421 の HTTP メッセージ署名 ** と ** は、RFC 9530 のコンテンツダイジェスト ** に基づいており、DID、キー、ドキュメント、リクエストの 4 つの層を真に接続しています。関係。

メッセージング側では、ANP の新しいバージョンは、すべてのセマンティクスを運ぶために大規模で包括的な単一の仕様を使用しなくなりました。**コア バインディング、アイデンティティとディスカバリー、プライベート チャットの基本、グループの基本、プライベート チャット E2EE、グループ E2EE、添付ファイルとオブジェクトの転送、フェデレーションとクロスドメイン ** の 8 つのプロファイルに分割されています。この結果、ビジネス セマンティクス、セキュリティ セマンティクス、オブジェクト送信、およびクロスドメイン呼び出しは相互に分離されますが、統合されたバインディング層を通じてこれらを再結合することができます。

新しいソリューションの価値を一文で要約すると、次のようになります。 ** ID の信頼性を高め、メッセージをより階層化し、暗号化をより標準化し、クロスドメイン コラボレーションを真に実装可能にします。 **

## 1.なぜアップグレードを続けるのか?

古いバージョン `did:wba` とインスタント メッセージング プロトコルの古いバージョンは、実際に一連の重要なアップグレードを完了しました。古いバージョンの ID スキームでは、クロスプラットフォーム認証プロセスに DID が導入されています。古いバージョンのインスタント メッセージング プロトコルも、以前の WebSocket ルーティングとインタラクティブ ハンドシェイクから、JSON-RPC 2.0 ベースのメッセージ形式、HPKE ベースのプライベート チャット E2EE、および送信者キー ベースのグループ チャット E2EE に進化しました。言い換えれば、古いソリューションはオリジナルではありません。これにより、「エージェントがチャットして暗号化できるようにする」という中心的な問題が解決されました。

しかし、プロトコルがさらにクロスドメイン相互接続、グループ ガバナンス、添付ファイルの送信、フェデレーテッド サービスの呼び出し、および長期的な標準化を指向すると、古いソリューションでは新たなボトルネックが露呈し始めます。

1. ** ID 認証の標準化と結合強度は十分ではありません。 **
古いバージョンの Did:wba はすでに署名認証を行うことができますが、DID パスとバインディング公開キーの間にデフォルトの強力なバインディングがありません。リクエストの署名は依然としてカスタム `Authorization: DIDWba ...` ヘッダーです。 DID ドキュメントのトップレベルの証明、最新の TLS ID 検証ルール、標準化されたチャレンジ メカニズムなどが十分に完成していません。

2. ** メッセージ プロトコルの構造はまだ比較的モノリシックです。 **
インスタント メッセージング仕様の古いバージョンでは、メッセージ フォーマット、トランスポート バインディング、E2EE、グループ、インターフェイスの例、およびその他の機能が同じドキュメントに記載されています。始めるのは早いですが、進化し続けるにつれて、境界はますます曖昧になっていきます。

3. **グループ、アタッチメント、フェデレーションなどの複雑なシナリオには、より明確な抽象化レイヤーが必要です。 **
グループ チャット E2EE の古いバージョンは、送信者キー + エポック ローテーションを使用して機能しますが、大規模なグループのスケーラビリティ、標準化、グループ ステータスのバインディング、およびグループ結果の監視の点でさらにアップグレードの余地があります。オブジェクト転送とフェデレーション クロスドメインは、古いバージョンでは明確な独立した機能レイヤーに分割されていません。

したがって、新しいソリューションは古いソリューションを覆すものではなく、古いソリューションによって築かれた基盤に基づいて「長期的に保守可能なプロトコルスタック」に向けて進化し続けます。

##  2. 新しい ID 認証スキーム: 「署名可能」から「強力なバインディング、強力な検証、および強力な相互運用性」へ

## 2.1 新しいバージョンの Did:wba の全体的なアイデア

新しいバージョン `did:wba` の中心的な目標は、「ドキュメントを検索できる」だけでなく、次の質問に答える DID を作成することです。

1. どのキーがこの DID にバインドされていますか?
2. この DID ドキュメントはプラットフォームによってサイレントに置き換えられましたか?
3. このリクエストは DID に対応する秘密鍵所有者によって開始されましたか?
4.  サーバーはインタラクションの数を増やさずに標準化された検証を完了できますか?

これらの問題に焦点を当て、did:wba の新しいバージョンは 4 層の設計を提供します。

* **DID レイヤー**: パスタイプ DID は、デフォルトでバインドされた公開キーのフィンガープリントを保持します
* **文書層**：`e1_` パス型DID強制D文書トップレベル `proof`
* **リクエストレイヤー**: ベース `Signature-Input` / `Signature` / `Content-Digest` 署名を要求して下さい
* **セッション層**: 認証後渡された `Authentication-Info` アクセストークンを返し 

## 2.2 パス DID デフォルト紹介 `e1_` ティエの公共のキー指紋

新規版がやった: wba 最も構造的な変化は、**新規パスID**デフォルトスキームを定義します。: DID パスの最後のセキュリティは、 `e1_` 公開鍵の指紋を結びます。 「サフィックス」とは意味しませんが、DID自体はパブリックキーに関連付けられている検証可能な構文を運ぶことを可能にします。

これにより、次の 3 つの直接的なメリットがもたらされます。

* **DID はユーザー自身のキー ** と強力なバインドを形成します
* **プラットフォームがアイデンティティ公開鍵をサイレントに置き換えるリスクが軽減されます**
* ** ID ローテーションの境界が明確になり、安定した名前がハンドル/WNS に渡されて解決されます **

新しいマスターの規則 デフォルト プロフィール はい `e1_`つまり、 **でぶっかけ25519**; また、付録で保持 `k1_` 互換性への互換性のある拡張 **秒数256k1** エコロジー。つまり、新しいプログラムのメインラインは、時間をかけてより標準化され、相互運用性が向上することを意味しますが、既存の生態学的互換性を放棄するわけではありません。

対照的に、did:wba の古いバージョンのパスタイプ DID は単なる通常のパスであり、バインドされた公開キーのフィンガープリントを DID パス自体に直接配置しません。

## 2.3 DID 文書が「公開鍵のリスト」から「結合関係の証明」にアップグレードされました

Did:wba の DID ドキュメントの古いバージョンでは、すでに `authentication`、`keyAgreement`、`service` などのフィールドを表現でき、複数の検証方法タイプも許可されています。しかし、新しいバージョンでは、DID ドキュメントの役割がさらに強化され、「キーをリストする」だけでなく、「このドキュメントが DID パス バインディング関係と一貫していることを証明する」こともできます。

したがって、デフォルトの `e1_` プロファイルに対して、新しいバージョンではいくつかの重要な制約が追加されています。

* DID ドキュメントトップレベル **必要です。 `proof`**
* `proof` **必要です。**利用条件 `DataIntegrityProof + eddsa-jcs-2022`
* `proof.verificationMethod` 対応するEd25519の公共のキー、RFC 7638 kummprint **DID パスの最後のものでなければなりません `e1_` 指紋は同一です。** 

このステップは非常に重要です。 Did:wba の古いバージョンは、「認証要求」層での署名の検証に重点を置いています。新しいバージョンでは、**DID パス、バインディング キー、文書証明、および認証関係 ** が継続的な検証リンクに統合されます。

## 2.4 カスタムヘッダーから標準の HTTP メッセージ署名にアップグレードされたリクエスト認証

旧バージョンの Did:wba のリクエスト認証方法は次のようにカスタマイズされています。

```http
Authorization: DIDWba did=..., nonce=..., timestamp=..., verification_method=..., signature=...
```

このソリューションは使用できますが、本質的には依然としてプロトコルプライベート形式であるため、既存の HTTP セキュリティ メカニズムや標準エコシステムとの統合には役立ちません。

新しいバージョンの Did:wba は、標準化されたルートに直接切り替わります。

* 利用条件 **RFC 9421の特長** ・・・ `Signature-Input` とりあえず `Signature` ヘッド式リクエストの署名
* 利用条件 **RFC 9530の特長** ・・・ `Content-Digest` ビンドメッセージの完全性
* 認証で渡された **`Authentication-Info`** アクセストークンを返し
* 認証が失敗したときに使用 **`WWW-Authenticate` + `Accept-Signature`** チャレンジ情報やコンポーネントを次のリクエストでカバーする 

これは、新しいバージョンの ID 認証が「一連の DID 署名ヘッダーのカスタマイズ」を目的とするのではなく、成熟した HTTP 標準セマンティクスに DID 認証を組み込むことを意味します。エンジニアリングの実装にとって、この変更の価値は非常に大きくなります。

* より明確な報道のリクエスト
* サーバー側の課題がより標準化されました
* ミドルウェアとゲートウェイの接続が容易になりました
* 標準ライブラリと既存の実装は再利用しやすい

## 2.5 TLS、トークン、および高レベルの認証セマンティクスもより明確になりました

新しいバージョンの Did:wba では、いくつかの非常に重要なエンジニアリング上の問題も強化されました。

* **TLSサービス識別**: 古いバージョンは「共通名マッチング証明書」の表現に近いです。新しいバージョンは明示的に要求します `subjectAltName.dNSName` つまり、より共通に依存しない。 
* **トークンリターンモード**: 古いバージョンは、アクセストークンを通常のものにするのが近づき `Authorization: Bearer ...` ヘッドバックに対応。新しいエディションは、サービスエンドパスを明示的にリクエスト `Authentication-Info` アクセストークンを返します。 
* **手動でセマティクスを確認します**: DID 文書の旧バージョン `humanAuthorization` フィールド; 新しいエディションは、このフィールドを明示的に削除し、DID文書からトップレベルの承認された戦略とインターフェースの構文表現に「ワントヒューマンプレゼンスの確認」を削除します。 `authorizationLevel: user-presence-required`. これは、DIDファイルを「アイデンティティの宣言」関数に返し、あまりにも多くのビジネス認可の構文にブレンドするよりもむしろ。

| DID ドキュメント | 認定方法やサービスのリストに焦点を当てる                    | `e1_` パスタイプ DIDフォーストップレベル `proof`                       | 文書の完全性およびアイデンティティ結合の均一認証   |

| メッセージの完全性       | 標準フィールドのユニフォームなし                        | 利用条件 `Content-Digest`                                | 操作の防衛に特異的です。         |
| 成功トークンの後    | より意味のある。                           | パス。 `Authentication-Info` バックナンバー                        | HTTP認証の構文を一線で確認    |
| マニュアル確認         | DID 文書 `humanAuthorization`   | 認定ポリシーレベルまで移動                                           | 委任された責任からのアイデンティティの分離        |
| TLS 検証       | CNマッチへのクローザー                       | 明示的に使用 `subjectAltName.dNSName`                      | 現代のTLS練習と並んで     |

一文で要約すると: ** 新しいバージョンの Did:wba は、「DID は誰か」、「文書が信頼できるかどうか」、「リクエストが DID によって開始されたかどうか」の 3 つの要素を、完全で標準的な検証可能なリンクに結合します。 **

## 3.新しいエンドツーエンドのインスタント メッセージング プロトコル: 「単一メッセージ プロトコル」から「階層化プロトコル スタック」へ

## 3.1 1 つの大きな仕様から 8 つのプロファイルに進化

古いバージョンのインスタント メッセージング プロトコルの利点は、直感的であることです。メッセージ形式、トランスポート バインディング、プライベート チャット、グループ チャット、E2EE、インターフェイスの例がすべて 1 つのドキュメントで説明されており、読者はそれを入手した後に基本バージョンを実装できます。

しかし、その問題も明らかです。プロトコルが拡張し続けるにつれて、すべての機能が 1 つの仕様に詰め込まれ、境界はますます曖昧になっていきます。たとえば、どれがバインディング レイヤーの問題で、どれがビジネス レイヤーの問題で、どれが暗号化レイヤーの問題で、どれがオブジェクト送信の問題で、どれがクロスドメイン フェデレーションの問題であるかが、徐々に混在していきます。

## 3.2 新しいプロトコルは「チャット API」ではなく、「エージェント エコシステムのクロスドメイン通信標準」です

古いバージョンのプロトコルの読み取りエクスペリエンスは、「メッセージング システム API 仕様」に似ています。新しいバージョンのプロトコルの位置付けはより高いレベルにあります。解決したいのは、**異なるドメイン、異なるプラットフォーム、異なる実装のエージェントがどのように相互に通信できるか**です。

したがって、新しい協定では、次のようないくつかの第一級の概念に重点が置かれています。

* **エージェント DID**
* **グループ DID**
* **ANPメッセージサービス**
* **グループホストサービス**
* **オブジェクトサービス**

これは、プロトコルが単に「メッセージを送信する」だけではなく、次のことを明示的に記述し始めることを意味します。

* 正体を知る方法
* メッセージの対処方法
* グループのステータスを分類するのは誰ですか?
* そのオブジェクトを管理しているのは誰ですか?
* クロスドメイン成功セマンティクスはどの層を保持しますか?

##  IV.新しいメッセージプロトコルのコア技術ルート

## 4.1 統合された外部バインディング: より厳格な JSON-RPC 2.0

ここで特に強調する必要があります: ** JSON-RPC 2.0 を導入するのは新しいバージョンが初めてではありません。 ** 従来のインスタント メッセージング プロトコルは、ユニファイド メッセージング形式としてすでに JSON-RPC 2.0 を使用しています。新しいバージョンの本当の変更は、これに基づいてそれをさらに強化し、制度化することです。

P1 の新しいバージョンの主な強化点は次のとおりです。

* `params` **必要です。**オブジェクト
* `id` **必要です。**非空文字文字列
* **バッチバッチ**
* 通知は明示的な非同期通知にのみ使用されます
* ユニバーサル `params` 固定する上の構造 `meta / auth / body`
* 導入事例 `anp.get_capabilities` - 能力相談をしています。
* 導入事例 `operation_id`、`message_id` 均一なハイフンとメッセージ識別子を作る
* 利用条件 `security_profile` 明確な差別 `transport-protected`、`direct-e2ee`、`group-e2ee` 

言い換えれば、新しいプロトコルは「JSON-RPC への切り替え」ではなく、JSON-RPC をプロトコル スタック全体の統合バインディング層に真に改善するものです。

## 4.2 均一同一証明の調査:`ANPMessageService` シングルエントランスとして

P2 の新しいバージョンの大きな変更は、Agent、C Clusters、Object から可能な限り多くの電力を結合することです。 **ユニファイド `ANPMessageService`** 以下。それは、その背後にある論理的役割、キー、グループ、結合、資本性およびオブジェクトを運びます。

インターフェイスとエンドポイントの説明がより「一般的」だった古いバージョンと比較して、新しいバージョンでは「ディスカバリー ポータル」と「機能ネゴシエーション」がよりプロトコル ベースになり、フェデレーション シナリオにより適しています。

## 4.3 プライベート チャット セキュリティ モデル: 「ワンステップ HPKE init」から「Prekey Bundle + X3DH-like + Double Ratchet-like」にアップグレードされました。

ここでも正確に表現する必要があります: ** プライベート チャット E2EE の古いバージョンは、初期の ECDHE 3 ステップ ハンドシェイクではなくなり、すでに HPKE 1 ステップ初期化 + チェーン ラチェットになっています。 ** したがって、新旧の比較は単純に「安全でないものから安全なものへ」と言うのではなく、「利用可能な HPKE セッションの初期化から、より成熟した非同期リンク構築モデルへ」と言うべきです。

新しいバージョンのプライベート チャット E2EE のコア テクノロジー スタックは次のとおりです。

* **プレキーバンドル**
* **署名付きプレキー/ワンタイムプレキー**
* **X3DH のような初期非同期リンク確立**
* **ダブルラチェットのようなフォローアップメッセージ保護**
* **AAD バインディング、アウトオブオーダー処理、リプレイ保護、セッション再構築**

この設計の重要性は次のとおりです。

1. ** は、非同期オフライン シナリオに適しています。 **: 送信者は、相手がオンラインで応答するのを待つ必要はありません。
2. ** は、純粋な HPKE init よりも成熟した IM セキュリティ モデル ** に近いです。
3. **クリアーな境界線。**:P5 は署名/アサート キーを明示的に要求し、 `keyAgreement` キーは分離され、バンドル署名が省略できないと強調されます。
4. **将来のアップグレードの余地を残す**: P5 は、v1 はポスト量子ソリューションではないが、PQXDH のようなアップグレードの余地を残していると明確に述べています。

## 4.4 グループ セキュリティ モデル: 送信者キーから MLS メインラインへの進化

グループ E2EE の古いバージョンのコア ソリューションは、**送信者キー + エポック ローテーション ** です。このソリューションは中小規模のグループ チャットでは非常に実用的ですが、限界も明らかです。

* 送信者キーの配布は **O(N)**
* グループメンバーの変更、歓迎、外部参加、グループステータスの証明などのシナリオは、長期的に標準化されたグループ暗号化モデルではエレガントに表現することが困難です

古いバージョンの仕様自体には、将来の方向性として **MLS 統合 ** が明確に記載されています。 P6 の新しいバージョンは、この「将来のルート」を幹線計画として直接前進させます。

* **MLS** グループ鍵ステートマシンとして
* **did:wba** をアイデンティティアンカーとして使用
* **行なった_ウィバ_結合の** MLS の署名キーは、 `agent_did`
* **グループホストサービス**は並べ替えと受信を担当しますが、デフォルトではグループ平文を保持しません
* `group_did`、`group_state_version`、`policy_hash` パスワードコミュニティのステートに結びます
* グループ メッセージは **MLS PrivateMessage** ベアラーを使用します

このステップは非常に重要です: ** グループ チャット E2EE はもはや「実行可能なグループ暗号化セットのカスタマイズ」ではなく、長期的な標準化の本線に直接接続されています。 **

## 4.5 証拠は改善します模倣します:`sender_proof`、`actor_proof`、`group_receipt`

古いバージョンのプロトコルでは、メッセージの暗号化とメッセージ送信が主な焦点でした。新バージョンでは、「誰がリクエストを開始したか」「誰がリクエストを受け付けて振り分けたか」「誰が復号権限を持っているか」の3つを厳密に分離している。

プライベートチャットでは:

* `sender_proof` 記事のプロテクションのため `direct.send` 観点からの眺め `sender_did` リリース
* ホップレベル認証は、特定のホップ発信者の身元を証明するだけです。 ** は ** 発信者認証を置き換えることはできません。

グループ内:

* `actor_proof` グループ操作やグループメッセージの開始をした方
* `group_receipt` グループホストが生成し、グループが操作やメッセージの承認とソートを行なったことを実証
* MLS メンバーの署名は、どの暗号メンバーがハンドシェイクまたは暗号文を生成したかを証明する責任があります。

これにより、新しいバージョンのグループ プロトコルはガバナンス シナリオにより適したものになります。すべての問題を 1 つの署名に混ぜるのではなく、**イニシエーター認証、グループ結果の証人、およびグループ内の機密性 ** の 3 層セマンティクスを同時に保持します。

## 4.6 添付ファイルとオブジェクト: メッセージからマニフェスト + オブジェクト サービスまでのインライン化

古いバージョンのプロトコルは、`image` や `file` などのメッセージ タイプをサポートし、大きなファイルの効率の問題を認識していますが、独立した完全なクロスドメインで再利用可能な添付オブジェクト仕様のセットを形成していません。

P7 の新しいバージョンでは、添付ファイルが正式に制度化されています。

* メッセージを渡すだけ。 **`attachment_manifest`**
* オブジェクト層のアップロードとダウンロードは、**オブジェクト サービス**を介して行われます。
* アクセス制御を通過しました**短いダウンロードチケット**
* より高い機密性が必要な場合は、**オブジェクトレベルの暗号化（object-e2ee）**を有効にします
* リレー **オブジェクトバイトストリームを転送しません **

これは、新しいプロトコルが「メッセージ コントロール プレーン」と「オブジェクト データ プレーン」を完全に分離することを意味します。エンジニアリング実装の場合、このステップは、クロスドメイン メッセージ リンクと大きなバイト ストリームとの結合を大幅に減らすため、ほぼ必須です。

## 4.7 フェデレーションとクロスドメイン: 「後で定義する」から正式にスタックに組み込むまで

古いバージョンのプロトコルでは、メッセージ サーバー間の通信プロトコルはこの仕様の範囲外であり、サーバー間の相互運用性は今後の作業方針であると明確に述べられていました。

P8 の新しいバージョンでは、この部分が主要な仕様システムに正式に組み込まれています。

*  ドメインを越える場合、** は新しい Relay メソッドを含めるのではなく、元のビジネス メソッド ** を直接使用します。
* 直接プライベートなインタードメイン。 `direct.send`
* グループ 運営 直接 クロスドメイン `group.create`、`group.send`、`group.add`、`group.remove` 待たせます。
* `attachment.get_download_ticket` オブジェクトサービス終了まで直接
* オブジェクト バイト ストリーム **クロスドメイン サービス呼び出しリンクを使用しないでください **
* グループ操作のクロスドメイン成功セマンティクスは、**グループホスト**の受け入れと並べ替えの対象となります。
* プライベート チャットのクロスドメイン セマンティクスが成功するには、**ターゲット エージェント ポータル サービス ** の承認が必要です。
* オリジナル `sender_proof` / `actor_proof` 中間サービスで書き換えられていないクロスドメインに保管する必要があります 

これは、新しいプロトコルがもはや単なる「単一ドメイン メッセージ API」ではなく、真に **フェデレーテッド エージェントの相互運用性** のプロトコル境界を持っていることを示しています。

## 5.エンドツーエンドのインスタント メッセージング プロトコル: 古いバージョンと新しいバージョン

| ディメンション | インスタントメッセージング仕様の旧バージョン | ANP プロファイルシステムの新バージョン | 変更の重要性 |
| ------- | ------------------------- | --------------------------------------------------------------------- | ------------- |
| 標準構造 | 単一の大きな仕様 | 8 つのプロファイル階層の組み合わせ | 明確な境界、個別にアップグレードが簡単 |
| 外層バインディング | すでに JSON-RPC 2.0 を使用しています | JSON-RPC 2.0 を引き続き使用し、より厳格な相互運用性制約を追加します | 統合バインディング層はより安定しています |

| プライベートチャットモデル    | `send` + 複数メッセージタイプ        | `direct.send` + ベースセマンティック+ E2EEオーバーレイ                                | セキュリティのセマンティックスからビジネスの構文を分離   |

| 原発の証明書   | メッセージ内容と暗号化に焦点を合わせる                | クリア `sender_proof` / `actor_proof` / ホップのauthの層                       | 横断面と監査に適した      |
| 添付ファイルオブジェクト    | ファイルメッセージは独立オブジェクトコードではなく、            | `attachment_manifest` +Object Service+ダウンローダーノート+オブジェクト暗号化                 | 大きい目的の移動工学      |
| クロスドメインフェデレーション | 将来の作業方向として | P8 クロスドメイン接続と成功セマンティクスを正式に定義 | 実際にはフェデレーテッドプロトコルの形式を持つ |

        

一文の要約: ** 古いバージョンはすでに動作するメッセージ プロトコルです。新しいバージョンでは、長期的に進化でき、クロスドメイン エージェント エコシステムに適したプロトコル スタックにアップグレードされました。 **

## 6.新プランの注目すべき5つの特徴

### 6.1 特徴1：より高度な標準化

ID 側は RFC 9421、RFC 9530、W3C Data Integrity に準拠しています。グループ暗号化側は MLS に移行します。メッセージ バインディング層は引き続き JSON-RPC 2.0 に基づいて構築され、強化されています。新しいソリューションは、製品の内部独自プロトコルではなく、明らかに長期的な標準化ルートに近いものです。

### 6.2 特徴 2: より強力な ID 結合

`e1_` 指紋パス + DID 文書証明は、DID、鍵、文書間のバインディングを「論理的に確立された」ものから「プロトコルで義務付けられた検証が確立された」ものに変更します。これは、新しい ID スキームにおける最も重要なセキュリティの改善点の 1 つです。

### 6.3 特徴 3: ビジネス層とセキュリティ層の実質的な分離

`transport-protected`、`direct-e2ee`、`group-e2ee` はスタック可能なセキュリティ プロファイルです。基本サービスは独立して実行でき、必要に応じてセキュリティ オーバーレイをスタックできます。この設計により、プロトコルは増分展開とその後のアップグレードの両方に適したものになります。

### 6.4 特徴 4: フェデレーションとオブジェクト送信がメインラインに参入

添付ファイル オブジェクト、ダウンロード チケット、クロスドメイン転送、グループ ホストの並べ替え、およびオブジェクト サービスの配置。古いバージョンではまだ「エンジニアリング実装の問題」または「将来の作業」と考えられていたこれらの内容は、現在では仕様の主要部分の一部になっています。

### 6.5 特徴 5: チャットだけでなく、エージェントのコラボレーションにさらに適しています

新しいバージョンのプロトコルのキーワードはメッセージだけでなく、次のことも含みます。

* DID
* 発見
* プルーフ
* ガバナンス
* オブジェクト
* フェデレーション
* 領収書

これにより、単なる「E2EE とのチャット インターフェイス」ではなく、** エージェント間の一連のクロスドメイン コラボレーション プロトコル ** に似ていることがわかります。

## 7.共有するときは何と言えばいいでしょうか？

この原稿を社外または社内で共有する場合は、主旨を次のように言うことをお勧めします。

### 最初のレベル: まずアップグレードの目標について話しましょう

これは用語を変更することではなく、アイデンティティをより信頼できるものにし、クロスドメインをより自然にし、グループ ガバナンスをより明確にし、プロトコルをより長期的に進化できるようにするためです。

### 第 2 レベル: アイデンティティについてもう一度話しましょう

3 つの単語を強調表示します。

* **パスバインド**
* **ドキュメント**
* **標準リクエスト署名**

###  3 番目の層: メッセージ プロトコルの階層化について話しましょう

オーディエンスが理解できるように:新しい合意は「チャットインターフェイス文書」ではなく、レイヤードプロトコルファミリーではありません。

### レベル4:暗号化経路の変更に焦点を当てる

* 「HPKE init」から「Prekey Bundle + X3DH のような + Double Ratchet like」へのプライベートチャット
* Senderkey + epoch から MLS のメインラインへのグループチャットアップグレード

### レベル5:最終的な工学価値

添付ファイルには、スタンドアローンのデータインタフェース、クロスドメイン直接ビジネスメソッド、グループ結果の確認とサービスが単一のアクセスを見つける。つまり、コーダ設計だけでなく、実際のシステムのための合意プロジェクトであることを意味します。
