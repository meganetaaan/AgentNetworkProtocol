# ANP リリース 1.1 正式リリース: エージェントのクロスドメイン通信に焦点を当てる

3 か月にわたる磨きを経て、先週、ANP 1.1 が正式にリリースされました。

このバージョンは、これまで定期的なコミュニティ ミーティングで何度も議論され、皆さんのフィードバックと実装に基づいて多くの調整が行われました。今日は、このバージョンのいくつかの主要な改善点と、その背後にある考え方のいくつかを正式に要約します。

このアップグレードには 2 つの主要な内容があります。1 つは自律的な ID 制御で、もう 1 つはメッセージ プロトコルのアップグレード、特にクロスドメイン通信と安全な通信です。

## 自律型アイデンティティ制御

ANP は常にエージェント ID の DID に基づいています。

DID の最大の利点は、ID、キー、サービス エントリを検証可能なドキュメントに含めることができることです。このようにして、異なるプラットフォームや組織が同じアカウント システムに依存する必要がなく、相互に識別および認証することもできます。

Did:web はこれを行うための良い方法です。 DID を既存の Web インフラストラクチャと組み合わせ、ドメイン名、HTTPS、`.well-known` などの成熟したメカニズムを直接再利用します。導入の敷居は比較的低く、既存のインターネット システムと容易に互換性があります。

しかし、did:web にも問題があります。DID ドキュメントは Web サーバー上でホストされています。つまり、サーバーに DID ドキュメントを変更できる機能がある場合、一部の高セキュリティ シナリオではユーザーの ID とキーの信頼性に影響を与える可能性があります。

たとえば、DID に基づいてエンドツーエンドの暗号化通信を行う場合、サーバーが DID ドキュメント内の鍵マテリアルを静かに置き換えることができれば、通信当事者はエージェントと安全に通信していると考えるでしょうが、実際には鍵が置き換えられている可能性があります。この問題は、通常のログイン認証ではそれほど明らかではないかもしれませんが、エンドツーエンド暗号化やクロスドメイン認証などのシナリオでは非常に重要になります。

そこで今回はdid:wbaをアップグレードしました。

ここでは正確である必要があります。DID ではユーザーの秘密キーを保持しません。また、秘密キーは決して DID に書き込まれてはなりません。 Did:wba が行うことは、バインドされた公開キーのフィンガープリントをパスタイプ DID で保持することです。簡単に理解すると、DID 自体とユーザーが管理する公開キーとの間に検証可能な結合関係を確立するということです。

これにより、検証者は、DID ドキュメントが Web サービスによってホストされている場合でも、DID パス内の公開キーのフィンガープリントが DID ドキュメントで宣言されたキーと一致するかどうかを確認できます。サーバーがサイレントにキーを置き換えることは、もはや簡単ではありません。

この結果、秘密キーに対するユーザーの制御が DID ID 自体により直接的に反映されるようになります。 DID はもはや Web アドレスの下にある単なるドキュメントではなく、ユーザーが実際に制御するキーとのより強い関係を持っています。

もちろん、did:web には依然として利点があります。安定していてシンプルで、互換性が高く、多くの低しきい値の展開シナリオに特に適しています。したがって、ANP 1.1 は Did:web を放棄することを意味するものではなく、ネイティブの Did:web と Did:wba の両方と互換性があります。さまざまなシナリオに応じてさまざまなソリューションを選択でき、相互接続することもできます。

アイデンティティの観点から、1.1 にはハンドルというもう 1 つの重要なデザインもあります。

なぜハンドルをデザインするのか?主な理由は 2 つあります。

一つ目の理由は読みやすさです。

DID は機械には優しいですが、人には優しくありません。完全な DID は非常に長いことが多く、チャット ウィンドウ、名刺、連絡先リスト、または招待リンクに表示するには適していません。ユーザーが手動で入力して記憶することも困難です。

したがって、次のような、人々が使用するのに適したロゴが必要です。

```text
alice.example.com
```

この形の方がユーザーにとって分かりやすく、広がりやすいです。

2 番目の理由は、did:wba の安定した ID を固定するためです。

公開キーのフィンガープリントは Did:wba パスにバインドされているため、基礎となるキーが変更されると、DID 自体も変更される可能性があります。これはセキュリティの観点からは合理的ですが、ユーザー エクスペリエンスの観点からは、誰もが長期的に安定した名前を望んでいます。

ハンドルはこの問題を解決するために設計されました。ハンドルは安定したままにすることができ、基になる DID はキー、セキュリティ ポリシー、またはデバイスの変更に応じてローテーションできます。ユーザーに表示されるのはハンドルであり、プロトコルが実際に検証されるときに、現在有効な DID に解析されます。

したがって、Handle は DID に代わるものではありません。 「どうやって人を識別するか」という問題を解決します。 DIDは「プロトコルをどう検証するか」という問題を解決します。

ハンドルと DID の関係は、ドメイン名と IP アドレスの関係に似ています。

## メッセージプロトコルのアップグレード

今回の 1.1 でのもう 1 つの大きな改善点は、メッセージング プロトコルです。

メッセージング プロトコルの最初のドラフトは機能しましたが、実装を進めていくと、まだいくつかの潜在的な問題があることがわかりました。

たとえば、添付ファイルのサポートは十分に完全ではなく、クロスドメインのコラボレーションにはまだいくつかの欠陥があり、エンドツーエンドの暗号化ソリューションは業界の成熟したソリューションからはまだはるかに遅れています。特に、前方セキュリティやグループ チャットのキー管理などの問題は十分に明確ではありません。

最適化を続ける前に、まず問題を再定義しました。

私たちは、ANP を Matrix のような非常に完全な IM プロトコルにすることを望んでいません。 Matrix は、クライアントからサーバー、サーバーからサーバー、マルチデバイスの同期、ルーム ステータス、履歴メッセージなどに至る一連の問題を解決します。この方向性は強力ですが、非常に重いものでもあります。

ANP が解決したい問題は異なります。

私たちがさらに懸念しているのは、異なるドメインおよび異なるシステムにあるエージェント間でクロスドメイン メッセージを通信する方法です。

各ドメイン内でのアカウント システムの実装方法、クライアントの登録方法、携帯電話番号と電子メールのどちらで認証するか、エージェント内に複数のデバイスやアクチュエーターが存在するかどうかなどについては、プロトコルの本行では定義したくありません。

これらすべてが定義されている場合、プロトコルの複雑さは非常に高くなり、その内容の多くは実際にはシステムの内部問題であり、クロスドメインの相互運用性の問題ではありません。

したがって、1.1 メッセージ プロトコルは 3 つのシナリオに重点を置いています。

まず、エージェントがプライベートおよびグループでどのようにチャットするかです。

2 番目は、添付ファイルと大きなオブジェクトをメッセージで送信する方法です。

3 番目は、必要に応じてエージェント間でエンドツーエンドの暗号化通信を実行する方法です。

これが問題の境界の定義です。

問題が明確に定義されたら、次の設計上の決定を下すことができます。ANP 1.1 はプロトコル層で複数のデバイスを定義しません。

複数のデバイスを使用すると、プロトコルが非常に複雑になります。異なるデバイス間でステータスを同期する方法、キーを同期する方法、オフライン メッセージと履歴メッセージを処理する方法はすべて非常に複雑です。また、システムが異なれば、複数のデバイスに対する要件も異なります。

私たちは、各システムがエージェント内に存在するデバイス、実行ノード、レプリカの数を決定する必要があると考えています。 ANP は、エージェントをクロスドメイン通信の主体としてのみ考慮します。このエージェントが外部にメッセージを送受信できる限り、内部でスケジュールを設定する方法はプロトコルの相互運用性の境界に入りません。

この決定により、プロトコルが軽量化され、より焦点が絞られるようになります。

### メッセージプロトコルとDIDの組み合わせ

このメッセージ プロトコルのアップグレードにおいて、非常に重要な設計は、メッセージ プロトコルと DID の徹底的な統合です。

当社は人物やエージェントに DID を割り当てるだけでなく、グループやメッセージング サービスにも DID を導入します。このようにして、メッセージング システム内でいくつかの異なる役割が形成されます。

1 つ目はエージェント DID で、メッセージの送信者と受信者です。もちろん、人間が DID を申請することもできます。

2 番目はグループ DID で、グループ自体の ID です。グループはサーバー内の通常のルーム ID ではなく、ドメイン全体で識別、検出、検証できるプロトコルのサブジェクトです。

3 番目はサービス DID で、メッセージング サービスを提供するサーバーの ID です。ドメイン間で通信する場合、サービスは相互に認証する必要もあります。ビジネス メッセージの送信者だけを見ることはできません。

この設計の後、アイデンティティ階層がより明確になります。

エージェント DID は、誰がメッセージを開始したかを証明するために使用されます。グループ DID は、グループの ID、グループ ステータス、およびグループ イベント シーケンスを証明するために使用されます。サービス DID は、どのサービスが現在のクロスドメイン呼び出しを開始したかを証明するために使用されます。

これらの DID を混在させることはできません。

たとえば、サーバーは、Alice のエージェントがメッセージを別のドメインに転送するのを支援できますが、メッセージが自分自身で送信されたと主張することはできません。サービス ID は「転送している」ことを証明することしかできず、ビジネス ID に代わることはできません。

完全性証明についても同様です。異なるロールは独自の DID を使用して、異なるレベルでオブジェクトを認証できます。エージェントはメッセージを開始したことを証明でき、グループ ホストは特定のグループ メッセージが受け入れられグループによって分類されたことを証明でき、サービスは特定の HTTP 呼び出しが実際に自分自身から発信されたものであることを証明できます。

これは、実装プロセス中に私たちが感じた深い感情でもあります。DID はクロスドメインに非常に適しています。

なぜなら、クロスドメイン システムが最も恐れているのは、アイデンティティ セマンティクスの混乱だからです。 DID では、各サブジェクトが独自の ID、独自のキー、独自の認証方法を持つことができ、これらの認証は同じ中央アカウント システムに依存しません。

将来、複数のデバイスをサポートする必要が生じた場合は、デバイスごとに DID を作成することもできます。

### クロスドメインメッセージには追加のレイヤーが含まれなくなりました

また、今回は非常に重要な設計上の決定があります。それは、クロスドメイン メッセージにはリレー プロトコルの追加レイヤーが含まれていないということです。

つまり、クロスドメインのプライベート チャットでは引き続き `direct.send` が使用され、グループ チャットのクロスドメインでは引き続き `group.send` が使用され、グループ メンバーの変更では引き続き元のグループ管理方法が使用されます。クロスドメイン プロファイルは、ターゲット サービスを検出する方法、現在のサービスを認証する方法、元の送信者証明書を保持する方法、および成功とみなされるタイミングのみを規定します。

この選択は簡単に思えるかもしれませんが、重要です。

ドメイン内にメソッドのセットが 1 つあり、ドメイン間で別の Relay メソッドのセットが発明された場合、プロトコルは長期的にはますます複雑になります。ビジネス セマンティクスは 2 つのセットに分割されるため、実装者は混乱しやすくなります。リレー層を検証する必要があるのか​​、それとも元のビジネス層を検証する必要があるのか​​?

そこで私たちは、ビジネスアプローチに一貫性を保つことにしました。クロスドメインは呼び出し境界を変更するだけであり、一連のビジネス セマンティクスを再定義すべきではありません。

### 添付ファイルとオブジェクトの転送

アタッチメントもこの機能強化の重要な部分です。

メッセージング サービスがファイル転送サービスになることは望ましくありません。大きなファイル、画像、オーディオ、ビデオなどのオブジェクトがメッセージとともにドメイン間で直接転送されると、コストと安定性に大きな問題が発生します。

したがって、1.1 ではメッセージとオブジェクトを分離します。

メッセージには、添付ファイルの説明 (添付ファイルのマニフェスト) のみが含まれます。実際のオブジェクトのアップロードとダウンロードには、独立した HTTPS チャネルが使用されます。クロスドメイン メッセージング サービスは、アップロード場所の申請、オブジェクトの送信、ダウンロード チケットの取得など、コントロール プレーンにのみ参加し、途中でファイル バイトを転送する責任は負いません。

これはよりエンジニアリング的であり、実際の展開により適しています。

オブジェクトにさらに高い機密性が必要な場合は、オブジェクト レベルの暗号化を有効にすることもできます。オブジェクト サービスはストレージと配布を担当できますが、オブジェクトのクリア テキストを知る必要はありません。

### エンドツーエンドの暗号化通信

最後に、エンドツーエンドの暗号化について話しましょう。

私たちはこの件を非常に真剣に受け止めています。一部の重要なシナリオでは、エージェント間のメッセージをサーバーが取得すべきではないためです。サーバーはルーティング、並べ替え、保存、配布を支援しますが、デフォルトではコンテンツを読み取る機能は備えていません。

プライベート メッセージのエンドツーエンド暗号化については、Signal のいくつかのアイデアを参照しています。送信者は受信者がオンラインになるまで待つ必要はありません。まず相手側が公開したリンク構築マテリアルを取得してから、暗号化されたセッションを開始します。後続のメッセージは、ダブル ラチェットと同様のメカニズムを通じてキーを継続的に更新するため、より優れた前方セキュリティがサポートされます。

グループ チャットのエンドツーエンド暗号化には、IETF の MLS (Messaging Layer Security) を使用します。

私たちは、送信者キー グループのキー スキームを自分たちで設計することを選択しませんでした。従来の送信者キー ソリューションは、小さなグループではシンプルに見えますが、メンバーにとっては、参加、脱退、メンバーのキック、およびキーのローテーションが非常に面倒になります。特にクロスドメインのシナリオでは、誰がキーを更新するか、誰がステータスを同期するか、誰が現在のグループのステータスを証明するかについて多くの問題が発生します。

MLS の利点は、安全なグループ通信のためにゼロから設計されていることです。より明確なグループ キー ステート マシンを備えており、メンバーの変更、キーの更新、グループ メッセージの暗号化をより適切に処理できます。 DID を使用して ANP のメンバーシップ ID をバインドし、グループ ホストを使用してビジネスの仕分けと領収書を担当し、MLS を使用してグループの暗号化ステータスを担当します。

このようにすると、自分でグループ暗号化プロトコルを再発明するよりも分業が明確になり、信頼性が高くなります。

ここでの私たちの主な仕事は、DID と MLS を統合することです。

## 次のステップの計画

ANP 1.1 のリリース後、私たちは 2 つの方向に焦点を当てます。

1 つ目の方向は、インテリジェント エージェントの権限制御と監査です。

エージェント間のコラボレーションには、メッセージを送信する機能だけでなく、誰が何をする権限を持っているか、最終結果を監査できるかどうかを知る必要もあります。ここでは、VC をサポートする W3C DID、つまり Verifiable Credentials を組み合わせて、よりきめ細かい権限表現と結果の認証を実現します。

VC は現在さまざまな方向で研究されており、エージェントのコラボレーションにおける承認、委任、監査のシナリオに非常に適していると考えています。

2 番目の方向は、メッセージング システムでのコンテキスト共有です。

エージェントのコミュニケーションは単に文章を送信するだけではなく、多くの場合、タスクの背景、ツールの呼び出し結果、コンテキストのステータス、コラボレーション プロセスを共有する必要があります。私たちは、プロトコルをやりすぎずに、エージェントがメッセージング システムでコンテキストをより適切に共有する方法を引き続き模索していきます。

全体として、ANP 1.1 は比較的重要なバージョン アップグレードです。 ANP は、「接続できること」から「ドメインを越えてコラボレーションし、コンテンツを検証し、保護できること」にさらに一歩前進します。

私たちの目標は依然として同じです。それは、今日の Web サービスのようなエージェントを、接続にオープンで、独立して展開され、クロスドメインでコラボレーションできるようにすることです。

リリース 1.1 は、この方向への一歩前進です。
