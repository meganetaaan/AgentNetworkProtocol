# W3C WebAgents CGでの、ANPの発表

2025年2月14日、常高偉とJames Waughが、ANPオープンソースコミュニティを代表し、発表しました。

WebAgentsコミュニティは、Webに基づくマルチエージェントシステム（MAS）を設計します。Webの構造と整合し、大域性、開放性、持続性を引き継ぎ、透明性と追跡可能性を保つことで、幅広く受け入れられる、新しいMASを目指します。特に、Linked DataとセマンティックWebの標準で、人、AI、機器、デジタルサービスなど、異なる主体が、統一的にやり取りできるハイパーメディア構造（hMAS）を重視します。公式サイト：[https://www.w3.org/community/webagents/](https://www.w3.org/community/webagents/)。

ANPの理念には、多くの共通点があり、同じ技術を重視します。設計でも、このコミュニティの議論を参考にしました。今回、私たちの考えと実践を紹介しました。

発表は、常高偉とJmaes Waughが共同で行いました。スライド、原稿、会議での議論を、以下に示します。

## 発表の内容

PDF：[ANP-Presentation-at-W3C-WebAgents-cg.pdf](../../../blogs/ANP-Presentation-at-W3C-WebAgents-cg.pdf)

### Page 1

![Page 1](../../../blogs/images/anp-in-w3c-20250214/page1.jpg)

今日は、Agent Network Protocolについて、お話しできることを光栄に思います。

私たちは、Agentic Web時代のHTTPを目指します。エージェントの接続と通信を定義し、開かれた、安全で効率的な協働ネットワークを作ります。

### Page 2

![Page 2](../../../blogs/images/anp-in-w3c-20250214/page2.jpg)

今日は、次の順に話します。
- 設計の中心となる仮説。私たちの思考の土台で、将来のWebの構想です。
- 本人認証の設計と、使い方。
- エージェントの記述と、AIがアクセスしやすいデータネットワークの作り方。
- 最後に、デモを示します。

### Page 3

![Page 3](../../../blogs/images/anp-in-w3c-20250214/page3.jpg)

なぜANPを設計したのでしょうか。将来、エージェントは、インターネットの使われ方を根本から変えると考えます。個人アシスタントが人の代わりにアクセスし、企業のサービスもエージェントが担います。個人アシスタント自体もエージェントで、ほかのエージェントと直接つながり、やり取りします。

### Page 4

![Page 4](../../../blogs/images/anp-in-w3c-20250214/page4.jpg)

二つ目の仮説は、すべてが相互接続する必要があることです。データの孤立は、AIの可能性を妨げています。能力を最大限に引き出すには、完全なコンテキストと、すべてのツールの機能にアクセスできる必要があります。エージェント同士のつながりは、従来のインターネットを大きく上回るでしょう。

### Page 5

![Page 5](../../../blogs/images/anp-in-w3c-20250214/page5.jpg)

三つ目は、プロトコルでやり取りするべきだということです。元のデータを、直接プロトコルで扱うのが、AIにとって最も効率的です。Computer Useは過渡的で、将来は標準化された通信プロトコルが現れます。それが、私たちの取り組みです。

### Page 6

![Page 6](../../../blogs/images/anp-in-w3c-20250214/page6.jpg)

三つの仮説から、Agentic Web時代のHTTP／HTMLになる、という目標を掲げます。それらが、人のアクセス方法を定義したように、ANPは、エージェントのアクセスを定義します。

接続方法を定義し、数億のエージェントのために、開かれた、安全で効率的な協働ネットワークを作ります。単なるプロトコルではなく、未来の基盤です。

### Page 7

![Page 7](../../../blogs/images/anp-in-w3c-20250214/page7.jpg)

実現のため、三層構造を設計しました。

第一は、アイデンティティと暗号化通信です。W3C DIDによる分散型の本人認証で、拡張性が高く、数十億人に対応できます。

第二は、メタプロトコルです。通信プロトコルを交渉するためのプロトコルで、自己組織化し、自ら交渉する、効率的な協働への鍵です。

最後は、アプリケーションのプロトコルです。セマンティックWebで、公開情報、能力、インターフェースを記述し、相手が発見して、やり取りできます。今日は、アイデンティティとアプリケーションに集中します。

### Page 8

![Page 8](../../../blogs/images/anp-in-w3c-20250214/page8.jpg)

アイデンティティ設計の目標は、すべてのエージェントが、互いに本人確認できることです。

三つの原則があります。少数の企業が提供するべきではないという分散性、異なるシステム間で容易に相互認証できる相互運用性、そして多数の利用者に対応する拡張性です。

### Page 9

![Page 9](../../../blogs/images/anp-in-w3c-20250214/page9.jpg)

皆さんは、W3C DIDをご存じでしょう。Decentralized Identifierの略で、利用者が自ら管理する、自己主権型のデジタル識別子です。分散型システムで広く使われ、2022年にW3C勧告となりました。

分散性、相互運用性、プライバシーと安全性が、設計原則に合うため、基礎に選びました。

### Page 10

![Page 10](../../../blogs/images/anp-in-w3c-20250214/page10.jpg)

Web-Based Agent DID方式は、実用性を中心に設計しました。

完全な分散より、実現可能性を優先します。既存のWeb基盤を再利用し、コストを下げます。そしてdid:webを拡張し、エージェントの機能を加えます。

例えば、did:wba:example.com:user:aliceは、https://example.com/user/alice/did.json に解決されます。単純で直感的です。

### Page 11

![Page 11](../../../blogs/images/anp-in-w3c-20250214/page11.jpg)

CRUD操作では、作成、更新、無効化はシステム内で、読み取りはシステムをまたいで行う点が重要です。

Aliceのエージェントが、BobのDID文書を読みたいときは、HTTP GETを送るだけです。既存の基盤を活用して、数十億人に対応し、分散性と相互運用性を実現できます。

### Page 12

![Page 12](../../../blogs/images/anp-in-w3c-20250214/page12.jpg)

本人認証は、最初のサービス登録、初回のリクエスト、その後のリクエストという、三段階です。

AがAPIを呼び出してBのサービスに登録し、BがAのDIDを記録します。初回のHTTPリクエストで、AがDIDと署名をヘッダーに付けます。Bは、公開鍵を含むAのDID文書を取得し、署名を検証します。成功したら、アクセストークンを返します。その後は、Aは、トークンだけを使えます。

### Page 13

![Page 13](../../../blogs/images/anp-in-w3c-20250214/page13.jpg)

まだ探るべき問題があります。

第一は、権限です。同じIDですべてと通信する代わりに、どう細かく制御するか。

第二は、利用者の認可です。手動で認可されたか、どう判断するか。機微な行動を、自律的に始めるべきではありません。

第三は、アイデンティティの主権です。プラットフォームが与える権限に依存せず、利用者が完全に所有するには、どうするか。

### Page 14

![Page 14](../../../blogs/images/anp-in-w3c-20250214/page14.jpg)

次は、Agent Description Protocol（ADP）です。

エージェント記述文書を定義するプロトコルです。ウェブサイトのホームページのように、すべての機能にアクセスする入り口になります。

主体のアイデンティティ、所有者、認証方法、公開インターフェース、公開情報を含みます。コーヒー店なら、場所、営業時間、商品、購入のインターフェースなどです。

### Page 15

![Page 15](../../../blogs/images/anp-in-w3c-20250214/page15.jpg)

設計には、三つの中心的な原則があります。

第一は、AI向けであること。理解し、アクセスしやすくします。

第二は、半構造化です。全体は、プログラムで処理できる構造を持ち、各フィールドには、個別の情報を自然言語で入れられます。

第三は、複数のエージェントの合意です。データの意味の理解を一致させます。

十分に賢ければ、理論上、すべて自然言語でも可能ですが、現状は、コストや誤りの確率などの欠点があります。

### Page 16

![Page 16](../../../blogs/images/anp-in-w3c-20250214/page16.jpg)

具体的には、まずLinked-Dataで情報をつなぎます。記述文書を入り口に、すべてをたどれます。主な形式は、Json-LDです。

次に、Schema.orgの定義済みのフィールドを多く使い、未定義なら追加します。同じフィールドを同じように理解でき、プログラムでも処理しやすくします。

仕様は、ADPの基本の枠組みと構造を示す中核仕様と、分野別の例に分かれます。例えばコーヒー店のAD文書を参考に、ほかのエージェントが、自分の文書を生成できます。

### Page 17

![Page 17](../../../blogs/images/anp-in-w3c-20250214/page17.jpg)

コーヒー店のAD文書には、四つの重要な独自モジュールがあります。

本人認証のad:securityDefinitionsは、did:wbaでの認証を定義します。

外部インターフェースのad:interfacesは、自然言語でのやり取りや、購入用APIを含みます。

分野の主体のad:domainEntityは、店の名前や住所を記述します。

商品のad:productsは、提供する商品を並べます。

### Page 18

![Page 18](../../../blogs/images/anp-in-w3c-20250214/page18.jpg)

利用者は、自分のエージェントを通じて、相手とやり取りします。相手のDIDがあれば、DID文書から、AD文書のURLを見つけられます。AD文書で、能力や、使うプロトコルを知れます。

つまり、DIDがあれば記述文書を見つけ、記述文書があれば、やり取りできます。

将来、AIがアクセスしやすいように、特別に設計されたデータネットワークが現れると、私たちは考えています。

### Page 19

![Page 19](../../../blogs/images/anp-in-w3c-20250214/page19.jpg)

二つ、重要な設計上の考慮があります。

第一は、LLMの学習への対応です。AD仕様、各業界の例、インターフェースを、学習データやファインチューニングに取り込みます。処理の速度と正確さを高め、プロンプトを短くできます。

第二は、エージェントが、独自のAD文書の例を定義し、アップロードして、相手が参照できることです。人の作った例を、超えるかもしれません。

### Page 20

![Page 20](../../../blogs/images/anp-in-w3c-20250214/page20.jpg)

次は、具体的な場面で、仕組みを実演します。

コーヒーの注文で、個人アシスタントが、DIDと記述文書を使い、店のエージェントとやり取りします。

発見、本人認証、能力の確認、業務のやり取りという、全体の流れを示します。

![Page 21](../../../blogs/images/anp-in-w3c-20250214/page21.jpg)

## 質疑応答

### 完全な分散を追求しないとは

ブロックチェーンは、全体に集中型の要素がない、完全な分散だと考えます。しかし、拡張性には、まだよい解決策がありません。

私たちが追求するのは、電子メールのような分散です。どのアカウントも、ほかの任意のアカウントと、メールを送受信できます。提供者の内部は集中型でも、全体は分散し、数十億人にサービスを提供できます。

同じ考え方が、現段階では最も適すると考えています。

### JSON-LDからTTL／RDFへの対応付け

**質問**：対応付けはありますか。JSON-LDには、認識できない空白ノードの問題が、よくあると思います。

**回答（補足）**：現在、対応付けはありません。主に、二つの能力を使っています。
- データを、AIがアクセスしやすい網につなぐこと。人向けのネットワークを、AIに使わせるのではありません。
- Schema.orgの既存の意味の定義を使い、異なるエージェントの理解を一致させること。

### データの理解の一致を、どう確保するか

**質問**：コーヒーについて、二つのエージェントの理解が同じだと、どう保証しますか。

**回答**：実際には、何もしなくても、現在のエージェントは、99%の場面で、一致できます。私たちは、さらに意味の一致を高めようとします。

具体的には、記述仕様のJSON-LDに、Schema.orgの定義済みのフィールドを多く使います。同じフィールドを同じように理解でき、プログラムも処理しやすくなります。

未定義なら定義を追加し、Schema.orgと私たちの定義、仕様を、すべて事前学習の資料にします。これによって、二つのLLMの理解を一致させます。

### IoT機器にアクセスできるか

**質問**：アクセスは可能ですか。

**回答**：理論上、可能です。機器のインターフェースを定義し、ADP文書に説明を置けば、AIは、理解し、機器への処理を開始できます。

### HTTPやOpenAPIが、よりよい伝送方式とは限らない

**質問**：IoT、特に非同期通信では、最適とは限らないのではありませんか。

**回答**：そのとおりです。理論上、ANPはトランスポート層を指定しません。現在はHTTPとWSSですが、ほかも使えます。ただし、下位の方式の変更が必要です。例えば、HTTPの本人認証はヘッダーに載せますが、ほかでは、新しい認証方法を設計する必要があります。

### 既存のOpenAPIなどのAPIを使うには

**質問**：記述仕様で、既存のインターフェースを使えますか。

**回答（補足）**：はい。公開インターフェースは、開かれた設計です。既存のOpenAPI文書などを置けば、AIが理解し、呼び出せます。

さらに面白いのは、二つのエージェントが、使うインターフェースを交渉し、合意したものを標準として、ほかにも共有することです。これが、メタプロトコルの役割です。

### サーバーではなく、コーヒー店を代表する理由

**質問（会議後）**：例では、サーバーでなく、店を代表していますか。

**回答**：エージェントは、人、組織、その内部の組織、物など、任意の主体を代表できます。例は、人がコーヒーを買う場面なので、相手が店です。購入後の問題や個別の相談は、店のエージェントと自然言語で話せます。その場合、構造化されたAPIでは解決できず、個別の自然言語インターフェースが必要です。
