# W3C-WebAgendas-CG 講演

2025年2月14日、長尾ウェイとジェームズ・ワーグが、エージェントネットワークプロトコル(ANP)のオープンソースコミュニティに代わってW3C WebAgents CG会議でAMPにプレゼンテーションを行いました。

W3C WebAgents コミュニティは、Web アーキテクチャと一貫した MAS の新しい種類を構築するために設計された Web ベースのマルチスマート システム (MAS) の設計に焦点を当てています。これにより、広範な受け入れを得るためにシステムの透明性とトレーサビリティを確保しながら、Web のグローバル、オープンおよび持続可能な機能を継承します。このコミュニティには、リンクされたデータやセマンティックな Web 規格を使用して、さまざまな企業間で統一された相互作用を促進するための特別な焦点があります。人的サービス(HMAS、人工知能、AI、人工技術)[https://www.w3.org/community/webagents/](https://www.w3.org/community/webagents/).

AMP テクノロジーの概念は WebAgents コミュニティと並んで多く、データやセマンティクスを連携させることも見かけています。AMP は webAgent コミュニティの議論を使用して設計されています。

講演は長尾とJmaes Wahghの共同制作で、PPTやプレゼンテーション、会議でのディスカッションなど、以下の発表を行いました。

id:wba CRD の動作を見てみましょう。システム内で作成、更新、解凍を行う重要な機能は次のとおりです。システム全体で読み上げが行われます。

例えば、アリスのスマートボディがBobのDIDファイルにアクセスしようとすると、HTTP GETリクエストのみ起動できます。この設計は既存のWebインフラストラクチャをフル活用し、ユーザーの数億をサポートし、インテリジェントなアイデンティティの相互運用性を低下させています。

### ページ 12

![ページ 12](../../../blogs/images/anp-in-w3c-20250214/page12.jpg)

id:wba の識別プロセスを見てみましょう。全工程は、初期サブスクリプション、最初のリクエスト、その後のリクエストの 3 つの段階に分けられます。

まず、API の購読者 B サービスを呼び出すと、B は A-ID を記録します。その後、最初の HTTP リクエストでは、A にはヘッダーに DID と署名が格納されます。要求に応じて、B は A で DID 文書を DID のドキュメントから受け取る、パブリックキーを使用して署名を確認します。検証が完了すると、B はアクセストークンを返します。その後のリクエストでは、このトークンを使用するだけです。

### ページ 14

![ページ 14](../../../blogs/images/anp-in-w3c-20250214/page14.jpg)

ANPの別の重要なモジュールに行きましょう:エージェント防衛生産(ADP)。

ADPとは?スマート文書を定義するプロトコルです。このドキュメントは、ウェブサイトのホームページのようなスマートボディのホームページとして考えられます。これにより、すべてのスマートボディの機能にアクセスすることができます。

スマートボディは、ドキュメントに含まれるものについて説明します。それは、それが所属する組織のアイデンティティ、所有者、認証方法、外部インターフェイス、および公開情報を含みます。例えば、このインテリジェントな人はコーヒーショップを表す場合、そのオープン情報は、位置、ビジネス時間、製品リスト、購入インターフェースなどの情報が含まれます。

### ページ 15

![ページ 15](../../../blogs/images/anp-in-w3c-20250214/page15.jpg)

ADPの設計は3つの中心の主義に基づいています。

第一にAI指向の設計です。プロトコルはAI用に特別に設計されており、理解しやすくアクセスしやすいようにします。

第二は、プロセス処理を容易にするために構造化された設計の一般的な使用である半構造の合意です。 そして同時分野は、個別化情報の伝達を促進する自然な言語を含むことができます。

3 つはマルチスマートコンセンサスです。インテリジェントな身体におけるデータのセマンティックスの理解の一貫性を高めるために。

理論的には、十分にスマートであればADPは自然言語を完全に使うことができます。しかし、このアプローチは、コスト、エラーレートなどの現在の段階で多くの欠点を持っています。

### ページ 16

![ページ 16](../../../blogs/images/anp-in-w3c-20250214/page16.jpg)

ADP デザインが何であるかを見てみましょう。

まず、Linked-Data技術を利用しています。インテリジェントなボディから情報を接続するために使用します。スマートエンティティティはエントリポイントとして文書を記述し、関連するすべての情報を通過することができます。Jason-LDをメインのドキュメントフォーマットで選択します。

その後、Schema.org があります。 Jason-LD のフィールドは、Scheema.org の定義済みフィールドに大きく使用されます。未定義のフィールドに遭遇した場合は、定義を追加します。これにより、複数のインテリジェントが同じフィールドを理解し、より簡単に処理されるようにします。

最後に、規範は2つの部分に分けられます。コアのADP例は標準と領域です。コア規範は、フィールドの例セクションでは、コーヒーショップのAD文書などのさまざまな分野におけるAD文書の例を記述していますが、他のインテリジェントな組織は独自のドキュメントを作成することを参照することができます。

### ページ 17

![ページ 17](../../../blogs/images/anp-in-w3c-20250214/page17.jpg)

特定のコーヒーショップADファイルでADPを理解しましょう。このドキュメントには4つの重要なカスタムモジュールが含まれています。

最初に、ID 情報モジュール(ad:security 条件)で、d:wba を使用して認証を行なう方法を定義します。

2 つは、外部インタフェース モジュール (ad:interfaces) で、API の定義と、自然言語の相互作用とインターフェイスの購入が含まれています。

第三は、スマートボディが、名前、住所などに対応するコーヒーショップの情報を説明するフィールドエンティティティ(ad:domainEntity)です。

4 つは、コーヒーショップから製品をリストする製品情報モジュール(ad:products)です。

![ページ 18](../../../blogs/images/anp-in-w3c-20250214/page18.jpg)

今後、AI専用のデータネットワークであるデータネットワークが誕生し、AIがアクセスしやすいようにするという確信をもちます。

## 質問と回答セッション

### 完全なまともな化を求めていないのは?

ブロックチェーンプログラムを完全に集中化し、構造全体に集中したモジュールがない場合に表示されます。しかし、ブロックチェーンの拡張問題はまだ良い解決策ではありません。

そのため、私たちが求める暗黙は、このようなブロックチェーンの完全な集中化ではなく、電子メールの集中化ではありません。つまり、任意の電子メールアカウントは別の電子メールアカウントと交換することができます。電子メールサービスプロバイダが一元化されていますが、全事業は分散され、それは十億度のユーザーを勤めながら、互いに接続します。

中心に行き、同じ考えをメールとデザインします。この段階で一番適切な選択肢だと思います。

### json-LD -> TTL/RDF マップの問題

詳細な質問:json-LD-> TTL/RDFマップはありますか? 私の意見では、Jason-LD設計は通常、認識されていない空白ノードの問題があります

回答(サプライヤー): json-LD-> TTL/RDFのマップは時間内にありません。JSON-LDは、主に2つの機能を使用しています。
- データ接続:AIが人のために設計されたネットワークにアクセスできるようにするのではなく、AIに簡単にアクセスできるネットワークにデータリンクを作成できます。
- 共存理解の一貫性:セマティクスネット技術の使用は、さまざまなインテリジェントな体内での構文理解の一貫性を高めるためにSchema.orgとして定義されています。

### データの理解の一貫性を確保するための方法

質問は詳細です: 2つのインテリジェントな人々は同じ方法でコーヒーを理解していることを保証する方法は?

回答:実際には、何もしない場合でも、スマートは、シーンの99%で一貫した方法でコーヒーを理解することができます。 私たちがする必要があることは、 2つのインテリジェントが均一な方法でコーヒーを理解していることを確認するために、より詳細な理解を向上させることです。

具体的には、スマート・デリバリー・コードJSON-LDの設計では、現在のセマンティック・ネットワークは、複数のインテリジェントが一貫した方法で同じ分野を理解し、より高度に有用であることを確認するSchema.orgフィールドを定義するために広く使用されました。

定義されていないフィールドがある場合、Schema.orgの定義、定義、私たちの規範を全てLLMから学習できるように事前訓練材料として再定義します。このようにして、LMは同じフィールドを一貫した方法で理解しています。

### アクセシブルなネットワーク機器

詳細な質問:インターネットは、インテリジェントな身体に利用可能な商品へのアクセスですか?

A: 理論的にアクセス可能です。AIは、オブジェクトネットワークデバイス用のインターフェイスを定義し、ADP(インテリジェント・説明プロトコル)文書のインターフェースの説明を記述する限り、オブジェクト・ネットワーク・デバイスを理解し、開始します。

### http と OpenAPI は必ずしもより良い伝送プロトコルではありません。

詳細な質問:インターネットのコンテキストでは、特にウォークインに直面した場合は、HTTPとOpenAPIは必ずしもより良い伝送プロトコルではありません。

A: はい。ANPは、現在HTTP、WSS、その他のプロトコルに転送レイヤープロトコルを必要としません。しかし、ボトムアッププロトコルにはいくつかの変更が必要です。例えば、HTTP認証情報はHTTTPヘッド上に行われているため、他のプロトコルでは新しい識別プログラム向けに設計されています。

### 既存の OpenAPI 規範など、既存の API インターフェイスを使用する方法

詳細な質問: スマートボディの説明の面では、OpenAPIインターフェイスなど、現在使用されているインタフェースは使えますか?

回答(追加回答): はい。スマートボディ説明規制では、インテリジェントなインターフェイスは、OpenAPIインターフェース文書などの既存の規範の統合をスマートボディ説明プロトコルに可能とし、AIは理解し、これらのインタフェースの呼び出しを開始しています。

これは状況です。2つのインテリジェントなボディがコミュニケーションをとり、他のスマートのノームとして交渉されたインターフェイスを共有したいというインターフェースを互いに交渉できる別のものを持っている方が、よりエキサイティングだと思っています。それはメタアグリーメントが何をしているかです。

### コーヒーショップを代表するスマートボディは、サーバーではなく、なぜですか?

詳細な質問(ポストセッションの問題):例えば、スマートボディはサーバーではなくコーヒーショップを表していますか?

この場合、スマートはコーヒーショップを代表しています。なぜなら、私たちはコーヒーカップを購入し、コーヒーショップとやり取りするシーンを持っているからです。 人間の知性は、アフターセールスの問題、パーソナライズ問題などの自然言語でしっかりしたスマートな操作に役立ちます。 構造化されたAPIはこの時間を解決できません。パーソナライズされた自然な言語インターフェイスを必要とする。
