# 最適なスマートボディ認証技術:OpenID Conect、APIキー、wba

## スマートは新しいI.D.の技術を必要とします。

特に、インテリジェントによって転送されるアイデンティティベースの技術のための新しいニーズの最も重要なことは、接続性です。

原則は簡単です:AIは、**完全なコンテキスト情報とすべてのツールにアクセスする機能を取得する機能**これは、それが適切かつ適切に作ることができる方法です。 多くのメーカーは今、この問題を解決するためにコンピュータ使用プログラムを使用するしようとしています。

<p align="center">
  <img src="../../../blogs/images/computer-use-product.png" width="50%" alt="computer use product"/>
</p>

しかし、インターネットとやり取りする最も効率的な方法ではないと思います。AIが人間のような方法でインターネットにアクセスできる方法であり、それが最善を尽くす(APIまたは通信プロトコル)デジタルワールドと相互作用する必要があります。

<p align="center">
  <img src="../../../blogs/images/agent-interview-Internet.png" width="50%" alt="agent-interview-Internet"/>
</p>

これは、接続の質問を含みます:APIまたはプロトコルがスマートボディによって使用されるときの認証方法、インターネットや他のインテリジェントな身体と相互作用する?特に、クロスプラットフォーム識別は、任意のインテリジェントな人物が接続できるように行われます。

## 現在の主流のクロスプラットフォーム認証技術

プラットフォーム間で多くのケースで使用できないインターネット上のID番号があります。あなたのマイクロ・インテリジェンスアカウントと同様に、ネイルシステムやその逆に識別できない。

しかし、インターネット上では多くのクロスプラットフォーム認証技術があり、当社の共通SSOのようなもので、Googleアカウントでたくさんのウェブサイトにログインすることができます。また、APIキーは、例えばOpenAIのKeyをあなたに使用したり、OpenAIのAPIにアクセスしたりできます。スマートな人のアイデンティティに合った技術を簡単に説明します。

### OpenID Connect(OIDC) の接続

OpenID Contact(OIDC)は、クライアントアプリケーションがユーザーのアイデンティティを検証し、ユーザーの基本的な情報にアクセスできるようにする OAuth 2.0 に基づく認証プロトコルです。OIDC は、標準の識別レイヤーを OAuth 2.0 に追加して、ログインとシングルポイント ログイン (SSO) シナリオに適しています。

[OpenID は公式の規則を接続します](https://openid.net/specs/openid-connect-core-1_0.html)。

今回は、Googleアカウント番号を使って、このサイトを実際にどのようにして実行しているかの例としてアクセスします。[Google ODCの公式ドキュメントアドレス。](https://developers.google.com/identity/protocols/oauth2/openid-connect)。

<p align="center">
  <img src="../../../blogs/images/openid-connect-fllow.png" width="50%" alt="openid-connect-fllow"/>
</p>

Googleアカウント番号を使用して3ウェイのウェブサイトは、2つの部品、プリプロセスとOouth 2.0プロセスで構成されています。
- プリプロセス
  - 会員登録 Google Platform アカウント
  - 項目/適用を作成して下さい
  - リダイレクトURLを含む項目/アプリケーションの設定
  - OAuth 2.0 へのアクセス
- Outlook 2.0 プロセス (認定コードのプロセスの場合)
  - 認証番号を取得する
  - アクセストークンとidトークン、idトークン
  - アクセストークンとIDトークンアクセスで、ユーザーの詳細(オプション)を取得します。 OpenID Conectプロセスでは、ユーザーの詳細は保護されたリソースとみなされます。

OpenID Connectの利点は次のとおりです。
- 簡略化されたユーザー識別プロセスを有効にする
- 用途は非常に広く、関連インフラが整備されています。
- より安全です。

インテリジェントな相互接続性に関するコンテキストでは、OpenID CONNECTにはいくつかの欠点があります。
- OpenID コンタクトは、ユーザーが ID サーバー(Google など)を使用して識別できる3つの方法のアプリケーションです。
- OpenID Connectは、ユーザーが登録のためにアイデンティティサーバーに行く必要がある中央プログラムです。複雑な事前操作プロセスで。
- プロセスは複雑で、複数のインタラクションが必要です。

### APIキー

APIキー(APIキー)は、アプリケーションやユーザーを「アプリケーションプログラミングインターフェイス(API)」に有効化するためのシンプルなドキュメントです。通常、ランダムに生成された文字と数字で構成された文字列ベースの識別子で、パスワード機能に似ています。ID認証、アクセス制御、および監視設定で使用できます。

<p align="center">
  <img src="../../../blogs/images/api-keys-flow.png" width="50%" alt="api-keys-flow"/>
</p>

API Keys を使用してユーザー ID を認証するプロセス:
- プリプロセス
  - プラットフォームに移動し、アカウント番号を登録します。
  - Fetch API キー
- APIキーの検証プロセス
  - 類似するセキュリティプロトコルのヘッダに API キーを追加
  - クライアントのAPIキーをサービス・パフォーマンス


API キーの利点は次のとおりです。
- 簡単、達成しやすく、対話型が少なくなります。
- 相互プラットフォームのアイデンティティをサポートし、PPI キーを持っている限り、互いに2つのアプリケーションで検証することができます
- APIサービスは、OpenAIやナショナルモデルAPIなど、広く利用されており、そのほとんどは識別用のAPIキーを使用します。

インテリジェントな相互接続性に関するコンテキストでは、API キーにはいくつかの欠点があります。
- セキュリティは低いです。APIキーを使用する多くのMCPサービスャーは、ユーザーが設定文書にAPIキーを書くように要求し、漏れの危険性を伴います。

<p align="center">
  <img src="../../../blogs/images/mcp-server-api-key-example.png" width="50%" alt="mcp-server-api-key-example"/>
</p>

- 事前処理やユーザログインなどは必須です。

## W3C DID ベースの認証技術: wba

### W3C の DID?

W3C DID(集中識別子、ID)は、従来の中央集中型アイデンティティ管理システムの依存性に対応するように設計された新しい非集中識別子規格です。 2022年に推奨基準として発行されます。[https://www.w3.org/TR/did-core/](https://www.w3.org/TR/did-core/)

最近ホットブルースキーとして知られるW3C DIDを使用して、すでに多くのアプリケーションがあります, まともなTwitterアプリケーション.

### どうすればいいですか?

やる: wba は[エージェントネットワークプロトコル(ANP)](https://github.com/agent-network-protocol/AgentNetworkProtocol)メソッドのコードを定義します。これは、Webインフラストラクチャに基づいており、これは、集中型識別を提供し、特にインターエージェントのアイデンティティのために設計されています。[d:wba方法論的仕様](https://github.com/agent-network-protocol/AgentNetworkProtocol/blob/main/chinese/03-did%3Awba%E6%96%B9%E6%B3%95%E8%A7%84%E8%8C%83.md)。

非常に同様のビジネスをした:メール:各プラットフォームには独自のアカウント番号がありますが、異なるプラットフォーム間で識別し、通信するのは非常に簡単です。 彼らは大規模なユーザーをサポートし、集中しながらWebインフラストラクチャに基づいています。

SmartA が SmartB のサービスにサブスクリプションを購読し、コールするのと同様に、認証および要求プロセスは次の通りです。

<p align="center">
  <img src="../../../blogs/images/did-wba-flow.png" width="75%" alt="did:wba-flow"/>
</p>

- プリプロセス
  - Smart A は、Smart B のサービスのサブスクリプションを最初に呼び、その署名を持つ DID をスマート A で実行し、A 開始サブスクリプションであることを知ったので、Smart A のサブスクリプションです。API サブスクリプションを使用すると、登録、ログイン、設定などの複雑な必須プロセスを削除し、2 つのスマート間で接続するコストを削減できます。
- 認証プロセス
  - SmartA は、http で最初のリクエストの頭に A DID とシグネチャを運ぶ。
  - スマートBは、サイトの頭部からA DIDと署名を抽出し、A DIDサーバーにA DIDの文書を取得するためにアクセスします。
  - SmartB は DID ドキュメントを受け取り、A の DID 文書の公開鍵を使用して A のシグネチャを検証します。
  - 検証後、スマートBは業務リクエストを処理し、運用データを返しながらアクセストークンに戻ります。
  - Smart A は、フォローアップリクエストでアクセストークンを運び、スマート B はアクセストークンの認証を完了します。

wba 識別プログラムメリット:
- セキュリティーレベルが高い。
- 大規模なユーザーや実装性をサポートするWebインフラのフル活用
- あらゆる2つのインテリジェントなボディやアプリケーションを識別できる中央設計です。
- プリエントリープロセスは、マニュアルユーザー登録と手動ユーザログイン設定なしのシンプルです。
- 認証プロセスはシンプルで、インタラクション数が増えません。

もちろん、wbaには欠点がいくつかあります。その最大のものは、2022年に発行された規範として、インフラは十分に開発されず、アプリケーションは比較的限られています。しかし、私たちはブルースキーのようなスターケースを見ることができます。

## コントラスト: wba 対 OpenID コンタクト/ API キー

スマートボディ識別の観点から、コントラストは:wba と OpenID CONNEC, API キーをしました。
- 安全:wbaとOpenID Conectは、APIキーよりも高いセキュリティが同じです。
- 複雑性: OpenID Connectは、最も複雑性が高く、API Keysには最低の複雑性があり、その間に:wba が実行されています。
- インターアクティブ: 少なくとも 対話型:wba と API キー、OpenID の概念との最も相互的な。
- プリプロセス:wbaはユーザマニュアル処理なしで、OpenID接続とAPIキーを手動で処理する必要があります。
- 中心に行く:wbaとAPIキーは、すべてのインテリジェントな人やアプリケーションが互いに通信することを可能にします。 OpenID接続はこの操作を行うことができません
- アプリケーション: OpenID Connect と API Keys は、スコープ内での比較的新しく限定されているながら、より広範な機能を備えています。

全体的な比較は次の通りです:
| 比較優位      | 行なった:wba          | OpenID 接続 | APIキー      |
|:-------|:--------|:---------------|:---------|
| セキュリティー      | グレード               | グレード             | メディス          |
| 複雑さ      | メディス             | グレード             | 低いです            |
| 相互作用の数    | ダウンロー               | 詳しくはこちら             | ダウンロー            |
| プリプロセス    | シンプル。マニュアルなし。     | 複雑な。手仕事を必要としています。   | 中型、マニュアル。  |
| 中央へ。    | あり。               | あり あり             | あり。            |
| 応用範囲    | 限定商品             | ワイド           | ワイド          |


上記から見ることができるように、id:wbaは、インテリジェントな相互接続だけでなく、OpenID Connect セキュリティとAPIキーのシンプルさ、大規模なユーザー使用をサポートしています。 一緒に取りました。 一緒にしました。

もちろん、OpenID Connect と API Keys は独自の役割を担っています。例えば、元のインターネットシステムに接続するときに、Smarts は OpenID Connect や API Keys を使用する必要があるかもしれません。
