# OpenAI のオペレーターによる AI とインターネット間の対話のための 4 つの技術ルートを見てください。

OpenAI の Operator がリリースされ、インテリジェント エージェントに関する激しい議論が再び引き起こされました。

Operator とは何かを紹介する記事がたくさんあります。公式ウェブサイトの紹介文もご覧ください: https://openai.com/index/computer-using-agent/。

簡単に言えば、オペレーターはブラウザーまたはコンピューターを操作して、日常のさまざまなタスクを完了するのに役立ちます。その最大の意義は、AIを現在のインターネットの世界と結びつけることができるということです。

この記事では主に、AIとインターネットの相互作用に関して現在出現している4つの技術ルートを比較してまとめています。この記事の要点は次のとおりです。

-  AI とインターネット間の対話のための現在の技術的ルートには、コンピューター使用エージェント、ヘッドレス ブラウザー (ヘッドレス ブラウザー)、クライアント側 API、およびリモート API/プロトコルが含まれます。
- Computer Use Agent: AI がインターネットにアクセスする能力を迅速に獲得できるようにします。オリジナルのアプリケーションは変更せずに AI にアクセスできます。ただし、このテクノロジは運用コストが高く、非同期タスクを実現できません。
- ヘッドレスブラウザ: タスクを非同期に実行でき、ランニングコストが低くなりますが、アクセスできるのはWebアプリケーションのみであり、Webアクセスの維持には一定のコストが必要です。
- デバイスサイド API: AI 携帯電話の現在の主流ソリューション。 APP は携帯電話上の API を携帯電話上の AI アシスタント (Siri など) に開き、AI アシスタントは API を呼び出してインターネットにアクセスします。このメソッドは非同期タスクを実行でき、優れたエクスペリエンスを提供します。ただし、これは携帯電話と APP のシナリオにのみ適用され、APP のオープン性に依存します。
- リモート API/プロトコル: これは AI がインターネットにアクセスするための最良の方法です。タスクを非同期に実行でき、ランニングコストが低く、自動 ID 認証をサポートします。ただし、アプリケーションの連携やバージョンアップが必要で、アクセスコストが高くつきます。
-  短期的には、Computer Use Agent (CUA) とヘッドレス ブラウザ テクノロジにはさまざまな制限がありますが、適切なシナリオが見つかれば、これら 2 つのテクノロジはすぐに実装され、商業的価値を生み出すことができます。
-  長期的には、最高のユーザー エクスペリエンスと最低の運用コストを提供できる API/プロトコル テクノロジーのルートについて、私たちは断固として楽観的です。元のシステムを変革するコストについては、AI のプログラミング能力が向上するにつれて、変革にかかるコストは徐々に低下すると考えています。プロトコルの標準化の問題については、将来必ず標準プロトコルが登場すると考えております。
-  さらに、私たちはプロトコル ソリューションの実装の可能性を模索しており、一定の進歩を遂げています。

## コンピュータ使用エージェント (CUA)

CUA テクノロジーの基本原理は、画面イメージをインターセプトし、モデルの視覚機能を使用してボタン、メニュー、テキスト フィールド、およびグラフィカル ユーザー インターフェイス (GUI) 内のその他の要素を識別することによって、人間の画面の視覚的理解をシミュレートすることです。

次に、仮想カーソルとキーボード入力を通じてインターフェイスと対話し、クリック、テキスト入力、スクロールなどの操作を実行して、AI、アプリケーション、インターネット間の対話を実現します。

この手法にはいくつかの利点があります。

1. 最大の利点は、** によって AI がインターネット ** と即座に対話できるようになり、今後 AI が多くのタスクを完了できるようになることです。

現在のインターネットは人間がアクセスできるように設計されています。 AI に人間をシミュレートさせるのが、AI がインターネットにアクセスする最速の方法です。

AI がインターネットに接続されると、現在の AI ツールの機能不足が解決され、人々が多くの貴重なタスクを完了できるようになります。商用実装も加速できます。

2. **データサイロを打破する**

CUA テクノロジーは、人とインターネットの間にパーソナル アシスタントを追加することにも相当します。このパーソナル アシスタントは既存のデータ アイランドを破壊し、ユーザーのすべての情報にアクセスできます。これにより、ユーザーはより賢明な意思決定を行うことができます。

3. ** アプリケーション修正コストが低い **

基本的に、AI で使用する前にアプリケーションを変更する必要はありません。

もちろん、このテクノロジーには明らかな欠点もいくつかあります。

1. **高い運用コスト**

CUA テクノロジーはモデルの視覚機能に依存しており、画像処理によりランニング コストが比較的高くなります。高価値のシナリオは実行できると思いますが、このテクノロジーを一般的な C サイドのユーザー シナリオに推進したい場合、課題はまだ非常に大きいと思います。

2. ** を非同期にすることはできません **

CUA テクノロジーは画面キャプチャに依存しており、コンピューター制御を AI に引き渡す必要があります。現時点では、人間はコンピュータを使用できません。

理想的なエクスペリエンスは、エージェントがタスクを非同期的に実行することです。たとえば、タスクがあると、AI アシスタントがバックグラウンドで処理します。処理が完了した後、または人間の介入が必要な場合、AI アシスタントは人間に介入するように通知します。

3. **頻繁なログイン操作が必要です **

C 側のシナリオでは、CUA は依然としてアプリケーションに入るときにユーザーにログインを要求し、ID 検証を自動的に完了することはできません。

4. **精度の問題は短期的に解決する必要があります**

CUA は、単純な Web ページ タスク (87%) では良好に機能しますが、複雑なローカル操作 (38.1%) や動的な Web ページ インタラクション (58.1%) では依然として明らかな欠点があります。

最後に、アプリケーション シナリオに関して言えば、**CUA は最初に B サイド シナリオ、特に一部の高価値でパーソナライズされたシナリオ ** に実装される可能性が最も高いと思います。操作が完全に反復的な場合は、RPA の方が適している可能性があります。

C 側のシナリオでは、プロフェッショナル ユーザー (ビデオ編集者など) が適切な着陸シナリオとなる可能性があります。

通常の C エンド ユーザー シナリオでは、運用コストやユーザー エクスペリエンス、さらには他の技術ルートとの競合により、CUA にはあまり競争力がない可能性があります。

## ヘッドレスブラウザ

ヘッドレス ブラウザは、グラフィカル ユーザー インターフェイス (GUI) を持たないブラウザです。コマンド ラインまたはプログラミング インターフェイスを通じてバックグラウンドで実行され、従来のブラウザと同じ操作 (Web ページの読み込み、JavaScript の実行、ページのレンダリングなど) を実行できますが、ビジュアル インターフェイスは必要ありません。

ヘッドレス ブラウザは AI のインターネット接続にどのように役立つでしょうか?
- Puppeteer などのヘッドレス ブラウザ フレームワークを使用して、Web アプリケーションの完全なページ データを取得できます (レンダリングせずにデータ コンテンツのみを取得します)。
- 次に、AI を使用してページ データを処理し、指定された操作を完了するために必要なページ要素を見つけます。
- AI または手動で記述されたコードを使用してヘッドレス ブラウザ フレームワーク API を呼び出し、ページ要素を操作して自動操作を実現します
- 上記のコードをAIのツールとして使用し、AIに呼び出して、AIがインターネットにアクセスできるようにします。

**ヘッドレス ブラウザ ソリューションの利点は **:

1. ** は** の非同期タスク処理を実現できます

ヘッドレス ブラウザはバックグラウンドで実行されるため、ユーザーのコンピュータの制御を掌握する必要はありません。タスクはバックグラウンドで非同期に実行でき、人間の介入が必要な場合にのみ通知されます。

2. ** は Web アプリケーションに適しており、アプリケーションの変更が必要ありません **

AI がインターネットにすばやくアクセスできるようにする Web アプリケーション。

3. **CUA技術**より運用コストが低い

テキストを処理し、コードを事前に記述することにより、ヘッドレス ブラウザ ソリューションのランニング コストは、ビジュアル機能に依存する CUA テクノロジよりも低くなります。

**ヘッドレス ブラウザ ソリューションの欠点は **:

1. ** は Web アプリケーションに限定されます **

Web 上で実行できないすべてのアプリケーションには、ヘッドレス ブラウザ ソリューションはアクセスできません。コンピューター上のローカル アプリケーションなど。 CUA にはこの制限はありません。

2. ** ページの適応コストが高い **

ページ適応には大量のコードを生成する必要があります。同時に、ページのアップグレードや変更により元のコードが無効になり、再生成、テスト、展開が必要になる場合があります。全体的な維持費は高額です。

3. **頻繁なログイン操作が必要です **

CUA の制限と同様に、ユーザーは引き続きログインする必要があり、認証を自動的に完了することはできません。


ヘッドレス ブラウザのもう 1 つの方法は、毎回全量のページ データを LLM に入力し、LLM に処理させることですが、この方法は非効率的でコストがかかりすぎます。このシナリオ専用に垂直モデルをトレーニングできる場合は、それが良い選択となる可能性があります。

ミニ プログラム プラットフォームは、ヘッドレス ブラウザーの実装に適したシナリオとなる可能性があります。ミニ プログラムは基本的に Web アプリケーションとみなすことができます。ミニ プログラム プラットフォームがアカウントの相互運用性の問題を解決できれば、プラットフォームはユーザーのアカウントを直接使用して、人間の介入なしにヘッドレス ブラウザーを通じてミニ プログラムと直接対話する AI アシスタントを構築できます。

## クライアントAPI

デバイス側 API テクノロジーは、オペレーティング システムを通じて標準化されたデバイス機能インターフェイスを開き、AI がセンサー、アプリケーション データ、ハードウェア機能を直接呼び出すことができるようにします。その中心原理は、AI が人間の操作をシミュレートすることなくアプリケーションと正確に対話できるように、システムレベルのインテント対話プロトコルを確立し、それによって AI とインターネット間の対話を実現することです。

**技術実装原則**

1. インテント登録メカニズム

アプリケーションは、オペレーティング システムに呼び出すことができる「スキル インテンション」 (「メッセージの送信」、「スケジュールの作成」など) を宣言し、パラメーターの形式と権限の範囲を定義し、グローバル機能ディレクトリを形成します。 iOS 18 の App Intents フレームワークは、すでに 200 以上のコア機能インターフェイスの登録をサポートしています。

2. セマンティックマッピングエンジン

システムに組み込まれた自然言語理解 (NLU) モジュールは、ユーザーの指示 (「撮った写真をワーク グループに送信する」) を構造化された API 呼び出しチェーンに変換し、フォト アルバム API、アドレス帳 API、インスタント メッセージング API を自動的に関連付けます。

3. セキュリティサンドボックスの仕組み

アプリケーション間のデータ フローは、信頼された実行環境 (TEE) を通じて実現されます。ユーザーから単一の承認を取得した後、AI は複数の API を組み合わせて呼び出すことができます (位置情報サービスとメモに同時にアクセスするなど) が、元のデータはデバイスの外には出ません。

**プログラムの利点**

1. インターフェース変更コストゼロ

アプリケーションは、既存の UI を変更せずに、標準インターフェイスを登録して実装するだけで済みます。さらなる変更は内部関数です。

2. 真の非同期タスク処理

AI はバックグラウンドで複数の API を呼び出すことができ (航空券、ホテル、レンタカーを同時に予約するなど)、ユーザーはいつでも中断できます。

3. パソコン利用エージェントソリューションよりもランニングコストが低い

AI ビジョン機能を使用しないため、Computer Use Agent ソリューションよりも運用コストが低くなります。

**ソリューションの欠点**

1. 深刻な生態学的断片化

さまざまなプラットフォームやメーカーのインターフェイス標準は統一されていません (Android と iOS のアプリ インテントと Honmeng Atomic Services)。

2. アプリケーションの未解決の問題

アプリケーションは携帯電話メーカーと一定の競争関係にあり、アプリケーションがコアデータを携帯電話プラットフォームにオープンすることは困難です。

3. シーン制限

現在、携帯電話上で使用されるアプリケーションが増えており、モバイル プラットフォームを持たないチャットボットはこのソリューションを使用できません。


## リモート API/プロトコル

AI が API またはプロトコルを通じてインターネットと直接対話できるようにします。たとえば、システムに外部に提供される API がある場合、AI は関数呼び出しやツールの機能を使用して API を呼び出し、情報の取得や対話型の操作を完了できます。

元のシステムの API は AI 向けに特別に設計されていません。呼び出しプロセス中に、ID 検証や権限制御などの操作を完了するために、事前にコードを記述してキーを構成する必要がある場合があります。

Anthropic の MCP や当社が設計した ANP など、AI またはエージェント専用に設計されたプロトコルもいくつかあります。彼らの共通の目標は、AI が最適な方法でインターネットにアクセスできるようにすることです。

MCP の正式名は Model Context Protocol です。大規模言語モデル (LLM) と外部データ ソースおよびツール間の通信方法を標準化し、AI システムがコンテキスト情報により効率的にアクセスして利用できるようにし、それによってモデルの応答品質と実用性を向上させることを目的としています。

ANP の正式名は、エージェント ネットワーク プロトコル、https://github.com/agent-network-protocol/AgentNetworkProtocol，是行业首个开源的智能体通信协议。ANP与MCP的区别是，ANP以智能体为中心，每个智能体都具有同等地位，目标构建一个高效的智能体协作网络。

**このソリューションの利点**:

1. ** AI に** で最適な方法でインターネットにアクセスさせます

CUA テクノロジーであれ、ヘッドレス ブラウザーであれ、AI は人間がインターネットをサーフィンするのをシミュレートします。これは、AI がインターネットにアクセスするための最良かつ最も効率的な方法ではありません。 AI は基礎となるデータを直接処理するのが最も得意です。

2. ** はタスク ** の非同期化を実現できます

AI はタスクを受け取ると、電卓の制御を占有することなく、バックグラウンドで API またはプロトコルを通じてタスクを処理できます。

3.**低い運用コスト**

CUA やヘッドレス ブラウザと比較して、API/プロトコルはランニング コストが低くなります。スクリーンショット データを処理する必要も、ページ データ コードを維持する必要もありません。

4. **自動 ID 認証**

DID などの分散型 ID 認証テクノロジーを使用することで、クロスプラットフォームの自動 ID 認証を実現でき、ユーザーは主要なリンク (支払いなど) に介入するだけで済みます。現時点では、私たちが設計した ANP はすでに DID スキームをサポートしていますが、MCP はまだ DID スキームをサポートしていません。

**このソリューションの欠点**:

1. **改造コストが高い**

関連するプロトコルをサポートするには元のシステムを変更する必要がありますが、これがこのソリューションの最大の欠点です。しかし、AIプログラミング技術の進歩により、変革にかかるコストは徐々に低下していきます。

2. ** の分野は初期段階にあり、規格が明確ではありません **

インテリジェント通信プロトコルの分野は、まだ非常に初期段階にあります。業界には既存のソリューションがあまりなく、標準も策定されていません。現在、この分野では多くの研究が行われており、主に Anthropic の MCP と私たちが設計した ANP です。

しかし、国内・国際規格のISOは、W3C、IFAAなどの関連研究にも関わっています。


## インフォメーション

今後3つの技術経路を全体として分析してみましょう。

短期的には、コンピューター使用エージェント(CUA)、ヘッドレスブラウザ技術、エンドサイドAPIはすべて制限されていますが、適切なシーンを見つける限り、素早く商用価値を着陸することができます。

長期的には、API/Protocol技術ルートが最高のユーザーエクスペリエンスと最低限の運用コストを提供するという確信を寄せています。 古いシステムに改装した費用については、AIのプログラミング能力が増加するにつれて、レトロフィットのコストは徐々に減少します。

また、現在、プロトコルプログラムの上陸可能性を模索し、進捗状況を把握しています。
