# インテリジェントエージェントのアイデンティティに関する 3 つの重要な問題: 相互接続、人間による認証、およびプライバシー保護

私たちは基本的に、パーソナルアシスタントからさまざまな専門サービスエージェントに至るまで、エージェントが前例のない方法で私たちのデジタルライフに参加することを確信しています。エージェント間の安全かつ効率的な対話を確保するには、完全な ID システムが必要です。

この記事では、エージェント ID が直面する 3 つの重要な問題について詳しく説明します。
- **相互接続**: すべてのエージェントが通信および共同作業できるようにする方法は、エージェントのアイデンティティに関する中心的な問題です。これにより、デジタルサイロを打破し、AI が真に完全なコンテキストを取得できるようになり、よりインテリジェントなインタラクティブなエクスペリエンスを提供できるようになります。
- **人間による承認**: 機密性の高い重要なリクエストの場合、そのリクエストが人間による手動承認であるか、エージェントによって自律的に開始されたリクエストであるかをどのように判断しますか?エージェントが人間に代わってインターネットにアクセスできるようにする必要がありますが、エージェントの権限を制限することもできる必要があります。
- **プライバシー保護**: エージェントが対話中にユーザーの個人情報を漏洩しないようにするにはどうすればよいですか?

これら 3 つの問題に関するエージェント通信プロトコル Agent Network Protocol (ANP) の考え方と設計を紹介します。

## エージェントのアイデンティティが重要な理由

インターネットの誕生以来、ID 認証はデジタル世界の中核的な問題となってきました。初期のユーザー名とパスワードから、後の 2 要素認証と生体認証に至るまで、認証テクノロジーは進化し続けています。現在、インテリジェント エージェントの時代の到来により、ID 認証は新たな課題に直面しています。

インテリジェント エージェントは、自律性、学習能力、意思決定能力を備えているという点で従来のソフトウェアとは異なります。エージェントのインターネットでは、エージェントは次のことを行う必要があります。
インテリジェント エージェントは、自律性、学習能力、意思決定能力を備えているという点で従来のソフトウェアとは異なります。エージェントのインターネットでは、エージェントは次のことを行う必要があります。

- **デジタル市民として **: 自分のアイデンティティを持ち、他のエージェントやシステムによって認識され、信頼される
- **ユーザーに代わって行動**: ユーザーに代わってさまざまなタスクやトランザクションを実行するための適切な権限を取得します。
- **クロスプラットフォーム コラボレーション **: さまざまなプラットフォーム上のエージェントやサービスとシームレスに対話し、コラボレーション ネットワークを形成します
- **ユーザーのプライバシーを保護**: ユーザーに代わって動作しながら、ユーザーのプライバシーとセキュリティを保護します

「エージェントのインターネットの違い」で説明したように、AI の能力を最大限に発揮するには、完全なコンテキスト情報を取得でき、インターネット上のすべてのツールを呼び出すことができ、得意な方法でインターネットと対話でき、他の AI と効率的に連携できる必要があります。これらすべての前提となるのは、強力で柔軟なインテリジェント ID システムです。

## 主要な問題 1: 相互接続 - アイデンティティの孤立を打ち破る

これはエージェントのアイデンティティに関する最も重要な問題であり、解決が最も困難です。

現在のインターネット環境では、アイデンティティ システムはほとんどがアイランド プラットフォームです。 WeChat アカウントは DingTalk では使用できません。また、Alipay アカウントを使用して JD.com で直接買い物をすることはできません。

エージェントは情報を取得してタスクを実行するためにさまざまなサービス間を自由に移動する必要があるため、このアイデンティティの断片化はエージェントの時代には深刻な障害となります。

あるエージェントが別のエージェントのサービスを呼び出したいが、それらが異なるプラットフォームに属し、異なる ID システムを使用している場合、コラボレーションは非常に複雑になり、ユーザーが手動で複数回介入する必要がある可能性があります。これは明らかに、ユーザーの負担を軽減するというエージェントの本来の意図に反しています。

### 既存ソリューションの分析

ソリューションを探す過程で、私たちはインターネット上のさまざまな既存の ID 認証テクノロジーを比較および研究しました。

- **OpenID Connect**: シングル サインオンに広く使用されていますが、その集中型の特性と複雑なプロセスは、エージェント間の効率的な対話には適していません。基本的に、OpenID Connect は、将来の ID の相互接続や相互運用性を解決するように設計されていません。
- **API キー**: API ドッキングに広く使用されており、シンプルかつ直接的ですがセキュリティが制限されており、ユーザーが手動で登録して構成する必要があります。登録と構成のプロセスにより、エージェントとの対話の効率が低下します。
- **ブロックチェーン・アイデンティティ・ソリューション**: 集中力が高いが、拡張と性能の課題。現在の技術で数十億人のユーザーを支持することで大きな課題となっています。
- **メールプロトコル**シンプルで分散性があり、この集中力は私たちの理想と一貫しています。電子メールプロトコルはメール操作のために設計されており、ボトムフロアでは既存の成熟したWebインフラストラクチャを再確立するためにHTTPを使用していません。
- **ノストラとATプロトコル**最近では、まだ広く使われているわけではありません。ATプロトコルは私にとって非常に良い合意であり、W3Cはそれをしました。この合意に基づいてBlueskyの適用は将来のマイクロインテリジェンスの方法は十分にあるかもしれません。
- **W3C のディッド**W3C は、識別子 (ID) コードを集中化し、2022 年に推奨される標準として公開された ID のカーネル化の問題に対処するように設計しました。インターネットは広く使用されていません。

### W3C DIDは、スマートな人を特定するための最良の方法です。

W3C DIDは、発売以来広く適用されていません。しかし、すべての技術が分析された後、W3C DIDは、最もインテリジェントなアイデンティティテクノロジーであり、それがより優れた新しいものの設計を困難であると確信しています。

理由はいくつかあります。
- W3C DIDは、インテリジェントな身体の接続の必要性に完全一致しているアイデンティティの集中および相互運用性のために意図的に設計されています。
- W3C DIDはより柔軟で、この段階では、下位のまともな化を阻害しません。例えば、DID を達成するためにブロックチェーンが使用されることを必要としません。これにより、開発者により多くのオプションを提供します。
- 既存の成熟したWebインフラを再利用し、スマートに数十億人の人々をサポートすることにより、成長率と重複を低下させることができるdo:webアプローチに基づいてスマートに新しいアプローチを設計しました。

今回、W3C DID規範を基本に、達成方法と組み合わせて、スマートボディに最適なアイデンティティプログラムがこの時期に実現しました。

## 重要な問題2: 人間力の強化 - 重要な操作のセキュリティを確保

エージェントが人間に代わってタスクを実行することが増えるにつれ、エージェントによって行われたリクエストが人間によって手動で承認されるかどうかという重要な問題がますます重要になります。

たとえば、エージェントはユーザーに代わって独立してホテル情報を閲覧できますが、実際の予約や支払いを行う場合は、人間から手動で承認を取得する必要があります。

この区別メカニズムが欠如していると、2 つのリスクが生じる可能性があります。1 つは、エージェントが過度に用心深く、簡単な操作を確認するために頻繁にユーザーの邪魔をすることです。もう 1 つは、エージェントが過度に自律的であり、重要な決定において必要な人間の監督が不足しているため、人間に資産の損失が発生することです。

### did:wba の人間による認証メカニズム

ANP プロトコルは、did:wba 仕様を通じて洗練されたソリューションを提案します。これは、人間の認証と自動エージェントの認証を明確に区別するメカニズムです。

Did:wba のドキュメントでは、特に人間による認証のための公開鍵情報を保存するための `humanAuthorization` フィールドを導入しました。

```json
"humanAuthorization": [
  "did:wba:example.com%3A8800:user:alice#WjKgJV7VRw3hmgU6--4v15c0Aewbcvat1BsRFTIqa5Q",
  {
    "id": "did:wba:example.com%3A8800:user:alice#key-3",
    "type": "Ed25519VerificationKey2020",
    "controller": "did:wba:example.com%3A8800:user:alice",
    "publicKeyMultibase": "z9XK2BVwLNv6gmMNbm4uVAjZpfkcJDwDwnZn6z3wweKLo"
  }
]
```

このメカニズムがどのように機能するかは次のとおりです。

1. **デフォルトの認証 **: 機密性の低い操作の場合、エージェントは人間の介入なしに署名と認証に通常の検証方法を使用できます。
2. **人権の承認**: 重要な業務(購入、支払い、プライバシーデータアクセスなど)`humanAuthorization`文書で定義されたキーは署名されます。これは通常、生体認証による目に見える手動の人間の承認を必要とします。

エージェント記述プロトコルでは、サービス プロバイダーは、人間による手動承認が必要なインターフェイスを明示的に指定できます。

```json
{
  "@type": "ad:StructuredInterface",
  "protocol": "YAML",
  "humanAuthorization": true,
  "url": "https://agent-network-protocol.com/api/purchase-interface.yaml",
  "description": "A YAML file for interacting with the intelligent agent through purchase."
}
```

このメカニズムを通じて、エージェントの自律性とセキュリティのバランスを実現します。エージェントは日常のタスクを自由に実行できますが、ユーザーの経済的セキュリティとデータ プライバシーを確保するために主要な操作は引き続き厳密に制御されます。

エージェントの開発者は、humanAuthorization に対応する秘密キーを安全に保存し、権限を分離する必要があります。たとえば、humanAuthorization は、ユーザーが生体認証 (指紋、顔認識など) によって認証された後にのみ署名に使用できます。

## 質問 3: プライバシー保護 - 行動追跡とプロファイリングの防止

インテリジェントなボディは、さまざまなプラットフォームでユーザーを表現するので、より繊細で、同様に重要な質問が挙げられます。ユーザーの行動を追跡し、分析する方法は? ユーザーが同じ識別子を使用して異なるサービスにアクセスする場合、ユーザーはユーザーの詳細な行動イメージを構築し、プライバシーに侵害することに協力することができます。

### ド: wba 多身性戦略

この問題に対処するため、APP Agreement は、do:wba のコードで複数のアイデンティティ戦略を提案します。

1. **主要なディッド**ユーザーは、通常、比較的安定しているマスターIDを持ち、社会的関係などの長期的アイデンティティを必要とするシーンを維持するために使用される。
2. **サブ-DD**ユーザーは、ショッピング、ケータリング予約、コンテンツサブスクリプションなど、さまざまなインタラクティブなシナリオで使用されているメインDIDに添付されている複数のサブIDを持っています。
3. **定期更新**: サブDDは定期的に更新することができ、古いIDは無効にすることができますし、より困難を追跡するために要求された新しいID。

異なる状況で異なるアイデンティティを使用するため、さまざまな DID 間のサブコーディネートを維持し、ユーザー管理を容易にしながら、クロスプラットフォームの動作接続を防止します。

最も重要なのは、ユーザーがデジタルアイデンティティをコントロールし、ユーザーが自分のアイデンティティ情報をどこにどのように提示するかを判断できるようにする設計です。
