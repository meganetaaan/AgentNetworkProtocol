# エージェントの最も適したアイデンティティ認証技術: OpenID Connect、API Keys の比較、および:wba をしました

## エージェントは、新しいアイデンティティ認証技術を必要とします

エージェントは、アイデンティティ認証技術の新しい要件を導入し、相互運用性が最も重要である - 具体的には、2つのエージェントが互いに接続して通信できるようにしています。

原則は簡単です:AIは、 **完全なコンテキスト情報を取得し、すべてのツールにアクセスする能力を持っている** 正しい決定を下し、適切な行動を取るために。 現在、多くのベンダーがコンピューター使用ソリューションを使用してこの問題を解決しようとしています。

<p align="center">
  <img src="../../blogs/images/computer-use-product.png" width="50%" alt="computer use product"/>
</p>

しかし、AIがインターネットとやり取りするのは最も効率的な方法ではないと私たちは信じています。 このアプローチは、AIがインターネットにアクセスする人間の方法を模倣します。, 人工知能は、最も有能なメソッドを使用してデジタルワールドと対話する必要があります (APIや通信プロトコル).

<p align="center">
  <img src="../../blogs/images/agent-interview-Internet.png" width="50%" alt="agent-interview-Internet"/>
</p>

エージェントがインターネットや他のエージェントとやり取りするために API やプロトコルを使用する際、アイデンティティ検証はどのように行われるべきかを相互運用性質問を提起します。 特に、どのエージェント間の接続を有効にするために、クロスプラットフォームのアイデンティティ検証を実装する方法は?

## 現主流のクロスプラットフォームのアイデンティティ認証技術

インターネット上の当社のIDアカウントは、相互プラットフォーム対応ではありません。 例えば、DingTalkシステムやその逆にWeChatアカウントが認識できません。

しかし、今日はインターネット上で多くのクロスプラットフォームの認証技術が搭載されています。例えば、一般的なSSO(シングルサインオン)など、Googleアカウントを使って多くのウェブサイトにログインすることができます。 また、API キーは OpenAI のキーとして API にアクセスできるので、API キーも用意しています。 これら2つの技術について簡単に紹介し、エージェントの身元認証に適したかどうかを調べましょう。

### OpenID Connect (OIDC) の接続

OpenID Connect(OIDC)は、クライアントアプリケーションがユーザー ID を検証し、基本的なユーザー情報(名前、メールなど)を取得できるように OAuth 2.0 上に構築された認証プロトコルです。 OIDC は、OAuth 2.0 のトップに標準化された ID レイヤーを追加し、ログインやシングルサインオン (SSO) のシナリオに適しています。

[OpenID は公式の指定を接続します](https://openid.net/specs/openid-connect-core-1_0.html)

OIDC プロセスを説明するために、Google アカウントを使用してサードパーティの Web サイトにログインします。 [Google OIDC 公式ドキュメント](https://developers.google.com/identity/protocols/oauth2/openid-connect).

<p align="center">
  <img src="../../blogs/images/openid-connect-fllow.png" width="50%" alt="openid-connect-fllow"/>
</p>

Googleアカウントを使用して、サードパーティのWebサイトにログインするには、2つの部分、予備プロセスとOAuth 2.0プロセスが含まれます。
- 予備プロセス
  - Googleプラットフォームアカウントを登録する
  - プロジェクト/アプリケーションを作成する
  - URIをリダイレクトするなど、プロジェクト/アプリケーションの設定
  - OAuth 2.0 クライアント ID とクライアントシークレットの取得
- OAuth 2.0 プロセス(認証コードを例にまとめて)
  - 認証コードの取得
  - ユーザ情報を含むアクセストークンとIDトークンを取得する権限コードを使用します。
  - アクセストークンとIDトークンを使用して、詳細なユーザー情報(オプション)にアクセスします。 OpenID Connect プロセスでは、詳細なユーザー情報が保護されたリソースとみなされます。

OpenID のメリットはコネクトします。
- ユーザ認証プロセスを簡素化
- 十分に確立されたインフラと広く利用された
- 高い安全性

エージェントの相互運用性を観点から、OpenID Connectにはいくつかの制限があります。
- OpenID Connect は、サードパーティのアプリケーションがユーザー認証のために ID サーバー (Google のような) を使用するようにします。 サードパーティのアプリケーションは、IDサーバーを使用して、本人間で認証することはできません。
- OpenID Connectは、ユーザーがアイデンティティサーバーに登録する集中ソリューションで、予備プロセスの複雑化を実現します。
- やり取りプロセスは複雑で、複数の取引所が必要です。

### APIキー

APIキーは、アプリケーションやユーザーがアプリケーションプログラミングインターフェイス(API)にアクセスするための簡単な資格情報です。 文字列ベースのアイデンティティ識別子で、通常はランダムに生成された文字と数字で構成されており、同様にパスワードに機能します。 認証、アクセス制御、使用状況監視、その他のシナリオに使用できます。

<p align="center">
  <img src="../../blogs/images/api-keys-flow.png" width="50%" alt="api-keys-flow"/>
</p>

ユーザー認証用の API Keys を使用するプロセス:
- 予備プロセス
  - プラットフォーム上でアカウントを登録する
  - API キーの取得
- APIキー認証プロセス
  - HTTPS のようなセキュアなプロトコルのリクエストヘッダーに API キーを追加します。
  - Server はクライアントの API キーを検証します。

API キーの利点:
- シンプルで、実装が容易で、最小限のやり取り
- 相互プラットフォーム認証をサポート。2つのアプリケーションは、各APIキーで同一の認証を確認できます
- OpenAIや国内モデルAPIなどのAPIサービスで広く利用されており、認証用のAPIキーをほとんど使用

エージェントの相互運用性を観点から、API キーにはいくつかの制限があります。
- セキュリティーを下げる。 認証用のAPIキーを使用して多くのMCPサーバーは、ユーザーが設定ファイルでAPIキーを書くように要求し、露出を危険にさらすことが多いです。

<p align="center">
  <img src="../../blogs/images/mcp-server-api-key-example.png" width="50%" alt="mcp-server-api-key-example"/>
</p>

- ユーザ登録やログインなど、事前プロセスを必要としている。

## W3C DIDベースの認証技術: をしました:wba

### W3C DIDとは

W3C DID(分散型識別子)は、従来の集中型のアイデンティティ管理システムの依存性に対応するように設計された新しい分散型識別子規格です。 2022年(平成20年)に推奨規格となりました。 仕様: [https://www.w3.org/TR/did-core/](https://www.w3.org/TR/did-core/)

現在、W3C DID仕様では、最近人気のBlueskyという代表的なアプリケーションで注目されているアプリケーションが多数あります。

### 何がした:wba

id:wba は DID メソッドの仕様で、 [エージェントネットワークプロトコル(ANP)](https://github.com/agent-network-protocol/AgentNetworkProtocol). . . 特にエージェント間の認証のために設計された、Webインフラに基づく分散認証を実装しています。 仕様: [d:wbaメソッド仕様](https://github.com/agent-network-protocol/AgentNetworkProtocol/blob/main/03-did%3Awba%20Method%20Design%20Specification.md).

機能のメールには、wba が似ています。異なるプラットフォームは独自のアカウントを持っていますが、さまざまなプラットフォーム間で簡単に認証と通信することができます。 両方とも、分散化を実現しながら、大規模なユーザーをサポートし、Webインフラをベースとしています。

エージェント A は、Agent B のサービスへの購読と呼び出しを望んでおり、認証およびリクエストプロセスは次の通りです。

<p align="center">
  <img src="../../blogs/images/did-wba-flow.png" width="75%" alt="did:wba-flow"/>
</p>

- 予備プロセス
  - Agent A は、Agent B のサービスサブスクリプションインターフェイスを Agent A の DID とシグネチャで呼び出します。B がサブスクリプションを Agent A から受け取ることを確認します。 API サブスクリプションを使用して、複雑な登録、ログイン、設定プロセスを削除し、2 つのエージェント間の接続コストを削減できます。
- 認証プロセス
  - Agent A は、HTTP ヘッダーに DID と署名を 1 つ目の HTTP リクエストに含めます。
  - Agent B が HTTP リクエストを受信すると、A's DID と HTTP ヘッダからシグネチャを抽出し、A's DID サーバーから A's DID ドキュメントを A's DID サーバから取得します。
  - A の DID ドキュメントを取得した後、A の DID 文書の公開鍵を使用して、A の署名を検証します。
  - 認証後、Aのビジネスリクエストを処理する Agent B は、アクセストークンとともにビジネスデータを返します。
  - Agent A は、アクセストークンを後続リクエストに持ち、A の Agent B はアクセストークンを確認することで認証します。

のメリット:wba認証:
- 高い安全性
- 大規模ユーザーをサポートし、Webインフラを有効活用し、導入性が強い
- 分散型設計により、あらゆる2つのエージェントまたはアプリケーション間で認証が可能
- 簡単な予備プロセス、手動ユーザー登録またはログイン設定は必要ありません
- 対話頻度を増加させない簡単な認証プロセス

もちろん、wbaには制限がいくつかあります。メインの1つは2022でリリースされた仕様として、そのインフラはまだ完全に開発されていないため、アプリケーションスコープは比較的限られています。 しかし、ブルースキーのような星のケースが現れているのは、その様子です。

## 比較:wba対OpenIDコネクト/APIキー

エージェント認証の観点から、OpenID ConnectとAPIキーで比較した:wba:
- セキュリティ:wba と OpenID Connect は、API キーよりも高いセキュリティレベルを持っています。
- 複雑性:OpenID Connectは、最も高い複雑性、APIキーが最も低い、間にあるdoed:wbaです。
- 相互作用周波数:wbaとAPIキーは、最小限のやり取りを必要とする, OpenID Connectは最も必要です.
- 予備プロセス: wba は手動ユーザの介入なしで操作できますが、OpenID Connect と API キーはマニュアルユーザー処理を必要とします。
- 分散化:wbaとAPIキーは、任意のエージェントやアプリケーション間の通信を有効にできます。 OpenID Connect は、
- アプリケーションスコープ: OpenID Connect と API キーは広く適用されますが、doed:wba はアプリケーションスコープの新規仕様です。

全体的な比較:
| 比較項目 | 行なった:wba | OpenID 接続 | APIキー |
|:-------|:--------|:---------------|:---------|
| セキュリティー | グレード | グレード | メディス |
| 複雑さ | メディス | グレード | 低いです |
| 相互作用の頻度 | 低いです | グレード | 低いです |
| 予備プロセス | 簡単、手動仕事無し | 複雑な作業を要求します。 | 中、手動仕事を必要として下さい |
| 分散化 | あり あり | ノーザン | あり あり |
| 応用範囲 | 限定商品 | ワイド | ワイド |

上記比較では、全てのエージェント間の相互接続をサポートするだけでなく、大規模なユーザー採用をサポートしながら、OpenID ConnectとAPIキーのシンプルさを兼ね備えたセキュリティも保有しているという点がわかります。 全体的に、id:wbaはエージェント間の認証のための最も適したソリューションです。

もちろん、OpenID Connect と API キーは、その役割を担っています。 例えば、エージェントが既存のインターネットシステムとインターフェイスする場合、OpenID Connect や API キーを使用する必要がある場合があります。
