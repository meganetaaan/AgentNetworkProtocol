# エージェント ID の 3 つの主要な問題: 相互運用性、人間による承認、およびプライバシー保護

パーソナルアシスタントからさまざまな専門サービスエージェントに至るまで、エージェントが前例のない方法で私たちのデジタルライフに参加することはほぼ確実です。エージェント間の安全かつ効率的な対話を確保するには、包括的な ID システムが必要です。

この記事では、エージェント ID が直面する 3 つの重要な問題について詳しく説明します。
- **相互運用性**: すべてのエージェントが通信して共同作業できるようにするにはどうすればよいですか?これはエージェントのアイデンティティに関する中心的な問題です。デジタル サイロを打破し、AI が真に完全なコンテキストを取得し、よりインテリジェントなインタラクティブなエクスペリエンスを提供できるようになります。
- **人間による承認**: 機密性の高い重要なリクエストでは、そのリクエストが人間によって手動で承認されたのか、エージェントによって自律的に開始されたのかをどのように判断すればよいでしょうか?エージェントの許可を制限しながら、エージェントが人間に代わってインターネットにアクセスできるようにする必要があります。
- **プライバシー保護**: エージェントが対話中にユーザーの個人情報を漏洩することをどのように防ぐことができますか?

エージェント ネットワーク プロトコル (ANP) と、これら 3 つの問題に関するその考慮事項と設計について紹介します。

## エージェントのアイデンティティが重要である理由

インターネットの誕生以来、ID 認証はデジタル世界の中核的な問題となってきました。初期のユーザー名とパスワードから、その後の 2 要素認証と生体認証に至るまで、本人確認テクノロジーは継続的に進化してきました。現在、エージェント時代の到来により、ID 認証は新たな課題に直面しています。

インテリジェント エージェントは、自律性、学習能力、意思決定能力を備えているという点で従来のソフトウェアとは異なります。エージェント Web では、インテリジェント エージェントは次のことを行う必要があります。

- **デジタル市民として行動**: 他のエージェントやシステムによって認識され、信頼される独自のアイデンティティを持つ
- **ユーザーに代わって行動**: ユーザーに代わってさまざまなタスクやトランザクションを実行するための適切な承認を取得します。
- **クロスプラットフォーム コラボレーション**: 異なるプラットフォーム上のエージェントやサービスとシームレスに対話し、コラボレーション ネットワークを形成します
- **ユーザーのプライバシーを保護**: ユーザーに代わって行動しながら、ユーザーのプライバシーとセキュリティを保護します

「Agentic Web の違い」で説明したように、AI の力を最大限に発揮するには、AI が完全なコンテキスト情報を取得し、インターネット上のすべてのツールにアクセスし、得意な方法でインターネットと対話し、他の AI と効率的に連携できるようにする必要があります。これらすべての前提条件は、強力で柔軟なエージェント ID システムです。

## 重要な問題 1: 相互運用性 - アイデンティティのサイロを打破する

これはエージェントのアイデンティティにとって最も重要かつ困難な問題です。

現在のインターネット環境では、アイデンティティ システムはほとんどがプラットフォームのサイロ化されています。 WeChat アカウントは DingTalk では使用できません。また、Alipay アカウントは JD.com でのショッピングに直接使用することはできません。

エージェントは情報を収集してタスクを実行するためにさまざまなサービス間を自由に移動する必要があるため、このアイデンティティの断片化はエージェント時代には深刻な障害になります。

あるエージェントが別のエージェントのサービスを呼び出す必要があるが、エージェントが異なる ID システムを持つ異なるプラットフォームに属している場合、コラボレーションは非常に複雑になり、ユーザーによる複数の手動介入が必要になる可能性があります。これは、ユーザーの負担を軽減するというエージェントの本来の意図に明らかに矛盾します。

### 既存ソリューションの分析

ソリューションを模索する中で、私たちはインターネット上に存在するさまざまな ID 認証テクノロジーを比較しました。

- **OpenID 接続**: シングルサインオンに広く使われますが、その集中的な性質と複雑なプロセスは、エージェント間の効率的な相互作用には適していません。 基本的には、OpenID Connectは、将来に向けたアイデンティティの相互運用性を解決する設計ではなかった。
- **APIキー**: API の統合に広く使われ、シンプルで直接的なものではなく、限られたセキュリティがあり、またユーザーによる手動登録と構成を必要とし、エージェントの相互作用の効率性を低下させます。
- **ブロックチェーンのアイデンティティソリューション**: 分散性が高いが、スケーラビリティとパフォーマンスの課題に直面しています。 現行の技術で、数億人のユーザーをサポートすることで大きな課題を提示します。
- **メールプロトコル**: シンプルで分散性があり、この分散化は私たちの理想と整合します。 しかし、電子メールビジネス向けには特にEメールプロトコルを設計し、そのコアでHTTPを使用しないため、既存の成熟したWebインフラを活用できません。
- **ノストラとATプロトコル**: 分散型プロトコルを生成するが、広く採用されていない。 ATプロトコルは、私は非常に最適化されているプロトコルです。また、W3C DIDを使用してアイデンティティ認証をします。そして、BlueskyアプリケーションはWeChatの将来の同等性になる可能性は非常によくあります。
- **W3C のディッド**: W3C分散型識別子(DID)仕様は、集中型のアイデンティティによって得られるさまざまな問題に対処するように設計され、2022年に推奨規格として公開されました。 しかし、インターネットでは広く使われていません。

### W3C DIDはエージェントのアイデンティティのための最もよい解決です

リリース後、W3C DIDは広く適用されていません。 しかし、すべての利用可能な技術を分析した後、W3C DIDはインテリジェントなエージェントにとって最も適したアイデンティティ技術であり、新しいものの設計はそれを改善するために圧倒されるのではないかとしっかりと確信しています。

いくつかの理由があります。
- W3C DIDは、分散化とアイデンティティの相互運用性のために生まれ、エージェントの相互運用性の必要性を完全に整列しました。
- W3C DID 実装はより柔軟です。DID のブロックチェーンを必要とするなど、特定の分散型実装を現在管理していません。 開発者は、より多くの選択肢を提供します。
- エージェントのdo:webメソッドに基づく新しいメソッド実装を設計しました。 既存の成熟したWebインフラを繰り返し活用しながら、分散化を実現し、数十億のエージェントに対応できる。

オリジナルのW3C DID仕様と当社の方法実装が組み合わさったのは、私の意見では、現在利用可能なインテリジェントエージェントに最適なアイデンティティソリューションです。

ソリューションの詳細な導入については、以下を参照してください。 [id:wba、Webベースの分散型識別子](did:wba,%20a%20Web-based%20Decentralized%20Identifier.md)

## 重要課題2:人間認証―重要な業務のセキュリティ確保

インテリジェントなエージェントは、人員の代わりにタスクを実行しているため、重要な問題が重要になります。エージェントが送信したリクエストは、人からマニュアル承認を受けているかどうかです。

例えば、エージェントはユーザーの代わりにホテル情報を自動閲覧することができますが、実際の予約と支払いに関しては、人からマニュアルの承認を得る必要があります。

このような差別メカニズムの欠如は、次の2つのリスクにつながる可能性があります。まず、エージェントは慎重に、頻繁にユーザーを中断して簡単な操作を確認します。 2つ目、エージェントは過度に自律的であり、重要な決定のための必要なヒューマン・監督を欠いて、潜在的な人間の財政的な損失を引き起こします。

### 人間認証機構:wba

ANPプロトコルは、d:wba 仕様によるエレガントなソリューションを提案します。人間の承認とエージェントの自動承認の明確な差別メカニズムです。

ド:wba ドキュメントでは、弊社が導入しました。 `humanAuthorization` 人為の許可のために特に公正なキー情報を格納するフィールド:

```json
"humanAuthorization": [
  "did:wba:example.com%3A8800:user:alice#WjKgJV7VRw3hmgU6--4v15c0Aewbcvat1BsRFTIqa5Q",
  {
    "id": "did:wba:example.com%3A8800:user:alice#key-3",
    "type": "Ed25519VerificationKey2020",
    "controller": "did:wba:example.com%3A8800:user:alice",
    "publicKeyMultibase": "z9XK2BVwLNv6gmMNbm4uVAjZpfkcJDwDwnZn6z3wweKLo"
  }
]
```

このメカニズムの動作原理は、次のとおりです。

1. **デフォルト認可**: 人的介入なしに、非感性操作のために、エージェントは署名と承認のための定期的な検証方法を使うことができます。
2. **人権の承認**: 重要な操作(購入、支払い、プライベートデータへのアクセスなど)、定義されたキーを使用して署名 `humanAuthorization` 一般的に、生物学的評価や類似の方法で人間からの明示的な、手動承認を必要とする必要があります。

エージェントの説明プロトコルでは、サービスプロバイダは、マニュアルの人的許可を必要とするインターフェイスを明確に指定することができます。

```json
{
  "@type": "ad:StructuredInterface",
  "protocol": "YAML",
  "humanAuthorization": true,
  "url": "https://agent-network-protocol.com/api/purchase-interface.yaml",
  "description": "A YAML file for interacting with the intelligent agent through purchase."
}
```

この仕組みにより、エージェントの自律性とセキュリティのバランスが取れます。エージェントは日々のタスクを自由に実行できます。重要な操作は厳密に管理され、ユーザーの金融セキュリティとデータプライバシーを確保します。

エージェントの開発者は、HumanAuthorizationに対応した秘密鍵を安全に保存し、許可分離を実行する必要があります。 例えば、人為認証のシグネチャは、生体認証(指紋、顔認識など)を通じてユーザを検証した後にのみ使用すべきです。

## 問題3:プライバシー保護-行動追跡とプロファイリングを防止

エージェントは、さまざまなプラットフォーム間でユーザーを代わって行動するにつれて、より微妙で等しく重要な問題が現れます。ユーザーの行動を追跡し分析する方法は? ユーザーが同じ識別子を使用して異なるサービスにアクセスする場合、これらのサービスはユーザーの詳細な行動プロファイルを作成するためにコラボレーションする場合があります。

### 多国籍戦略:wba

この問題に対処するため、ANPプロトコルは、do:wba 仕様のマルチアイデンティティ戦略を提案します。

1. **第一次DID**: ユーザーは、通常、社会的関係やその他の状況を持続的に維持するために使用される、比較的安定しているままに残っている主要なIDを持っています。
2. **サブID**: ユーザーは、同時に複数のサブIDをプライマリDIDに分けて所有しています。ショッピング、レストランの予約、コンテンツサブスクリプションなどさまざまなインタラクションシナリオで使用されます。
3. **定期更新プログラム**: サブIDは定期的に更新することができます。 古いIDは、要求された無効化され、新しいDIDが要求されるようになり、トラッキングの難しさが高まります。

このマルチレベルのアイデンティティアーキテクチャにより、ユーザーはさまざまなシナリオで異なる識別子を使用でき、クロスプラットフォームの動作相関を防ぎ、DID間のサブ座標関係を維持し、ユーザー管理が容易になります。

最も重要なのは、この設計により、ユーザーはデジタルアイデンティティをコントロールし、いつ、どこで、そして自分のアイデンティティ情報をどのように提示するかを決めることを可能にします。
