## 1.  ANP エンドツーエンド インスタント メッセージングとは何ですか?

ANP エンドツーエンド インスタント メッセージングは、** エージェントとエージェント ** のクロスドメイン インスタント メッセージング通信のための一連のプロトコル仕様です。

解決したいのは、「特定の製品内でチャットする方法」ではなく、次のことです。

- 異なるドメイン、異なるプラットフォーム、異なる実装にあるエージェントが相互に検出できる方法。
- プライベートおよびグループチャットメッセージを送信する方法;
- 必要な場合にエンドツーエンドの暗号化を提供する方法。
- 添付ファイルと大きなオブジェクトを転送する方法;
- クロスドメインシナリオでルーティング、中継、並べ替え、結果監視を完了する方法。

AMPの事業体と商人員は、 **エージェントID**. Messaging 1.2では、一般的な非E2EEプライベートチャット、グループ会話、Metionおよび添付操作はDIDアドレス、受信エリア内のエンドポイントファンアウトを維持します。 P3は、メンバーとDIDの更新のための契約の変更の結果、v1、P4を維持しています。 E2E v2プロファイルのみ、オープン安全なクロスドメインパスワード通信に必要な最小デバイス構文を使用します。`device_id` 新規事業のアイデンティティ、グループメンバー、または同じIDの下にパスワードエンドポイントです。 `target.kind`。

## 2. コアコンセプト

### 2.1 単一の中枢ではない連邦主義

ANP は、**フェデレーション** アーキテクチャを採用しています。これは、概念的には単一の中央サーバー アーキテクチャよりも電子メールに近いものです。

各エージェントまたはグループは、標準化されたサービスディスカバリー、サービスツーサービスの直接呼び出しおよび結果的機能によって接続されている次の領域と異なるドメインの一部であることができます。

- アイデンティティは分散されます;
- サービスアクセスを配布します。
- クロスドメインサービスコールは、
- しかし、各タイプの動作は明確な責任の境界を持っています。

プライベートチャットシーンでは、対象エージェントのドメインへのアクセスサービスがメッセージを受信します。グループシーンでは、ホストサービスはグループステータスシーケンシングとシーケンスされたグループイベントを担当しています。

### 2.2 アイデンティティ優先、サービスの優先順位

AMP のファーストクラスの識別子は、ユーザー名またはデバイス番号ではなく、

- `agent_did`
- `group_did`

AMP は、DID 文書を介したインタラクティブなサービスエンドポイントを特定し、フォローアップメッセージ配信、キーディスカバリー、グループサービスのディスカバリー、オブジェクト検索パスを作成します。現バージョンでは、DID ファイル用の AMP サービスポータルがそのまま凝縮されています。 `ANPMessageService`; プライベートチャット、グループチャット、キー素材へのアクセス、オブジェクトコントロール機能が統一されたポータルによって行われます。

Messaging 1.2では、装置の位置を宣言するためのDID E2EE v2ファイルは適用されたDD方法に従って確認されるID文書で完了しなければなりません `deviceManifest`、特定の規則はP2です。WBAに固有の根本的な要求は元のものに適用されません `did:web`. エントリーは、現在のデバイスエンドポイントの識別、署名キーリファレンス、E2EEキークォートとサポートされたプロファイル識別子および依存関係のみを開示します。 Base だけが Manifest が要求されていないことを確認しました。製品ドメイン、トークン、復元状態、レジストリバージョン、ドキュメントチェックポイント内のロールは ANPwire 構文ではありません。

### 2.3 層の設計、ない「UCPs」

ANPはすべての質問を1つの文書に詰めるだけでなく、9つのプロファイルにそれらを引き裂く:

- P1/P2:共同記述および同一証明
- P3 / P4:プライベートとコミュニティの会話のための基本的なビジネス構文
- P5 / P6: プライベートとグループ E2EE オーバーレイ
- P7: 添付ファイルと大きなオブジェクト
- P8: 連邦、クロスボーダーサービスコールおよびグループインシデントディストリビューション

そのような設計の利点は:

- (a) 基本的なメッセージとセキュリティの拡張性の管理

- プライベートチャット、グループ会話、アンコール、および連盟は明確です。
- 以降、パッケージをオーバーターンする必要はありません。

### 2.4 制御とデータ分離

ANP の区別:

- **コントロール**(a) 団体、会員、追加、キックオフ、コンピテンシーコンサルティング、請求およびクロスドメインサービスコール;

特に、別館シーンでは、ANPは明示的に使用します。

## 3. コア設計

### 3.1 外付けの実装:JSON-RPC

UTM は ANP の **JSON-RPC 2.0の特長**それを締めて下さい:

- `params` (a) 使用されるオブジェクトの形態;
- `id` (a) 文字列を使う。
- 時計は使用しないでください。
- ノンコンプライアンスは、明確なウォークイン通知のためにのみ使用されます。

目的は、異なる言語、プラットフォーム、サービス間での均一/応答/ミステークモデルをシンプルに保つことです。

### 3.2 プライベートとコミュニティベースのモデリング

AMP は、漠然とした大きなオブジェクトを「メッセージ」するのではなく、明確な区別をします。

- `direct.send`: 会話のプライベート
- `group.send`: グループへのトーク

同時に、グループでは「メッセージ送信」だけでなく、

- `group.create`
- `group.join`
- `group.add`
- `group.remove`
- `group.leave`
- `group.update_profile`
- `group.update_policy`

これは、グループガバナンス、グループステータス、クラスター暗号化の自然な接続を可能にします。 P4 v2は定義されていません `group.invite`、`group.accept_invite` または標準的な入力オブジェクト;招待リンクまたは参加トークンは、展開の延長であり、できません `group.join` 成功前に確立された標準的な会員。

Messaging 1.2 は、デバイスレベルのビジネスメンバーを作成していません。P3 Direct Base v1 および P4 Group Base v2 の会員、役割、戦略、ディスパッチおよび通知は DID によって管理されます。P4 v2 は DID のみのメンバーの関係を使用し、P2 検証結果を持つメンバー ID を投稿することによって更新されます。P5/P6 v2EE のみ配信と MLS パスワードリーフはデバイスによって管理されます。

### 3.3 E2EE と明示的に共存

ANP は、次の機能を可能にします。

- `transport-protected`: セキュリティーを転送するだけ
- `direct-e2ee`: 専用にエンド暗号化
- `group-e2ee`:コールツーエンド暗号化

つまり、財団は自己持続的です。セキュリティオーバーレイは優先されます。これは、異なるシナリオで段階的な展開とさまざまなレベルのセキュリティを容易にします。

## 4. コア技術ルート

### 4.1 伝達およびメッセージ結合:JSON-RPC 2.0

ANP は、JSON-RPC 2.0 を統一メッセージバインドとして使用し、「関数呼び出しの同時処理」ではなく、クロスドメインプロトコルの一貫性を提供する。

- リクエスト形式
- 応答形式
- エラーモデル
- 容量の相談インターフェイス
- ステップ通知メカニズム

これにより、AMP はプライベートチャット、グループ会話、添付ファイルコントロール、クロスドメインサービスコールなどの異なる設定で同じ外部レベルのプロトコル形状を共有できます。

### 4.2 プライベートチャットツーエンド暗号化:X3DHのような+ダブルラチェットのような

AMP プライベートチャット E2EE では、以下のテクニカルルートを使用します。

- アイデンティティのアンカー:ANP-02およびP2によって、を含む確認される代理店DID `did:wba` オリジナル。 `did:web`
- 鍵が見つかった: DID 文書を通じて公開 `ANPMessageService` 交通アクセス
- 初期チェーンビルディング:`X3DH-like`
- フォローアップメッセージ保護:`Double Ratchet-like`

- DID ドキュメントの認証キーは、識別するために使用されます。
- DID ドキュメント `keyAgreement`(例:X25519) 相談のため;
- 固定されたオフラインチェーンのためのプレキーバンドル。
- ラチェットは、すべてのメッセージキーの転がり、無秩序な許容および再実行に従うのに使用されています。

直接E2EE v2では、PreKeyバンドル、ステップフォワード、ラチェットステート、AAD、リロールおよびメールボックスは、それぞれに異なっています `(DID, device_id)`. 同じ論理メッセージは、各正当な受信デバイスが暗号化され、別々に送信され、機器のプライベートな状態が共有できないことです。

エージェントのウォークスルー通信に適したルートで、より強いパッケージにアップグレードできます。

### 4.3 グループツーエンドの暗号化: MLS +デバイス上でのDID結合

AMP クラスター E2EE のメインラインは、次の機能を使用します。

- **メルマガ** (a)グループ キーの状態機械として;
- **DID方式で検証したエージェントDID** 同一のアンカーとして、機器の適格性はP2のマニフェスト規則によって定義されます。
- **グループホストサービス** リターンの権限でソートされるように。

つまり、

- グループメッセージの投稿 `PrivateMessage` (a) ローディング;
- 会員、削除、歓迎、外部アクセス `KeyPackage / Commit / Welcome / External Commit` 完了;
- `group_did`、`group_state_version`、`policy_hash` (b)パスワードコミュニティと連携する。
- `group_receipt` 証明書は「グループが操作/メッセージを受信し、シーケンスします。」です。

グループ E2EE v2 では、運用メンバー DID は複数の認証 MLS リーフを所有することができます。各リーフは、KeyPacackage とプライベートなステータスを結合するために別のデバイスを使用します。 1 つのデバイスリーフを追加または削除しても、DID クラスのメンバーの追加または削除を意味するわけではありません。

円筒の機械のセットを製作するよりも長期基準に適しているアプローチです。

### 4.4 添付ファイルとオブジェクト: マニフェスト + 独立 HTTPS ダウンロード + 選択的なオブジェクトレベルの暗号化

附属書プログラムは3層構造を追従する:

1. **組織図**: 渡るだけ `attachment_manifest`
2. **アクセス層**: オブジェクトサービスによるダウンロードとドキュメントの短期ダウンロードの管理
3. **コンテンツ層**: オブジェクト自体のオブジェクトレベルの暗号化(必要に応じて)`object-e2ee`）

したがって:

- 大型オブジェクトは、クロスドメインサービスを介してリンクを呼び出すことはありません。
- 長期ストレートチェーンではなく、ロケータを作るためのリンクをダウンロードします。
- リンクが漏れても、オブジェクト暗号化によるものでなければ第三者は、そのリンクがないことを保証することができます。

直接E2EE v2では、アップロードされたオブジェクトと同じです。 `object_key` 複数のデバイス設計暗号化メッセージを使用して、各受信機を送信します。 グループ E2EE v2 では、現在の Epoch MLS アプリケーション メッセージで保存します。 P7 は残っています `anp.attachment.v1`、デバイスでオブジェクト、アクセス付与またはチケットステータスをコピーしません。

### 4.5 連邦:サービスからサービスへの直接呼び出し

AMP の定義は:

- サービスディスカバリー
- 直接サービスコールへのクロスドメインサービス
- グループホストのソート
- アタッチメントコントロール用のクロスドメイン呼び出し
- `attachment.get_download_ticket` ♪ 秋の最終ポイント♪

重要な原則の1つは次のとおりです。

- 古いビジネスメソッドを使用して直接クロスドメインを使用するか、別のRelay パッキング契約を追加するのではなく、ターゲットサービスと相互作用する方法を制御する方法。
- オブジェクトバイトは、HTTPSから独立してダウンロードする必要があります。
- グループホストは、グループホストの受け入れとソートのための成功したクロスドメインの構文として使用されます。
- プライベートチャットは、ターゲットエージェントポータルサービスの受け入れのためにクロスドメインの成功構文として使用されます。
- P8 v1 連合は、機器が送信/受信であることを宣言する際に、E2EE v2 データを保存し検証するだけです。通常、P3/P4/P7 操作は DID アドレスを保持し、受信フィールド内でエンドポイントのファンアウトを保ちます。ゲートウェイは、これらの操作にデバイスを追加したり、E2EE 配信のためにファンアウトを隠すことはありません。

## 5. 主要設計トレードオフ

ANPには、いくつかの意識的な設計トレードオフがあります。

### 5.1 機器のエンドポイントからビジネスアイデンティティの分離

v1.1 ベースラインは、エージェントの内部詳細として機器、端末、コピーを検討しています。 Messaging 1.2 は、一般的なメッセージの DID 位置境界を維持します。 P3、P7、P8 は v1 を保持し、P4 は v2 に変更されます。これは、DD のみのメンバーの関係とホストの調整の更新が更新されるためです。 P5/P6 v2 は、E2EE パスワードのエンドポイントを調節して、キー、共有 Ratchet、コンサルテーションを行うなどの公共デバイスを、MID のキーやファン ID をキーで保持する必要のない機器を欠かせません。

### 5.2 グループガバナンスは、極端な匿名性を優先します

グループシーンでは、ANP も次のようになります。

- スポンサー認証(リクエスト開始)
- 結果のウィットネス(可否)
- グループ分類(MLS)

これは、純粋に匿名チャットではなく「支持されたエージェント」を好むことを意味します。

### 5.3 アネックスセキュリティは「隠されたリンク」に依存しません

ANPは、コアセキュリティツールとして「絶対的に隠されているダウンロードリンク」を使用していませんが、次の機能を使用します。

- 制御ダウンローダー
- ショートタイム URL
- オブジェクト暗号化

リンクが漏れている場合でも、意味のある明確さは常に利用可能ではありません。

## 7. インフォメーション

ANPのコアはチャットプロトコルではなく、セットをしています。 **エージェントエコロジーのクロスボーダー通信規格**。

思考の基本的なラインは、次のようにまとめることができます。

- **連邦主義**: 電子メールのような交差ボーダー相互接続性;
- **アイデンティティ優先度**: 統一アンカーとしてDIDを使用して;
- **E2EE v2 デバイスが安全**: DID は、DID レベルのビジネス ID と一般的なメッセージ位置の境界を変更することなく複数の独立したパスワードエンドポイントを開くことができます。
- **レイヤーデザイン**: 操作、暗号化、アンexes、連盟の分離;
- **E2EE オプションのスーパースイング**: 財団の合意は独立して運営することができ、オーバーレイは必要に応じて安全かつ有効です。
- **添付ファイルのダウンロードは直接**(a) 送信された人間、オブジェクトは独立した HTTP(S) データ インターフェイスを行きます;
- **グッドガバナンス**: 特にグループシーンでは、アイデンティティとソート、終了、暗号化の両立が伴います。

これにより、APPは、合意の達成可能なシステムと、その後の長期標準化進化のための基礎として機能することができます。
