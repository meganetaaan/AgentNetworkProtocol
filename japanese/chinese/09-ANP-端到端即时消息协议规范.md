## 1. ANP エンドツーエンド・インスタントメッセージングとは

これは、**Agent 間のドメインをまたぐインスタントメッセージ通信**のための仕様セットです。

ある製品内のチャット方法ではなく、次の問題を扱います。

- 異なるドメイン、プラットフォーム、実装の Agent 同士が、どう発見し合うか。
- 私信とグループメッセージをどう送るか。
- 必要な場合に、どうエンドツーエンド暗号化を提供するか。
- 添付や大きなオブジェクトをどう転送するか。
- ドメイン間で、ルーティング、中継、順序付け、結果の証明をどう行うか。

業務上のアイデンティティと認可の主体は、引き続き **Agent DID** です。Messaging 1.2 の通常の非 E2EE 私信、グループメッセージ、Mention、添付操作は、すべて DID 宛てを維持し、複数エンドポイントへの配信は受信ドメイン内で行います。P3 は v1 を維持し、P4 はメンバーと DID 更新の契約変更のため v2 を採用します。E2EE v2 Profile だけが、安全なドメイン間暗号通信に必要な最小限のデバイスの意味を公開します。`device_id` は、同一 DID 配下の暗号学的エンドポイントを表し、新たな業務上のアイデンティティ、グループメンバー、`target.kind` ではありません。

## 2. 基本的な考え方

### 2.1 単一の中心ではなくフェデレーション

ANP は、単一の中央サーバーよりも電子メールに近い、**フェデレーション型（Federated）**のアーキテクチャです。

Agent やグループは異なるドメインに所属でき、標準化されたサービス発見、サービス間の直接呼び出し、結果の証明で相互接続します。つまり：

- アイデンティティは分散しています。
- サービスの入り口も分散しています。
- ドメインをまたぐサービス呼び出しが可能です。
- 操作の種類ごとに、責任の境界が明確です。

私信では、宛先 Agent の所属ドメインの入り口サービスが受信を担います。グループでは、Group Host Service がグループ状態の順序付けとイベントの直列化を担います。

### 2.2 アイデンティティとサービス発見を優先

第一級の識別子は、利用者名やデバイス番号ではなく、次のものです。

- `agent_did`
- `group_did`

DID 文書で対話可能なサービスエンドポイントを発見し、メッセージ送信、鍵の発見、グループサービスの発見、オブジェクトサービスの発見につなげます。現在、DID 文書で公開する ANP のサービス入り口は `ANPMessageService` に統一され、私信、グループ、鍵資料へのアクセス、オブジェクト制御などを担います。

Messaging 1.2 で、デバイス宛ての E2EE v2 Profile を宣言する DID は、適用メソッドに従って検証した DID Document に、完全な `deviceManifest` を提供する必要があります。詳細は P2 に従います。WBA 固有のルート署名要件を、ネイティブな `did:web` に適用してはなりません。項目に公開するのは、現在のデバイスエンドポイント識別子、署名鍵と E2EE 鍵の参照、対応 Profile の識別子と依存先だけです。Base の発見だけなら Manifest は不要です。製品内の役割、token、復旧状態、Registry の版、文書の checkpoint は、ANP の wire の意味ではありません。

### 2.3 一体化せず階層に分割

すべての問題を一文書に詰め込まず、9つの Profile に分けます。

- P1 / P2：共通バインディングとアイデンティティの発見。
- P3 / P4：私信とグループの基本業務の意味。
- P5 / P6：私信とグループの E2EE Overlay。
- P7：添付と大きなオブジェクト。
- P8：フェデレーション、ドメイン間サービス呼び出し、グループイベント配信。
- P9：グループメッセージの mention と selector の意味。

この設計には、次の利点があります。

- 基本メッセージの意味と、安全性の意味を分離できます。
- 平文モードと暗号化モードを共存させられます。
- 私信、グループ、添付、フェデレーションの区分が明確です。
- 一つの層を更新するたびに、全プロトコルを作り直す必要がありません。

### 2.4 制御プレーンとデータプレーンを分離

次のものを明確に区別します。

- **制御プレーン**：グループ作成、参加、メンバー追加・削除、能力交渉、チケット発行、ドメイン間サービス呼び出しなど。
- **データプレーン**：私信、グループメッセージ、添付オブジェクトの内容。

特に添付では、次の方式を採用します。

- メッセージには **manifest（目録）**を含めます。
- オブジェクトの内容は、独立した HTTP(S) チャネルでダウンロードします。
- ドメイン間のサービス呼び出し経路は、オブジェクトのバイト列を転送しません。

## 3. 主要な設計

### 3.1 共通の外側のバインディング：JSON-RPC

共通の外側のバインディングは **JSON-RPC 2.0** を使い、次の制限を加えます。

- `params` はオブジェクト形式。
- `id` は文字列。
- batch は使いません。
- Notification は、明示的に定められた非同期通知だけに使います。

実装を簡潔に保ちつつ、異なる言語、プラットフォーム、サービスで要求・応答・エラーのモデルを統一するためです。

### 3.2 私信とグループを別々にモデル化

メッセージを曖昧な巨大オブジェクトにせず、明確に区別します。

- `direct.send`：私信。
- `group.send`：グループメッセージ。

グループでは、送信のほかに次の操作も扱います。

- `group.create`
- `group.join`
- `group.add`
- `group.remove`
- `group.leave`
- `group.update_profile`
- `group.update_policy`

これにより、管理、状態、暗号化をつなげられます。P4 v2 は、`group.invite`、`group.accept_invite`、標準 invitation オブジェクトを定義しません。招待リンクや Join Token は配備側の拡張であり、`group.join` が成功する前に、標準のメンバー状態を成立させることはできません。

Messaging 1.2 は、デバイス単位の業務メンバーを作りません。P3 Direct Base v1 の配信と、P4 Group Base v2 のメンバー、役割、ポリシー、送信、通知は、すべて DID 単位で管理します。P4 v2 は DID-only のメンバー関係を採用し、Host が P2 の検証結果に従ってメンバーの DID 更新を調整します。デバイス単位で管理するのは、P5/P6 v2 の E2EE 配信と MLS の暗号学的 Leaf だけです。

### 3.3 平文と E2EE の共存

次の方式を使えます。

- `transport-protected`：転送の安全性だけに依存。
- `direct-e2ee`：私信のエンドツーエンド暗号化。
- `group-e2ee`：グループのエンドツーエンド暗号化。

基本 Profile は単独で動作でき、安全性の Overlay をその上に重ねます。段階的な配備や、場面に応じた安全性の選択を容易にします。

## 4. 技術方針

### 4.1 転送とメッセージバインディング：JSON-RPC 2.0

JSON-RPC 2.0 は、関数呼び出しを模擬するためではなく、ドメイン間プロトコルに次の共通基盤を与えるために使います。

- 要求形式。
- 応答形式。
- エラーモデル。
- 能力交渉インターフェース。
- 非同期通知。

私信、グループ、添付制御、ドメイン間呼び出しなどで、一貫した外側のプロトコル形式を共有できます。

### 4.2 私信の E2EE：X3DH-like + Double Ratchet-like

私信の E2EE は、次の技術方針です。

- アイデンティティの基点：ANP-02 と P2 に従って検証された Agent DID。`did:wba` とネイティブな `did:web` を含みます。
- 鍵の発見：DID 文書で公開された `ANPMessageService` を使います。
- 初期接続：`X3DH-like`。
- 後続メッセージの保護：`Double Ratchet-like`。

それぞれの役割は次のとおりです。

- DID 文書の認証鍵でアイデンティティを証明します。
- DID 文書の `keyAgreement`（X25519 など）で鍵合意を行います。
- Prekey Bundle で、相手がオフラインでも非同期に接続を開始できます。
- Ratchet で、メッセージごとの鍵更新、順序の前後への対応、リプレイ防止を行います。

Direct E2EE v2 では、PreKey Bundle、非同期 Session、Ratchet State、AAD、リプレイ状態、Mailbox を、両者の具体的な `(DID, device_id)` に結び付けます。同じ論理メッセージを、正当な各受信デバイスに個別に暗号化して提出し、デバイス間で非公開状態を共有してはなりません。

Agent の非同期通信に適し、より強い暗号スイートへの移行余地も残す方針です。

### 4.3 グループ E2EE：MLS と DID・デバイスの結合

グループ E2EE の主な構成は次のとおりです。

- **MLS**：グループ鍵の状態機械。
- **DID メソッドに従って検証した Agent DID**：アイデンティティの基点。デバイスの適格性は P2 の Manifest 規則で定義します。
- **Group Host Service**：順序付けと受領証の権威。

具体的には：

- グループのアプリケーションメッセージは `PrivateMessage` で運びます。
- メンバー追加・削除、Welcome、外部参加などは、MLS の `KeyPackage / Commit / Welcome / External Commit` で行います。
- `group_did`、`group_state_version`、`policy_hash` を、暗号学的なグループ状態に結び付けます。
- `group_receipt` は、操作やメッセージをグループが受理し、順序付けしたことを証明します。

Group E2EE v2 では、一つの業務メンバー DID が、認証済みの MLS Leaf を複数持てます。各 Leaf は、デバイスに結び付く独立した KeyPackage と非公開状態を使います。デバイス Leaf の追加・削除だけでは、DID 単位のグループメンバーを追加・削除したことにはなりません。

独自のグループ暗号状態機械を発明するより、長期的な標準に適した方法です。

### 4.4 添付とオブジェクト：Manifest、独立した HTTPS ダウンロード、任意のオブジェクト暗号化

添付は三層構造です。

1. **メッセージ層**：`attachment_manifest` だけを運びます。
2. **アクセス層**：Object Service と短期ダウンロードチケットで制御します。
3. **内容層**：必要なら、オブジェクト自身を暗号化します（`object-e2ee`）。

そのため：

- 大きなオブジェクトは、ドメイン間サービス呼び出しの経路を通りません。
- ダウンロードリンクは、長期の直接リンクではなく locator にできます。
- リンクが漏れても、オブジェクト暗号化によって第三者に平文を渡さずに済みます。

Direct E2EE v2 では、一つのアップロード済みオブジェクトと `object_key` を、デバイスごとの複数の暗号化メッセージから参照し、鍵は各受信デバイスへ個別に送れます。Group E2EE v2 では、現在の epoch の MLS Application Message に鍵を入れます。P7 は `anp.attachment.v1` を維持し、object、Access Grant、Ticket の状態をデバイスごとに複製しません。

### 4.5 フェデレーション：サービス間の直接呼び出し

フェデレーション層は次を定義します。

- サービス発見。
- ドメイン間のサービス同士の直接呼び出し。
- Group Host の順序付け。
- 添付制御プレーンのドメイン間呼び出し。
- `attachment.get_download_ticket` の最終的な呼び出し先。

重要な原則は次のとおりです。

- 独立した Relay ラッパープロトコルを追加せず、元の業務メソッドや制御メソッドで、対象サービスと直接やり取りします。
- オブジェクトのバイト列は、独立した HTTPS ダウンロードにします。
- グループ操作のドメイン間での成功は、Group Host の受理と順序付けを意味します。
- 私信のドメイン間での成功は、宛先 Agent の入り口サービスの受理を意味します。
- P8 v1 は、外側の E2EE v2 Profile が送信・受信デバイス識別子を宣言する場合だけ、それを保持・検証します。通常の P3/P4/P7 は DID 宛てを維持し、複数エンドポイントへの配信は受信ドメイン内で行います。ゲートウェイは、その操作にデバイス selector を足さず、E2EE 配信を隠れて複数宛先へ展開することもしません。

## 5. 主な設計上の選択

ANP は、意図的に次の選択をしています。

### 5.1 業務アイデンティティとデバイスエンドポイントの分離

v1.1 では、デバイス、端末、複製を Agent の内部詳細としました。Messaging 1.2 は、通常メッセージの DID 宛てという境界を維持します。P3、P7、P8 は v1 を保ち、P4 は DID-only メンバー関係と Host 調整の更新のため v2 になります。P5/P6 v2 は暗号学的エンドポイントの境界を調整し、デバイス鍵や Ratchet の共有、隠れた暗号化配信の展開、MLS Leaf の曖昧さを避けるために必要な、最小のデバイス識別子と鍵の結合を公開します。DID は引き続き業務アイデンティティであり、製品内のデバイス管理は対象外です。

### 5.2 最大の匿名性よりグループ管理を優先

グループでは、次のものを同時に維持します。

- 発信者の証明：誰が要求を開始したか。
- グループ結果の証明：グループが受理したか。
- グループ内メッセージの機密性：MLS。

純粋な匿名チャットよりも、管理を行いやすい Agent のプロトコルを重視しています。

### 5.3 添付の安全性を隠されたリンクに依存させない

ダウンロードリンクを完全に隠すことを主要な安全策にせず、次を使います。

- 管理されたダウンロードチケット。
- 短期 URL。
- オブジェクト単位の暗号化。

これにより、リンクが漏れても意味のある平文を取得できるとは限らなくなります。

## 7. まとめ

ANP の中核は、チャットプロトコルを作ることではなく、**Agent の生態系に向けたドメイン間通信標準**を作ることです。

基本的な考え方は次のとおりです。

- **フェデレーション**：電子メールのようにドメイン間で相互接続します。
- **アイデンティティ優先**：DID を共通の基点にします。
- **デバイスの安全性を考慮した E2EE v2**：一つの DID が複数の独立した暗号エンドポイントを公開でき、DID 単位の業務アイデンティティや通常メッセージの宛先の境界を変えません。
- **階層化**：業務、暗号化、添付、フェデレーションを分けます。
- **E2EE の任意の重ね合わせ**：基本プロトコルは単独で動き、安全性の Overlay を必要に応じて有効にします。
- **添付の直接ダウンロード**：メッセージで manifest を運び、オブジェクトは独立した HTTP(S) データプレーンで取得します。
- **管理のしやすさ**：特にグループで、アイデンティティ、順序付け、受領証、暗号化を同時に考慮します。

ANP は、実装可能なプロトコル体系であると同時に、長期的な標準化の発展の基盤にもなります。
