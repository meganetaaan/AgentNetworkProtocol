## 要旨

本稿は、分散型識別子（DID）とエンドツーエンド暗号化通信技術に基づき、エージェント間でプラットフォームをまたぐ認証と安全な通信を実現するためのプロトコルを提案します。W3C DID仕様、ブロックチェーン、TLSを組み合わせ、低コストで効率的かつ安全な認証・暗号化通信方式を設計します。allというDIDメソッドを導入し、異なるプラットフォームの識別体系を相互運用可能にして、HTTPSなどの標準プロトコルで認証します。DID文書の生成・検証とDIDベースのエンドツーエンド暗号化を詳述し、効率的で安全な短期鍵の交渉と通信の流れを示します。最後に、エージェント協調ネットワークの将来と、DIDベースの識別体系の幅広い応用を検討します。

## 1. はじめに

エージェントは、AndroidやiOSに続く重要なプラットフォームになろうとしています。将来、個人、組織、企業は、それぞれサービスを提供するエージェントを持つでしょう。エージェントは単独では存在できず、人間の需要を満たすため他のエージェントとの協調を必要とします。例えば個人アシスタントは、衣食住や移動に関わるエージェントと連携して生活を支援します。衣料品店のエージェントも、生産、設計、流通など上流・下流のエージェントと密接に連携します。この協調ネットワークは、より高度なサービスを提供する次世代インターネットの重要な構成要素となります。

ネットワークを効率よく動かすには、互いを発見して接続し、本人確認、安全な暗号化通信、標準方式による協働を行う必要があります。

現在、多くのエージェントはプラットフォーム固有のIDに依存しており、異なるプラットフォームの識別体系を相互接続できず、低コストな接続を妨げています。また、TLSなど既存の安全な通信方式は主にクライアント・サーバー間で使われ、認証局（CA）が発行する証明書に依存します。エージェントが低コストで効率的かつ安全に暗号化通信する、理想的な方式はまだありません。

そこで、W3C DID、ブロックチェーン、TLSを組み合わせ、異なるプラットフォームのIDを低費用でつなぐ方法と、低費用・高効率・安全な暗号化通信の方法を提案します。プロトコルによる協働の構想も示します。

## 2. DIDに基づくクロスプラットフォームのアイデンティティ認証

W3C DID（分散型識別子、参考文献[2]）は、従来の中央集約型の身元管理における、中央への依存、プライバシーとデータの制御、相互運用、安全性の課題に取り組む新しい識別子の標準です。

W3C DID仕様をベースに、新DID方式の設計によりアイデンティティ認証スキームを提案します。 この方法は、ID の相互運用性の利点を活用し、アイデンティティ検証プロセスを簡素化し、相互運用性の欠如と異なる集中システム間のアイデンティティ検証の複雑さと冗長性を解決します。

### 2.1 DID 方法 "all" (アライアンス)

DID メソッドは、DID の作成、解決、更新、および非アクティブ化の方法を規定する分散型識別子(DID)の実装です。 各 DID メソッドは、特定のブロックチェーンや分散型ネットワークに関連付けられており、そのネットワークと相互作用するための具体的なルールを定義します。

既存のDIDメソッドの多くはブロックチェーンを基盤とし、その技術の現状から、拡張性や商用化に大きな課題があります。Webベースのメソッドはドメイン名と深く結び付き、Web事業者にDID関連操作への対応を求めるため、複雑さを増します。

コンソーシアムブロックチェーンと同様に、 "all" (Alliance) という新しい DID メソッドをご提案します。 この方法の標準をサポートするすべてのサービスプロバイダは、外部にDID関連サービスを提供することができます。 DID ユーザーは、価格設定、サービスレベル、評判などの要因に基づいて 1 つ以上のプロバイダーを選ぶことができます。 このメソッドをサポートするすべてのサービスプロバイダは、サービスドメインをブロックチェーン上の特定のメモリ領域に登録して、「all」メソッドのすべてのユーザーがサービスプロバイダーの完全なリストにアクセスできるようにします。

また、DID クリエイターは DID ドキュメントのホスティングサービスドメインを指定して、DID 解決者に特定のサービスプロバイダやユーザホストサーバーから DID 文書を取得できるように通知することができます。

最後に、すべての"all"メソッドの全ての操作はHTTPSのような標準Webプロトコルを使用して既存のWebインフラストラクチャを活用します。

### 2.2 「all」メソッドの設計

allメソッド設計の中核は、暗号技術でDID文書の改ざん防止を確保し、コンソーシアムのノードでシステムの分散性を維持することです。

「all」メソッドでDIDの作成、解決、更新、および非アクティブ化のためのすべての操作は HTTPS を使用します。 コアプロセスは次の通りです。

![コアプロセス:すべてのメソッド](../../../images/did-all-core-flow.png)

1. 利用者Aは、ブロックチェーンなどの分散保存先からallメソッドのサービスドメイン名一覧を取得するか、自前のDIDサービスを使います。

2. User A は DID と DID ドキュメントを作成し、 1 つ以上のノードを選択し、DID 文書をホストする HTTP リクエストを開始します。

3. ユーザーBは、ブロックチェーンや分散ストレージから「all」メソッドサービスドメインリストも取得します。

4. ユーザ B は、サービスドメインノードから、ポーリングまたは同時クエリを使用して DID ドキュメントを問い合わせます。

DID allメソッドの設計仕様：[02-did:allメソッド設計仕様](02-did-all方法规范.md)

ここでのDIDは、"did:all:14qQqsnEPZy2wcpRuLy2xeR737ptkE2Www@example.com:443"です。

allメソッドの一意な識別子は、verificationMethod内の公開鍵から、Bitcoinのアドレス生成に似た方法で生成します。CAなどの第三者なしで、文書の公開鍵がDIDに対応するか検証できることが利点です。例えば、次のように行います。

- 検証側は文書を読み、まず安全な経路で取得したDID自体の正しさを確認します。
- 公開鍵から生成したDIDが文書内のDIDと一致するか確認します。一致すれば、その公開鍵は正しいものです。
- 公開鍵でproof部分の署名を検証します。成功すれば、文書は改ざんされていません。

これにより、DID文書自体の改ざんや、ホスティング事業者が無断で文書を書き換えることを、効率的かつ低コストに防ぎます。

対応する秘密鍵が漏えいした場合、利用者はDIDの失効・更新処理を開始し、関係者へDIDの更新を通知できます。

### 2.4 プラットフォームをまたぐ認証の流れ

DIDに基づくクロスプラットフォームのアイデンティティ認証では、既存のアイデンティティシステムを放棄する必要はありません。 DIDは、元のシステムの内部ロジックを変更しないように、2つのシステム間でのアイデンティティ認証のためにのみ使用することができます。 例えば、ユーザーは1つまたは複数のDIDを申請し、既存のIDにそれらを結合することができます。

それぞれプラットフォームAとプラットフォームBに登録された2人のユーザー、A、Bがそれぞれ存在します。 以下は、AとBがお互いのDID文書を探し、メッセージサービスを入手し、通信する方法について説明しています。

![クロスプラットフォームのアイデンティティ認証プロセス](../../../images/cross-platform-identity-authentication-process.png)

**プロセスの説明:**

1. AとBが、対面のスキャン、SMS、WeChat、公開の照会など、信頼できる経路でDIDを交換します。
2. それぞれが相手のDIDを自分のサーバーへ送り、サーバーがDID文書を照会します。
3. 返された文書のID、公開鍵、署名が正しいか検証します。正しければ文書は改ざんされていないと判断し、メッセージサービスのエンドポイントを取り出して、暗号化通信を開始します。

## 3. エンドツーエンド暗号化通信

本節は、DIDを持つ2者が互いの識別を検証した後、安全かつ効率的にエンドツーエンド通信する方法を説明します。通信の安全性を最優先とし、データの暗号化・完全性・前方秘匿性の確保、中間者攻撃・リプレイ攻撃の防止を図ります。

### 3.1 スキームの概要
このソリューションは、TLSやブロックチェーンなどの実践において実証済みの高セキュリティ技術を活用し、DIDに基づくエンドツーエンドの暗号化通信スキームの設計に組み込む。 このスキームは、異なる2つのプラットフォームでユーザー間で安全な暗号化通信に使用できます。

WebSocketの上に、DIDに基づくメッセージのルーティングと短期鍵の交渉の仕組みを設計しました。DIDを持つ両者が、文書の公開鍵と自身の秘密鍵を使い、ECDHE（楕円曲線一時Diffie-Hellman）で短期鍵を交渉します。その有効期間内に鍵でメッセージを暗号化して通信します。ECDHEにより、第三者のメッセージ代理や中間者が転送しても、不正に復号できないようにします。

インターネット上で広く使用されているため、Websocketプロトコルを選択し、利用可能なインフラが多岐に渡り、スキームの早期推進に不可欠です。 また、Websocketの上にエンドツーエンドの暗号化方式を設計しているため、Websocketセキュアプロトコルを使用する必要はありません。そのため冗長暗号化と復号の問題を回避します。

現在の方式は、本質的には、転送層の暗号化をアプリ層の暗号化で置き換え、既存の基盤を使いながら、普及の難しさを下げます。

全体的なプロセスは次の通りです:

![エンドツーエンド暗号化](../../../images/end-to-end-encryption-process.png)

注：第三者のメッセージサービスが存在しない構成も可能であり、利用者は自前のサービスを使えます。

現在、双方向プロトコルであるため、Websocketプロトコルのみをサポートしています。 今後、HTTPプロトコルをサポートして、より多くのシナリオを拡大していくことを検討します。 また、今後トランスポート層でのエンドツーエンド暗号化方式の導入を検討し、より多くのシナリオで活用できる体制を構築します。

### 3.2 暗号化された通信プロセス

異なるプラットフォームの利用者A（DID-A）とB（DID-B）がいるとします。両者はDID SERVERで、公開鍵を含む相手の文書を取得できます。

暗号化された通信を実行するには、AとBは、短期鍵の作成を開始する必要があります。 短期鍵を作成するプロセスは、TLSの一時的な暗号化キーの生成に似ています。 これらのキーは有効期限があり、期限が切れる前に、作成プロセスは新しいキーを生成し、それらを更新するために再起動する必要があります。

A と B が交渉された短期鍵を保持したら、A はメッセージを B に送信したい場合、A はキーを使用してメッセージを暗号化し、メッセージサーバーを介してメッセージングプロトコルを介して B に送ることができます。 メッセージを受信すると、B はキー ID を使用して対応するキーを受け取り、キーを使ってメッセージを復号化します。 対応するキーが見つからなかったり、期限が切れてしまった場合は、B はエラーメッセージを送信します。A に通知して、短期鍵の更新プロセスを開始します。 短期キーを更新した後、A はメッセージを再送できます。

```plain
Client (A)                                      Client (B)
|                                                 |
| -- Initiate Short-term Key Creation Process --> |
|                                                 |
|      (Create Temporary Encryption Key)          |
|                                                 |
| <---- Temporary Key Created ----                |
|                                                 |
|       (Key has an expiration time)              |
|                                                 |
|      (Monitor Key Validity)                     |
|                                                 |
|   (Before expiration, restart creation process) |
|                                                 |
| (A and B now have a negotiated short-term key)  |
|                                                 |
| ---- Encrypted Message ---->                    |
|                                                 |
|     (Encrypt message using short-term key)      |
|     (Send via message server)                   |
|                                                 |
| <---- Receive Encrypted Message ----            |
|                                                 |
|     (Find stored key using key ID)              |
|     (Decrypt message)                           |
|      (If key not found or expired)              |
|                                                 |
| <---- or Error Message ----                     |
|                                                 |
|      (Notify A to update short-term key)        |
|                                                 |
```

### 3.3 短期キーの交渉プロセス

短期鍵作成プロセスは、以下の違いで、TLS 1.3の主要交換プロセスと基本的に似ています。

- 全体では、SourceHello、DestinationHello、Finishedの3つのメッセージだけを使います。それぞれTLSのClientHello、ServerHello、Finishedに対応します。TLSのようにクライアントとサーバーを区別せず、送信元と送信先だけを区別します。
- EncryptedExtensions、Certificate、CertificateVerifyなど、他のメッセージは必要ありません。具体的には：
  - EncryptedExtensionsは現時点では省略しますが、将来、暗号の拡張情報を伝えるために追加する可能性があります。
  - CertificateとCertificateVerifyは主にサーバーの公開鍵の安全性を確保するものですが、この方式ではDIDアドレスと公開鍵の対応で正しさを確認するため、必要ありません。各公開鍵がただ1つのDIDに、各DIDがただ1つの公開鍵に対応します。
- SourceHelloとDestinationHelloにはそれぞれの署名があり、メッセージの完全性を確保しているため、Finishedではハンドシェイクメッセージのハッシュ化・暗号化を行いません。
- 送信元と送信先は、複数の短期鍵交渉を同時に開始できます。複数の鍵を並行して保持し、異なる種類のメッセージの暗号化に使えます。

プロセス全体図は以下です。

```plain
Client (A)                                          Server (B)
   |                                                    |
   |  ---------------- SourceHello ---------------->    |
   |                                                    |
   |         (Include public key and signature)         |
   |                                                    |
   |                                                    |
   |  <------------- DestinationHello ------------      |
   |                                                    |
   |         (Include public key and signature)         |
   |                                                    |
   |                                                    |
   |  -------- Finished (Include verify_data) ------->  |
   |                                                    |
   |  <-------- Finished (Include verify_data) -------- |
   |                                                    |
   |                                                    |
```

短期鍵の交渉処理：[did:allメソッドに基づくエンドツーエンド暗号化通信プロトコル](04-基于did的端到端加密通信技术协议.md)

## 4. 今後の展望

### 4.1プロトコルベースのインテリジェントコラボレーション

通信プロトコルの特定の設計について議論するものではありませんが、このような設計はインテリジェントエージェントのネットワークを形成するために不可欠です。

大規模言語モデルにより、ソフトウェアの自然言語理解が大きく進み、人と機械のやり取りにも大きな影響が見えています。自然言語は重要なインターフェースになるでしょう。それなら、ソフトウェア同士の言葉にもなれるでしょうか。非常に興味深い課題です。

音声通話やインターネットのアプリなど、従来のソフトウェアは、厳密に定義したバイナリまたはテキストのプロトコルで連携します。一方が標準に厳密に従わないと連携が失敗し、しばしばプログラマーが手動でバグを修正してコードを再配置する必要があります。

AIが自然言語を理解し、自動的にコードを生成することができるとき、より柔軟なインタラクションプロトコルを定義し、自然言語のフィールドの詳細説明で、AIがプロトコルを正確に理解できるようにすることができますか? 2つのシステム間の初期の統合とテストプロセスは、AIによって処理される可能性があり、両当事者が合意した特定のフィールドを交渉し、コードを変更して、交渉されたプロトコルに適応させ、自動的にバグをテストし、バグを修正し、結果を確認し、2つのシステム間で低コストの統合を実現することができます。

### 4.2 技術実装の推奨事項

提案されたスキームは、ユーザーの自律性を十分に考慮し、サードパーティのDIDホスティングサービスやメッセージサービスまたはセルフホストサービスの使用から選択することができます。 どちらのオプションも同等のセキュリティを提供します。

ユーザーがセルフホストサービスを選択すると、災害復旧、拡張性、安全性（DoSやリプレイ攻撃の防止など）を考慮する必要があります。

開発コストと運用コストを考慮し、特に中小規模のユーザーには、プロフェッショナルなサードパーティサービスを使用することをお勧めします。

### 4.3 DIDネイティブアイデンティティシステム

本稿ではDIDをプラットフォーム間の本人確認だけに使いましたが、用途はさらに広がると考えます。中央への依存、プライバシーとデータの制御、相互運用、安全性を根本的に解決する、DIDを前提とした身元体系を期待します。

### 4.4 マルチメディアフォーマットのサポート

現在、プロトコル設計はテキストコンテンツを送信するだけをサポートしています。 インターネットは、オーディオ、ビデオ、ファイルなどのマルチメディアコンテンツの膨大な量をホストし、ライブストリーミングやRTCなどのリアルタイム音声およびビデオコンテンツを配信します。

今後、これらのマルチメディアフォーマットをサポートし、インテリジェントエージェント間のより包括的なコラボレーションを可能にしていく予定です。

### ブロックチェーンに基づく4.5分散ソリューション

私たちが設計したDIDは、ブロックチェーンアドレスに本質的に同等であり、ブロックチェーンのウォレットアドレスとしても機能します。 これにより、ブロックチェーンに基づく完全に分散型アイデンティティシステムを構築することができます。 DID 文書をパブリッククエリのためにブロックチェーンに公開することができます。DID ベースの取引と決済の容易化、インテリジェントなエージェント間の価値の移動をより便利にするブロックチェーン上でビジネス関連のトークンを作成できます。また、ブロックチェーンが組織する分散コンピューティングパワーを活用して、分散型インテリジェントエージェントメッセージサービスネットワークを形成します。 未来の可能性はもっとあるはずです。

### 4.6 バイナリ通信プロトコル

現在の通信プロトコルは、主にWebSocket+JSONに基づいており、TLSなどのバイナリプロトコルと比較して効率の不利な点が発生しています。 未来のインフラを目指し、将来的にはトランスポート層バイナリプロトコルを開発する予定です。

## 5. 結論

本稿は、DIDに基づく、プラットフォームをまたぐ認証とエンドツーエンド暗号化通信の方式を提案しました。allメソッドにより識別体系間の相互運用の課題を解決し、認証を簡素化します。HTTPSとブロックチェーンで文書の改ざん防止とシステムの分散性を確保し、TLSなどを参考にした短期鍵の交渉により、機密性と完全性を備えた暗号化通信を実現します。エージェントネットワークの協調や、DIDを基盤とする識別体系の応用・将来の方向性も示しました。広い応用の可能性を持ち、効率的で安全なエージェントネットワークの基盤となる方式です。
