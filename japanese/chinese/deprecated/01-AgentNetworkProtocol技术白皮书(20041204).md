## インフォメーション

本稿では、スマートボディクロスプラットフォームのアイデンティティ認証とセキュアな通信の現在の課題に対応するため、機密性の高い識別子(DDID)およびエンドツーエンド暗号化通信技術を提案しています。W3C DID仕様を組み合わせることで、チェーン技術とTLSプロトコルをブロックすることで、低コストで効率的かつ安全なクロスプラットフォームの識別と暗号化されたコミュニケーションプログラムを設計します。

## 1. 導入事例

スマートは、Android、iOS、および将来の個人、組織、企業など、さまざまな知能がそれ自身に提供するように、次の重要なプラットフォームになります。スマートな人は独立して存在することはできません、それは他のインテリジェントな人々と仕事をする必要があります。 パーソナルアシスタントはまた、食品や衣類などのライフ関連インテリジェンスサービスを必要とするインテリジェントなボディであり、衣料品店のスマートボディは生産、設計、チャネルなど、様々な知的に対処する必要があります。 インテリジェントなネットワークは、次世代のインターネットを提供することができるでしょう。

スマートネットワークの効率的な機能には、インテリジェントが互いに接続し、お互いにそれぞれ確認できること、相互に認証し、安全かつ暗号化を伝え、標準的なプロトコルで効率的に作業することが必要です。

現在のスマートの大部分は、プラットフォームIDに依存しています。異なるプラットフォーム間でのアイデンティティシステムがアクセスできず、インテリジェンスはプラットフォーム全体で低コストに接続できません。一方、現在のセキュアな通信プログラム(例えば、TLS)の大部分は、クライアントからサービス通信のために使用され、認証機関がCA(証明書局)証明書を発行するだけでなく、インテリジェント間の低コスト、効率的な安全な暗号化通信のための非常に理想的なオプションはありません。

このコンテキストでは、DID に異なるプラットフォームを配置し、インテリジェントな個人がコストで電子的に通信できるようにする低コストのプログラム、効率的かつ安全なレベル、W3C DID (集中型識別子) 規制、ブロックチェーン技術、TLS(トランスポート層セキュリティ)技術、プロトコルベースのスマートボディのアイデアなど、さまざまなプラットフォームを組み合わせて通信することができます。

## 2. DIDベースのクロスプラットフォームアイデンティティ

W3C DID (集中識別子、集中識別子に行く)[2]従来の一元化されたアイデンティティ管理システム、プライバシーおよびデータ制御、相互運用性およびセキュリティの集中化のような問題に対処するために設計されている識別子の新しいタイプ。

当社では、W3C DD規格に基づく新しいDIDアプローチを設計しました。これにより、DIDの相互運用性を活用し、同一証明プロセスを簡素化し、異なる集中システム間の相互運用性が欠如し、複雑さとアイデンティティ検証の問題が長くなります。

### 2.1 DID 方法アライアンス

DID メソッド (DDMethod) は、DID の作成、解釈、更新、およびキャンセル方法を提供する、集中された識別子 (Decentrazed Identifier, DID) の達成方法です。各 DID メソッドは、特定のブロックチェーンまたは DEC ネットワークにリンクされ、そのネットワークとのやり取りのための特定のルールを定義します。

既存の定義された DID メソッドの大部分は、ブロックチェーン設計に基づいており、ブロックチェーン技術フェーズに限定され、拡張、商品化、ランディングに非常に大きな問題があります。 Web ベースの DID アプローチは、ドメインの名前の深さに縛られ、Web サービスプロバイダが DID 関連の操作をサポートしていることを要求しています。これは、Web サービスプロバイダーにとって複雑です。

当社では、同行のブロックチェーンにリンクする新しいDID方法論(同盟)を提案しています。つまり、このメソッドの標準をサポートするすべてのサービスプロバイダは、外部の世界へのサービスを提供できます。DIDユーザーは、すべてのサービスプロバイダーの価格、レベルのサービス、評判などに応じて1つ以上のサービスを選ぶことができます。このアプローチをサポートしている全てのサービスは、ブロックチェーンの特定のメモリに独自のサービスドメイン名を記述して、すべてのすべてのサービス利用者が完全なサービスリストを提供することを保証します。

DID の作成者は、DID ドキュメントのホスティングサービスドメインで DID を指定して、 DD クエリーを通知し、特定のサーバーやユーザーが構築したサーバに DID 文書にアクセスすることができます。

最後に、Allメソッドは、既存のWebインフラストラクチャを利用するすべてのアプローチを有効にするには、httpsなどの標準的なWebプロトコルを使用して動作します。

### 3. 暗号化されたエンドツーエンドコミュニケーション

このセクションでは、DIDを保持する当事者が相互識別後の安全で効率的なエンドツーエンドの通信を実施する方法について説明します。 彼らのコミュニケーションでは、セキュリティは不可欠であり、データの暗号化、データ完全性、機密性を転送し、中人を防ぎ、再エントリー攻撃に対する保護などを必要とします。

#### 3.1 プログラムの概要

プログラムは、TLS、ブロックチェーンなどの練習で既にテスト済みの高セキュリティ技術に引き込まれています。これらの技術は組み合わされ、DIDベースのエンドツーエンド暗号化通信プログラムが2つの異なるプラットフォームのユーザー間の安全な暗号化通信のために設計されています。

当社は、ID の当事者が DID ファイル内の秘密鍵を使用できる Websocket 合意と短期キー協議に基づいてニュース ルーターを設計しました。また、ECDHE (Elliptic Curve Diffie-Hellman Ephemeral) を使用して、鍵の有効期間中に重要なメッセージの暗号化による通信を確保します。ECDHE は、そのような情報が、Triangular Agent などの不正な通知であっても、その情報が偽りなく侵害されることを保証します。

インターネット上で非常に広く使用されているため、Websocketプロトコルを選択し、早期の拡張に不可欠である利用可能なインフラの大きな取引があります。 同時に、再分類の問題が回避されるように、Websocketセキュリティ協定を再び使用する必要はありません。

弊社の現在のプログラムは、既存のインフラに基づく合意を促進しやすくなる、アプリケーションレベルの暗号化で送信レイヤーの暗号化を置き換えることに不可欠です。

全体的なプロセスは以下に示されます:

![エンドツーエンド暗号化](../../../images/end-to-end-encryption-process.png)

コメント: メッセージサービスには3人のパーティーが存在しないため、ユーザーは自分のニュースサービスを使用することができます。

今後、Websocketの合意は2方向の合意であり、今後 http プロトコルのサポートを検討するからです。また、トランスファーレベルにエンドツーエンド暗号化プログラムが達成されるため、より多くのシーンで使用できることを検討します。

#### 3.2 暗号化された通信プロセス

プラットフォームの2人の場合、A(DD-A)、B(ID-B)、A、Bは、DIDの各ドキュメントにアクセスでき、また、文書には公開鍵が含まれている。

暗号化された通信を行うには、AとBは短期鍵プロセスの作成を開始する必要があります。短期鍵を作成するプロセスは、TLSの一時的な暗号化用に類似しています。これは1つの有効期間を持ち、その周辺で期限切れになる前に短期鍵プロセスの作成を再起動し、新しいキーを生成して更新する必要があります。

A と B が協議の後に短期鍵を保持する場合、A はメッセージを B に送信したい場合、メッセージをキーで暗号化し、メッセージ送信プロトコルを使用して B にメッセージを送信し、メッセージサービス担当者から送信します。B の受領後、保存されたキーはキー ID に従って発見され、暗号化されたメッセージは復号化されます。対応するキーが見つからなかったり、キーが期限切れてしまった場合は、間違ったメッセージを送信し、更新された短期鍵がプロセスが再送信されるかを A に通知してください。
```plain
Client (A)                                      Client (B)
|                                                 |
| -- Initiate Short-term Key Creation Process --> |
|                                                 |
|      (Create Temporary Encryption Key)          |
|                                                 |
| <---- Temporary Key Created ----                |
|                                                 |
|       (Key has an expiration time)              |
|                                                 |
|      (Monitor Key Validity)                     |
|                                                 |
|   (Before expiration, restart creation process) |
|                                                 |
| (A and B now have a negotiated short-term key)  |
|                                                 |
| ---- Encrypted Message ---->                    |
|                                                 |
|     (Encrypt message using short-term key)      |
|     (Send via message server)                   |
|                                                 |
| <---- Receive Encrypted Message ----            |
|                                                 |
|     (Find stored key using key ID)              |
|     (Decrypt message)                           |
|      (If key not found or expired)              |
|                                                 |
| <---- or Error Message ----                     |
|                                                 |
|      (Notify A to update short-term key)        |
|                                                 |
```

#### 3.3 短期鍵相談プロセス

短期鍵作成プロセスは、以下の点で TLS1.3 の暗号化キー交換に基本的に似ています。

- TLSの ClientHello と SeverHello に相当する、SonceHello、Detininghello、Finished は3つのメッセージのみが利用できます。当社のプロセスではクライアントやサービスがないので、ソースと目的だけではありません。

- EnrichptedExtensions、証明書、証明書などの他のソースは必要ありません。

  - 暗号化された拡張子は、時間内に利用できませんが、暗号化拡張機能のパスに追加される場合があります。

  - 証明書、証明書の確認は不要です。これらのメッセージの主な目的は、サービスの公開鍵が安全であることを確認することですので、公の鍵とDIDアドレスを一致させることで、DID-to-publicキーの正しさを検証します。つまり、パブリックキーが決定されているため、1つのIDのみが、DDは1つだけあることを決定します。 DDは、その存在が1つしかないことを決定します。

- 署名がすでにSourseHelloとDestinyhelloに含まれているため、ハングークをハスリングして暗号化しなくなったので、メッセージの完全性を保証します。

- Source and Destination は複数の短期鍵の相談を同時に起動でき、さまざまな種類のメッセージ暗号化で使用できるキーがいくつかあります。

フローチャート全体は以下の通りです。
```plain
Client (A)                                          Server (B)
   |                                                    |
   |  ---------------- SourceHello ---------------->    |
   |                                                    |
   |         (Include public key and signature)         |
   |                                                    |
   |                                                    |
   |  <------------- DestinationHello ------------      |
   |                                                    |
   |         (Include public key and signature)         |
   |                                                    |
   |                                                    |
   |  -------- Finished (Include verify_data) ------->  |
   |                                                    |
   |  <-------- Finished (Include verify_data) -------- |
   |                                                    |
   |                                                    |
```

### 4.1 合意に基づくスマートコラボレーション

コミュニケーションにおける合意の具体的な設計はここで議論されていないが、インテリジェントな組織にとっては共同ネットワークを形成する必要不可欠です。

大規模な言語モデリング技術が発展するにつれて、ソフトウェアシステムは自然言語の理解を大きく高めており、人間とのやりとりに大きな影響を与えることは広く考えられます。自然言語は人の間で重要なインターフェイスであることができます。その言語はソフトウェア間で主要な対話的な言語になりますか?私たちはこれが非常に興味深い主題だと思います。

AIが自然言語を理解し、自動的にコードを生成することができるとき、私たちはより広い対話的な合意を定義し、それが正確に合意を理解することができるように自然言語のフィールドを記述することができますか? 2つのシステム間の最初の相互接続プロセスはAIによって行われる可能性があり、それは、両方の締約国で合意した特定のフィールドを決定するための協議に基づいて、コードを修正して、2つの側面の交渉された協定に収まるように、自動テスト、バグの修復、検証結果と最終的に2つのシステムインターフェイスを低コストで完了させる。

### 4.2 技術的実現の推奨事項

当社が設計したプログラムでは、DIDホスティングサービス、ニュースサービスなど、ユーザーのSを完全に考慮に入れ、セキュリティ面では違いません。

ユーザーが独自のサービスを構築する場合、災害の調製や拡張、安全などの重要な特性を考慮に入れる必要があります(再エントリー攻撃を防ぐ)。

開発・輸送コストは、特に小型・中型ユーザー、専門的三脚サービスを利用することをお勧めいたします。

### 4.3 DIDの第一次同一証明システム

今回は、クロスプラットフォームのアイデンティティのみにDIDを使用していますが、今後はDIDの未来のユーティリティはそれよりもはるかに多くあると思います。従来の一元化されたアイデンティティ管理システム、プライバシーおよびデータ制御、相互運用性、セキュリティなどの重要な問題に対処するため、将来的には第一世代のDID識別システムを見たいと思っています。

### 4.4 マルチメディアフォーマットのサポート

プロトコルはテキストコンテンツのみをサポートするように設計されています。

これらのフォーマットのメディアコンテンツは、将来的にサポートされています。これにより、インテリジェントな人々の間でより包括的なコラボレーションが可能になります。

### ブロックチェーンに基づく4.5度集中プログラム

私たちが設計したDIDは、基本的にブロックチェーンアドレスと同じであり、それらはまたブロックチェーン用のウォレットアドレスとして使用することができます。したがって、ブロックチェーンに基づいて完全に偏ったアイデンティティシステムを構築することはオプションになります。私たちは、誰もがそれらを見ることができるように、ブロックチェーンにDIDファイルを投稿することができます。ブロックチェーン内のビジネス関連のトークンを作成して、DIDベースの取引と決済によってより簡単に送信されるようにします。ブロックチェーンを使用して分散アルゴリズムを整理し、偽造されたネットワークを形成する。

### 4.6 バイナリ通信契約

現在の通信契約は、TLSバイナリプロトコルと比較して効率性に自然な欠点を持つWebsocket+jsonによって支配されます。将来のインフラになるという目標を掲げ、転送層に基づいてバイナリベースのプロトコルを開発します。

## 5. インフォメーション

この論文は、スマートボディネットワークにおける識別と安全な通信の課題に対応する革新的でDIDベースのクロスプラットフォーム認証およびエンドツーエンド暗号化通信プログラムを提供します。 DIDに対する「オール」アプローチを導入することにより、異なるインタープラットフォーム識別システム間の相互運用性を保ち、識別プロセスを合理化します。このプログラムは、HTTPSプロトコルとブロックチェーン技術を使用して、IDファイルの非mutilabilityおよびシステム分布特性を保証します。
