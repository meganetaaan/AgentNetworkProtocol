## 1. バージョン境界

このディレクトリのドキュメントは、元の1.1文書ベースラインを置き換えるANP Messaging 1.2コードコレクションを形成します。 P6は、その全体にこのディレクトリに含まれていますが、安定したMLSエクスポートタイプの登録のしきい値が完成するまで候補のままです。 含めることは、安定した相互運用可能なリリースステータスに達したP6 v2を表すものではありません。

- **プロフィールのマスター版**独立した相談をマークするなど `anp.direct.base.v1` または `anp.direct.e2ee.v2`。
- **Messagingコードブック版**座標方式でリリースされたドキュメントとディレクトリをマークします。ANP Messaging 1.2は、V1とv2のプロファイル識別子の両方を意図的に含んでいます。
- 各Profileには独立したライフサイクルがあります。新しいプロファイルへの依存は、メインバージョンをアップグレードするためにチェーン内の他のプロファイルロックアップを必要としません。
- P1、P2、P3、P7、P8、P9 管理バインディングは v1 規制を維持します。P4 は、ハンドルバックされたメンバーシップモードを削除し、スイッチング方法を開き、ホストがワイヤー制御とステータスマシンを変更するための新しい DID を追加しているため、v2 を使用します。
- P5 直接 E2EE および P6 グループ E2EE は、マルチイケメン ワイヤー条件とパスワードステータスマシンが V1 と互換性がないため v2 を使用します。
- エージェント DID は、ビジネス ID を残します。この DID のパスワードデバイスエンドポイントが Profile によって要求される場合にのみ、メッセージング 1.2 が導入されます `device_id`。
- 通常の非E2EEプライベートチャット、グループ会話、メンションおよび添付操作は、機器の自作者を必要としたり、持ち運びしたりすることなくDIDアドレスを維持します。 これらの操作のためのデバイスは、ローカルでDIDドメインを受信するから外出されます。
- デバイスの場所のセキュリティ操作は、そのファイルが完全な依存性セットと有効な電流を宣言した必要があります `deviceManifest`DIDが1つのデバイスしか持っていなくても、ベースはマニフェストを必要としません。また、合成も行います。
- `meta.profile` 通訳・能力相談のご依頼は、唯一のバージョンです。 `meta.anp_version` 選択またはプロフィールセットが暗黙的である場合。
- 達成しない()**MUST NOT**) v1から、v1からエンドのフィクションデバイスとして、P5/P6 v2をサポートしたり、v2 E2EEリクエスト/セッションを静かにv1にダウングレードしたりします。

標準リリースではSDK、サービス、製品などは表現しません。

## 3. 混合バージョンの機能ステートメント

通常の v1 メッセージとマルチデバイス E2EE v2 サービスが宣言できます。

```json
{
  "supported_profiles": [
    "anp.core.binding.v1",
    "anp.identity.discovery.v1",
    "anp.direct.base.v1",
    "anp.group.base.v2",
    "anp.attachment.v1",
    "anp.federation.relay.v1",
    "anp.direct.e2ee.v2",
    "anp.group.e2ee.v2"
  ]
}
```

これは、直接ベース、添付ファイルまたはフェデレーションv2の存在を必要としない一連の法的機能です。 各特定のリクエストは、1つのプロファイルのみを選択します:一般ベースv1、直接E2EE v2、グループベースv2、暗号化されたグループe2E v2。

## 4. プロフィールバージョンのルール

古い実現が、必須ワイヤフィールドの追加、削除または再デクラインの名前フィールドを追加したり、フィールドの意味を変更したり、シグネチャやAADカバレッジの変更、スチリウムなどのキーまたはステータスマシンの変更、セキュリティモードのセマティクスを変更するなど、プロファイルメインバージョンをアップグレードします。

分離の明確化、既存の境界を定義する禁止文を追加し、例を修復し、新しいオーバーレイと組み合わせの説明を追加します。オプションの拡張対応後方を追加し、文書内の内部の矛盾を回復してもプロファイルメインバージョンを変更しません。

Profilewire のみ `.v1`、`.v2` これはメインバージョンです。 1.1、1.2などの小さなバージョンは、メッセージングコードブックからあります。**MUST NOT** Profilewireロゴに表示します。

## 5. 株式決定書作成

すべてのメッセージング1.2プロファイルは、次の説明を使用します。

1. エージェントIDは、ベースメッセージのワイヤIDとアドレスです。`device_id` プロファイルによって自己宣言されるオプションのパスワードエンドポイント; それは表示されるとき、それは透明ではありません, DIDデバイスの名前空間で唯一の1であり、Dvice DIDではありません, ビジネスメンバー, ロール, ハードウェア識別子または `target.kind`。
2. `deviceManifest` デバイスを安全に宣言するDIDの現在の公開コレクションです。完全なDIDは、独立したエンドポイント、証拠、EPOCT、ハッシュまたはCASプロトコルを持たないメソッド検証されたDID文書に埋め込まれています。ベースのみが必要なわけではありません。
3. マニフェストのエントリーのみが含まれています `device_id`、`signing_key_id`、`e2ee_key_id` とりあえず `profiles[]`;製品領域における役割、トークン、レジストリの状態、回復および秘密鍵を含むバー。
4. P3、P4、P7 通常のプロセスと P9 ペイロードは、一般的なビジネスである DID またはグループ DID の操作にのみ使用されます。**MUST NOT** リクエストまたは持ち運び `sender_device_id`、`recipient_device_id` または `requester_device_id`P5/P6 は E2EE 装置、セルフおよび操作上の目的の残りを所有します `meta.target.did`。
5. 既存の `anp-rfc9421-origin-proof-v1` データ情報プログラムスキーム; P5/P6 `.v2` プロファイルIDは、自動的に証拠v2を作成しません。 ベースプロファイル認証標準DID。 P5 / P6デバイスフィールド **MUST** オーバーレイの定義で一年中接触する:この操作が使用されるとき `auth.origin_proof` , 校正キーは、選択したマニフェストエントリに一致しなければなりません; P5 MTIテキストは、セッションと認定された AAD セルフポートを結合してデバイスによって送信されます。
6. ANP 専用カメラに展開 `document_version`、`document_hash` またはチェックポイントフィールド; 呼び出し主は、資格変更時に現在のメソッド検証済みのDID文書をリツールします。
7. 機器のセキュリティサイトでは、各デバイスが署名/E2EEプライベートキー、PreKey、ダイレクトラチェットステート、MLSプライベートステータスとリレイをそれぞれ使用し、デバイス間でコピーすることを禁止します。
8. からだ まで `deviceManifest` 削除されたデバイスは、彼らがいたように使用しないでください `device_id` これは、アイデンティティドメインとパーマチュアルです。**MUST NOT** オーバーレイフィールドのエンドポイントの変更と混乱。例えば、P6はグループからMLSリーフを削除します:現在有効なマニフェストデバイス `device_id`新しくパスワードで再構築できる。
9. P6 缶バッジを保持し、MLS 外部タイプを時間内に使用 `0xF0A1` 必須のリーフノードデバイスバインディングをロードします。IANAディストリビューションではなく、安定した登録コードポイントが公開された日付で固定されます。
10. 放棄されたを要求する新しい `meta.anp_version`. 受取人は、互換性や診断のためにフィールドだけを保持するかもしれません。 **MUST NOT** プロファイルまたは追加のプロファイルセットをサポートするために、これを使用します。
11. Messagingwire活動は完全なDIDだけを使用します。 人間の可読性の名前および決断は会員または承認の継続性を定義しないでMessagingwireプログラムの外にあります。
12. メソッド固有の DID 移行、発信者およびサービスでは、以前に認証された DID から登録されたマイグレーションチェーンを検証し、ビジネス戦略の確保を行います。 `alsoKnownAs` または同じパスは、継続性を承認できません。
13. P4 v2 は、現在の DID と一般会員のメタデータをメンバーのメタデータだけに保存します。 エージェント DID 移行は、経験やビジネス戦略によって受け入れられ、同じ内部のメンバーレコードを更新し、生成します `member-did-updated`, 履歴メッセージを書き換える, 返信, 署名またはDID.
14. 共通の DID リクエスト認証は [ANP-02](../02-ANP-基于DID的身份认证协议.md)、メッセージバインディングは P1、DID メソッドの検証は P2 に従います。`did:wba` と `did:web` は、同じメッセージ規則、フィールド、署名／AAD 形式を使用します。
