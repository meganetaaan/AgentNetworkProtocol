# セマンティック Web ロードマップ

https://www.w3.org/DesignIssues/Semantic.html

**Tim Berners-Lee**

**日付：** 1998 年 9 月

**最終更新：** $Date: 1998/10/14 20:17:13 $

**位置付け：** セマンティック WWW のアーキテクチャについて、大局的な計画を示す試み。

**編集状況：** 草案。意見を歓迎する。

**上位：** 設計上の課題

## 概要

これは将来に向けたロードマップであり、思考実験でしか検証していないアーキテクチャ計画である。

依頼を受けて作成した将来の Web 設計ロードマップの一部で、20,000 フィートの高さから見渡すような視点に立つ。概説では足りないほど詳しい説明が必要な領域を、アーキテクチャの概説から切り出したものだ。

20,000 フィートの高さからでは、大きなものでもわずかしか触れられないのは避けられない。ここでいうアーキテクチャとは、物事をどう組み合わせられると考えるかである。ゆっくり変化しているとしても、これは更新し続ける文書だと理解してほしい。

Web データを扱うアプリケーション群を結び付け、一貫した論理データのネットワーク、セマンティック Web を形成するための計画である。

## はじめに

Web は、人同士の通信だけでなく、機械も参加して支援できる情報空間として設計された。その大きな障害の 1 つは、Web の情報の大半が人の閲覧用であることだ。列の意味が少なくとも何らかの用語では明確に定義されたデータベースから作られていても、Web を巡回するロボットにはデータの構造が明らかでない。機械を人のように振る舞わせる人工知能の問題をいったん脇に置き、セマンティック Web では機械処理可能な形で情報を表す言語を開発する。

本書は、技術を順に導入し、現在の Web から、機械による推論が広く強力に使われる Web へ段階的に進むためのロードマップを示す。

これまでの設計上の決定と原則を定義する、Web アーキテクチャに関する説明に続く文書である。

## 機械が理解できる情報：セマンティック Web

セマンティック Web はデータの Web であり、ある意味では世界規模のデータベースに似ている。この基盤を作る理由は別の場所［Web の将来に関する講演など］で述べているので、ここでは私の考えるアーキテクチャだけを概説する。

### 基本的な表明モデル

意味についての表明を扱う汎用的な Web をどう定式化するか考えると、最小限の設計原則から、十分に一般性の高い共通モデルを基礎にする必要がある。共通モデルが一般的であってこそ、想定する任意のアプリケーションをそこへ対応付けられる。この共通モデルが Resource Description Framework である。

RDF モデルおよび構文仕様を参照。

共通モデルとしては極めて単純である。そのため、その上に多くの層を積まなければ、モデルだけでは多くのことはできない。基本モデルは表明と引用、すなわち表明についての表明という概念だけを含む。これを導入する理由は、(a) いずれ必要になること、(b) 初期の RDF アプリケーションの多くがデータについての「メタデータ」を扱い、論理より先に、表明についての表明が基本となることだ。（RDF の想定用途では、表明はあるリソースの記述の一部で、そのリソースはしばしば暗黙の引数になるため、表明をリソースの属性と呼ぶ。）

数学的には、この段階の言語には否定も含意もなく、非常に限定的である。事実の集合があれば、任意の問いに証明があるかどうかを簡単に判断できる。事実にも問いにも、問題を難しくするだけの表現力がないからだ。

この段階でも用途は多い。メタデータ表現の大半をこのレベルの RDF で扱える。カード式索引情報（Dublin Core）、プライバシー情報（P3P）、スタイルシートと文書の関連付け、知的財産のラベル、PICS ラベルなどが例である。ここで扱うのは通常は単純なデータの表現であって、問い合わせや推論規則を表す言語ではない。

このレベルの RDF 文書には強い機能がないため、アプリケーションをわざわざ RDF に対応付ける理由が分かりにくいこともある。理由は、個々の用途では限定的で単純なデータでも、後でほかの用途のデータと結び付いて Web を形作ると期待しているからだ。Web 全体で動くアプリケーションは、共通の枠組みで各用途の情報を組み合わせられなければならない。例えばアクセス制御の論理は、プライバシー、グループへの所属、データ型を組み合わせてアクセスを許可・拒否できる。後の段階の問い合わせでは、データ表現言語があまり強力でない領域も含め、多分野のデータを参照する強力な論理式を使えるだろう。本書の目的の 1 つは、その実現計画を示すことだ。

### スキーマ層

RDF の基本モデルによって黒板上では多くのことをできるが、道具はまだ少ない。表明と引用のモデルを得て、どのような新形式のデータでも対応付けられるようになった段階である。

次には、新しい属性の存在を宣言するスキーマ層が必要だ。さらに、その使い方、通常は適用できる対象の型も制限したい。こうしたメタ表明が、文書の初歩的な検査を可能にする。SGML の DTD が要素の配置を検査するように、RDF のスキーマは、例えば運転免許証の「名前」に車種ではなく人名を使っているかを検査する。

どの基本要素を導入すべきか、この段階で次の層を定義せずに有用な言語を多く定義できるかは、まだ明らかでない。現在この領域には RDF スキーマの作業部会がある。スキーマ言語は、許される組み合わせについて単純な表明をすることが多い。SGML DTD をモデルにすれば、極めて限定的な機能の言語にできる。スキーマ言語の制約は、次の論理層のより強い式へ簡単に展開できるが、機能を制限するため、ここではそうしない。例えば、属性 foo が一意だとスキーマに記述できる。展開すれば、任意の x について、y が x の foo で z も x の foo なら y と z は等しい、となる。これはこの層にはない論理式だが、当面、汎用推論エンジンではなく専用のスキーマエンジンだけが扱うなら問題ない。

ある言語でこのようなことをする場合、論理的な定義が明確なままであるよう注意しなければならない。こうした場面は多くなるだろう。後に、スキーマ言語の論理的な意味を理解し、ほかの論理情報と組み合わせることによってしか実行できない推論をしたくなるかもしれない。

### 変換言語

名前空間に関する作業での進化可能性の要件として、ある RDF スキーマの文書を別のスキーマへ変換する規則に従うには、汎用 RDF をある程度理解する必要がある（変換先の扱いはもともと知っていると考える）。

最小能力の原則に従えば、含意（推論規則）はあっても否定はない言語にできる。（実際には A から B を導く規則を簡単に書け、B がたまたま偽であっても「偽」と書く手段がない、という点は興味深い。しかし形式上はパラドックスを書く力がなく、これで安心する人もいる。以下で表現力が増すときには、矛盾した文を作る能力の有無に頼らず、アプリケーションが個々の文書の表現力を明示的に制限する。スキーマはその制限を記述するのに便利な場所になる。）

この層の簡単な例は、独立に作られた 2 つのデータベースを Web で公開し、意味上のリンクで結び、一方の問い合わせを他方へ変換できるようにすることだ。友人テーブルの「where」と場所テーブルの「zip」が同じ意味だと誰かが気付き、別の人が場所テーブルの「zip」と従業員テーブルの「zip」も同じ意味だと記録する。図の矢印のように続く。これにより、Fred という名前で郵便番号 02139 の従業員を探す範囲を、従業員から友人へ広げられる。必要なのは RDF の「同値」属性だけである。

### 論理層

次は論理層だ。ある種類の文書から別の種類の文書を導く規則、自己矛盾しない規則群による文書検査、未知の用語を既知の用語へ変換して問い合わせを解くことなどを可能にするため、文書に論理を記す手段が必要になる。引用は既にあるので、次が述語論理（否定、論理積など）、さらに次が量化（すべての x について y(x)）である。

この段階の RDF の用途は、ほぼ想像力だけに制限される。簡単な例は、独立に構築・公開したデータベースを意味上のリンクでつなぎ、相互に問い合わせを変換することだ。新言語が必要に見えた多くの事柄が、適切な RDF を書くだけの問題になる。述語計算と引用の力を持つ言語ができれば、個別の用途の言語を定義する際に必要なのは次の 2 点だ。

1. 受信側の推論エンジンに必要な有限の能力を定め、理解を期待する完全な RDF の部分集合を定義する。
2. 制限された言語の文書群で式を効率よく伝送するため、略記用の関数を定義してもよい。

疑問があれば、次も参照：

「セマンティック Web が意味しないこと――よくある質問への回答」。

下の路線図は、セマンティック Web の重要な循環を示す。左の Web 側では、HTTP で URI から特定の MIME 型を持つビット列として文書表現を得て、XML、次に RDF として解析し、RDF グラフや論理層の式を作る。右の意味側では、RDF グラフに URI への参照が含まれる。鍵への信頼と文書内の文の意味を組み合わせることで、セマンティック Web エンジンが別の URI を参照解決することになる。

### 証明の検証――証明言語

RDF モデルは推論エンジンの形式を定めない。問いに答える、つまり証明を見つけるための究極の完全なアルゴリズムはないので、明らかに未解決の問題である。しかし、開発のこの段階ではそれを解かない。多くの用途では、かなり制限された規則で証明を作り、相手は一般的な証明を検証するだけでよい。それは簡単である。

例えば Web サイトへのアクセス権を与えるとき、その権利を持つ理由を Web サーバーに説明する文書を渡せる。証明は、裏付けとなるすべての資料へのポインターを持つ、表明と推論規則の鎖［正確には DAG］になる。

プライバシーや多くの電子商取引でも同じである。ネットワークで送る文書は完全な言語で書くが、問い合わせれば結果が計算でき、多くの場合に証明となるよう制約する。HTTP の「GET」は、クライアントが応答を受ける権利の証明を含む。応答は、その内容が本当に要求されたものである証明になる。

### 進化する規則言語

論理層の RDF は既に推論規則を表現できる。例えば「x の所属組織の郵便番号が y なら、x の勤務先の郵便番号は y」と書けるはずだ。こうした文を Web に散在させるだけでも将来は興味深いが、短期的に再現可能な結果を得るには、特定用途に合わせて文書の表現力を制限する必要がある。

RDF エンジンに必要な基本機能は 2 つある。

1. バージョン n の実装が、n+1 の文書の読み方を推論できるだけの RDF スキーマを読めること。
2. 同じか似た機能を持つ B 型のアプリケーションと完全に独立して開発された A 型が、B 型のデータを処理するために十分なスキーマ情報を読み、処理できること。

（進化可能性についての記事を参照。）

RDF の論理層は推論規則を作る言語として十分である。ただし、個々の推論エンジンのヒューリスティクスを解決するものではない。セマンティック Web により、推論エンジンはさらに開かれた実りある研究領域になる。つまり規則は書けるが、その適用順序はこの段階では指示しない。

例えば米国議会図書館のスキーマが「author」、英国図書館のスキーマが「creator」を使うなら、少量の RDF で、任意の人 x とリソース y について、x が y の（LoC）author なら x は y の（BL）creator だと書ける。これが進化可能性を解く規則である。処理系はどこで見つけるのか。バージョン 2 の文書を見つけ、1 へ変換したいなら、2 のスキーマが規則を含むか指し示すのが自然だ。独立した 2 つのスキーマの関係を事後的に記述するなら、どちらかに規則へのポインターを追加できる。しかし社会的に難しい場合は、注釈の問題の別の例となる。両者をつなぐ第三者の索引で解決できる。実際、検索エンジンに一方のスキーマへの参照をすべて尋ね、両者の間の規則が結果にあるか調べれば、効率よく実現できる。

### 問い合わせ言語

問い合わせ言語もある。問い合わせは、返してほしい結果についての表明と考えられる。原理的には、論理層の RDF であらゆる場合を表せる。ただし実際のエンジンには固有のアルゴリズムや索引があり、特定の種類の問い合わせに答えられる。

実際には次のいずれかで役立つ語彙が開発されるだろう。

1. よく使われる強力な問い合わせを、数式を何ページも使わず簡潔に表せる。
2. 計算可能性の点で興味深い、一定の制約を持つ問い合わせを表せる。

SQL は両方を実現する言語である。

問い合わせ言語を RDF の論理に基づいて定義することが大切なのは明らかだ。例えばリソースの著者を尋ねるなら、ある x について「x は p1 の著者である」という形の表明を求める。すべての著者の完全な一覧なら、すべての著者が含まれ、集合の各要素が著者である集合を求める。

Web 検索のアルゴリズムや、Web 以前の論理システムの証明探索が多様なことから、セマンティック Web にもさまざまな形式の問いに答えるエージェントが存在するだろう。

有用な一歩は、Web の特定部分、例えばサイト内を有限の深さまで探すといった、特定の問い合わせエンジンを規定することだ。場面によって複数の選択肢があるだろう。

さらに上位の一歩は、問い合わせエンジンの記述言語を規定することだ。基本的には、エンジンが返せる問い合わせの種類を一般的に示す。これにより、多数の中間エンジンを介して検索と推論を連鎖させられる。

### デジタル署名

公開鍵暗号は可能性を根本から変えた画期的な技術である。既存文書へ署名ブロックを飾りのように足すことはできるが、推論システムへの後付けとして信頼の論理を扱う試みは、汎用性の限られたものだった。信頼を考慮して推論するには、汎用論理モデルを、署名された表明の鍵を含むよう拡張する必要がある。

あらゆる論理と同様、上に何が作れるかを見るまでは、この基礎は魅力的でないかもしれない。鍵を第一級の対象として導入し（URI は公開鍵そのもののリテラルでもよい）、鍵に帰属する表明について一般的に推論することが、その基礎になる。

実装上は推論エンジンを署名検証システムへ結び付ける。文書を表明の木として解析するだけでなく、誰がどの表明に署名したかという表明の木としても解析する。証明検証では、推論規則には論理を、署名付き文書の表明には署名を検査する。

結果として、公開鍵を基礎とする各種のセキュリティ・信頼システム間の関係を表現し、推論できるシステムになる。

RDF が証明言語を持つ段階になるとデジタル署名が重要になる。ただし、その開発の大半は RDF と並行して進められる。

W3C の署名作業には、DSig1.0 で署名した「pics」ラベルの経験や、さまざまな署名文書の提出など、多方面から情報が寄せられている。

### 用語索引

意味上の表明が世界規模でつながれば、現在（1998 年）HTML ページに適用している検索技術を、単語ではなく RDF オブジェクトの索引へ直接応用できるかもしれない。それだけでも、巨大な本としてではなく巨大なデータベースとして Web を効率よく検索できる。

バージョン A から B への変換要件は既に満たしている。そのため、2 つのデータベースが、例えば仮想的なものを含む RDF ファイルの大きな配列として存在すれば、当初のスキーマが違っても、後から同値性を記述することで両方を検索して問い合わせに答えられる。

## 将来のエンジン

HTML を索引化する検索エンジンは多くの答えを見つけ、Web の大部分を覆うが、不適切な答えも多く返す。そうした検索には「正しさ」の概念がない。一方、論理エンジンは正しいと証明できる答えだけに出力を制限できるが、大量に絡み合うデータを探って有効な答えを作ることが難しい。可能性の組み合わせ爆発が常に厄介なのである。

しかし検索エンジンの成功の規模を見ると、この前提を再検討する必要があるかもしれない。将来のエンジンが推論と検索を組み合わせれば、両者の長所を得て、非常に実用的な効果を持つ一定範囲の問題で、実際に証明を構成できるかもしれない。ある用語の出現箇所をほぼ網羅した索引にアクセスし、論理で、問題解決に使えるもの以外を除外できるだろう。

組み合わせ爆発自体はなくならないが、現実の多くの問題は、開かれた Web 上で数段、例えば 2 段の推論を行い、残りを与えられた証明や、制約と理解しやすい計算可能なアルゴリズムのある領域で処理して解決できるだろう。特定種類の問題を効率よく解くエンジンやアルゴリズムには、強い商業的動機もあるはずだ。現在の検索索引に似た、中間結果のキャッシュを作ることも考えられる。

任意の問いへの回答を保証する機械は依然ないが、日常生活、特に商取引における実際の問題に答える能力は、かなり高くなる可能性がある。
