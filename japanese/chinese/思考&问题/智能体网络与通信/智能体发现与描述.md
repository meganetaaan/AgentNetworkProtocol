## A2S へのフィードバック

URL：
https://github.com/keithagroves/agent-to-service/blob/main/README.md

私たちの構想と一致する点：

- 発見と記述はメタプロトコル交渉よりコストが低く、将来の大半のエージェント通信はこの方法になるはずです。一方、メタプロトコルは個別の通信能力を提供するため、依然として価値があります。
- アーキテクチャ図も構想と一致しています。エージェントやサービスを発見し、その記述情報を返す発見・索引サービスが必要です。
- OpenAPI によるサービス記述もよい選択です。

その他：

- Flow Control がプロトコルの一部なのか、よく分かりません。A2S ではなくエージェントの計画の一部かもしれません。私の理解では、A2S は主として不可分な API の記述を担い、それらの組み合わせはエージェントに任せられます。ここでの設計意図はまだよく分かりません。
- 同様に、集約機能もエージェント内部に実装する方がよいかもしれません。
- タスクについては、プロトコル内で複雑なフローを記述する方法を設計しているように見えます。これはエージェントが API 提供側に送って実行させるものですか。それとも、エージェントが複雑なフローを記述するための規約を定義していますか。
- 私の理解では、Agent-to-Service Protocol 自体は不可分な能力の記述に集中し、flow、task、集約などは Agent 側に置いて、Agent の実装者に任せる方が適切かもしれません。
- エージェントの記述は Web サイトのように、検索・発見サービスが能動的に収集できるべきです。Web 検索エンジンと Web サイトの関係に似ています。違いは、Web サイトが人間向けで、エージェントは AI 向けだということです。

**バックエンドサービスを作り、エージェントに能力を登録してもらい、その文書一覧を読み取り、外部向けの検索インターフェースを公開できないでしょうか。PyPI のようなものです。**

インターフェースの記述には OpenAPI、JSON-RPC、あるいはセマンティック Web の規約を使えます。
