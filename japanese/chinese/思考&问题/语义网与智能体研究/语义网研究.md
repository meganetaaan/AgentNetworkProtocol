セマンティック Web は、かなり前から現在のエージェントネットワークに似た構想を示し、実現のための多くの技術を定義していた。初期の記事を参照できる。

進め方：

- Tim のセマンティック Web 関連記事をすべて調べる。
- 有用性を問わず、関連仕様をすべて読む。
- semantic web と agentic web の比較研究をまとめる。
  - 場面、構想、技術。
  - 仕様の長所と短所。

制約：

- 設計時には機械の知能が足りず、Web 技術者はデータを説明し、規則で理解と推論を深めようとした。
- 今は機械の知能が向上し、不要な仕様もあるが、交換に適した優れたものもある。
- 一部を利用して共通のデータ交換方式を作れば、協働コストを下げられる。各者が別々に定義し、毎回複雑に交渉するのは高コストだ。

大まかな案：
RDF、json-ld、lind-data で資源を記述する。エージェントも資源であり、資源を別の資源へつなぎ、API も資源の一部とする。

`@ytpe:"@id"` のように、あるフィールドが IRI であると指定するものは、今の AI なら簡単に検出でき、あまり必要ないかもしれない。冗長な部分もある。

一方 schema.org は、交渉を低コスト化し、理解を一致させるため有用だ。

json-ld は柔軟すぎ、規範的でないフィールドも多い。協働へ影響するだろうか。

web3.0 は semantic web ではなく agentic web なのかもしれない。セマンティック Web とは異なる方法で、そこで描いた場面を実現する。

特に価値があるもの：

- 構想：agentic web と同じである。
- link data：人向けでなく、機械や AI がアクセスできるようデータを相互につなぐ。どちらにも、人が見るためだけの Web でなく、機械が巡回しやすいデータ網が必要だ。
- RDF、json-ld、schema.org：エージェントを記述し、相互理解の費用を下げられる。

案として、各エージェントが Web 上のデータ取得方法と操作を記す文書を提供する。認証が必要なら DID を使えるが、別方式でもよい。認証自体を任意にしてもよい。

# API 記述仕様

## OpenAPI

RESTful API の構造を統一形式で記述し、設計、開発、テスト、文書生成を効率化する。

主な特徴：

- **機械可読**：JSON/YAML で、道具が直接解析・処理できる。
- **環境・言語非依存**：特定の言語・フレームワークに依存せず、RESTful サービスに使える。
- **自動化ツール**：Swagger、Postman、Redoc などで対話的文書、コード、テストを生成できる。

主な用途：

- 分かりやすい可視化された API 文書。
- 完成前に記述から生成する API Mocking。
- クライアント・サーバーのコード生成。
- 記述からのテスト生成。

ツール群が豊富で RESTful API に適する。高性能の需要には gRPC の方がよい場合もある。HTTP に結び付いている。

**インターフェイスの記述ファイルに相当し、そこから AI がコードを自動生成できるので、交渉の一種ともいえる。**

メタプロトコルとの比較：

長所：

1. 交渉せず、一方が OpenAPI を作り、他方がそれからコードを生成してやり取りできる。
2. 既に普及し、受け入れられている。

短所：

1. 多すぎる OpenAPI の間に共通の合意がなく、対話のコストが高い。
2. 固定的で交渉できず、個別調整が難しい。
3. HTTP に結び付き、HTTP でしか使えない。

旧称 Swagger の OpenAPI は、RESTful API の構造を標準形式で定義し、設計・開発・文書化・テストを簡単にする。特徴と用途をさらに挙げる。

- **標準記述**：JSON/YAML にエンドポイント、メソッド、要求・応答、引数、認証を記す。
- **自動文書**：Swagger UI などで、使い方、引数、戻り値を示す動的・対話的なページを生成する。
- **可視化と操作**：文書から直接リクエストを試し、応答を見られる。
- **言語非依存**：Python、Java、Node.js など、RESTful に対応する環境で使える。
- **コード生成**：Swagger Codegen などでクライアント・サーバーの骨組みを作り、開発を早める。

利用場面：API の設計と文書化、生成文書からの自動テスト、他のアプリが記述を読んで行う統合、コード生成による作業削減。

## GraphQL

データを記述・操作する言語で、REST に基づく。問い合わせと変更ができ、指令で実行方法や結果を制御できる。

下位の転送プロトコルには依存しない。OpenAPI と同様に API を記述する方法だ。

| 特徴 | GraphQL | OpenAPI（REST） |
|---|---|---|
| データ取得 | 必要なものを取得 | 固定したデータを返す |
| 記述 | Schema の動的定義 | YAML/JSON の静的定義 |
| 操作 | 問い合わせ、変更、購読 | CRUD |
| 文書 | GraphiQL などのリアルタイム文書 | Swagger などの静的文書 |
| 性能 | 動的解析で最適化が必要 | 固定エンドポイントで直接的 |
| 拡張 | 高い拡張性、旧 Schema と互換 | 版管理が必要 |
| リアルタイム | 購読に標準対応 | 標準対応なし |

# JSON-RPC

メタプロトコルで JSON-RPC を使う方式を交渉し、その後 JSON-RPC で対話してもよい。交渉自体を json-rpc へ改めることも考えられる。

JSON-RPC 2.0 仕様：
https://www.jsonrpc.org/specification

JSON による軽量な遠隔手続き呼出のプロトコル。最新の 2.0 は、JSON で符号化した要求・応答での呼出を定義する。

特徴：

- 理解・処理しやすい JSON。
- JavaScript、Python、Java など複数言語。
- 非同期呼出で複数の要求・応答を扱える。
- エラー情報を返せる。
- HTTP Basic、OAuth 2.0 などの複数の認証方式。

用途：Web アプリ、分散システム、ブロックチェーンでの遠隔手続き呼出。

# HAL

**HAL は資源から別の資源へ移動するために使える有用な技術だ。**

Hypertext Application Language は、API の資源を記述するハイパーテキストの言語である。標準的なハイパーメディアリンクで応答を整理・簡素化し、クライアントが資源を発見・操作できるようにする。資源間の関係をリンクで示すことで、自己記述的な移動と操作を可能にする。

主な特徴：

- **ハイパーメディア駆動**：各応答に関連資源へのリンクと対話方法が含まれる。
- **自己記述**：データだけでなく更新・削除・関連資源取得などの操作リンクがあり、全エンドポイントを事前に知らなくても使える。
- **JSON/XML 対応**：既存の Web アプリと統合しやすい。

基本構造は 2 部分である。

- _links：他の資源へのリンク。self は現在、next は次の資源など、関係で示す。
- _embedded：含まれる資源、例えば入れ子の資源。

利用者の情報を返す API の例：

json
コードをコピー
{
  "_links": {
    "self": { "href": "/users/123" },
    "orders": { "href": "/users/123/orders" }
  },
  "name": "John Doe",
  "age": 30,
  "_embedded": {
    "orders": [
      {
        "orderId": 1,
        "total": 100,
        "_links": {
          "self": { "href": "/orders/1" }
        }
      }
    ]
  }
}

_links は現在の利用者と注文へのリンクを、_embedded は注文情報と各注文の具体的なリンクを含む。

用途：

- RESTful API を自己記述的にし、発見性と使いやすさを高める。
- 固定エンドポイントに頼らず、リンクから次の操作を動的に決める。
- 複数システムがハイパーメディアで互いを発見・操作し、統合する。

資源と関係を単純かつ強力に表し、API を理解・利用しやすくする方法である。

# セマンティック Web 関連

Position-Statement-Yousouf-Taghzouti  
Web エージェントのコンテンツ交渉を支援する知識層  
Yousouf Taghzouti

World Wide Web は情報管理システムとして提案された [1]。相互接続された多数の資源へ普遍的にアクセスできる。資源とは参照する価値のあるすべてで、その状態を示す表現は複数あり得る。HTML/PDF などの媒体型、英語/アラビア語など、複数の次元で異なる。コンテンツ交渉はその中から適切な表現を選ぶ仕組みである。

人とエージェントは資源を閲覧・操作して目的を達成する [4]。検索エンジンのクローラーによる巡回と索引化は有名な例だ [3]。

セマンティック Web は意味と構造をコンテンツへ与える拡張を目指す。Berners-Lee らの記事 [2] は、相互対話して目的を果たすエージェントを描く。サーバーから知識を抽出する際、表現が複数ならコンテンツ交渉が必要だが、サーバーの使う交渉属性を事前に知らないことがあり難しい。

提案手法は、知識層で交渉を支援し、対話と異種システムの相互運用性を高める。まず CNCO（Content Negotiation Characteristics Ontology）で交渉特性を記述する。次に、前段で得た交渉可能資源の記述を利用し、マルチエージェント指向のプログラミング基盤で、資源発見、推論、交渉時の行動をモデル化して処理する。

CNCO と補助語彙の開発では、交渉の最新概観と特性を記した文献 [6] を参考にした。

図 1 は CNCO の簡略図である。交渉の次元、様式、プロトコル、制約の伝達方法という 4 語彙を定義した。最初の 3 つは cnco、cnco、cnco のクラスのインスタンスを提供し、直接資源を記述する。最後は cnco を定義する概念と属性を提供する。（訳注：原文では各 cnco に続く名称が欠けているため、補っていない。）

Listing 1 は、このオントロジーと 4 語彙による記述を示す。HMAS オントロジー（https://purl.org/hmas/）を cnco:NegotiableResource と宣言し、表現を交渉可能にする。次元は媒体型、様式は能動型、プロトコルは HTTP で、accept ヘッダーに制約を載せる。

# RDF

資源を表すデータモデルで、形式を定めない。

- **組織間の交換**：政府、医療、金融などで共通の構造記述として使う。
- **異種データの統合**：三つ組に統一し、関係型・文書型などのデータベースを共通の意味モデルへ統合して横断照会する。
- **メタデータの標準化**：学術出版、データ倉庫、文献・デジタル資源管理に使う。Dublin Core は RDF ベースの例で、図書館や公文書館で使う。
- **資源管理**：文書、画像、動画などのメタデータで自動処理・検索を助ける。
- **Linked Data**：URI で異なる集合をつなぎ、システム間で関連付ける中核技術。政府の各部門の情報を結び、分野横断で調べられるようにする例がある。

Linked Data は、RDF、URI、HTTP などの標準技術で集合を結び、Web 上に問い合わせ可能な相互接続データ網を作る公開方法である。

# JSON-LD

https://www.w3.org/TR/json-ld/

JavaScript Object Notation for Linked Data は、Linked Data とセマンティック Web データの標準形式である。JSON を拡張し、リンクと名前空間で意味を表す。

特徴：

- **JSON ベース**：既存の道具・ライブラリと互換で、組み込みやすい。
- **リンク**：@context で意味の文脈を定義し、共通の識別子で集合をつなぐため、別システムも理解・利用できる。
- **名前空間と文脈**：@context の URL などで各フィールドの意味・用途を定め、値だけでなく理解する規則も持つ。
- **相互運用性**：同じ意味で理解し、柔軟なリンクによって Web 全体で共有・流通できる。

基本は標準 JSON オブジェクトであり、@context で意味の文脈、@id と @type で一意の識別子や型を示す。

```json
{
  "@context": "http://schema.org",
  "@type": "Article",
  "headline": "How to Use JSON-LD for SEO",
  "description": "Learn how JSON-LD can help improve your website's SEO and visibility in search engines.",
  "image": "https://example.com/image.jpg",
  "author": {
    "@type": "Person",
    "name": "John Doe"
  },
  "publisher": {
    "@type": "Organization",
    "name": "Example News",
    "logo": {
      "@type": "ImageObject",
      "url": "https://example.com/logo.png"
    }
  },
  "datePublished": "2024-12-25",
  "url": "https://example.com/how-to-use-json-ld-for-seo"
}
```

**RDF は関係と標準的な意味を表すデータモデルで、複数の形式で表せる。JSON-LD も RDF を表現できる。**

```json
{
  "@id": "http://example.com/book/1",
  "title": "The Great Gatsby",
  "author": {
    "@id": "http://example.com/person/123",
    "name": "F. Scott Fitzgerald"
  }
}
```

@id は URI を表し、別の資源へリンクする。@type は URI で示す資源の型である。同じ @id という文字列でも、キーか値かによって意味が異なる。

@context は JSON 文書のフィールドの意味を示す。

### JSON-LD と RDF の関係

RDF は「主語（Subject）→述語（Predicate）→目的語（Object）」という三つ組の意味モデルである。JSON-LD のキー・値は次のように対応する。

- 主語：@id または空白ノード。
- 述語：文脈内のフィールド URI による対応。
- 目的語：値の直接変換、または他の資源の URI 参照。
- 相互運用性：JSON-LD は RDF の直列化形式で、RDF/XML や Turtle と相互変換できる。

###

```json
{
  "@context": {
    "name": "http://schema.org/name"
  },
  "@id": "http://me.markus-lanthaler.com/",
  "name": "Markus Lanthaler"
}
```

これは資源を表す。name は資源の名前という属性で context に定義され、@id はその IRI を示す。

# wot-thing-description

TD は、JSON-LD で thing を記述する仕様である。

**本質的には JSON-LD を拡張し、標準キーワードに加えて、thing 用の標準フィールドを定める。同様に JSON-LD を基礎とする Agent Description（ADs）を定義できる。**

この仕様を学び、ADs を実装する。

### WoT Thing Description とは

W3C Web of Things（WoT）作業部会が、IoT 機器の意味的な情報と対話機能を記述するために定めた仕様。JSON-LD で示す機器のメタデータ文書と考えられ、セマンティック Web と組み合わせ、統一した記述と対話のモデルを提供する。

---

### 主な役割

1. **能力の意味的な記述**：RDF/OWL で標準化し、機械に理解させる。**属性、操作、イベント**と、型番・メーカーなどのメタデータを含む。
2. **相互運用性**：異なる機器、プラットフォーム、プロトコルの接続を標準記述で解決する。
3. **発見と統合**：道具が機器を発見し、対話コードを自動生成する。意味検索で条件に合う機器を探せる。
4. **開発・拡張の簡素化**：GET、PUT などの共通モデルで複雑さを減らし、機器ごとの適合作業をせず動的に拡張する。

---

### 主な利用場面

1. **スマートホーム**：電球、温度調節器、防犯カメラなどをブランドを越えて接続する。Google Home と Apple HomeKit の機器の相互操作など。
2. **産業 IoT（IIoT）**：センサー・制御器の機能を記述して監視・管理し、産業自動化へ滑らかに統合する。
3. **スマートシティ**：街灯や駐車場センサーを記述し、収集とサービス改善に使う。
4. **エッジとクラウド**：TD を公開して機器管理とタスク割当を行う。
5. **研究開発**：IoT と意味データの深い融合を探索する。

### よく利用する分野・プラットフォーム

1. **家庭とプラットフォーム**：Apple HomeKit、Google Nest が意味技術と組み合わされ、統一管理を行う。
2. **産業**：OPC UA などを補完し、機器を意味的に記述する。
3. **意味とオープンデータ**：Linked Open Data が TD で IoT の資源を記述する。
4. **ミドルウェアと開発環境**：Eclipse Ditto、Node-WoT が TD に対応する。
5. **標準化団体**：W3C、ISO、IEC などが利用を進める。

# OWL（Web Ontology Language）

規則体系のようなもので、生成 AI とは異なる方向である。

オントロジーを表す標準言語で、セマンティック Web を支える。概念、クラス、関係、属性などの構造を定義する構文と意味を提供し、機械の理解を可能にする。異なる情報源の共有と推論を支え、賢く相互運用可能な Web を作る。

特徴：

- **オントロジー**：分野の知識構造として種類と関係を定義し、強い表現力で記述する。
- **意味に基づく推論**：定義した規則から新事実を導く。例えば「A の実例で、B とある関係を持つなら C の実例かもしれない」。
- **豊かな表現力**：RDF より複雑なクラス・関係を表す。継承、共通部分・和集合、値の型や数値などの属性制約を記述できる。
- **推論可能性**：論理規則と制約によって、新情報から既存規則で新しい知識を自動推論する。

# 署名からの鍵の復元

受け取った署名から公開鍵を復元し、指定された利用者のメッセージか判断する技術。例えばビットコインのアドレスは公開鍵の hash なので、復元した鍵で相手を確認でき、別途取得する通信を減らせる。

EcdsaSecp256k1RecoveryMethod2020

- **概要**：secp256k1 を使う ECDSA の一種で、署名から公開鍵を復元する。ブロックチェーンや暗号通貨で使う。
- **用途**：ビットコインなどで、特に署名検証時の鍵復元に広く使う。
- **安全性**：secp256k1 と同等で、復元が必要な場面に適する。

# DID ベースのエンドツーエンド暗号化には X25519KeyAgreementKey2019 を使える

現代の TLS、特に TLS 1.3 で重要な鍵交換アルゴリズムとなっている。性能と安全性に優れ、暗号化通信と鍵合意に広く推奨される。X25519 の対応拡大に伴い、今後の標準・用途でも広く使われると見込まれる。

# Schema.org

RDF の語彙である。

Google、Microsoft、Yahoo、Yandex が共同で始めた、共通でプラットフォームを越える構造化データモデルの公開標準。各種サイト用のマークアップにより、検索エンジン、アプリ、サービスが内容の意味を理解し、検索・表示・理解を改善する。

多くの型と属性を定義する大きな語彙を持つ。例えば：

- Person：名前、誕生日、職業など。
- Movie：監督、俳優、公開日など。
- Organization：名称、住所、連絡先など。
- Event：時刻、場所、チケット情報など。

# OWL

W3C が定義した、複雑な知識分野と論理推論を表すオントロジー言語。RDF/RDFS を基礎とし、より複雑な論理関係を表せる。

中核概念：

- **オントロジー**：概念・属性・関係についての形式的定義。
- **Class**：人、動物などの集合。
- **Property**：友人である、所属するなどの関係。
- **Individual**：張三、ある猫などの具体例。
- **Relation**：クラス同士やクラスと個体との関連。
- **Description Logic（DL）**：推論を支える論理的基盤。

# 参考資料

主要な関連標準：

**RDF（Resource Description Framework）**

- 基本データモデル。
- 主語・述語・目的語で関係を表す。
- RDF/XML、Turtle、N-Triples などで直列化。
- 交換・共有の共通基盤。

**RDFS（RDF Schema）**

- RDF を拡張する基本語彙。
- クラスと属性の階層を定義。
- 単純な推論。
- 基礎的なオントロジーと語彙の構築。

**OWL（Web Ontology Language）**

- 記述論理に基づく言語。
- RDFS より強い表現力。
- 複雑なクラス定義と属性制約。
- 自動推論と知識発見。
- OWL Lite、OWL DL、OWL Full の 3 部分言語。

**SKOS（Simple Knowledge Organization System）**

- 分類体系やシソーラスを表す。
- RDF ベース。
- 概念間の関係。
- 軽量な分野知識に適する。

**Dublin Core**

- デジタル資源のメタデータ。
- 題名、作成者、主題など 15 の中核要素。
- 図書館とデジタル収蔵で広く利用。
- RDF と併用可能。

**FOAF（Friend of a Friend）**

- 人と社会的関係の語彙。
- RDF ベース。
- ソーシャルネットワークのデータを構築。
- 基本的な個人情報の記述。

**Schema.org**

- 構造化マークアップの語彙。
- 主要検索エンジンが支援。
- ページの意味を強化。
- RDFa、JSON-LD などに対応。

主な用途：知識グラフ、賢い検索、統合、メタデータ管理、意味に基づく推論、オープンデータ、電子図書館、意味付き Web サービス。

選定では、用途の複雑さ、モデル化の需要、推論の要求、道具の対応、既存システムとの互換性を考える。

通常は組み合わせる。例えば RDF を基礎モデル、OWL をオントロジー、Dublin Core をメタデータ記述に使う。
