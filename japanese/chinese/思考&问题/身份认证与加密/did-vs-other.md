OIDCは、シンプルで安全かつクロスプラットフォームと複数のデバイスをサポートし、近代的なアイデンティティシステムで最も広く使用されている合意の1つです。

## OpenID Conect で Google にアクセス (OIDC)
OpenID Contact(OIDC)を使用してGoogleへのアクセスは、ユーザーが自分のGoogleアカウントでログインすることができます。 これは、従来のユーザー名/暗号よりも安全かつ簡単です。 以下は、詳細なアプリケーションと技術アクセスプロセスです:

**プレパラリーワーク**

1.  **Googleアカウント番号を取得した:** あらゆる業務のベースとなります。
2.  **Google Cloud Platform(GCP)でアイテムを作成する(オプションが推奨されます):** 必須ではありませんが、GCP のプロジェクトの作成はアプリケーションや証拠の管理を向上できます。他の Google Cloud サービスを使用する必要がある場合は、この必要があります。
3.  **アプリケーションの種類を決定します。** アプリケーションはWebアプリケーション、モバイルアプリケーション(Android/iOS)、デスクトップアプリケーションです。これは、その後の構成に影響します。

**Google API コンソールで OAuth 2.0 証明書を設定する**

1.  **Google API コンソールにアクセス:** 営業部 [https://console.developers.google.com/](https://www.google.com/url?sa=E&source=gmail&q=https://console.developers.google.com/)。
2.  **アイテムを選択または作成します。** GCP でプロジェクトを作成したら、選択します。それ以外の場合は新しい項目を作成します。
3.  **「ドキュメンタリー」ページへのナビゲーター:** 左側のメニューで「ドキュメント」を選択します。
4.  **Oouth 2.0 クライアント ID を作成します。** 「証明書を作成」をクリックし、「Outlook Client ID」を選択します。
5.  **用途の種類を選択します。** お使いのアプリケーションの種類に応じて「Web アプリケーション」、Android および「iOS」を選択します。
6.  **詳細は構成します。**
      * **名称:** クライアント ID の名を指定します。
      * **認証された JavaScript ソース(Web アプリケーションの場合)** アプリケーションが配置されているドメイン名またはソースを指定します。例えば:`http://localhost:8080` または `https://yourdomain.com`。
      * **認証された再オリエンテーションURI(Webアプリケーションの場合):** Google は、アプリケーション用の URI にユーザをリダイレクトするサーバーを認可するを指定します。例えば:`http://localhost:8080/callback` または `https://yourdomain.com/callback`。
      * **パッケージ名とSHA-1署名証明書指紋(Androidアプリケーションの場合):** このページは、Androidアプリの認証に使用されます。
      * **バンドルID(iOSアプリケーションの場合):** 申請できる唯一の識別子です。
7.  **作成:** Create ボタンをクリックします。
8.  **クライアント ID とクライアントキーをフェッチ:** 作成が完了すると、クライアント ID と顧客キーが取得されます。この情報は、特にクライアントのキーを安全に保ち、クライアントのコードにそれを明示しないでください。

**III. 技術的アクセスプロセス(Webアプリケーション例)**

1.  **認証されたURLを作成:** ユーザを認証されたGoogleサーバにリダイレクトするURLを、次のパラメーターを使用して構成します。
      * `client_id`: Google API コンソールで取得したクライアント ID。
      * `response_type`: 設定 `code`(認証コードストリームの場合は、推奨します。)
      * `scope`: アプリケーションがアクセスする必要があるユーザー情報の範囲を指定します。例えば:`openid email profile`(OpenID、メールアドレス、基本個人データのご請求)
      * `redirect_uri`: Google API コンソールで設定する URI をリダイレクトします。
      * `state`: 偽造(CSRF)攻撃のクロスサイトリクエストを防止するためにランダムに生成された文字列。
      * `nonce`: 攻撃を再生しないようにランダムに生成された文字列。
    <!-- end list -->
    ```
    https://accounts.google.com/o/oauth2/v2/auth?
    client_id=YOUR_CLIENT_ID&
    response_type=code&
    scope=openid%20email%20profile&
    redirect_uri=YOUR_REDIRECT_URI&
    state=YOUR_STATE&
    nonce=YOUR_NONCE
    ```
2.  **反復の対処:** ユーザーが承認することに同意したら、Googleはユーザをアプリケーションにリダイレクトし、URL(%1)の認可コードを含んでいます。`code`とりあえず `state` パラメーター。
3.  **認証 `state` パラメーター:** 領収書の検証 `state` パラメータが以前の世代からあるかどうか `state` パラメータは一貫しています。
4.  **認証コードを使用してトークンとIDにアクセスします。** 下記のパラメーターを含むGoogleトークンエンドポイントにPOSTリクエストを送信します。
      * `code`: URL リダイレクトから取得した認証コード。
      * `client_id`: クライアントID
      * `client_secret`: クライアントキー
      * `redirect_uri`: 再オリエンテーションURI
      * `grant_type`: 設定として `authorization_code`。
    <!-- end list -->
    ```
    https://oauth2.googleapis.com/token
    ```
5.  **認証IDトークン:** トークンエンドポイントから取得したIDトークンの署名と宣言を確認します。 Googleが提供する公開鍵を使用して、シグネチャを検証する必要があります。 `aud` (オーディエンス) ステートメントはクライアント ID にマッチします。
6.  **ユーザーの情報を使用する:** IDトークンは、ユーザーID、メールアドレス、名前などのユーザーに関する基本情報が含まれています。この情報は、ユーザーの識別とパーソナライズされたエクスペリエンスを提供することができます。

**IV. その他の重要な問題**

  * **スコープ:** 実際にアプリケーションに必要なユーザー情報だけをリクエストしてください。
  * **セキュリティのベストプラクティス:** HTTPS を常に使用し、クライアントキーを安全に保ちます。
  * **Google でユーザーライブラリ:** GoogleはOIDCの統合プロセスを簡素化できるさまざまなプログラミング言語でクライアントライブラリを提供します。
  * **認可されたコードストリーム(推奨):** 管理されたコードストリームは、セキュリティを強化するために、見えないフローではなく、一貫して使用されます。

これらの手順は、OpenID 連絡先をGoogleに使用するのに役立ちます。 特定のアプリケーションの種類やニーズに応じて、いくつかの調整が必要な場合があります。

**重要なポイント:**

  * **AppIDおよびAppSecretのための保証:** AppSecret を安全に保ち、クライアントコードにそれを明示しないでください。すべてのリクエストはサーバー上で行われるべきです。
  * **URLの一貫性を再生:** 開いた無線プラットフォームの設定のURLは、コードで使用するURLと完全に一致していることを確認してください。そうしないと承認プロセスが完了しません。
  * **ステートパラメータのの重要性:** 利用条件 `state` パラメータは、CSRFによる攻撃を効果的に防止することができます。
  * **ユニオンの使用:** 同じWIOSアカウントで複数のアプリケーションで同一のユーザーを識別する必要がある場合は、unionidを使用します。

# エスエムピーエス
SAML(Security Asservation Markup Language、Securely Claimed Tag Language)は、さまざまなエンティティティティ(IDプロバイダーやサービスプロバイダなど)の間でユーザー識別と認証されたデータの安全な交換のためのXMLベースのオープンスタンダードです。SAMLは、ビジネス環境における単一ポイントアクセス(シングルサインオン、SSO)のシナリオで最も頻繁に使用されます。



# APIトークン

APIトークンは、APIへのアクセスを検証し承認するために使用される唯一の識別子です。 それらは通常、機械間通信に使用されます。 APIトークンは、特にユーザーのやり取りが要求されていない状況で、APIアクセスを保護する簡単な効果的な方法を提供します。
