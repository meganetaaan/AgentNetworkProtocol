# DID の問題

長所はコストの低さで、did web よりも低い。did web では自分でデプロイするか、他者のサービスに依存する必要があり、後者では実際には自分で制御できない（URL に公開鍵のハッシュを入れる設計で、制御権を得られるかもしれない）。

## 仕様

分散型識別子（DID）は、検証可能な分散型デジタルアイデンティティを実現する新しい種類の識別子である。DID が指す対象（人、組織、物、データモデル、抽象的な実体など）は、DID のコントローラーが決定する。一般的なフェデレーション型識別子と異なり、DID は中央レジストリ、アイデンティティプロバイダー、認証局から切り離せるよう設計されている。具体的には、DID 関連情報の発見を他者が支援することはあっても、**DID コントローラーが、他者の許可を一切得ずに制御権を証明できる**設計である。DID は DIDsubject と DID 文書を結び付ける URI であり、その主体に関連する信頼できるやり取りを可能にする。

DID 文書は、暗号学的素材、検証方法、サービスを記述できる。それらは DID コントローラーが DID の制御権を証明するための仕組みを提供する。サービスは DID 主体に関連する信頼できるやり取りを支援する。DIDsubject がデータモデルなどの情報リソースなら、DID 主体自体を返す手段を提供する場合もある。

**テストスイートで仕様への適合性を検証できる。**公開時点では、実験的な DID メソッド仕様が 103 件、実験的な DID メソッドドライバー実装が 32 件、この仕様への適合性を判定するテストスイートが 1 件あり、適合性テストスイートには 46 件の実装が提出されている。DID Core の issue と DID Core Test Suite の issue には、仕様変更につながり得る最新の問題と変更提案の一覧があるので注意してほしい。公開時点では、これ以上の実質的な問題、変更、修正は見込まれていない。

この仕様で定義する分散型識別子（DID）は、グローバルに一意な新しい種類の識別子である。個人や組織が信頼するシステムを使って、自分の識別子を生成できるようにすることを目指す。これらの識別子により、実体は**デジタル署名などの暗号学的証明による認証を使い、その制御権を証明できる**。

分散型識別子の生成と表明は実体自身が制御するため、**各実体は必要なアイデンティティ、役割、やり取りの分離を維持できるよう、任意の数の DID を持てる**。

この仕様は、DID の生成、永続性、解決、解釈を支える技術や暗号方式を特定しない。例えば、フェデレーション型や中央集権型のアイデンティティ管理システムに登録された識別子を基に、分散型識別子を作ることもできる。実際、ほぼあらゆる種類の識別子システムに DID のサポートを追加できる。**これにより、中央集権型、フェデレーション型、分散型の識別子の世界をつなぐ相互運用性の橋ができる**。また、分散台帳、分散ファイルシステム、分散データベース、ピアツーピアネットワークなど、信頼する計算基盤と連携する特定の DID を設計できる。

これらの要因から、発行機関に依存しない「自己主権型」のグローバルに一意な識別子が必要な場合がある。汎用一意識別子（UUIDs）[] はその役割を果たすが、UUID の制御権は証明できない。

## ユースケース

コントローラー、要求者、主体：

- コントローラーと主体は通常同一だが、従業員が雇用主に代わって DID を管理する場合や、親が子に代わって DID を使う場合など、異なることもある。
- DID コントローラーと要求者は、人でも対話型システムでもよい。ただし本書では簡単のため、操作を行う人として両者を表す。
- DID を制御する操作を実行できるのは DID コントローラーだけだが、既知の DID を調べたり検証したりする際は誰でも要求者になれる。自分の DID を調べる DID コントローラーも含まれる。

分散型識別子の最大の特徴は「アイデンティティプロバイダー」がないことかもしれない。その役割は、コントローラーが DID の管理に使い、要求者が DID の利用に使う分散型システムに組み込まれている。DID の登録には分散台帳技術（DLT）が使われると想定されている。

## 概念

ユースケース：https://www.w3.org/TR/did-use-cases/

authenticate：認証する
認証とは、実体が 1 つ以上の検証方法を使い、特定の属性を持つことや特定の鍵を制御することを証明する処理（通常は何らかのプロトコル）である。DID の一般的な例は、DID 文書で公開された公開鍵に対応する秘密鍵の制御権を証明することである。

decentralized identifier (DID)：分散型識別子（DID）
暗号学的に生成・登録されるため、中央登録機関を必要としない、グローバルに一意で永続的な識別子。一般形式は DID Core 仕様 [DID-CORE] が、個々の DID スキームは DID メソッド仕様が定義する。すべてではないが、多くの DID メソッドは**分散台帳技術（DLT）や、その他の分散型ネットワーク**を利用する。

DID controller：DID コントローラー
DID 文書を変更できる実体。1 つの DID に複数のコントローラーが存在してもよい。DIDdocument のトップレベルに任意の controller 属性として表せる。DID コントローラーが DID 主体である場合もある。

DID メソッド
特定の検証可能データレジストリに対応するため、特定の DID スキームをどう実現するかを定義する仕様。DID メソッド仕様では、DID の作成、解決、無効化、および DID 文書の作成・更新を行う具体的な操作を明記しなければならない。

services：サービス
**1 つ以上のサービスエンドポイントを通じ、DID 主体や関連実体と通信・対話するための手段**。例として、**発見サービス、プロキシサービス、ソーシャルネットワークサービス、ファイルストレージサービス、検証可能クレデンシャルのリポジトリサービス**がある。

verification method：検証方法
処理やプロトコルと組み合わせ、証明を独立して検証するためのパラメーター群。例えば公開鍵をデジタル署名の検証方法として使い、署名者が対応する秘密鍵を持つか検証できる。

この定義における「検証」と「証明」は広く解釈する。例えば Diffie-Hellman 鍵交換では、公開鍵を使って暗号化用の共有対称鍵を合意することがある。これは鍵合意処理の完全性を保証する。したがって、説明に「検証」「証明」という語がなくても、別種の検証方法といえる。

Authenticate 5.2.2：認証
要求者は、DID を提示した人が本当に DID コントローラーであるか、特定のサービスエンドポイントのコントローラーとして指定されているかを確認したい場合がある。認証処理では DID 文書内の cryptographicmaterial を使い、主張された Controller が本当に制御権を証明できるかを、通常はチャレンジ・レスポンスで確かめるべきである。DID 文書やメソッドは、update、delete 操作とは別に、サービスエンドポイントごとの証明を許してもよい。この分離によって、頻繁に行うと想定されるトランザクション用の証明と、まれに行う制御権の証明を区別できる。

Resolve 5.3.1：解決
デモ以外で DID を使う最初の手順は、DID を具体的な DID 文書へ解決し、対応する暗号学的素材とサービスエンドポイントを得ることである。その方法はメソッドごとに定め、DID ワーキンググループの対象範囲外とする。

Dereference 5.3.2：参照解決
DID の参照解決は、DID 文書内の素材を使ってリソースを返す。サービスエンドポイントを指定せずに参照解決した場合、既定では DID 文書自体を返すと想定される。DID と service parameter を組み合わせて DID URL にすると、DID を DID 文書へ解決し、名前でエンドポイントを探して発見した、そのサービスエンドポイントの指すリソースを返す。この仕組みにより要求者は、その DID の現在のサービスエンドポイントを動的に発見してやり取りできる。基盤の serviceendpoints が変わっても変わらない、永続的なサービス識別子を提供できる。

Deactivate 5.5.1：無効化
コントローラーは DID を削除する代わりに無効化できるべきである。これにより authentication や derefencing など、後続処理が機能しなくなる。多くの分散型システムでは記録の物理削除を保証できない。実際、分散台帳はしばしば「不変」であるとされる。メソッドは削除と同等の効果を得るため、無効化手順を定義すべきである。その仕組みはメソッドごとに異なるため、「非アクティブ」のメッセージも異なる。

# DID WEB メソッド

DID は認証・認可、DID の検証、完全性を実現する方法を定めていない。

DID web の信頼の中心は DNS にある。

did:web メソッドは DNS で Web サーバーを解決するため、did:web 識別子の解決はすべて DNS プロバイダーに追跡される可能性がある。また DID 文書は Web サーバーに保存されるため、DIDDocument リソースを取得するたびに、Web サーバーが DID 文書の解決を追跡できる。依拠当事者は、解析時の追跡を軽減するため、信頼できる汎用リゾルバーサービスで群衆に紛れるプライバシー（herd privacy）を得ること、VPN サービスの利用、TOR ネットワーク経由の解決を検討すべきである。この問題に対処する新しい解決策として draft-pauly-dprive-oblivious-doh-03 もある。
