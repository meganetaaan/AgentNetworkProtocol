# Agent Network Protocol（ANP）と IETF の AI エージェント通信フレームワークの比較分析

IETF Internet-Draft *“Framework, Use Cases and Requirements for AI Agent Protocols”*（draft-rosenberg-ai-protocols-00）は Rosenberg と Jennings が執筆したもので、AI エージェントの通信に必要なプロトコルの枠組みと要件を検討する。インターネットでのやり取りに必要なプロトコル、ユースケース、要件を整理し、IETF が今後標準化を行う可能性に備えることが主な目的である。

https://datatracker.ietf.org/doc/draft-rosenberg-ai-protocols/

## 1. 目標、設計思想、利用場面

- **ANP の構想と利用場面**：ANP は「Agentic Web 時代の HTTP」を目指すオープンソースのエージェント通信プロトコルである。エージェント同士の接続方法を定義し、開かれ、安全で効率的な大規模協働ネットワークを構築する。プラットフォーム中心のインターネットからプロトコル中心へ転換し、閉鎖的な「デジタルの孤島」を開いた相互接続へ変える思想を持つ。分散型の方法でデータの孤島をなくし、各エージェントを情報の消費者であると同時にサービス提供者にする。どの相手でも自由に発見・接続・対話できるようにする。**開放性**（あらゆるプラットフォームから参加）、**安全性**（エンドツーエンド暗号化と分散型アイデンティティによる信頼）、**効率的な協働**（自律的な組織化と交渉）を特に重視する。個人の AI 助手が第三者サービスを直接使う、企業内の多数の AI サービスをつなぐ、IoT の自律エージェントが通信するなど、億単位のエージェントによる開かれた協働を想定する。

- **IETF 草案の目標と利用場面**：Rosenberg と Jennings による draft-rosenberg-ai-protocols-00 は、必要な通信の枠組みと要件を探索するものである。具体的な実装よりも**枠組みとなる指針**を示し、利用者対エージェント、エージェント対 API、エージェント対エージェントに分けて機能要件と技術課題を考える。旅行の検索・価格比較・予約、財務情報を使う融資の提案、好みと履歴による衣服の推薦などの**ユースケース**で要件を導く。利用者との対話、外部 API による情報取得・操作、複数エージェントの協働が必要になる。複数サービスを使って複雑な仕事を支援する**個人 AI 助手**や、他社のエージェントを呼ぶ**ドメインをまたぐ協働**などを対象とする。既存プロトコルの不足を明らかにし、汎用通信標準を展望することが狙いである。

## 2. 抽象化の階層、主要機能、仕組み

- **ANP のアーキテクチャと主要な仕組み**：明確な**3 層構造**を定義する。最下層の**アイデンティティ・暗号化通信層**は W3C DID と既存 Web 基盤を使い、中央機関に依存せず異なるプラットフォームの相互認証とエンドツーエンド暗号化を行う。中間の**メタプロトコル層**は、異なるインターフェイスや能力を持つ相手と、利用する通信プロトコルを交渉し、自律的な組織化と効率的な協働を支える。最上位の**アプリケーションプロトコル層**はセマンティック Web 技術で能力と対応プロトコルを記述・管理する。JSON-LD などを使って**記述文書**、サービスのインターフェイス、製品、機能を示し、「誰で何ができるか」を理解させる。さらに**発見**と**プロトコル管理**を含む。ドメインの `.well-known` に記述一覧を公開し、クローラーや検索エンジンで索引化して意味に基づく探索を可能にする。自然言語や構造化 API などの対応形式も標準形式で告知する。認証→交渉→能力記述・発見をつなぎ、**DID による信頼できる身元交換、公開鍵・秘密鍵による安全な通信、動的なプロトコル交渉、意味に基づく記述と探索**を中核とする。

- **IETF の抽象化と仕組み**：厳密な階層は定めず、通信関係から**3 種類の主な場面**を識別し、それぞれに支援するプロトコルを求める。

  1. **利用者 ↔ AI エージェント**：利用者とエージェントの通信インターフェイスである。利用者発・エージェント発の**セッション開始**と対話形式を扱う。代理行動を適切に認可するため、利用者の身元と権限を確かめる**認証**が重要だ。テキスト・音声などのチャネル能力も合わせる必要がある。例えば Web 音声で利用者と話すなら、協働先も音声を扱えるか考える。チャット、音声助手、メールなどを含み、機微な操作や最終判断に先立つ利用者の同意も重視する。
  2. **AI エージェント ↔ API・ツール**：LLM エージェントがクライアントとして、Web サービス、API、文書、データベースなどを使う通信である。適切な道具の**発見**、OAuth などの**認証と認可**、金融取引など影響のある操作に対する**利用者確認**が必要になる。OpenAPI や利用説明など、AI が効率よく確実に使える API の記述・インターフェイスへの調整も議論する。
  3. **AI エージェント ↔ AI エージェント**：異なる組織や個人の能力を直接利用し、**エージェントネットワーク**を作る。**相互発見**、直接接続・中継・アドレス指定を含む**経路と接続**、開始・進捗・結果・完了・異常終了を扱う**ライフサイクル管理**、文脈・引数・中間結果・出力を送る**データ転送（Data Transferrance）**が求められる。ドメインをまたぐ**認証と認可**も複雑になる。A が利用者に代わって B へ支払いを頼む場合などの**利用者確認**、LLM へ渡す悪意ある内容による**プロンプトインジェクション**も課題だ。発見用ディレクトリ、ハンドシェイク、タスク管理、文脈の包装・伝送、安全な認可など一式が必要である。草案は方式を指定せず、MCP、A2A、Agntcy などの既存方式の達成点と不足を分析する。

**まとめ**：ANP は認証、安全な通信、交渉、意味に基づく記述・発見を明確な層に分ける。IETF 草案は 3 種類の通信場面ごとに要件を示す。ANP の認証層はドメインをまたぐ認証、記述・発見は能力の告知、メタプロトコルはチャネルや呼出形式の選択に対応する。ただし ANP は具体的な解決の枠組みで、IETF 草案は技術を限定せず要件を抽出するものである。

## 3. 技術実装とプロトコル機構の共通点・相違点

ANP と、草案が分析する Google A2A などを、通信、認証、ライフサイクル、文脈の転送、呼出方法について比較する。

- **通信モデルとメッセージ形式**：ANP は成熟した Web 技術、主に HTTP(S) を使い、複数の形式を認める。**構造化インターフェイス**は JSON-RPC 2.0、OpenAPI などで定義でき、RESTful API なども公開できる。単一の RPC には限定しない。**自然言語インターフェイス**は、テキストの LLM プロンプトなどで自由な対話を可能にし、厳密な構造化要求・応答とは限らない。一方、草案にある Google の *Agent-to-Agent（A2A）* は明確に**JSON-RPC 2.0**を使い、HTTP 上の要求・応答で他のエージェントへ仕事を頼む。agent card という能力記述や引数など、豊かな**メタデータ**も扱う。ANP は REST、JSON-RPC、自然言語など**柔軟で多様**、A2A は**RPC 型**を重視する。いずれも HTTP と JSON で既存環境へ統合しやすい。

- **同期・非同期呼出**：ANP の既定の HTTP 要求・応答は同期的だが、設計によって非同期化できる。長時間の HTTP 接続、WebSocket、Server-Sent Events などの**サーバープッシュやコールバック**、まず受付を返して後で結果を送る方式などが考えられる。公式文書は単一の非同期方式を指定しないが、技術的に拡張可能である。人の認可や遅延を記述できることも、外部イベントを待つ呼出を示唆する。A2A は**同期・非同期を明示的に支援**し、完了を待つか、バックグラウンドで実行してコールバック・イベントで artifact を返す。非同期には SSE やポーリングなどが使われる可能性が高い。IETF 草案には実装の詳細はないが、業界資料では HTTP と SSE による更新が示されている。したがって**双方で非同期を実現できる**が、A2A は区別を仕様化し、ANP は個々のインターフェイスに選択を委ねる。長時間の仕事を、要求を塞ぎ続けずに完了させる目的は同じである。

- **認証と信頼**：ANP の特徴は**分散型アイデンティティ（DID）**だ。例えば `did:wba:example.com:alice` に対応する取得可能な文書に、公開鍵、検証方法、記述文書 URL などのサービスエンドポイントを載せる。面識のない相手とも、第三者なしに鍵を交換し、相互認証と暗号化通信を行える。**Web ベースの DID メソッド** `did:wba` は HTTPS と DNS で文書を公開・解決する。公開鍵で**署名を検証**し、さらにエンドツーエンド暗号化セッションを作れる。草案の既存方式は伝統的で、例えば A2A は主に **OAuth2.0 トークン**を使う。相手が認めるトークンで呼出の認可を示し、認可サーバーや事前交換した API 資格情報などの**中央集権的な信頼**に近い。Agntcy は草案では**認証・認可をまだ扱わず**、信頼を別途確立するとされる。DID は事前の共有鍵や第三者への依存なく、自律的に検証できる身元を与え、開いたネットワークに向く。A2A などは OAuth/OpenID などを継承する。ANP は DID と公開鍵を信頼の起点とし、他方は**信頼する第三者**や事前の資格情報を使う違いがある。DID は事前の信頼のないドメイン間で柔軟だが基盤が要る。OAuth は既存サービスへなじむが、ドメインを越える汎用性と自律性ではやや弱い。

- **ライフサイクルと呼出手順**：開始、監視、完了、取消も重要だ。ANP は現在発見と接続を中心とし、専用のタスク管理プロトコルはない。**公開インターフェイスを API のように呼ぶ**ので、アプリケーション層で制御する。単純な HTTP は 1 往復であり、長時間の処理なら受付後にコールバックできるが、アプリ側で定義しない限り ID による統一的な状態追跡はない。A2A は専用の**ライフサイクル管理**を設け、進捗、中間・最終結果、完了通知、artifact、途中の追加質問や利用者メッセージの中継を扱う。単発要求ではなく持続する**セッション**として捉える。Agntcy の Agent Connect Protocol（ACP）にも同期・非同期呼出やエージェント実行のコンテナ化があるが、呼出の基本が中心で、IETF の全要件は満たさない。ANP は通常 1 呼出が 1 対話で、多段対話は自然言語インターフェイスなどで維持する。A2A は明確な完了まで状態を扱う**セッション管理**を持つ。つまり A2A は管理可能な手続き、ANP は独立した**インターフェイス**を中心とし、後者はアプリの論理で連鎖させる。今後メタプロトコルが手順管理を増す可能性はあるが、現状の詳細な管理は A2A の方が成熟して見える。

- **文脈の転送とデータ共有**：呼出先が仕事を行うには、利用者の意図、既知情報、環境の引数などが必要だ。ANP は**構造化引数**と**意味の記述**を使う。A が B を呼ぶとき、OpenAPI/JSON-RPC などの契約に従う JSON の引数を送る。schema.org などによる**自己記述的**な形式なら、開発者が異なっても理解しやすい。記述文書のサービス・製品・インターフェイスから、必要な資格情報や token も準備できる。ただし対話履歴を包むような共通形式は指定せず、送る内容はアプリ側で決める。IETF は Data Transferrance を重要要件とし、A2A は**メタデータと Payload**による複雑な構造や、ストリーミングなどの**継続的な転送**を支援する。A が利用者の意図や会話の一部を B に渡す例がある。Agntcy の Manifest も相手の能力の文脈を記す。ただし長期会話の継続共有やプライバシーのフィルタリングはまだ探索段階で、草案は不足を指摘する。ANP は**インターフェイスの構造と意味**に重点を置き、IETF はタスクの引継ぎや共同状態まで含む**より全面的な共有**を求める。将来の標準では、セッション文脈の形式や経路上のデータ型が定められるかもしれないが、ANP は現状、個々のアプリケーションプロトコルへ委ねている。

- **呼出方式と対話の形**：要求・応答、購読・通知、対話による協働などがある。ANP は**柔軟かつ多様**で、構造化 API は同期・非同期の要求・応答を、自然言語インターフェイスは**開かれた会話**を支える。A と B が人のように会話し、B の LLM が意図を理解して、内部機能の呼出や質問を選べる。各往復は呼出だが、厳密に定義済みの引数は必須でない。**命令的な API 呼出**と**会話**の両方を扱う。草案中の A2A は主に**明確なタスクの命令呼出**だが、利用者メッセージの**中継（passthrough）**も考える。A が利用者と音声で話す場合、B へ音声を渡したり、B に会話を引き継いだりする。そのため相手の音声対応などのチャネル能力を事前に知る必要がある。Agntcy はスキル発見と複数の呼出技術をメタデータに含め、同期呼出や非同期メッセージを告知できる。ANP はインターフェイス駆動と対話駆動の両方、IETF は対話の引継ぎも含むタスク駆動を主に議論する。ANP の `humanAuthorization` は、人の確認が必要なインターフェイスを示す。この**人の承認を待つ呼出**では、利用者や管理者の確認まで実行しない。IETF も、機微な代理間操作で利用者確認を必須の仕組みとする。理念は一致するが、ANP は既に記述用の印を持ち、草案は導入を促す。ANP は API・自由な会話・人の承認にまたがり、IETF は明確な呼出契約と確認を重視し、既存方式の拡張を望んでいる。

## 4. 機能と設計の重複、補完、違い

- **重なる点**：**発見、能力記述、認証、安全な通信、呼出管理**を重視する点は共通する。ANP の `.well-known/agent-descriptions` と Agntcy の DHT によるスキルディレクトリは、どちらも異なるプラットフォーム間の発見を解く。JSON-LD の Agent Description と Agntcy の OASFramework は**能力・インターフェイスの標準的な告知**に対応する。安全性では、ANP は DID と公開鍵、A2A は OAuth を使う。**利用者確認と人の認可**も、ANP の humanAuthorization と草案の User Confirmation で共通する。発見、交渉、呼出、信頼という目標の**重複は大きい**。ANP の多くの機能は、IETF が必要と考えるものに当たる。

- **補完と協調**：ANP は**実際に試せるオープンソースの道筋**、IETF は**標準化の観点から包括的な要件分析**を提供する。草案は MCP、A2A などの長短を分析する。ANP は名指しされないが、JSON-RPC 呼出や意味による記述など、その発想を組み合わせている。**完全に分散したコミュニティ主導**の実例として、IETF に経験を提供できる。did\:wba や意味記述の詳細が将来の標準に入る可能性もある。逆に、**ドメイン間の信頼連鎖、細粒度の認可、プロンプトインジェクション対策**など、未解決の要件は ANP 改善の方向を示す。対立ではなく、ANP が実装・検証し IETF が合意と標準を形成する**補完的な協調**が期待できる。

- **違いと潜在的な衝突**：同じ目標でも、将来の標準をめぐる競争はあり得る。第 1 に**身元体系**で、ANP は DID、大企業の A2A などは OAuth/OIDC を選ぶ。統合できなければ互換性のない 2 方式になり得るが、DID から OAuth token を発行する適合層なども考えられる。第 2 に**中央集権と分散**で、ANP は検索エンジンと DID ディレクトリによる自律的な開放網を目指す一方、Google A2A は現状特定の連合で動く。大手が中央登録や管理された生態系を好めば、アーキテクチャの選択に矛盾が出る。第 3 に、互換性なく別々に進むと資源が分散し、開発者は迷い、環境が断片化する。ただし IETF 著者は Agntcy なども調べており、ANP などの開いたコミュニティと OpenAI/Google などの対話によって衝突は減らせる。JSON-LD/schema.org と OASF の違いのように、変換や統一が可能な技術差もある。主な潜在的衝突は**生態系の主導権と仕様の統一性**で、機能は似ているため、分断より相互接続・共通標準を目指せる。

## 5. 適する場面と限界

- **ANP の利用場面**：**多数の主体が参加する開放網**に適する。中央管理なしで、個人の助手と第三者サービスが能力とインターフェイスを公開し、発見と認証で直接通信できる。同じプラットフォームへの登録や中央サーバーでの調整は不要だ。金融と商取引のエージェントが融資付きの自動車購入を相談するなど、異業種間でも共通プロトコルによって信頼と透明性を得て、統合コストを下げられる。HTTP/DID/JSON-LD という Web 標準に基づくため、通常のブラウザーやサーバーで**プラットフォーム・生態系を越えた AI 統合**を行える。**限界**として、発展途上で、高度なライフサイクルや多彩なリアルタイム対話は開発中かもしれない。DID は一般の開発者に不慣れで、文書の公開など学習・運用コストがある。公開エンドポイントや DNS を想定するので、NAT 配下の機器などには補助が要る。HTTP の 1 呼出の負荷は通常の Web と同程度でも、大規模な発見や経路制御、ブロードキャストストームの防止は課題だ。検索索引中心なので専用発見サービスほど即時性がない可能性もある。IETF などの標準として未採用で、**生態系と影響力**を築き、十分な開発者・組織を集められるかが成否を左右する。

- **IETF 草案の利用場面**：それ自体は配備できるプロトコルではないが、幅広い AI の対話に原則を適用できる。**成熟した標準**を待つ組織には全景を示す。多国籍企業などは、独自方式を避けるため内部と提携先で共通標準を望むかもしれない。銀行と買物のエージェントなど**ドメイン・組織を越えた協働**を重視するため、信頼と安全性の考慮は**高い安全要求**にも向く。人との対話と API 利用も含み、LLM を製品へ組み込む際の指針となる。**限界**は現状が情報提供の提案であり、MCP や A2A なども発展中で、普遍的標準がないことだ。全機能を使うには複数技術と不足の補完が必要で、そのまま使える解決策はない。草案も既存標準では多くの用例を満たせないと認める。正式標準までは A2A、Agntcy、ANP などの**並行した進化**を追う必要がある。多数の利害関係者の合意には時間がかかり、新たなモデル能力などの変化に即応できない**調整の難しさ**もある。設計で要件を落とさず将来の標準に備える**上位の指針と評価項目**に向くが、現時点の実現には ANP/A2A などの実装が要る。広範な草案なので個々の状況の細部までは扱わず、詳細な方策には後続版や RFC を待つ必要がある。
