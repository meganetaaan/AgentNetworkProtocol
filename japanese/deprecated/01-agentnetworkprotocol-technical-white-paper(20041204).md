## アブストラクト

この論文は、分散型識別子(DID)とエンドツーエンドの暗号化された通信技術ベースのプロトコルを提示し、クロスプラットフォームのアイデンティティ認証とインテリジェントエージェント間の安全な通信の課題に対処します。 W3C DID 仕様、ブロックチェーン技術、および TLS プロトコルを統合することにより、この論文は低コストで効率的かつ安全なクロスプラットフォームのアイデンティティ認証と暗号化された通信ソリューションを設計します。 プロトコルは、インテリジェントエージェントが異なるプラットフォーム間でアイデンティティの相互運用性を達成し、HTTPSのような標準的なプロトコルを介してアイデンティティ認証を実行できるように「all」というDIDメソッドを導入しています。 ドキュメントは、DID文書の生成と検証プロセス、およびDIDベースのエンドツーエンド暗号化通信メカニズムを詳細に説明し、効率的な短期鍵交渉と暗号化通信フローを確保します。 最後に、紙はインテリジェントエージェントのコラボレーションネットワークとDIDベースのアイデンティティシステムに関する広範なアプリケーション見通しのための将来の方向を探ります。

## 1. 導入事例

インテリジェントなエージェントは、AndroidとiOSの次の重要なプラットフォームになるように表彰されます。 将来的には、個人や組織、企業それぞれがインテリジェントなエージェントを保有し、サービスを提供します。 インテリジェントなエージェントは独立して存在できません。他のインテリジェントなエージェントと共同作業し、人のニーズを満たす必要があります。 例えば、パーソナルアシスタントは、衣類や食品、住宅などのライフ関連インテリジェントなエージェントが生活サービスを提供するために必要不可欠なエージェントです。 同様に、衣料品店のインテリジェントなエージェントは、生産、設計、および流通などの上流および下流代理店と密接に連携する必要があります。 インテリジェントエージェントで構成されたコラボレーションネットワークは、次世代インターネットの重要なコンポーネントであり、よりインテリジェントなサービスを人々に提供することができます。

インテリジェントエージェントネットワークの効率的な運用には、インテリジェントエージェントが接続を確立し、相互に見つけ、アイデンティティ認証を実行し、安全な暗号化通信を実施し、標準的なプロトコルを使用して効率的なコラボレーションを実現します。

現在、ほとんどのインテリジェントエージェントはプラットフォーム固有のID IDに依存しており、異なるプラットフォーム間でアイデンティティシステムを相互接続することは不可能であり、インテリジェントなエージェント間の低コストのクロスプラットフォーム接続を防止します。 また、既存のセキュアな通信ソリューション(TLSなど)は、主にクライアントサーバ通信に使用され、証明書の発行済証明書に依存しています。 インテリジェントなエージェントが低コスト、効率的かつ安全な暗号化された通信を実行できる理想的なソリューションは今ありません。

W3C DID(分散型識別子)仕様、ブロックチェーン技術、TLS(トランスポート層セキュリティ)技術を組み合わせて、この論文は、異なるプラットフォーム ID をブリッジし、インテリジェントエージェントが低コストで効率的かつ安全な暗号化通信を実行できるようにする方法を低コストのソリューションを提案します。 また、プロトコルに基づくインテリジェントなエージェントのコラボレーションのためのビジョンも提示します。

## 2. DIDに基づくクロスプラットフォームのアイデンティティ認証

W3C DID(分散型識別子)は、集中的な依存性、プライバシーおよびデータ制御、相互運用性、セキュリティなどの伝統的な一元化されたアイデンティティ管理システムで問題に対処するために設計された新しいタイプの識別子規格です。

W3C DID仕様をベースに、新DID方式の設計によりアイデンティティ認証スキームを提案します。 この方法は、ID の相互運用性の利点を活用し、アイデンティティ検証プロセスを簡素化し、相互運用性の欠如と異なる集中システム間のアイデンティティ検証の複雑さと冗長性を解決します。

### 2.1 DID 方法 "all" (アライアンス)

DID メソッドは、DID の作成、解決、更新、および非アクティブ化の方法を規定する分散型識別子(DID)の実装です。 各 DID メソッドは、特定のブロックチェーンや分散型ネットワークに関連付けられており、そのネットワークと相互作用するための具体的なルールを定義します。

既存のDIDメソッドはブロックチェーンベースのもので、現在のブロックチェーン技術によって制限され、スケーラビリティと商用化における重要な問題に直面しています。 Web ベースの DID メソッドは、ドメイン名に深く結び付けられ、Web サービスプロバイダが DID 関連の操作をサポートし、Web サービスプロバイダーへの複雑性を追加します。

コンソーシアムブロックチェーンと同様に、 "all" (Alliance) という新しい DID メソッドをご提案します。 この方法の標準をサポートするすべてのサービスプロバイダは、外部にDID関連サービスを提供することができます。 DID ユーザーは、価格設定、サービスレベル、評判などの要因に基づいて 1 つ以上のプロバイダーを選ぶことができます。 このメソッドをサポートするすべてのサービスプロバイダは、サービスドメインをブロックチェーン上の特定のメモリ領域に登録して、「all」メソッドのすべてのユーザーがサービスプロバイダーの完全なリストにアクセスできるようにします。

また、DID クリエイターは DID ドキュメントのホスティングサービスドメインを指定して、DID 解決者に特定のサービスプロバイダやユーザホストサーバーから DID 文書を取得できるように通知することができます。

最後に、すべての"all"メソッドの全ての操作はHTTPSのような標準Webプロトコルを使用して既存のWebインフラストラクチャを活用します。

### 2.2 「all」メソッドの設計

「all」メソッドの設計のコアは、DID 文書の不全性を確保するために暗号技術を使用しており、コンソーシアムノードを利用してシステム分布を維持することです。

「all」メソッドでDIDの作成、解決、更新、および非アクティブ化のためのすべての操作は HTTPS を使用します。 コアプロセスは次の通りです。

![コアプロセス:すべてのメソッド](../../images/did-all-core-flow.png)

1. User A は、まず「all」メソッドサービスドメインのブロックや他の分散ストレージから取得するか、セルフホスト型 DID サービスを使用します。

2. User A は DID と DID ドキュメントを作成し、 1 つ以上のノードを選択し、DID 文書をホストする HTTP リクエストを開始します。

3. ユーザーBは、ブロックチェーンや分散ストレージから「all」メソッドサービスドメインリストも取得します。

4. ユーザ B は、サービスドメインノードから、ポーリングまたは同時クエリを使用して DID ドキュメントを問い合わせます。

DID「all」方式の設計指定: [02-did:all メソッドの設計仕様](02-did:all%20Method%20Design%20Specification.md)

「all」メソッドでは、認証方法の公開鍵に基づいて一意の識別子が生成されます。Bitcoinアドレス生成に似たプロセスに従います(詳細な説明については、以下を参照してください。 [02-did:all メソッドの設計仕様](02-did:all%20Method%20Design%20Specification.md)):

- 検証者は DID ドキュメントを読み込み、まず DID の正しい性(セキュアなチャネルで保持)を検証します。

- 最後に、公開鍵を使って、校正セクションの署名情報を検証します。 検証が成功すると、DID ドキュメントは改ざんされていない。

DID 文書が改ざんされないように、DID ドキュメントのホスティングサービスをプライベートな変更から防止するための効率的かつ低コストのソリューションです。

公開鍵に対応するユーザーの秘密鍵が侵害されている場合、ユーザーは関連するDIDのリボケーションとDIDの更新プロセスをトリガーして、関連する当事者にDIDを更新することができます。

### 2.4 十字プラットフォームのアイデンティティ認証プロセス

DIDに基づくクロスプラットフォームのアイデンティティ認証では、既存のアイデンティティシステムを放棄する必要はありません。 DIDは、元のシステムの内部ロジックを変更しないように、2つのシステム間でのアイデンティティ認証のためにのみ使用することができます。 例えば、ユーザーは1つまたは複数のDIDを申請し、既存のIDにそれらを結合することができます。

それぞれプラットフォームAとプラットフォームBに登録された2人のユーザー、A、Bがそれぞれ存在します。 以下は、AとBがお互いのDID文書を探し、メッセージサービスを入手し、通信する方法について説明しています。

![クロスプラットフォームのアイデンティティ認証プロセス](../../images/cross-platform-identity-authentication-process.png)

**プロセスの説明:**

1. ユーザーは、AとBは、インパーソンスキャン、SMS、WeChat、または公共の問い合わせなどの信頼できる手段によってDIDを交換します。
2. ユーザーは、それぞれ DID を各サーバーに送信し、DID 文書を DID 経由で照会します。
3. 返された DID 文書に基づいて、 ID、公開鍵、および正しさの署名を検証します。 正しい場合、DID ドキュメントが改ざんされていないことを示します。 メッセージを抽出し、暗号化された通信プロセスを開始します。

## 3. エンドツーエンド暗号化された通信

それぞれのアイデンティティを相互に検証した後、DIDを保持する2人の当事者が安全で効率的なエンドツーエンドの通信を行うことができる方法について説明します。 セキュリティは通信プロセスにパラマウントされ、データの暗号化、データ完全性、前方秘密、マンイン・ザ・ミドル攻撃の防止、および再プレイ攻撃を保証します。

### 3.1 スキームの概要
このソリューションは、TLSやブロックチェーンなどの実践において実証済みの高セキュリティ技術を活用し、DIDに基づくエンドツーエンドの暗号化通信スキームの設計に組み込む。 このスキームは、異なる2つのプラットフォームでユーザー間で安全な暗号化通信に使用できます。

弊社では、Websocketプロトコルの先頭にDIDベースのメッセージルーティング機構と短期キーネゴシエーションメカニズムを設計しました。 DIDを保持する当事者は、DID文書と秘密鍵で公鍵を使用することができます。 ECDHE(エリプティックカーブディフィールマンエフェメラルド)を使用して短期キー交渉を実行できます。 その後、キーの有効期間内にメッセージを暗号化して安全な通信を実現することができます。 ECDHEは、サードパーティのメッセージエージェントやインターメディアリーが転送しても、メッセージを悪意的に暗号化できないことを保証します。

インターネット上で広く使用されているため、Websocketプロトコルを選択し、利用可能なインフラが多岐に渡り、スキームの早期推進に不可欠です。 また、Websocketの上にエンドツーエンドの暗号化方式を設計しているため、Websocketセキュアプロトコルを使用する必要はありません。そのため冗長暗号化と復号の問題を回避します。

弊社の現在のスキームは、アプリケーションレイヤー暗号化を基本的に使用し、トランスポートレイヤーの暗号化を交換し、既存のインフラを利用しながらプロトコルプロモーションの難易度を削減します。

全体的なプロセスは次の通りです:

![エンドツーエンド暗号化](../../images/end-to-end-encryption-process.png)

※第三者のメッセージサービスは存在せず、利用者は自分のメッセージサービスを利用することができます。

現在、双方向プロトコルであるため、Websocketプロトコルのみをサポートしています。 今後、HTTPプロトコルをサポートして、より多くのシナリオを拡大していくことを検討します。 また、今後トランスポート層でのエンドツーエンド暗号化方式の導入を検討し、より多くのシナリオで活用できる体制を構築します。

### 3.2 暗号化された通信プロセス

プラットフォームの2人、A(DID-A)とB(DID-B)の2人で対応します。 AとBの両方が、それぞれの公開鍵を含むDID SERVERから各DID文書を取得できます。

暗号化された通信を実行するには、AとBは、短期鍵の作成を開始する必要があります。 短期鍵を作成するプロセスは、TLSの一時的な暗号化キーの生成に似ています。 これらのキーは有効期限があり、期限が切れる前に、作成プロセスは新しいキーを生成し、それらを更新するために再起動する必要があります。

A と B が交渉された短期鍵を保持したら、A はメッセージを B に送信したい場合、A はキーを使用してメッセージを暗号化し、メッセージサーバーを介してメッセージングプロトコルを介して B に送ることができます。 メッセージを受信すると、B はキー ID を使用して対応するキーを受け取り、キーを使ってメッセージを復号化します。 対応するキーが見つからなかったり、期限が切れてしまった場合は、B はエラーメッセージを送信します。A に通知して、短期鍵の更新プロセスを開始します。 短期キーを更新した後、A はメッセージを再送できます。

### 3.3 短期キーの交渉プロセス

短期鍵作成プロセスは、以下の違いで、TLS 1.3の主要交換プロセスと基本的に似ています。

- プロセス全体には、TLSの ClientHello、ServerHello、および完了したメッセージに対応する SourceHello、DestinationHello、Finished という3つのメッセージのみが含まれます。 クライアントとサーバーの役割が異なる TLS とは異なり、当社のプロセスはソースと宛先のみを含みます。
- 暗号化された拡張子、証明書、およびCertificateVerifyなどのその他のメッセージは必須ではありません。 具体的に:
  - 暗号化された拡張子は、現在許可されていませんが、後で暗号化拡張機能を伝えるために追加される場合があります。
  - 証明書と証明書認証は、サーバーの公開鍵が安全であることを主として確認するため、これらのメッセージが不要なためです。 DIDアドレスと公開鍵の通信は、DIDの公鍵の正性を検証するために使用します。つまり、各公開鍵が1つのDIDのみに対応し、各DIDは1つの公的なキーだけに対応するからです。
- 完了したメッセージは、 SourceHelloとDestinationHello メッセージがそれぞれに署名を組み入れているため、ハンズキーメッセージを暗号化し、メッセージの完全性を確保することができません。
- ソースと宛先は、複数の短期鍵の交渉を同時に開始できます。複数のキーが異なる種類のメッセージを暗号化するための同時存在できるようにします。

プロセス全体図は以下です。

```plain
Client (A)                                          Server (B)
   |                                                    |
   |  ---------------- SourceHello ---------------->    |
   |                                                    |
   |         (Include public key and signature)         |
   |                                                    |
   |                                                    |
   |  <------------- DestinationHello ------------      |
   |                                                    |
   |         (Include public key and signature)         |
   |                                                    |
   |                                                    |
   |  -------- Finished (Include verify_data) ------->  |
   |                                                    |
   |  <-------- Finished (Include verify_data) -------- |
   |                                                    |
   |                                                    |
```

## 4. エクスポ

### 4.1プロトコルベースのインテリジェントコラボレーション

通信プロトコルの特定の設計について議論するものではありませんが、このような設計はインテリジェントエージェントのネットワークを形成するために不可欠です。

大型の言語モデル技術の進歩により、自然言語のソフトウェアシステム理解が大幅に改善され、人体コンピュータの相互作用に大きな影響を与えています。 自然言語が人体コンピュータの相互作用のための重要なインターフェイスになることができることを広く期待しています。 自然言語はソフトウェアシステム間で重要なコミュニケーション言語になりますか? とても興味深いトピックだと私たちは信じています。

従来のソフトウェア システム, 音声コールサービスやインターネットアプリケーションを提供するなど, 一般的には、厳密に定義されたバイナリまたはテキストプロトコルを使用して相互作用. 相手が基準に厳密に従わないと、インタラクション障害につながることができます。多くの場合、プログラマがバグや赤字コードを手動で修正する必要があります。

AIが自然言語を理解し、自動的にコードを生成することができるとき、より柔軟なインタラクションプロトコルを定義し、自然言語のフィールドの詳細説明で、AIがプロトコルを正確に理解できるようにすることができますか? 2つのシステム間の初期の統合とテストプロセスは、AIによって処理される可能性があり、両当事者が合意した特定のフィールドを交渉し、コードを変更して、交渉されたプロトコルに適応させ、自動的にバグをテストし、バグを修正し、結果を確認し、2つのシステム間で低コストの統合を実現することができます。

### 4.2 技術実装の推奨事項

提案されたスキームは、ユーザーの自律性を十分に考慮し、サードパーティのDIDホスティングサービスやメッセージサービスまたはセルフホストサービスの使用から選択することができます。 どちらのオプションも同等のセキュリティを提供します。

ユーザーがセルフホストサービスを選択すると、災害の回復、スケーラビリティ、セキュリティなどの重要な機能を考慮する必要があります(例えば、DoSや再生攻撃に対する保護)。

開発コストと運用コストを考慮し、特に中小規模のユーザーには、プロフェッショナルなサードパーティサービスを使用することをお勧めします。

### 4.3 DIDネイティブアイデンティティシステム

本紙では、DIDのみをクロスプラットフォーム認証に利用します。 しかし、今後はDIDの今後のアプリケーションがこの先を超越して拡大していくと確信しています。 従来の一元化されたアイデンティティ管理システムにおける集中的な依存性、プライバシーおよびデータ制御、相互運用性、セキュリティに関する問題を徹底的に解決するDIDネイティブなアイデンティティシステムの存在感を期待しています。

### 4.4 マルチメディアフォーマットのサポート

現在、プロトコル設計はテキストコンテンツを送信するだけをサポートしています。 インターネットは、オーディオ、ビデオ、ファイルなどのマルチメディアコンテンツの膨大な量をホストし、ライブストリーミングやRTCなどのリアルタイム音声およびビデオコンテンツを配信します。

今後、これらのマルチメディアフォーマットをサポートし、インテリジェントエージェント間のより包括的なコラボレーションを可能にしていく予定です。

### ブロックチェーンに基づく4.5分散ソリューション

私たちが設計したDIDは、ブロックチェーンアドレスに本質的に同等であり、ブロックチェーンのウォレットアドレスとしても機能します。 これにより、ブロックチェーンに基づく完全に分散型アイデンティティシステムを構築することができます。 DID 文書をパブリッククエリのためにブロックチェーンに公開することができます。DID ベースの取引と決済の容易化、インテリジェントなエージェント間の価値の移動をより便利にするブロックチェーン上でビジネス関連のトークンを作成できます。また、ブロックチェーンが組織する分散コンピューティングパワーを活用して、分散型インテリジェントエージェントメッセージサービスネットワークを形成します。 未来の可能性はもっとあるはずです。

### 4.6 バイナリ通信プロトコル

現在の通信プロトコルは、主にWSS+JSONに基づいており、TLSなどのバイナリプロトコルと比較して効率の不利な点が発生しています。 未来のインフラを目指し、将来的にはトランスポート層バイナリプロトコルを開発する予定です。

## 5. コンテンツ

革新的なクロスプラットフォームのアイデンティティ認証とエンドツーエンド暗号化通信ソリューションをDIDに基づいて導入し、インテリジェントエージェントネットワークにおけるアイデンティティ検証とセキュアなコミュニケーションの課題に対応します。 DID の「オール」方式を導入することで、異なるプラットフォーム間での相互運用性の問題を解決し、アイデンティティ検証プロセスを簡素化します。 ソリューションは、HTTPSプロトコルとブロックチェーン技術を活用して、DID文書の誤認性やシステムの分散性を確保します。 また、TLSやブロックチェーン技術から描画することで、エンドツーエンドの暗号化通信を実現し、データの機密性と完全性を確保する効率的なかつ安全な短期鍵交渉機構を設計しています。 紙は、インテリジェントエージェントネットワークのコラボレーションのためのビジョンを提示し、DIDベースのアイデンティティシステムの可能性のあるアプリケーションと将来の方向性を探求します。 全体的に、このペーパーは広範囲の塗布の見通しと解決を提供します、理性的な代理店ネットワークの有効で、安全な操作のための基礎を置きます。
