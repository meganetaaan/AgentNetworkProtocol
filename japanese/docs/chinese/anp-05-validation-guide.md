# ANP-05 実装検証ガイド

- 状態：参考情報としての検証ガイド。未リリースのプロトコル草案に対応
- プロトコルの基準：[ANP-05 v0.7](../../chinese/05-ANP-基于DID的授权协议.md)
- Profile：OAuth `anp.authorization.oauth2.cimd.v1-draft1`；VC `anp.authorization.vc.v1-draft2`
- 英語版：[Implementation Validation Guide](../anp-05-validation-guide.md)

本ガイドはANP-05から抽出した実装検証シナリオを収録します。プロトコル要件と適合規則は、特に[第14節](../../../chinese/05-ANP-基于DID的授权协议.md#conformance)を含むプロトコル本文を正とします。以下の章節番号はすべてプロトコル本文を指します。

## 検証シナリオ

以下は設計上のシナリオであり、特定の実装が合格したという宣言ではありません。宣言した役割と能力に応じて、該当する正常系と関連するすべての拒否経路を検証します。未実装の任意機能は非対応として記録し、合格と報告してはいけません。本ガイドはJWT/VC署名検証、エンドツーエンド認可、相互運用テストの実行結果を記録するものではありません。

OAuthでは、各フロー開始前に選択した処理モードを記録します。`cimd`は標準CIMD認可サーバーを使い、ANPメタデータの提供、DID解決、DIDバインディング検証を要求しません。`did_bound`はANPバインディング検査を追加し、`anp_cimd_binding`を宣言したASは、対象エンドポイントで受け入れるCIMDクライアントに検査を強制します。アルゴリズム、アサーションのaudience/type、コールバック処理、リソース指定、mix-up攻撃対策について選択したASの能力とポリシーを記録します。必須検査の失敗後に、弱い設定へ切り替えて再試行してはいけません。`did_bound`と記したシナリオは、拡張を宣言していない通常のCIMDサーバーにその要件を課しません。VCシナリオとProfileは独立しており、変更しません。

| ID | シナリオと期待される結果 |
| --- | --- |
| AUTHZ-01 | `did_bound`で、承認済みCIMD URLクライアント、メソッド検証済み`did:wba`文書、検証済みのURL／メタデータ／鍵バインディング、クライアントクレデンシャルのポリシーがある場合、対象を制限したトークンを発行する。対応を宣言したDIDメソッドごとにこの正常系を繰り返す。 |
| AUTHZ-02 | `did_bound`で、承認済みかつWBAに関連付いたCIMDクライアントには、宣言されたWBAバインディングと現行OAuth鍵認可に合格した場合だけ発行する。 |
| AUTHZ-04 | ユーザー承認済みの認可コードで、リダイレクト、state／セッション、S256 PKCEが一致する場合、ユーザー主体とリソースを維持する。 |

| AUTHZ-10 | 有効なDID証明があっても、受入審査に通らない、権限がない、またはクライアント自身の権限でユーザーのリソースを読もうとする場合、そのアクセス権を与えない。 |
| AUTHZ-11 | 不正／再使用の認可コード、コールバックやPKCEの不一致、scope/resourceの拡大、他クライアントのリフレッシュトークンを拒否する。 |
| AUTHZ-12 | 現在状態の確認でCIMD鍵の削除が判明した場合、新たに認証しない。`did_bound`では古い解決結果の更新失敗、DID無効化、DID鍵認可の削除も失敗とする。アイデンティティ／URL移行で認可を自動継承しない。 |
| AUTHZ-13 | DID／メタデータ／contextの取得、リダイレクト、DNSリバインディングによるSSRFを阻止し、トークンを発行しない。本番でCIMDとその中のURLを取得する際は特殊用途IP宛てを拒否する。draft-02の唯一の例外は、AS自身が同一loopbackインターフェースにある開発／テストである。loopbackコールバックの許可は、そのアドレスの取得を認可しない。 |
| AUTHZ-14 | クライアントアサーションをリソーストークンとして使う、ANP-02のキャッシュトークンへ置き換える、AS/RSのaudienceが不正な場合、拒否する。 |

| AUTHZ-18 | 非対応の処理モード、または`did_bound`必須時に`anp_cimd_binding`が宣言するProfile改訂が不正なら拒否し、クライアントの身元を変更せず、認証強度も下げない。通常の`cimd`はこの拡張を要求しない。 |

| AUTHZ-23 | A向けの受信トークンをBへ提示したら拒否する。独立に認可されたB向けトークンは成功する。 |
| AUTHZ-26 | 公開クライアントが鍵を持つ、またはPKCEを使うだけで機密クライアントとみなす、そのクライアントクレデンシャル設定を拒否する。 |
| AUTHZ-27 | 信頼できるRS/ASの文脈でだけscopeチャレンジを受け入れ、再承認し、再試行を制限する。チャレンジで黙って権限昇格してはいけない。 |
| AUTHZ-29 | 自己公開による受入れを有効にし、未知のCIMD URLに有効なメタデータ／クライアント証明と独立に承認された認可がある場合、事前保存クライアント記録や登録API呼出しなしで発行できる。`did_bound`ではDID関連付けも検証する。 |
| AUTHZ-30 | 初回接触の受入れを無効にした、ポリシーが拒否した、無効化済みクライアントがキャッシュ追出し後に再登録する場合は拒否する。現在の身元・ポリシー検査を迂回しない。 |
| AUTHZ-31 | CIMD応答がリダイレクト、CIMD/JWKS応答が制限超過、セキュリティフィールド重複、不正形式ならcode/token発行前に拒否する。`did_bound`では`ANPCIMD` serviceの欠落／曖昧さ、DIDへの逆リンク不正、ダイジェスト欠落、未認可鍵も失敗とする。有効な標準JWKSは正常入力である。 |

| AUTHZ-33 | メタデータに高権限scopeやclient_credentialsが列挙されても、リソースの認可とはみなさない。更新にも有効な認可トークンのバインディングが必要である。 |

| AUTHZ-76 | 標準`cimd`フローは、CIMDと`private_key_jwt`を宣言し、双方が対応する署名アルゴリズムを使うサーバーで成功できる。`anp_cimd_binding`、DIDリゾルバー、`anp_profile`、`anp_application_type`、必須の`anp_did`は要求しない。その結果はASによるDID検証を主張しない。 |
| AUTHZ-77 | リクエストの`client_id`、アサーションのiss/sub、CIMDの`client_id`、最終メタデータURLは同一のHTTPS文字列である。DID形式のclient_id、綴りの不一致、3xx応答、未認可の置換URLは失敗し、リダイレクトを追って不一致を修復しない。 |
| AUTHZ-78 | `did_bound`では、被害者の公開鍵を別DIDへコピーする、自己宣言の`anp_did`を追加する、片側だけから他方を指すことでは、被害者とのバインディングは成立しない。検証済みDIDからの厳密なURL逆リンク、メタデータダイジェスト、認可鍵集合、実際の署名鍵の保有証明が必要である。 |
| AUTHZ-79 | `did_bound`では`anp_oauth_keys`は空でなく、現行DIDの`authentication`内のメソッドを参照する。公開鍵素材で実際のJWKS署名鍵と照合する。不透明な形式でもDID形式でも`kid`で検査を迂回できず、文字列形式だけで権限を得ない。 |
| AUTHZ-80 | `jwks_uri`使用時、有効なCIMDダイジェストが固定するのはURIであり、そのURIが現在返すバイトではない。`did_bound`ではCIMDダイジェストが有効でも、外部署名鍵が置換済み、または認可一覧にない場合は拒否する。`jwks`と`jwks_uri`を併記した文書も拒否する。 |
| AUTHZ-81 | 期限切れや不整合のCIMD/JWKS/DIDキャッシュは、必須の新鮮なバインディング検査を満たさない。`did_bound`の鮮度上限は300秒、または適用されるより厳しい制限である。ダイジェスト／鍵の変更を発見したら関連スナップショットを無効化し、キャッシュ追出しで無効化状態を消さず、必須更新を完了できなければ拒否する。 |
| AUTHZ-82 | 必須`did_bound`検査の失敗、またはASの宣言能力不足で停止し、`cimd`への切替え、client_id変更、認証強度の低下をしない。`anp_cimd_binding`宣言ASは必須バインディングを欠くクライアントを拒否する。クライアントのオプトアウトや発見ヒントの省略でも強制検査を迂回できない。フロー開始前の`cimd`選択は、クライアントとAS双方のポリシーが許可する場合だけ可能である。 |
| AUTHZ-83 | 同一DIDが新しいCIMD URLを指すよう変更された場合、新たなOAuthクライアントとして扱い、旧consent・認可コード・リフレッシュトークンを継承しない。URLは同じでも関連DIDが変わる場合、ポリシーに従ってバインディングと認可を再審査する。 |

## シナリオ識別子の管理

シナリオ識別子は安定した証拠参照であり、連番必須のリスト番号ではありません。廃止済みの03、19、24、25、28、34–40と、0.6で廃止した51、52、58は再使用しません。0.4の追加要件は41から、0.5のVCシナリオは51から（ロールクレデンシャルは61–64）、0.6の直接提示シナリオは65–75です。0.7はこれらVCシナリオを維持し、URLクライアントのアイデンティティとモード別検査に合わせて既存OAuthシナリオを更新し、CIMD／バインディングの76–83を追加しました。欠番があっても表中のシナリオは免除されません。証拠にはシナリオIDに加え、プロトコルの改訂と選択モードも記します。
