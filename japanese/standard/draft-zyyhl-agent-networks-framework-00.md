--- 抽象的

このドキュメントは、Agent Network Protocol (ANP) プロトコルに基づいて AI エージェント ネットワークのフレームワークを定義します。 信頼ドメイン内のAIエージェントネットワークにおけるAIエージェント通信をサポートする基本的な機能を提供します。

--- 中間

# 導入事例

## プロフィール
AIエージェント技術の開発に伴い、アプリケーションシナリオを継続的に拡大しています。 初期の簡単なタスク実行から複数のエージェント間で複雑なコラボレーションタスクまで、エージェントはさまざまなフィールドで大きな可能性を発揮しています。 個々のエージェントの強みを最大限に活用し、タスク実行の質と効率性を向上できるマルチエージェントコラボレーションモデルです。 しかし、マルチエージェントのコラボレーションに対する需要が高まるにつれて、エージェント間で標準化された通信プロトコルを定義して、広域相互接続、クロスドメインの相互運用性、および安全なコラボレーションが対処する緊急の問題となっている。

AIエージェントの通信ニーズを満たし、マルチエージェントコラボレーションの広範なサービスを促進するため {{I-D.stephan-ai-agent-6g}}、相互接続、相互運用性をサポートし、信頼ドメイン内のエージェント間のスケーラビリティを保護する標準化されたエージェント通信プロトコルを定義する必要は不可欠です。

このドラフトでは、エージェントネットワークプロトコル(ANP)をベースラインとして利用し、さらなる説明を提案します。

## スコープ
ネットワークサービスドメインの分裂の観点から、展開拠点をベースとした3種類のエージェントを、ネットワークの外部代理店やネットワークサイドエージェント、エージェントなどから簡単に分類できます。 このドラフトは、主にオペレータのネットワーク内で管理されたエージェント間の通信に焦点を当てています。 エージェントの2つのタイプの通信:

- 同一ネットワークサービスドメインに登録された端末側エージェント間の通信。

- 端末側エージェントとネットワーク側のエージェント間の通信は、同じネットワークサービスドメインで登録されています。

- ネットワークサービスドメインに登録されたネットワーク・サイドのエージェント間の通信。

また、異なるネットワークドメインに登録されたエージェント間の通信は、このドラフトの範囲内では行われません。

# 用語と定義

# デジタル識別子

会員登録、発見、コミュニケーションの流れにデジタルアイデンティティ機構を採用。

- 参加登録:デジタルアイデンティティは、通信フロー中に認証とアドレスをベースとしてAIエージェントのグローバル一意の識別子を持っています。 複数のエージェント関連の属性(キャパビリティ/スキル/サービス)は、デジタルアイデンティティに含まれており、同時に識別子で登録されています。 デジタルアイデンティティの関連資格情報は、検証に使用できます。

- 発見:登録されたAIエージェントは、識別子または機能に基づいて他のエージェントによって発見することができます。 エージェントは異なるドメインで発見することができます。

- コミュニケーション:AIエージェントは、発見されたデジタルアイデンティティから得られた識別子で初期メッセージを送ることで、他のAIエージェントと通信することができます。 ネットワークは、このネットワークを使用することができます
ターゲットAIエージェントにメッセージをアドレス化しルーティングするための識別子。
 
- 認証: 通信施設では、AIエージェントは認証のために識別子の資格情報を使うことができます。 認証後には、属性が交渉できます。

- 認可:人間通信と比較して、AIエージェントのコミュニケーションは、常に明示的に許可される必要があります。 属性ベースの認可メカニズムは、ユーザー認証でも、直接エージェントの承認と委任された承認の両方をサポートできます。

上記の要件を満たすためには、W3C分散型識別子(DID){{DID}}と検証可能な認証情報(VC) {{VC Card}}が基本デジタルアイデンティティコンポーネントとして標準であることを提示することを推奨しています。

- DID: コアDID仕様は、特定の計算インフラを使用して分散型識別子を構築するために、実装者を必要としません。これにより、既存の成熟技術と十分に確立されたネットワークインフラストラクチャを完全に活用して、DIDを構築することができます。

- VC: VC は、AI エージェントの属性のコンテナとして使用できます。 AIエージェントの属性は、VCによって検証できる異なるソースから来ることができます。 これにより、横断的なコミュニケーションの相互運用性が向上します。


# エージェントの説明

ドキュメントのフォームにエージェントの説明(AD)が存在します。 AD文書は、エージェントにアクセスするためのエントリポイントとして機能します。 ウェブサイトのホームページに同様に機能します。 エージェントの名前、アフィリエイトエンティティティティ、機能、インタラクション API やプロトコルなどの情報を取得するには、この AD ドキュメントから取得できます。 エージェント間のデータ通信とコラボレーションが実現できる情報です。

## エージェントの説明 ドキュメント形式

Agent 説明(AD)文書は、エージェントの外部エントリ ポイントとして機能し、次の形式で提供することができます。

### 自然言語の形式

AI機能の進歩を重んじると、AD文書は自然言語で完全に記述できます。

### 構造化されたフォーマット

異なるエージェントは、異なる機能を持つモデルをさまざまな機能で活用する可能性があるため、多様なモデル間で同じデータの一貫性と正確な解釈を保証するために構造化されたアプローチが推奨されます。 構造化されたフォーマットは複数の文書タイプを支えます:

- ジェイソン

- JSON-LD(ジョンズ)

- その他の構造文書フォーマット


## エージェント情報インタラクション機構

エージェントの説明文書には、次の2種類のリソースが含まれます。

### インフォメーション

エージェントは、以下の種類のデータを提供できます。

- テキストファイル(例:.txt、.csv、.json)

- .jpg, .png, .svg などの画像ファイル

- ビデオファイル(例:.mp4、.mov、.webm)

- オーディオファイル(例:.mp3、.wav、.aac)

- その他のファイル


### インターフェース

エージェントインターフェイスは2つのタイプに分類されます。

- 自然な言語インターフェイス:
エージェントは、自然言語の相互作用を通じてパーソナライズされたサービスを提供し、人間のようなコミュニケーションと適応的な応答をサポートしています。

- 構造化されたインターフェイス:
定義済みのプロトコルを使用して、効率的で標準化されたサービスデリバリーを容易にし、相互運用性と機械間接的な自動化を保証します。


## セキュリティメカニズム

Agent 説明(AD)文書のセキュリティ設定は必須です。 エージェントレベルでのセキュリティ・定義は、セキュリティ・メンバーによって有効化されなければなりません。 この設定は、エージェントのインタラクションに必要なセキュリティメカニズムを構成する。

- グローバルスコープ: セキュリティーが AD ドキュメントのルートレベルで宣言されると、文書内のすべてのリソースはアクセスのためにこのセキュリティメカニズムを強制しなければなりません。

- リソース・スペフィックスコープ: 個々のリソース内でセキュリティが定義されている場合は、指定されたセキュリティ条件が満たされた場合のみ、そのリソースへのアクセスが付与されます。

- 優先ルール:リソースレベルのセキュリティがルートレベルのセキュリティと競合する場合には、リソースレベルの定義は優先されます。


## 完全性検証

悪意のある改ざん、偽装、またはエージェントの説明(AD)文書の再使用を防ぐため、検証メカニズムの証拠はAD文書構造に組み込まれています。 証拠の定義は、仕様書 {{VC Card}} に準拠するものとします。

# エージェント登録

エージェント登録には、次の2つのモードが含まれています。

## 自己宣言モード

このモードでは、AIエージェントは外部から提供されたリソース(情報やインターフェイスなど)をLinked-Data技術を使用して相互接続し、エージェントの説明文書を通じてネットワーク化されたエコシステムを形成します。 その他のAIエージェントは、これらのエージェントプロファイル文書に記載されているメタデータを使用して適切なリソースを選択的に取得することができます。 自己宣言モードの利点:

- 既存のインターネットアーキテクチャとの互換性:エージェントの公開情報を検索エンジンインデックス化を促進し、効率的なエージェントデータネットワークの作成を可能にします。

- プライバシー保護の強化:リモートデータをローカルシステムに引き出すことで、タスクデリゲーションモデルに固有のユーザーのプライバシー漏洩リスクを軽減します。

- 階層構造:多数のエージェント間でスケーラブルな相互作用をサポート


## 集中登録モード

このモードでは、AIエージェントが一元化されたエージェント登録サーバーに属性を登録します。 AIエージェントが信頼ドメイン(Aの手順1)に登録する必要があるパラメータは、次のものが含まれます。

- 名前: エージェントの名前は、ユニークで通常文字列として表されるわけではありません。

- デジタル識別子:ネットワークプロバイダによって構成されるエージェントのグローバル一意ID。

- 説明: 天然言語に基づいて、エージェントの関連の詳細のより簡潔な要約を提供します。

- アドレス: URL、FQDN 等であるかもしれないエージェントのアクセスアドレス。

- バージョン: Agent の現在のバージョン。

- 機能: 通信機能、インタラクションモード、マルチモーダル機能など、エージェントがサポートする機能 通信機能とは、エージェントがサポートする通信プロトコル(http/2, http/3, A2A, ANP, MCPなど)を指します。 対話モードには、リクエスト応答やサブスクリプション通知などが含まれる場合があります。 多項的機能は、エージェントがテキスト、画像、ビデオ、リアルタイムのオーディオなど、処理できるデータモダリティを指します。

- サービス: エージェントが提供できるサービス。 情報通信、AIサービス、センシングサービス、コンピューティングサービスなど

- スキル:エージェントがサポートするスキルの詳細な説明のリスト。 それぞれのスキルの内容には、氏名、ID、対応するサービス、簡単な抽象的な内容、必須入力などが含まれます。

- インターフェイス:エージェントが提供できるAPIインターフェース。

- セキュリティ関連情報:例えば、ライセンス、認証資格、エージェントのキー。


# エージェントディスカバリー

エージェント登録、エージェントディスカバリーには、次の2つのモードが含まれています。

## 積極的な検出モード(自己宣言モードに応答)

この操作モードでは、AIエージェントは、標準化された検出プロトコル(例えば検索エンジンなど)を通じて、ピアエージェントからエージェントの説明(AD)文書を動的に取得します。 これらのAD文書は、リンクされたデータネットワーク内のターゲットを絞ったクローリング操作のための構造化されたエントリポイントとして機能します。 クローリング機構は、選択的なリソース検索を実行し、セマンティック情報とサービスインターフェイスの両方を網羅し、倫理的なクロールポリシーに付着します。

## 集中型クエリモード(中央化登録モードへの対応)

このモードでは、AIエージェントの検出はエージェント登録サーバーに依存し、ディスカバリープロセスは「クエリマッチング」と「応答フィードバック」の2つのフェーズで構成されています。

1) クエリマッチングフェーズ:

開始AIエージェント Aは、登録サーバーに機能ディスカバリーリクエストを送信し、サーバー画面で、機能データベースに基づいてターゲットエージェントと一致します。 パラメータは構造化されるべき(あいまいな説明を避けるため)。 以下に例を示します。

    - 要件説明:「医療画像解析」
	
    - 位置範囲:「基地局BS-001の1キロ以内」
	
    - 実時間条件:「潜在能力≤100ms」
	
    - 保安レベル:「医療用資格VC」が必要です。
	
	
エージェント登録サーバーは、ローカル登録エージェントの説明と要件に一致します。 マッチング完了後、デジタル識別子、アドレス、機能などを含む「ターゲットエージェントリスト」が生成されます。

2) 結果のフィードバック段階:

エージェント登録サーバーは、マッチングした結果をイニシエータAIエージェントに送り返し、イニシエスタは結果に基づいてエージェントを選択し、そのエージェントとのセッション確立を開始します。

# タスク

## プロフィール

タスクのコア機能は、通信に関与するAIエージェントが「何をすべきか」に合意できるようにすることです。これにより、誤解によるコラボレーション障害を回避することができます。

エージェントの発見やコミュニケーション手順でタスクを使用することができます。

- エージェントディスカバリー:タスクの説明に基づいて、マッチング機能を持つAIエージェントを取得する。

- コミュニケーション:Coordinator Agent(A)が Execution Agent(Agent Bなど)への通信リクエストを開始した際、リクエストメッセージはタスクの説明を運ぶことができます。 また、画像、動画、ファイルなどのその他の補助情報もタスクの達成に役立つタスクの説明と共に送信することもできます。

図2に示す例では、AIエージェント(Agent B に送信されるタスク0など)でタスクを実行できます。 複雑なタスクがAIエージェントによって受信されると、このタスクは一連のサブタスク(例、task1とサブタスク2)に分割され、タスクチェーンとして知られるクリアな実行シーケンスで、AIエージェントのグループ(例えば、サブタスク1がAgent Bに送信されたサブタスク2はAgent Cに送られた)によって実行できます。 タスクチェーンは、複数のAIエージェントがポリシーに基づいて特定のシーケンスで異なるタスクを実行し、複数のAIエージェントを共同して複雑なタスクを達成することができます。 エージェント通信プロトコルは、タスクチェーン情報をカプセル化するためにサポートする必要があります。例えば、下流ネットワーク輸送(IP、MPLSなど)とは独立しています。

~~~
+---------+                                  +---------+
|         |------------send task0----------->|         |
| Agent A |                                  | Agent B |
|         |<-task status/result notification-|         |
+---------+                                  +---------+

+---------+                                  +---------+
|         |-----------send sub-task1-------->|  Agent  |
|         |<-task status/result notification-|    B    |
|         |                                  +---------+
| Agent A |                                  +---------+
|         |-----------send sub-task2-------->|  Agent  |
|         |<-task status/result notification-|    C    |
+---------+                                  +---------+
~~~
タイトル「タスクとサブタスクの割り当て」

タスクは、AIエージェント間の通信セッションを確立するメッセージや、AIエージェント間での確立されたセッションを別途送信することができます。 AIエージェント間の通信セッションでは、各々の独立したものやコンテキストを介した関連性があるものを含むことができます。

タスクは、グローバル固有のタスクIDで識別されます。 タスク ID は、タスクを作成または割り当てるエージェントによって生成され、実行する責任のあるエージェントにタスクと共に送信されます。

## タスク・ステート

タスクを完了する時間の長さに基づいて、タスクは次のように分類できます。

- 短期タスク: これらのタスクは、天気をクエリするなどの簡単なタスクに素早く実行し、完了することができます。

- 長期タスク: これらのタスクは、長時間の期間を必要とするか、複数のラウンドの相互作用または記事を書くなどの待機期間を延長することが必要です。 長期タスクの実行中、AIエージェントは、必要に応じてタスクの状態や中間結果を同期させることができます。

タスクの状態は実行AIエージェントによって維持され、必要に応じてタスクステータスをエージェント間で同期させることができます。

## タスクのコーディネート

AIエージェント通信プロトコル設計 MUST タスクメッセージの転送を容易にするために、エージェント通信サーバーのサポートを検討してください。 エージェント通信サーバー SHOULD タスク要件に基づいてメッセージをスケジューリングし、転送を優先して、効率的なエージェントのコラボレーションを確保し、トランスミッションQoSの目標を達成します。

この優先化スキームは、混雑やリソースのコンテンツシナリオで重要なメッセージが優先的に処理されるようにします。

タスクを Execution Agents に委任すると、Coordinator Agent は、エンドユーザーの連絡先情報、タスク自体、Coordinator Agent が知られる履歴設定情報、および作業の実行を容易にするために必要な会話データを含むことができます。 例えば、旅行計画の場合、これは歴史的に予約されたフライト/ホテルの好みを伴うか、最近のユーザー ダイアログのような動的に知覚されたコンテキストを伴うかもしれません。 AIエージェントプロトコルは、コンテキストタイプ、長さ制約、エンコーディングフォーマットの標準化された定義により、タスク実行の有効性を高めるためにコンテキスト共有メカニズムを継続的にサポートする必要があります。

# メッセージモード

二つの次元からAIエージェントのメッセージモードを定義します。 コミュニケーションの場として、ポイントツーポイント通信(2AIエージェント)とグループコミュニケーション(3つ以上のAIエージェント)に分けられ、この次元に基づく2つのサブセクションに分割される。 一方、AIエージェント間の通信は、直接通信と間接通信に通信を分割する中間ノードの参加を必要とするかという次元で、各サブセクション内の分類においてさらなる精緻化が図れます。

## ポイントツーポイントコミュニケーション

ダイレクト・コミュニケーション:AIエージェントは、処理のための中間ノードの必要性なしに、直接プロトコルメッセージを送受信したり、AIエージェントはこれらの中間ノードの気にしています。
間接通信:AIエージェント間のコミュニケーションは、エージェント通信サーバの処理・修復を要し、AIエージェントはエージェント通信サーバーに意識してやり取りしなければなりません。 エージェント通信サーバーの機能には以下が含まれますが、以下に限定されません。

- AIエージェントのアクセス制御(AIエージェントのメッセージのIDや権限に基づいてブロックする)

- アプリケーションレイヤープロキシ(AIエージェントの通信動作の監視/監査を容易にしたり、AIエージェントのアイデンティティを隠すための)。

- リレー(コミュニケーションメッセージの転送、クロスドメイン通信を容易にするなど)

- 交通集計(ツリー構造のトラフィック規制、通信効率の改善)

- 認証とメッセージのやり取りを2つのコミュニケートパーティ間で処理します。

## グループコミュニケーション

コミュニケーションコラボレーションをうまく達成するために、エージェントはグループを動的に形成することができます。 グループ内でのエージェントが送信する情報は、同じグループ内の他のエージェントで同時に受信できます。

## PUB/SUB コミュニケーション

このモードでは、AIエージェントが情報を送信すると、AIエージェントがどのAIエージェントに受け取る必要があるのかは分かりません。 エージェント通信サーバーに情報を公開し、このエージェント通信サーバは、購読状況に基づいて、サブスクライブエージェントに情報を配信します。 パブ/サブ通信は、大規模なグループ通信シナリオに適した情報配信の一般的かつ効率的な方法です。

# 多変性

AIエージェント間のインタラクションは、テキスト、ファイル、ドキュメント、画像、構造データ、リアルタイムのオーディオ/ビデオストリームなど、多変性をサポートしなければなりません。 異なる多変性や伝送モード(リアルタイムストリーム、またはプッシュ通知など)のデータサイズは異なる場合があります。

上記のようなトラフィック特性を付与し、エージェント通信プロトコルは、上記のマルチモーダルデータ伝送をサポートすべきです。 同時に、エージェント通信プロトコルと他のレイヤーの可能なプロトコルは、マルチモーダルデータが区別され、認識できるという原則で設計されているはずです。これにより、パフォーマンスの検証やリソース効率性を向上させるために、差別化されたポリシーで処理できます。 例えば、異なるマルチモーダルデータが異なる品質保証の異なる輸送ストリームで送信することができます。 または、同じ輸送の流れの中で送信することができますが、異なるポリシー(例えば、伝送優先)で。

# セッション管理

実行エージェント(Agent B)、Coordinator Agent(Agent A)を発見した後は、通信するセッションを確立する必要があります。

## セッションの設置と管理

エージェントBとの通信の前に、A Agentはまず、Agent Communication Serverと安全な接続を確立する必要があります。 エージェント A は、エージェント通信サーバーの認証を受けなければならない。 同様に、Agent B は、Agent Communication Server がセキュアな接続を確立するために認証する必要があります。

そのため、エージェント通信サーバーは、Agent や Agent B の状態など、登録エージェントのステータス管理をサポートする必要があります。

エージェントBとの通信を行うため、Aは、エージェントコミュニケーションサーバーへのセッション・インストール要求を開始します。 権限の確認後、Agent Communication Server は、セッション ID をグローバルに一意のセッション ID を新しいセッションに割り当てることにより、セッションの確立を進めます。 セッションのライフサイクル全体を通して、全てのアクティビティとデータを関連付けるIDを使用します。 応答的に、Agent Communication Server はセッションテーブルを維持する必要があります。これは、セッションに関与するすべてのエージェントに関する情報を含む、特にセッションイニシアクターに関する情報が含まれます。

認証と認可後、Agentは、Agent Bに直接接続を初期化することもできます。 この場合、制御面とデータ平面を分離することができます。

## 差別化された QoS 保証

セッションの確立中に、A Agent はセッションの関連する QoS 要件を提供できます。 その結果、エージェント通信サーバーは、セッションのQoSを確実にするために、これらの要件に応じてメッセージを処理し転送を優先することができます。

# ルーティング

## エージェントIDベースのルート検索

このセクションで説明したシナリオは、エージェントが別のエージェント(またはエージェントのグループ)にメッセージを送信し、送信エージェントのIDやグループIDを受け取ったことを知らせるときです。 セクション6の通信モードの2つの主要なタイプに従って、状況は次のように分類することができます。

- 点間対ポイント通信(P2P):

	- 直接通信モードでは、エージェントは受信者のIDを使用して対応するIPアドレスを調べます。これにより、メッセージが受信者に送信できるようにします。

	- 間接通信モードでは、エージェントはIDの検索タスクを Agent コミュニケーション サーバーに委任することができます。これにより、IDに基づいてメッセージ送信者エージェントにメッセージを送信できます。

- グループコミュニケーション:

	- エージェントは、グループ ID の検索タスクを Agent コミュニケーション サーバーに委任し、同じグループで受信者のエージェントにメッセージを送信する責任を負います。

## 準道ベースのルートの解像度

このセクションで説明したシナリオは、エージェントが特定の機能や属性を持つ他のエージェントと通信したいというときにありますが、まだ自分のIDを知らないのです。 この場合、エージェントが記述する機能や属性に基づいて基準を満たす Agent ID を検索するには、セマンティックな検索システムが必要です。 取得したIDに従って、メッセージがルーティングされます。

+--------------------------------------------------------+

+--------------------------------------------------------+
|            Application Layer (e.g.,HTTP, SIP)          |
+--------------------------------------------------------+

+--------------------------------------------------------+
|         Transmission Layer (e.g.,UDP, TCP, QUIC)       |
+--------------------------------------------------------+

AIエージェント通信層:このレイヤーは、上記のすべての機能を含むエージェント間での基本的なコミュニケーション機能を提供します。

- AIエージェント間の双方向双方向通信をサポートし、AIエージェントはコミュニケーションリクエストの開始と受信の両方を可能とする。 同じ通信セッションでは、エージェントは複数のモジュールデータを送信したり、マルチモーダルデータを受信したりすることができます。

- プロトコルの柔軟な拡張メカニズムをサポートし、エージェント通信のますます多様な機能要件を満たすことができます。

伝達層: この層 SHALL 次の機能を提供します。

- モバイルシナリオでは、トランスポートレイヤーはQoSルールを変更した上でQoSパラメータを動的に最適化し更新する必要があります。

- 多項データストリームのマルチプレックス化、マルチパス伝送機能(MPTCP、MPQUIC)を達成するために、エージェントから複数のソースデータの柔軟な送信管理をサポートする必要があります。

- トランスポートレイヤーは、未完成のデータパケットを新しいリンクに送信するか、データをバックアップリンクに切り替えるかのいずれかで、エージェント通信のモビリティ管理を有効にする必要があります。

# セキュリティの考慮事項

人工知能エージェント通信のセキュリティは、このドラフトでは詳しくありません。 独立性を考慮し、次の側面から他の提案を通して個別に議論できると提案します。

- アイデンティティ:AIエージェントは、エンボディされたロボットから仮想アシスタントまで様々で、異なるアイデンティティとクレデンシャルストレージのアプローチを紹介します。 プロトコルは、SIMベースのロボット、証明書ベースのAIアシスタントなど、これらの要件を満たす統一された互換性メカニズムを考慮する必要があります。

- 認証:AIエージェントは、エージェントとコアネットワーク間のプライマリ認証など、単一の信頼できるドメインによって提供される認証メカニズムを再使用できます。 エージェントが直接認証プロセスを簡素化する可能性があるため。

- 認可:エージェント通信の現在の慣行は、既存の OAuth 2.0 関連メカニズムに依存しています。 直接の承認、委任された承認およびユーザー認可のための別の承認メカニズムがあると考慮されるべきです。

- 相互ドメインセキュリティ:このドラフトは、一つの信頼ドメイン内の通信に焦点を当てました。 しかし、AIエージェントのクロスドメイン信託とセキュリティも次のステップで考慮すべきです

- ディスカバリープライバシー:AIエージェントの出版物は、所有者の承認を得る必要があります。 天然人である可能性がある所有者に関連した可能性のある機密情報を考慮して、すべてのエージェントカード/説明/アイデンティティが公開されるべきではありません。

- タスクプライバシー:タスクの実行に関与するエージェントは、タスクの説明の最小化の原則に従うべきです。つまり、各エージェントがタスクを完了するために必要な最低限の情報のみを受け取る必要があります。機密情報への不正なアクセスを防ぐためです。 また、コンテキスト共有はユーザーのプライバシーに影響を及ぼす可能性があるため、特にユーザーの名前、年齢、住所などの機密情報について、コンテキスト共有のスコープに関する制限を考慮することが重要です。
